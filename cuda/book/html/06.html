CUDA C++ 为熟悉 C++ 语言的用户提供了一条简单途径，使其能够编写在设备端执行的程序。

它由一组最小化的 C++ 语言扩展和一个运行时库组成。

核心语言扩展已在“编程模型”一章介绍。借助这些扩展，程序员可以将内核定义为 C++ 函数，并在每次调用内核时使用新的语法指定网格和线程块的维度。所有语言扩展的详细说明参见“C++ 语言扩展”。凡是使用了这些扩展的源文件，均须按照“使用 NVCC 编译”一节介绍的方法由 nvcc 编译。

“CUDA 运行时”一节将介绍运行时库。它提供在主机端运行的 C/C++ 函数，用于分配与释放设备内存、在主机内存和设备内存之间传输数据，以及管理带有多个设备的系统等。运行时的完整说明可查阅 CUDA 参考手册。

CUDA 运行时建立在更底层的 C API——CUDA 驱动程序 API——之上；应用程序也可以直接使用驱动程序 API。驱动程序 API 暴露了更底层的概念，因而提供了额外控制能力。例如，CUDA 上下文（context）与主机进程具有相似作用，CUDA 模块（module）则类似于动态加载的库。大多数应用程序不需要这些额外控制能力，因此无需直接使用驱动程序 API。使用运行时 API 时，上下文和模块管理由系统隐式完成，代码因此更加简洁。由于运行时 API 和驱动程序 API 能够互操作，确实需要某些驱动程序功能的应用仍可以以运行时 API 为主，仅在必要时调用驱动程序 API。驱动程序 API 在本书“驱动程序 API”章节中介绍，完整说明请参见相应参考手册。

6.1 使用 NVCC 编译（Compilation with NVCC）

内核可以使用 CUDA 指令集架构 PTX 编写，具体见 PTX 参考手册；但通常使用 C++ 等高级语言更高效。在这两种情况下，内核都必须经由 nvcc 编译为二进制代码，才能在设备上执行。

nvcc 是一个编译器驱动程序，用来简化 C++ 或 PTX 代码的编译过程：它提供简洁、熟悉的命令行选项，并调用实现不同编译阶段的多种工具。本节概述 nvcc 的工作流程和常用命令行选项；完整说明参见 nvcc 用户手册。

6.1.1 编译工作流程（Compilation Workflow）

6.1.1.1 离线编译（Offline Compilation）

使用 nvcc 编译的源文件，可以同时包含主机代码（在主机上执行）和设备代码（在设备上执行）。nvcc 的基本工作流程是先将设备代码与主机代码分离，然后：

  1. 将设备代码编译成汇编形式（PTX 代码），和／或二进制形式（cubin 对象）。
  2. 修改主机代码，将“内核”一节介绍的 <<<...>>> 语法（详见“执行配置”）替换为所需的 CUDA 运行时函数调用，以便从 PTX 代码或 cubin 对象加载并启动各个已编译内核。

修改后的主机代码可以作为 C++ 源码输出，随后交由其他工具编译；也可以由 nvcc 在最后一个编译阶段调用主机编译器，直接生成目标代码。

之后，应用程序可以采用两种方式：一是链接已编译的主机代码（这是最常见的方式）；二是忽略修改后的主机代码（如果存在），改用 CUDA 驱动程序 API 加载并运行 PTX 代码或 cubin 对象。

6.1.1.2 即时编译（Just-in-Time Compilation）

应用程序在运行期间加载的 PTX 代码，会由设备驱动程序进一步编译为二进制代码。这一过程称为即时编译（JIT compilation）。即时编译会增加应用程序加载时间，但也能让应用程序受益于新版设备驱动程序中的编译器改进。正如“应用程序兼容性”一节所述，对于编译应用程序时尚未出现的设备，即时编译也是使应用程序能够在其上运行的唯一途径。

当设备驱动程序为应用程序即时编译 PTX 代码时，会自动缓存生成的二进制代码，以免在后续运行同一应用程序时重复编译。该缓存称为计算缓存（compute cache）。升级设备驱动程序后，缓存会自动失效，以便应用程序能够使用新版驱动程序内置的即时编译器所带来的改进。

可以通过环境变量控制即时编译，详见“CUDA 环境变量”。除使用 nvcc 编译 CUDA C++ 设备代码外，还可以使用 NVRTC 在运行时将 CUDA C++ 设备代码编译为 PTX。NVRTC 是 CUDA C++ 的运行时编译库，详见 NVRTC 用户指南。

6.1.2 二进制兼容性（Binary Compatibility）

二进制代码与具体架构有关。cubin 对象通过 -code 编译器选项指定目标架构来生成。例如，使用 -code=sm_80 编译会生成适用于计算能力 8.0 设备的二进制代码。

二进制兼容性保证从较早的次版本向较新的次版本成立，但不保证反向兼容，也不保证跨主版本兼容。换言之，为计算能力 X.y 生成的 cubin 对象，只能在计算能力为 X.z、且 z ≥ y 的设备上执行（主版本 X 必须相同）。

注意：二进制兼容性只支持桌面平台，不支持 Tegra；桌面平台与 Tegra 之间也不支持二进制兼容性。

6.1.3 PTX 兼容性（PTX Compatibility）

有些 PTX 指令只在计算能力较高的设备上得到支持。例如，Warp Shuffle（线程束混洗）函数仅受计算能力 5.0 及以上的设备支持。-arch 编译选项指定将 C++ 编译为 PTX 时所假定的计算能力。因此，使用了线程束混洗函数的代码，需要采用 -arch=compute_50 或更高的计算能力进行编译。

面向某一计算能力生成的 PTX 代码，总可以进一步编译成面向不低于该计算能力的二进制代码。不过，由旧版 PTX 编译产生的二进制代码可能无法使用某些硬件特性。例如，以计算能力 6.0（Pascal）为目标生成的 PTX，再编译为面向计算能力 7.0（Volta）设备的二进制代码时，并不会使用 Tensor Core 指令，因为 Pascal 架构尚不支持 Tensor Core。因此，其最终性能可能不如使用新版 PTX 直接生成的代码。

针对架构条件特性（architecture-conditional features）编译的 PTX 代码只能在完全匹配的物理架构上运行，不具备前向或后向兼容性。例如，以 sm_90a 或 compute_90a 编译的代码只能在计算能力 9.0 的设备上运行，不支持向前或向后兼容。

6.1.4 应用程序兼容性（Application Compatibility）

为了在特定计算能力的设备上执行，应用程序必须加载与该计算能力兼容的二进制代码或 PTX 代码，具体规则参见“二进制兼容性”和“PTX 兼容性”。尤其对于未来可能出现的更高计算能力架构（在当前尚无法为其生成二进制代码），应用程序必须包含能够在该设备上进行即时编译的 PTX 代码。

哪些 PTX 和二进制代码被嵌入 CUDA C++ 应用程序，可由 -arch、-code 或 -gencode 编译选项控制，详见 nvcc 用户手册。例如：

nvcc x.cu \
  -gencode arch=compute_50,code=sm_50 \
  -gencode arch=compute_60,code=sm_60 \
  -gencode arch=compute_70,code="compute_70,sm_70"

上述命令通过前两个 -gencode 选项嵌入兼容计算能力 5.0 和 6.0 的二进制代码，通过第三个选项嵌入兼容计算能力 7.0 的 PTX 和二进制代码。生成的主机代码会在运行时自动选择最合适的代码，具体为：

  • 计算能力 5.0 和 5.2 的设备：使用 5.0 二进制代码；
  • 计算能力 6.0 和 6.1 的设备：使用 6.0 二进制代码；
  • 计算能力 7.0 和 7.5 的设备：使用 7.0 二进制代码；
  • 计算能力 8.0 和 8.6 的设备：使用在运行时编译为二进制代码的 PTX。

例如，x.cu 中可以针对计算能力 8.0 及以上的设备包含一个使用线程束归约操作的优化代码路径。宏 __CUDA_ARCH__ 可用于根据计算能力区分不同代码路径，但只在设备代码中定义。比如，以 -arch=compute_80 编译时，__CUDA_ARCH__ 的值为 800。如果针对架构条件特性使用 sm_90a 或 compute_90a 编译 x.cu，则代码只能在计算能力为 9.0 的设备上运行。

使用驱动程序 API 的应用必须将代码编译成单独的文件，并在运行时显式加载和执行最合适的文件。

Volta 架构引入了独立线程调度（Independent Thread Scheduling），从而改变了 GPU 调度线程的方式。对于依赖此前架构中特定 SIMT 调度行为的代码，独立线程调度可能改变参与执行的线程集合，造成错误结果。为了帮助开发者迁移代码，同时实施“独立线程调度”一节所介绍的修正措施，Volta 开发者可以使用编译选项组合 -arch=compute_60 -code=sm_70，选择使用 Pascal 式线程调度方式。

nvcc 用户手册给出了 -arch、-code 和 -gencode 选项的各种简写形式。例如，-arch=sm_70 是 -arch=compute_70 -code=compute_70,sm_70 的简写形式，它也等价于 -gencode arch=compute_70,code="compute_70,sm_70"。

6.1.5 C++ 兼容性（C++ Compatibility）

编译器前端按照 C++ 语法规则处理 CUDA 源文件。主机代码支持完整的 C++，但设备代码只完整支持 C++ 的一个子集，详见“C++ 语言支持”。

6.1.6 64 位兼容性（64-Bit Compatibility）

64 位版本的 nvcc 以 64 位模式编译设备代码（即指针宽度为 64 位）。以 64 位模式编译的设备代码只支持与同样采用 64 位模式编译的主机代码配合使用。

6.2 CUDA 运行时（CUDA Runtime）

CUDA 运行时实现在 cudart 库中。应用程序可以通过 cudart.lib 或 libcudart.a 静态链接该库，也可以通过 cudart.dll 或 libcudart.so 动态链接。需要动态链接 cudart.dll 或 cudart.so 的应用通常会在安装包中包含这些库。只有在不同组件链接到同一 CUDA 运行时实例时，才可以安全地在组件之间传递 CUDA 运行时符号的地址。运行时的所有入口函数都以 cuda 为前缀。

正如“异构编程”一节所述，CUDA 模型假设系统包含各自拥有独立内存的主机与设备。“设备内存”一节概述用于设备内存管理的运行时函数。

“共享内存”介绍如何利用“线程层次结构”中提到的共享内存提升性能；“页锁定主机内存”介绍为实现内核执行与主机—设备数据传输重叠而需要的页锁定主机内存；“异步并发执行”介绍支持系统各层次异步并发执行的概念和 API；“多设备系统”说明如何将该模型扩展到主机连接多个设备的情形；“错误检查”介绍如何正确检查运行时返回的错误；“调用栈”涉及管理 CUDA C++ 调用栈的运行时函数；“纹理与表面内存”说明这些提供另一种设备内存访问方式、并开放部分 GPU 纹理硬件能力的存储空间；“图形互操作性”介绍运行时与 OpenGL、Direct3D 互操作的功能。

6.2.1 初始化（Initialization）

从 CUDA 12.0 开始，调用 cudaInitDevice() 和 cudaSetDevice() 会初始化运行时及指定设备关联的主上下文（primary context）。如果没有调用它们，运行时会在处理其他运行时 API 请求时按需隐式使用设备 0 并自行初始化。测量运行时函数执行时间、解释首次调用返回的错误码时，需要考虑这一行为。在 CUDA 12.0 以前，cudaSetDevice() 不会初始化运行时，开发者通常使用空操作性质的 cudaFree(0)，把运行时初始化从其他 API 活动中隔离出来，以便分别分析时间开销和错误处理。

运行时会为系统中的每个设备创建一个 CUDA 上下文（另见“上下文”）。该上下文是相应设备的主上下文，会在首次执行需要该设备有效上下文的运行时函数时初始化，并由应用程序中的全部主机线程共享。创建上下文时，如有必要，设备代码会经即时编译后加载到设备内存。这些过程对开发者是透明的。如需实现驱动程序 API 互操作等功能，可以通过驱动程序 API 访问设备的主上下文，详见“运行时 API 与驱动程序 API 的互操作”。

主机线程调用 cudaDeviceReset() 时，会销毁该线程当前所操作设备的主上下文（“当前设备”的定义见“设备选择”）。此后，任何以该设备为当前设备的主机线程再次调用需要上下文的运行时函数时，都会创建新的主上下文。

注意：CUDA 接口使用进程启动时初始化、进程终止时销毁的全局状态。CUDA 运行时和驱动程序无法检测这些状态是否已失效。因此，在主程序初始化阶段或 main 结束后的终止阶段，以显式或隐式方式使用这些接口，可能导致未定义行为。

从 CUDA 12.0 起，cudaSetDevice() 在切换主机线程的当前设备后会显式初始化运行时。此前的版本则将新设备上的初始化延迟到后续首次调用运行时函数。由于这一变化，现在检查 cudaSetDevice() 返回值以发现初始化错误尤为重要。

参考手册的错误处理和版本管理章节中的运行时函数不会触发运行时初始化。

6.2.2 设备内存（Device Memory）

线性内存与 CUDA 数组

“异构编程”一节已经说明，CUDA 编程模型假设系统由主机和设备组成，两者分别拥有独立的内存。由于内核要从设备内存读取数据、在其中工作，运行时因而提供设备内存的分配、释放和复制函数，也提供主机内存与设备内存之间的数据传输功能。

设备内存既可以以线性内存形式分配，也可以以 CUDA 数组形式分配。CUDA 数组是一种针对纹理读取优化的不透明内存布局，详见“纹理与表面内存”。

线性内存分配在一个统一的地址空间中，这意味着分别分配的对象可以通过指针互相引用，例如二叉树或链表中的对象。地址空间的大小取决于主机系统（CPU）以及所用 GPU 的计算能力。

表 1：线性内存地址空间（Linear Memory Address Space）

GPU 计算能力 x86_64（AMD64） POWER（ppc64le） ARM64
最高 5.3（Maxwell） 40 位 40 位 40 位
6.0（Pascal）或更新 最多 47 位 最多 49 位 最多 48 位

注意：在计算能力 5.3（Maxwell）或更早的设备上，CUDA 驱动程序会创建一段尚未提交的 40 位虚拟地址预留区，以保证分配得到的内存指针位于受支持的地址范围内。这段地址在系统中会显示为“已预留虚拟内存”，但只有应用真正分配内存时才会占用物理内存。

一维向量内存分配与数据传输

线性内存通常通过 cudaMalloc() 分配、由 cudaFree() 释放，主机与设备间的数据传输通常使用 cudaMemcpy()。在“内核”一节的向量加法例子中，需要把向量从主机内存复制到设备内存。完整流程如下：

// 设备端代码
__global__ void VecAdd(float* A, float* B, float* C, int N)
{
    int i = blockDim.x * blockIdx.x + threadIdx.x;
    if (i < N)
        C[i] = A[i] + B[i];
}

// 主机端代码
int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // 在主机内存分配输入向量 h_A、h_B
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);
    float* h_C = (float*)malloc(size);

    // 初始化输入向量
    ...

    // 在设备内存分配三个向量
    float* d_A;
    cudaMalloc(&d_A, size);
    float* d_B;
    cudaMalloc(&d_B, size);
    float* d_C;
    cudaMalloc(&d_C, size);

    // 将输入向量从主机复制到设备
    cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, size, cudaMemcpyHostToDevice);

    // 启动内核
    int threadsPerBlock = 256;
    int blocksPerGrid =
        (N + threadsPerBlock - 1) / threadsPerBlock;
    VecAdd<<<blocksPerGrid, threadsPerBlock>>>(d_A, d_B, d_C, N);

    // 将结果从设备复制回主机，结果位于 h_C
    cudaMemcpy(h_C, d_C, size, cudaMemcpyDeviceToHost);

    // 释放设备内存
    cudaFree(d_A);
    cudaFree(d_B);
    cudaFree(d_C);

    // 释放主机内存
    ...
}

二维与三维线性内存分配

还可以使用 cudaMallocPitch() 和 cudaMalloc3D() 分配线性内存。对于二维或三维数组，推荐使用这些函数，因为它们会采用合适的填充（padding）以满足“设备内存访问”一节所述的对齐要求，从而在访问各行地址，或者利用 cudaMemcpy2D()、cudaMemcpy3D() 在二维数组与其他设备内存区域之间复制时，获得更好的性能。

访问数组元素时必须使用函数返回的行跨度（pitch，也称 stride）。下面的代码分配一个大小为 width × height 的二维浮点数组，并演示如何在设备代码中依次访问元素：

// 主机端代码
int width = 64, height = 64;
float* devPtr;
size_t pitch;
cudaMallocPitch(&devPtr, &pitch,
                width * sizeof(float), height);
MyKernel<<<100, 512>>>(devPtr, pitch, width, height);

// 设备端代码
__global__ void MyKernel(float* devPtr,
                         size_t pitch, int width, int height)
{
    for (int r = 0; r < height; ++r) {
        float* row = (float*)((char*)devPtr + r * pitch);
        for (int c = 0; c < width; ++c) {
            float element = row[c];
        }
    }
}

下面的代码则分配大小为 width × height × depth 的三维浮点数组，并展示在设备代码中遍历数组元素的方式：

// 主机端代码
int width = 64, height = 64, depth = 64;
cudaExtent extent = make_cudaExtent(width * sizeof(float),
                                    height, depth);
cudaPitchedPtr devPitchedPtr;
cudaMalloc3D(&devPitchedPtr, extent);
MyKernel<<<100, 512>>>(devPitchedPtr, width, height, depth);

// 设备端代码
__global__ void MyKernel(cudaPitchedPtr devPitchedPtr,
                         int width, int height, int depth)
{
    char* devPtr = devPitchedPtr.ptr;
    size_t pitch = devPitchedPtr.pitch;
    size_t slicePitch = pitch * height;
    for (int z = 0; z < depth; ++z) {
        char* slice = devPtr + z * slicePitch;
        for (int y = 0; y < height; ++y) {
            float* row = (float*)(slice + y * pitch);
            for (int x = 0; x < width; ++x) {
                float element = row[x];
            }
        }
    }
}

注意：为防止过度分配内存、进而影响系统整体性能，应用应根据问题规模向用户请求所需的分配参数。若内存分配失败，可以回退到其他较慢的内存类型（如 cudaMallocHost()、cudaHostRegister() 等），或返回错误并告知用户所需、但未获批准的内存数量。如果应用因某种原因无法向用户请求分配参数，则推荐在支持相应功能的平台上使用 cudaMallocManaged()。

通过运行时 API 访问全局变量与符号

CUDA 参考手册列出了在以下内存之间复制数据的各种函数：使用 cudaMalloc() 分配的线性内存、使用 cudaMallocPitch() 或 cudaMalloc3D() 分配的线性内存、CUDA 数组，以及在全局或常量内存空间中声明的变量对应的内存。

6.2.3 设备内存的 L2 访问管理（Device Memory L2 Access Management）

当一个 CUDA 内核反复访问全局内存中的某一数据区域时，可以将这类内存访问视为持久访问（persisting accesses）；相反，如果某个数据区域只被访问一次，这类访问可被视为流式访问（streaming accesses）。

从 CUDA 11.0 起，计算能力 8.0 或更高的设备可以影响数据在 L2 缓存中的驻留行为，因而有望提高全局内存访问的带宽并降低延迟。

6.2.3.1 为持久访问预留 L2 缓存（L2 Cache Set-Aside for Persisting Accesses）

可以将 L2 缓存的一部分预留给针对全局内存的持久访问。持久访问可以优先使用这部分预留的 L2 缓存；普通访问或流式访问仅在持久访问未占用该部分空间时，才能使用这部分缓存。

可以在设备允许的范围内调整持久访问所用的 L2 缓存预留大小：

cudaGetDeviceProperties(&prop, device_id);
size_t size = min(int(prop.l2CacheSize * 0.75),
                  prop.persistingL2CacheMaxSize);
// 为持久访问预留 L2 的 3/4，或者使用设备允许的最大值
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);

当 GPU 配置为多实例 GPU（MIG）模式时，L2 缓存预留功能被禁用。

使用多进程服务（MPS）时，不能通过 cudaDeviceSetLimit 修改 L2 缓存的预留大小。取而代之，必须在 MPS 服务器启动时，通过环境变量 CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT 指定预留大小。

6.2.3.2 持久访问的 L2 策略（L2 Policy for Persisting Accesses）

访问策略窗口（access policy window）指定全局内存中的一段连续区域，并为该区域内的内存访问指定一种在 L2 缓存中的持久性属性。

下面的示例说明如何通过 CUDA 流（stream）设置 L2 持久访问窗口。

CUDA Stream 示例

cudaStreamAttrValue stream_attribute; // 流级别的属性数据结构
stream_attribute.accessPolicyWindow.base_ptr =
    reinterpret_cast<void*>(ptr);     // 全局内存数据指针
stream_attribute.accessPolicyWindow.num_bytes = num_bytes;
    // 持久访问区域的字节数；不能超过
    // cudaDeviceProp::accessPolicyMaxWindowSize
stream_attribute.accessPolicyWindow.hitRatio = 0.6;
    // 缓存命中比例的提示值
stream_attribute.accessPolicyWindow.hitProp =
    cudaAccessPropertyPersisting;     // 命中时的访问属性
stream_attribute.accessPolicyWindow.missProp =
    cudaAccessPropertyStreaming;      // 未命中时的访问属性

// 将这些属性设置到 cudaStream_t 类型的 CUDA 流上
cudaStreamSetAttribute(stream,
    cudaStreamAttributeAccessPolicyWindow,
    &stream_attribute);

内核随后在该 CUDA 流中运行时，位于全局内存 [ptr, ptr + num_bytes) 范围内的数据访问，比访问其他全局内存地址更可能在 L2 缓存中保持驻留。

也可以按下例所示，在 CUDA 图（CUDA Graph）的内核节点（Kernel Node）上设置 L2 持久访问属性。

CUDA Graph Kernel Node 示例

cudaKernelNodeAttrValue node_attribute; // 内核节点级别属性结构
node_attribute.accessPolicyWindow.base_ptr =
    reinterpret_cast<void*>(ptr);       // 全局内存数据指针
node_attribute.accessPolicyWindow.num_bytes = num_bytes;
    // 持久访问字节数，不能超过设备访问策略窗口的最大大小
node_attribute.accessPolicyWindow.hitRatio = 0.6;
node_attribute.accessPolicyWindow.hitProp =
    cudaAccessPropertyPersisting;       // 命中时的访问属性
node_attribute.accessPolicyWindow.missProp =
    cudaAccessPropertyStreaming;        // 未命中时的访问属性

// 将属性设置到 cudaGraphNode_t 类型的 CUDA 图内核节点上
cudaGraphKernelNodeSetAttribute(node,
    cudaKernelNodeAttributeAccessPolicyWindow,
    &node_attribute);

参数 hitRatio 用来指定在访问中被赋予 hitProp 属性的比例。上述两个例子均将 hitRatio 设为 0.6；因此，位于 [ptr, ptr + num_bytes) 范围内的内存访问约有 60% 被赋予持久属性，约有 40% 被赋予流式属性。具体哪些访问获得持久属性，由近似等于 hitRatio 的概率随机决定；该概率分布取决于硬件架构和内存区域大小。

例如，假设预留的 L2 缓存大小为 16 KB，而 accessPolicyWindow 中的 num_bytes 为 32 KB：

  • hitRatio = 0.5：硬件会从 32 KB 窗口中随机选择约 16 KB 的访问，赋予持久属性并缓存到预留的 L2 区域。
  • hitRatio = 1.0：硬件会尝试将整个 32 KB 窗口缓存到预留的 L2 区域。由于预留空间比窗口小，缓存行会不断被逐出，最终在预留区中保留最近使用的约 16 KB 数据。

因此，可以通过 hitRatio 避免缓存行频繁抖动（thrashing），减少数据在 L2 缓存内外的搬运量。

当多个 CUDA 流并发执行时，设定小于 1.0 的 hitRatio，还可以手动调节不同访问策略窗口占用的 L2 缓存容量。例如，假设 L2 预留区大小为 16 KB，两个不同流中的并发内核各自有一个 16 KB 的访问策略窗口。如果两个窗口的 hitRatio 都为 1.0，那么它们竞争同一份共享 L2 资源时，可能互相逐出对方的缓存行。如果两个窗口都使用 0.5，则更不容易逐出自身或对方的持久缓存行。

6.2.3.3 L2 访问属性（L2 Access Properties）

CUDA 针对不同类型的全局内存访问定义了三种属性：

  1. cudaAccessPropertyStreaming：具有流式属性的内存访问，其缓存行更容易被优先逐出，因此数据不太可能长期驻留在 L2 缓存中。
  2. cudaAccessPropertyPersisting：具有持久属性的内存访问，其缓存行会在 L2 预留区内得到优先保留，因此数据更可能驻留在 L2 缓存中。
  3. cudaAccessPropertyNormal：该属性强制把此前指定的持久访问属性重置为普通状态。此前 CUDA 内核中使用过的持久数据，可能在用途结束后仍长期留在 L2 缓存中，减少后续不使用持久属性的内核可利用的缓存容量。给访问策略窗口设置 cudaAccessPropertyNormal，便会移除先前的持久驻留优先级，使这些访问恢复为未配置持久属性时的普通状态。

6.2.3.4 L2 持久性示例（L2 Persistence Example）

下面的示例展示如何为持久访问预留 L2 缓存、通过 CUDA 流让内核使用预留区，以及如何在使用结束后将 L2 缓存重置。

cudaStream_t stream;
cudaStreamCreate(&stream); // 创建 CUDA 流

cudaDeviceProp prop;    // CUDA 设备属性变量
cudaGetDeviceProperties(&prop, device_id); // 查询 GPU 属性

size_t size = min(int(prop.l2CacheSize * 0.75),
                  prop.persistingL2CacheMaxSize);
// 为持久访问预留 3/4 的 L2 缓存，或预留设备允许的最大值
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);

size_t window_size = min(prop.accessPolicyMaxWindowSize,
                         num_bytes); // 取窗口上限与需求的较小值

cudaStreamAttrValue stream_attribute; // 流级别属性结构
stream_attribute.accessPolicyWindow.base_ptr =
    reinterpret_cast<void*>(data1); // 全局内存数据指针
stream_attribute.accessPolicyWindow.num_bytes = window_size;
stream_attribute.accessPolicyWindow.hitRatio = 0.6;
stream_attribute.accessPolicyWindow.hitProp =
    cudaAccessPropertyPersisting;
stream_attribute.accessPolicyWindow.missProp =
    cudaAccessPropertyStreaming;

// 设置该 CUDA 流的访问策略窗口
cudaStreamSetAttribute(stream,
    cudaStreamAttributeAccessPolicyWindow,
    &stream_attribute);

for (int i = 0; i < 10; i++) {
    cuda_kernelA<<<grid_size, block_size, 0, stream>>>(data1);
    // data1 被内核重复使用，可受益于 L2 持久驻留
}

cuda_kernelB<<<grid_size, block_size, 0, stream>>>(data1);
// 同一流中的另一个内核也可以受益于 data1 的 L2 持久属性

// 将访问策略窗口大小置零以禁用该窗口
stream_attribute.accessPolicyWindow.num_bytes = 0;
cudaStreamSetAttribute(stream,
    cudaStreamAttributeAccessPolicyWindow,
    &stream_attribute);

cudaCtxResetPersistingL2Cache(); // 移除 L2 中的持久属性缓存行
cuda_kernelC<<<grid_size, block_size, 0, stream>>>(data2);
// data2 现在可按普通方式使用完整的 L2 缓存

6.2.3.5 将 L2 访问属性重置为普通状态（Reset L2 Access to Normal）

前一个 CUDA 内核所使用的持久 L2 缓存行，可能在使用结束后仍停留在 L2 中很长时间。因此，把 L2 访问属性重置为普通状态很重要，可以使后续流式访问或普通访问以正常优先级使用 L2 缓存。可以通过三种方式恢复普通状态：

  1. 对原先配置为持久访问的内存区域应用 cudaAccessPropertyNormal 访问属性。
  2. 调用 cudaCtxResetPersistingL2Cache()，将所有持久 L2 缓存行恢复为普通状态。
  3. 长期没有被访问的缓存行最终也会自动恢复为普通状态。但是自动重置所需时间不确定，因此强烈不建议依赖此机制。

6.2.3.6 管理 L2 预留缓存的利用率（Manage Utilization of L2 Set-Aside Cache）

不同 CUDA 流中并发执行的多个内核，可以各自为其流设置不同的访问策略窗口。但是，所有这些并发内核共享同一份 L2 缓存预留区。因此，预留区的总体使用量是各内核使用量的总和。当持久访问涉及的数据量超过预留区容量时，把某些访问设为持久访问所带来的好处会减少。

为了管理 L2 缓存预留区的利用率，应用程序应考虑：

  • L2 预留缓存区的大小；
  • 可能并发执行的 CUDA 内核；
  • 所有可能并发执行的 CUDA 内核所使用的访问策略窗口；
  • 何时以及如何重置 L2，使普通或流式访问能够以同等优先级使用此前预留的 L2 缓存容量。

6.2.3.7 查询 L2 缓存属性（Query L2 Cache Properties）

与 L2 缓存有关的属性包含在 cudaDeviceProp 结构体中，可通过 CUDA 运行时 API cudaGetDeviceProperties 查询。相关设备属性包括：

  • l2CacheSize：GPU 上可用的 L2 缓存容量。
  • persistingL2CacheMaxSize：可为持久内存访问预留的最大 L2 缓存容量。
  • accessPolicyMaxWindowSize：访问策略窗口允许的最大大小。

6.2.3.8 控制持久访问的 L2 预留容量（Control L2 Cache Set-Aside Size for Persisting Memory Access）

持久访问的 L2 缓存预留大小，可使用 CUDA 运行时 API cudaDeviceGetLimit 查询，并使用 cudaDeviceSetLimit 按 cudaLimit 类型设置。所设置的大小不得超过 cudaDeviceProp::persistingL2CacheMaxSize。

6.2.4 共享内存（Shared Memory）

共享内存的作用

正如“变量内存空间说明符”（Variable Memory Space Specifiers）所述，共享内存通过 __shared__ 内存空间说明符来分配。

如“线程层次结构”中所介绍，并在“共享内存”部分进一步说明的那样，共享内存的访问速度通常远高于全局内存。它可以用作暂存内存（scratchpad memory），或作为由软件管理的缓存，从而减少 CUDA 线程块对全局内存的访问。下面通过矩阵乘法展示这一用法。

不使用共享内存的矩阵乘法

首先考虑一个不利用共享内存的直接实现。对于输出矩阵 C 的每个元素，一个线程读取矩阵 A 的一行以及矩阵 B 的一列，完成对应元素的计算，如图 8 所示。因此，A 中的元素会从全局内存读取 B.width 次，而 B 中的元素会读取 A.height 次。

以下为原书中不使用共享内存的实现。假设矩阵均按**行优先（row-major）**顺序存储，且矩阵维度为线程块大小的整数倍。

// 矩阵以行优先顺序存储：
// M(row, col) = *(M.elements + row * M.width + col)
typedef struct {
    int width;
    int height;
    float* elements;
} Matrix;

// 线程块大小
#define BLOCK_SIZE 16

// 矩阵乘法内核的前向声明
__global__ void MatMulKernel(const Matrix, const Matrix, Matrix);

// 矩阵乘法：主机端代码
// 假设矩阵维度均为 BLOCK_SIZE 的整数倍
void MatMul(const Matrix A, const Matrix B, Matrix C)
{
    // 将 A、B 复制到设备内存
    Matrix d_A;
    d_A.width = A.width; d_A.height = A.height;
    size_t size = A.width * A.height * sizeof(float);
    cudaMalloc(&d_A.elements, size);
    cudaMemcpy(d_A.elements, A.elements, size,
               cudaMemcpyHostToDevice);

    Matrix d_B;
    d_B.width = B.width; d_B.height = B.height;
    size = B.width * B.height * sizeof(float);
    cudaMalloc(&d_B.elements, size);
    cudaMemcpy(d_B.elements, B.elements, size,
               cudaMemcpyHostToDevice);

    // 在设备内存中为 C 分配空间
    Matrix d_C;
    d_C.width = C.width; d_C.height = C.height;
    size = C.width * C.height * sizeof(float);
    cudaMalloc(&d_C.elements, size);

    // 启动内核
    dim3 dimBlock(BLOCK_SIZE, BLOCK_SIZE);
    dim3 dimGrid(B.width / dimBlock.x, A.height / dimBlock.y);
    MatMulKernel<<<dimGrid, dimBlock>>>(d_A, d_B, d_C);

    // 将结果 C 从设备内存复制回主机内存
    cudaMemcpy(C.elements, d_C.elements, size,
               cudaMemcpyDeviceToHost);

    // 释放设备内存
    cudaFree(d_A.elements);
    cudaFree(d_B.elements);
    cudaFree(d_C.elements);
}

// 由 MatMul() 调用的矩阵乘法内核
__global__ void MatMulKernel(Matrix A, Matrix B, Matrix C)
{
    // 每个线程将计算得到的一个 C 元素累加到 Cvalue 中
    float Cvalue = 0;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    for (int e = 0; e < A.width; ++e)
        Cvalue += A.elements[row * A.width + e]
                * B.elements[e * B.width + col];

    C.elements[row * C.width + col] = Cvalue;
}

使用共享内存的分块矩阵乘法

下面考虑使用共享内存的矩阵乘法。在这种实现中，每个线程块负责计算输出矩阵 C 的一个正方形子矩阵 Csub，线程块中的每个线程则负责计算 Csub 中的一个元素。

如图 9 所示，Csub 可以看作两个矩形矩阵的乘积：一个是 A 中与 Csub 对应行相同的子矩阵，另一个是 B 中与 Csub 对应列相同的子矩阵。这些矩形矩阵进一步拆分成若干边长为 BLOCK_SIZE 的方形子矩阵，以适应设备的资源限制。Csub 可以表示为这些方形子矩阵乘积的累加和。

每次计算一对子矩阵乘积时，先由线程块中的线程把相应的两个方形子矩阵从全局内存装入共享内存，每个线程负责加载各子矩阵中的一个元素；然后各线程计算乘积中的相应元素。各线程把子矩阵乘积的结果累加在自己的寄存器中，全部计算完成后，再把结果写回全局内存。

这种分块计算方式利用了访问速度较快的共享内存，显著节省了全局内存带宽。原书指出：矩阵 A 仅需从全局内存读取 B.width / BLOCK_SIZE 次，而矩阵 B 仅需读取 A.height / BLOCK_SIZE 次。

为了用同一种类型高效表示完整矩阵及其子矩阵，下面给之前的 Matrix 类型新增一个 stride（跨度）字段，并使用 __device__ 函数读取、写入矩阵元素，以及获取一个子矩阵。

图 9：使用共享内存的矩阵乘法（Matrix Multiplication with Shared Memory），原书印刷页 39。

分块矩阵乘法的完整示例

// 矩阵以行优先顺序存储：
// M(row, col) = *(M.elements + row * M.stride + col)
typedef struct {
    int width;
    int height;
    int stride;
    float* elements;
} Matrix;

// 获取矩阵中的一个元素
__device__ float GetElement(const Matrix A, int row, int col)
{
    return A.elements[row * A.stride + col];
}

// 设置矩阵中的一个元素
__device__ void SetElement(Matrix A, int row, int col,
                           float value)
{
    A.elements[row * A.stride + col] = value;
}

// 获取 A 的一个 BLOCK_SIZE × BLOCK_SIZE 子矩阵 Asub；
// 该子矩阵相对于 A 左上角向下偏移 row 个子矩阵、
// 向右偏移 col 个子矩阵
__device__ Matrix GetSubMatrix(Matrix A, int row, int col)
{
    Matrix Asub;
    Asub.width    = BLOCK_SIZE;
    Asub.height   = BLOCK_SIZE;
    Asub.stride   = A.stride;
    Asub.elements = &A.elements[A.stride * BLOCK_SIZE * row
                                + BLOCK_SIZE * col];
    return Asub;
}

// 线程块大小
#define BLOCK_SIZE 16

// 矩阵乘法内核的前向声明
__global__ void MatMulKernel(const Matrix, const Matrix, Matrix);

// 矩阵乘法：主机端代码
// 假设矩阵维度均为 BLOCK_SIZE 的整数倍
void MatMul(const Matrix A, const Matrix B, Matrix C)
{
    // 将 A、B 复制到设备内存
    Matrix d_A;
    d_A.width = d_A.stride = A.width;
    d_A.height = A.height;
    size_t size = A.width * A.height * sizeof(float);
    cudaMalloc(&d_A.elements, size);
    cudaMemcpy(d_A.elements, A.elements, size,
               cudaMemcpyHostToDevice);

    Matrix d_B;
    d_B.width = d_B.stride = B.width;
    d_B.height = B.height;
    size = B.width * B.height * sizeof(float);
    cudaMalloc(&d_B.elements, size);
    cudaMemcpy(d_B.elements, B.elements, size,
               cudaMemcpyHostToDevice);

    // 为 C 分配设备内存
    Matrix d_C;
    d_C.width = d_C.stride = C.width;
    d_C.height = C.height;
    size = C.width * C.height * sizeof(float);
    cudaMalloc(&d_C.elements, size);

    // 启动内核
    dim3 dimBlock(BLOCK_SIZE, BLOCK_SIZE);
    dim3 dimGrid(B.width / dimBlock.x, A.height / dimBlock.y);
    MatMulKernel<<<dimGrid, dimBlock>>>(d_A, d_B, d_C);

    // 将结果 C 复制回主机内存
    cudaMemcpy(C.elements, d_C.elements, size,
               cudaMemcpyDeviceToHost);

    // 释放设备内存
    cudaFree(d_A.elements);
    cudaFree(d_B.elements);
    cudaFree(d_C.elements);
}

// 由 MatMul() 调用的矩阵乘法内核
__global__ void MatMulKernel(Matrix A, Matrix B, Matrix C)
{
    // 当前线程块的行、列索引
    int blockRow = blockIdx.y;
    int blockCol = blockIdx.x;

    // 每个线程块负责 C 的一个子矩阵 Csub
    Matrix Csub = GetSubMatrix(C, blockRow, blockCol);

    // 每个线程在寄存器中累加 Csub 的一个元素
    float Cvalue = 0;

    // 当前线程在子矩阵中的行、列索引
    int row = threadIdx.y;
    int col = threadIdx.x;

    // 遍历计算 Csub 所需的所有 A、B 子矩阵对；
    // 逐对相乘，并把结果累加起来
    for (int m = 0; m < (A.width / BLOCK_SIZE); ++m) {
        // 取得 A、B 当前参与乘法的子矩阵
        Matrix Asub = GetSubMatrix(A, blockRow, m);
        Matrix Bsub = GetSubMatrix(B, m, blockCol);

        // 分别用共享内存保存 Asub、Bsub
        __shared__ float As[BLOCK_SIZE][BLOCK_SIZE];
        __shared__ float Bs[BLOCK_SIZE][BLOCK_SIZE];

        // 每个线程从设备内存向共享内存各加载一个元素
        As[row][col] = GetElement(Asub, row, col);
        Bs[row][col] = GetElement(Bsub, row, col);

        // 先同步，确保所有子矩阵元素均已加载
        __syncthreads();

        // 计算子矩阵乘积，并累加该线程负责的元素
        for (int e = 0; e < BLOCK_SIZE; ++e)
            Cvalue += As[row][e] * Bs[e][col];

        // 再次同步，确保上一轮计算完成，
        // 然后才能加载下一对子矩阵
        __syncthreads();
    }

    // 将 Csub 中的一个元素写回设备内存
    SetElement(Csub, row, col, Cvalue);
}

这里的关键顺序是：加载两个数据块 → 同步 → 执行乘法和累加 → 再次同步 → 加载下一组数据块。两个 __syncthreads() 的作用不同：前者保证参与计算的共享内存数据已经准备好，后者确保该轮线程已完成读取和计算，避免数据在下一轮加载时被过早覆盖。这一流程与原书示例保持一致。

6.2.5 分布式共享内存（Distributed Shared Memory）

工作原理与生命周期

计算能力 9.0 引入的线程块集群，使集群内的线程能够访问参与该集群的所有线程块的共享内存。这些分散在不同线程块中的共享内存合称分布式共享内存（Distributed Shared Memory，DSM）；相应的地址空间称为分布式共享内存地址空间。

同一线程块集群中的线程可以对分布式地址空间中的地址进行读取、写入或原子操作，不论该地址属于本地线程块，还是集群内另一个远程线程块。无论内核是否使用 DSM，静态或动态共享内存大小的指定方式仍然是以每个线程块为单位。因此，分布式共享内存的总大小等于：

\[ \text{DSM 总大小}=\text{每个集群的线程块数量}\times\text{每个线程块的共享内存大小} \]

要访问分布式共享内存，相关线程块必须都已存在。使用 Cluster Group API 中的 cluster.sync()，可以保证集群中的所有线程块均已开始执行。

还必须确保：一个线程块退出以前，所有涉及其共享内存的 DSM 操作都已经完成。例如，当其他线程块正准备读取本线程块的共享内存时，必须先确保远程读取完成，本线程块才可退出。

用分布式共享内存计算直方图

CUDA 提供了访问 DSM 的机制，应用程序可以利用它提高效率。以直方图计算为例：一种常见方法是先在每个线程块的共享内存中计算局部直方图，然后通过全局内存原子操作累积结果。

这种方式受共享内存容量限制；如果直方图桶（bin）的数量太多、一个线程块的共享内存无法容纳，就可能需要直接在全局内存中进行统计和原子更新。DSM 为两者之间提供了一个中间层：根据直方图桶的总大小，可以选择使用普通共享内存、分布式共享内存，或直接在全局内存中计算。

以下示例根据桶数量，在共享内存或 DSM 中计算直方图。代码依照原书保留类型和 API 名称，中文化了注释；跨页断行已经合并。

#include <cooperative_groups.h>

// 使用分布式共享内存的直方图内核
__global__ void clusterHist_kernel(int *bins, const int nbins,
                                   const int bins_per_block,
                                   const int *__restrict__ input,
                                   size_t array_size)
{
    extern __shared__ int smem[];
    namespace cg = cooperative_groups;
    int tid = cg::this_grid().thread_rank();

    // 获取集群对象、当前线程块在集群中的序号和集群大小
    cg::cluster_group cluster = cg::this_cluster();
    unsigned int clusterBlockRank = cluster.block_rank();
    int cluster_size = cluster.dim_blocks().x;

    for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x) {
        smem[i] = 0; // 将共享内存中的局部直方图清零
    }

    // 集群同步确保所有块均已完成共享内存清零；
    // 同时确保所有线程块均已启动且并发存在
    cluster.sync();

    for (int i = tid; i < array_size; i += blockDim.x * gridDim.x) {
        int ldata = input[i];

        // 确定对应的直方图桶
        int binid = ldata;
        if (ldata < 0)
            binid = 0;
        else if (ldata >= nbins)
            binid = nbins - 1;

        // 计算该桶所属的集群内线程块和局部偏移量
        int dst_block_rank = (int)(binid / bins_per_block);
        int dst_offset = binid % bins_per_block;

        // 获取目标线程块的共享内存指针
        int *dst_smem = cluster.map_shared_rank(smem, dst_block_rank);

        // 使用原子更新目标桶
        atomicAdd(dst_smem + dst_offset, 1);
    }

    // 确保所有 DSM 访问结束，避免某个线程块在其他线程块
    // 尚未完成访问它的共享内存时就提前退出
    cluster.sync();

    // 把本线程块的直方图结果累加至全局内存
    int *lbins = bins + cluster.block_rank() * bins_per_block;
    for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x) {
        atomicAdd(&lbins[i], smem[i]);
    }
}

提示：上例中的 clusterBlockRank 和 cluster_size 变量与原书保持一致，虽然在后续代码片段中没有直接使用。

根据直方图大小配置集群

上面的内核可以在运行时根据分布式共享内存需求选择线程块集群大小。如果直方图规模较小，只用一个线程块的共享内存就能存下所有桶，那么可以把集群大小设置为 1。

下面的代码片段展示了如何根据所需共享内存容量动态配置和启动集群内核。例子中 cluster_size = 2 只是一个示范值。

// 使用可扩展的内核启动 API
{
    cudaLaunchConfig_t config = {0};
    config.gridDim = array_size / threads_per_block;
    config.blockDim = threads_per_block;

    // 集群大小由直方图规模决定。
    // 若 cluster_size == 1，则仅使用线程块本地共享内存，
    // 不需要跨线程块的分布式共享内存。
    int cluster_size = 2; // 示例值
    int nbins_per_block = nbins / cluster_size;

    // 动态共享内存大小按每个线程块指定；
    // 整个集群的 DSM 总大小为：
    // cluster_size * nbins_per_block * sizeof(int)
    config.dynamicSmemBytes = nbins_per_block * sizeof(int);

    CUDA_CHECK(::cudaFuncSetAttribute(
        (void *)clusterHist_kernel,
        cudaFuncAttributeMaxDynamicSharedMemorySize,
        config.dynamicSmemBytes));

    cudaLaunchAttribute attribute[1];
    attribute[0].id = cudaLaunchAttributeClusterDimension;
    attribute[0].val.clusterDim.x = cluster_size;
    attribute[0].val.clusterDim.y = 1;
    attribute[0].val.clusterDim.z = 1;

    config.numAttrs = 1;
    config.attrs = attribute;

    cudaLaunchKernelEx(&config, clusterHist_kernel,
                       bins, nbins, nbins_per_block,
                       input, array_size);
}

代码说明： 上面是原书的说明性代码片段，所用 CUDA_CHECK 宏和若干变量需要由外围程序定义；不能直接把该片段当作完整可运行程序。原书示例使用按整除计算的桶分配方式，实际使用时还应核对桶数量与集群大小之间的关系。

6.2.6 页锁定主机内存（Page-Locked Host Memory）

什么是页锁定内存

CUDA 运行时提供了若干函数，以便使用页锁定主机内存（page-locked host memory，也称 pinned host memory，常译为“固定页内存”）。它与通过 malloc() 分配的普通可分页主机内存不同。

  • cudaHostAlloc() 和 cudaFreeHost()：分别分配和释放页锁定主机内存。
  • cudaHostRegister()：把一段通过 malloc() 等方式分配的主机内存设为页锁定状态。具体限制见 CUDA 参考手册。

页锁定内存带来的优势

使用页锁定主机内存有以下几项好处：

  1. 对于支持该能力的设备，在页锁定主机内存与设备内存之间进行的数据复制，可以与内核执行并发进行。相关机制参见“异步并发执行”（Asynchronous Concurrent Execution）。
  2. 对于某些设备，页锁定主机内存可以映射到设备地址空间，从而不必再显式把数据从主机内存复制到设备内存，或从设备内存复制回主机内存。详见“映射内存”（Mapped Memory）。
  3. 对于带有前端总线（front-side bus）的系统，页锁定主机内存与设备内存之间的数据传输带宽会比普通可分页内存更高。如果进一步启用写合并（write-combining）功能，还可以获得更高的带宽，详见“写合并内存”（Write-Combining Memory）。

注意： 在不支持 I/O 一致性的 Tegra 设备上，页锁定主机内存不会被缓存；这类 Tegra 设备也不支持 cudaHostRegister()。

CUDA 的 simpleZeroCopy 示例附带了关于页锁定内存 API 的详细文档。

6.2.6.1 可移植内存（Portable Memory）

一块页锁定主机内存可以配合系统中的任意设备使用，详情参见“多设备系统”（Multi-Device System）。但默认情况下，上述页锁定内存带来的好处，仅适用于该内存块分配时所在的当前设备，以及可能与该设备共享同一统一地址空间的其他设备（参见“统一虚拟地址空间”）。

如果希望系统中所有设备都能够享受这些优势，就需要在调用 cudaHostAlloc() 时传入 cudaHostAllocPortable 标志，或者在调用 cudaHostRegister() 时传入 cudaHostRegisterPortable 标志，以将相应内存标记为可移植的页锁定内存。

6.2.6.2 写合并内存（Write-Combining Memory）

默认情况下，页锁定主机内存分配后是可缓存的。调用 cudaHostAlloc() 时，也可以传入 cudaHostAllocWriteCombined 标志，把它分配为写合并内存。

写合并内存能够释放主机 L1 和 L2 缓存资源，使系统的其他部分可以使用更多缓存。此外，写合并内存在通过 PCI Express 总线传输时，不需要被嗅探（snoop），因此数据传输性能最多可提升 40%。这一数值为原书针对该情形给出的说明，并不意味着所有系统都会获得同样幅度的提升。

从主机端读取写合并内存非常缓慢，因此通常只应将其用于主机主要进行写入的内存数据。

应避免使用 CPU 原子指令操作写合并（WC）内存，因为并非所有 CPU 实现都保证这一功能能够正常工作。

6.2.6.3 映射内存（Mapped Memory）

页锁定主机内存还可以映射到设备的地址空间。实现方式是在调用 cudaHostAlloc() 时传入 cudaHostAllocMapped 标志，或者在调用 cudaHostRegister() 时传入 cudaHostRegisterMapped 标志。

因此，这样的内存块通常具有两个地址：

  • 主机地址：由 cudaHostAlloc() 或 malloc() 返回。
  • 设备地址：通过 cudaHostGetDevicePointer() 获取；内核随后便可用此指针访问相应内存。

一个例外是：由 cudaHostAlloc() 分配的内存，在主机和设备使用统一地址空间时，相关指针行为有所不同，详见“统一虚拟地址空间”（Unified Virtual Address Space）。

直接访问主机内存的优势

内核直接访问主机内存的带宽并不等同于访问设备内存时的带宽，但具有一些优势：

  1. 无须额外分配设备内存，也不需要显式复制主机内存与设备内存中的对应数据块；必要的数据传输由内核访问隐式触发。
  2. 不需要专门使用 CUDA 流（参见“并发数据传输”）来重叠数据复制与内核执行，因为由内核引发的数据传输会自动与内核执行重叠。
同步要求与使用限制

然而，映射的页锁定内存在主机和设备之间共享，因此应用程序必须使用 CUDA 流或事件来同步内存访问（参见“异步并发执行”），以避免潜在的读后写、写后读或写后写竞争风险。

如果需要为任何映射的页锁定主机内存获取设备端指针，那么必须在调用其他任何 CUDA API 之前，先通过 cudaSetDeviceFlags() 设置 cudaDeviceMapHost 标志，以启用页锁定内存映射。否则，cudaHostGetDevicePointer() 将返回错误。

如果设备不支持映射页锁定主机内存，调用 cudaHostGetDevicePointer() 也会失败。应用程序可以通过查询设备属性 canMapHostMemory 判断是否支持该功能：支持时属性值为 1（参见“设备枚举”）。

还应注意，针对映射页锁定内存执行的原子操作（参见“原子函数”），从主机或其他设备的角度来看，不保证具有原子性。

此外，CUDA 运行时要求：由设备发起、针对主机内存中自然对齐的 1、2、4、8 和 16 字节加载与存储操作，在主机和其他设备看来必须保持为单次访问。在某些平台上，硬件可能把对内存的原子操作拆分为独立的加载和存储操作；这些组成操作仍然必须满足自然对齐访问的保持要求。

CUDA 运行时不支持这样的 PCI Express 总线拓扑：其中某个 PCI Express 桥接器会把一个自然对齐的 8 字节操作拆分成多个操作。原书还指出，NVIDIA 当时并未发现会拆分自然对齐 16 字节操作的 PCI Express 拓扑。

6.2.7 内存同步域（Memory Synchronization Domains）

6.2.7.1 内存栅栏干扰（Memory Fence Interference）

部分 CUDA 应用程序的性能可能下降，原因是内存栅栏或刷新操作必须等待的内存事务超出了 CUDA 内存一致性模型真正要求的范围。

下面考虑一个示例。该示例涉及 GPU 流式多处理器（SM）上的两个线程，以及 CPU 上的一个线程。

__managed__ int x = 0;
__device__ cuda::atomic<int, cuda::thread_scope_device> a(0);
__managed__ cuda::atomic<int, cuda::thread_scope_system> b(0);
线程 1（SM） 线程 2（SM） 线程 3（CPU）
x = 1; while (a != 1); while (b != 1);
a = 1; assert(x == 1); assert(x == 1);
— b = 1; —

累积性与可见性。 CUDA 内存一致性模型保证上述断言为真。因此，在当线程 2 写入 b 并被线程 3 观察到之前，线程 1 对 x 的写入必须对线程 3 可见。

对 a 的 release/acquire（释放/获取）操作提供的内存顺序保证，仅足以使 x 对线程 2 可见，而不足以直接保证线程 3 也能看见，因为 a 的作用域仅限于设备。对 b 的释放/获取操作提供的是系统作用域的内存顺序；它必须保证线程 3 不仅能够看到线程 2 自身写入的内容，而且能够看到那些已经对线程 2 可见、由其他线程写入的内容。这种性质称为累积性（cumulativity）。

GPU 在执行过程中无法判断：哪些写入是由源代码层面的同步关系保证可见的，哪些只是由于执行时序碰巧变得可见。因此，GPU 必须保守地将较广范围内、尚未完成的内存操作纳入考虑。

这有时会造成干扰：GPU 可能需要等待一些从源程序要求来看并不必然需要等待的内存操作，导致内存栅栏或刷新操作花费更长时间。

内存栅栏既可能像这个示例中的内置函数或原子操作那样显式出现，也可能为了在任务边界实现 synchronizes-with（同步于）关系而隐式出现。

典型场景。 当一个内核在 GPU 本地内存中执行计算，同时另一个并行内核（例如来自 NCCL 的内核）与对等设备通信时，局部计算内核结束时会隐式刷新其写入，以满足与后续任务之间的同步要求。它可能因此不必要地等待通信内核经由速度较慢的 NVLink 或 PCIe 发出的部分乃至全部写入。

6.2.7.2 使用同步域隔离流量（Isolating Traffic with Domains）

从 Hopper 架构的 GPU 和 CUDA 12.0 开始，**内存同步域（memory synchronization domains）**提供了一种缓解上述干扰的方法。程序通过明确标注内存同步域，帮助 GPU 缩小栅栏操作需要覆盖的事务范围。

每次内核启动都被赋予一个域 ID。写入操作与栅栏操作均标记此 ID；栅栏只对与自身域相匹配的写入建立顺序关系。对于前面“本地计算与远程通信并发”的例子，可以把通信内核放在另一个域中。

跨域同步要求。 在同一 GPU 上，不同域之间的顺序关系或同步要求必须通过**系统作用域栅栏（system-scope fence）**实现；同一个域内，**设备作用域栅栏（device-scope fence）**仍然足够。这是满足累积性的必要条件：一个域内的栅栏不会自动涵盖另一个域的内核所发出的写入。换句话说，应当先将跨域流量刷新到系统作用域，以满足累积性要求。

此机制改变了 thread_scope_device 的作用域含义。不过，默认情况下内核仍使用域 0，因此能够维持向后兼容性。

6.2.7.3 在 CUDA 中使用同步域（Using Domains in CUDA）

逻辑域与物理域。 CUDA 通过启动属性 cudaLaunchAttributeMemSyncDomain 和 cudaLaunchAttributeMemSyncDomainMap 提供同步域功能。前者在逻辑域 cudaLaunchMemSyncDomainDefault 与 cudaLaunchMemSyncDomainRemote 之间选择；后者负责将逻辑域映射到物理域。

远程逻辑域是为执行远程内存访问的内核准备的，以便将其内存流量与本地内核的流量隔离。选择哪个同步域，并不会改变内核在语义上被允许访问哪些内存。

可使用设备属性 cudaDevAttrMemSyncDomainCount 查询域数量。Hopper GPU 具有 4 个同步域。为便于跨架构移植，较旧设备也可以使用这一功能接口，不过 Hopper 之前的设备会报告只有 1 个域。

逻辑域有助于组合不同层次的软件。例如，NCCL 等软件栈较底层的组件，可以为单次内核启动指定具有实际意义的逻辑域，而无须关心其外围应用的架构。较高层的软件则可以通过映射规则控制逻辑域对应的物理域。

未显式设置时，内核所使用的逻辑域默认为“默认域”。在多于一个物理域的 GPU 上，默认映射将默认逻辑域映射到物理域 0，将远程逻辑域映射到物理域 1。从 CUDA 12.0 开始，某些库可以把内核标记为远程逻辑域，例如 NCCL 2.16。

这样，应用程序或其他框架通常不需要修改代码，就能获得这一机制带来的好处。另一种用法是按照不同执行流来分配物理域，例如使用 NVSHMEM、或者不存在明显的计算与通信分界的程序：可以令流 A 的两个逻辑域都映射到物理域 0，而流 B 的两个逻辑域都映射到物理域 1。

示例：在远程逻辑域中启动内核
// 使用远程逻辑域启动内核
cudaLaunchAttribute domainAttr;
domainAttr.id = cudaLaunchAttrMemSyncDomain;
domainAttr.val = cudaLaunchMemSyncDomainRemote;
cudaLaunchConfig_t config;

在进行执行流捕获（stream capture）时，这两类属性都会复制到图节点中。执行 CUDA Graph 时，图会使用各节点自身的属性，间接决定物理域；图被启动到哪个执行流，该执行流上设置的域属性不会影响图本身的执行。

6.2.8 异步并发执行（Asynchronous Concurrent Execution）

CUDA 将下列操作作为能够彼此并发执行的独立任务提供给应用程序：

  1. 主机上的计算。
  2. 设备上的计算。
  3. 从主机到设备的内存传输。
  4. 从设备到主机的内存传输。
  5. 同一设备内部的内存传输。
  6. 不同设备之间的内存传输。

这些操作实际能够达到多高的并发程度，取决于具体设备支持的功能以及计算能力，以下各节将进一步说明。

6.2.8.1 主机与设备之间的并发执行（Concurrent Execution between Host and Device）

异步调用的工作方式。 异步库函数在设备完成相应任务之前，就把控制权返回给主机线程，因此主机能够继续执行其他工作。借助异步调用，多个设备操作可以被连续加入队列，待设备资源可用时由 CUDA 驱动程序执行。这减少了主机线程管理设备的工作负担，使其有机会处理其他任务。

以下设备操作相对于主机通常是异步的：

  • 内核启动。
  • 同一设备内的内存复制。
  • 大小不超过 64 KB 的内存块从主机到设备的复制。
  • 函数名带有 Async 后缀的内存复制操作。
  • 内存设置函数调用。

调试时禁用异步启动。 开发者可以把环境变量 CUDA_LAUNCH_BLOCKING 设置为 1，在系统范围内让 CUDA 应用程序的内核启动不再异步。此功能仅供调试使用，不应当作为确保生产程序可靠运行的方法。

使用 Nsight 或 Visual Profiler 等性能分析器收集硬件计数器时，除非启用了并发内核性能分析，否则内核启动会表现为同步操作。异步内存复制如果涉及未进行页锁定的主机内存，也可能表现为同步操作。

6.2.8.2 并发内核执行（Concurrent Kernel Execution）

计算能力为 2.x 及以上的部分设备能够同时运行多个内核。应用程序可检查设备属性 concurrentKernels 来查询这一能力（参见“设备枚举”）：支持时该属性值为 1。

设备能够同时执行的内核启动数量上限取决于其计算能力，原书表 21列出了相关上限。

来自一个 CUDA 上下文的内核，不能与另一个 CUDA 上下文的内核直接并发执行。GPU 可能通过时间片切换，保证不同上下文都能取得执行进展。如果希望不同进程的内核同时在同一 SM 上运行，则需要启用 MPS（Multi-Process Service）。

大量使用纹理资源或本地内存的内核，通常更难与其他内核并发执行。

6.2.8.3 数据传输与内核执行的重叠（Overlap of Data Transfer and Kernel Execution）

部分设备能够在执行内核的同时，异步地向 GPU 复制数据或从 GPU 复制数据。应用程序可以检查设备属性 asyncEngineCount（参见“设备枚举”）来查询这一能力：支持该功能的设备，此属性值大于 0。如果复制过程涉及主机内存，则主机内存必须是页锁定内存。

同一设备内部的内存复制也可能与内核执行同时进行（设备须支持 concurrentKernels 属性），和／或与设备的输入、输出复制同时进行（设备须支持 asyncEngineCount 属性）。设备内部的复制使用标准内存复制函数发起，源地址和目标地址均位于同一设备上。

6.2.8.4 并发数据传输（Concurrent Data Transfers）

计算能力为 2.x 及以上的部分设备，可以使向设备传输数据与从设备传输数据相互重叠。应用程序可通过 asyncEngineCount 属性查询该能力：对于支持这一功能的设备，此属性值为 2。要实现上述重叠，参与传输的主机内存必须为页锁定内存。

6.2.8.5 执行流（Streams）

执行流是什么。 应用程序通过 CUDA 执行流来管理以上并发操作。一个执行流由一系列按顺序执行的命令组成，这些命令可能由不同的主机线程发出。不同执行流中的命令则可能以彼此不同的顺序运行，也可能同时运行；这种行为不受保证，所以不能依赖它来保证程序正确性，例如在没有必要同步的情况下让不同内核互相通信，其行为未定义。

执行流中的命令只有在其所有依赖条件满足之后才可以执行。依赖既可能来自同一流内先前提交的命令，也可能来自其他流。同步调用成功完成后，可以保证相关命令均已执行完毕。

6.2.8.5.1 创建与销毁执行流（Creation and Destruction of Streams）

创建流对象，并在一系列内核调用以及主机与设备之间的内存复制操作中，将该对象作为 stream 参数传入，即可定义一个执行流。

下面的示例创建两个执行流，并在页锁定主机内存中分配一个 float 类型的数组 hostPtr：

cudaStream_t stream[2];
for (int i = 0; i < 2; ++i)
    cudaStreamCreate(&stream[i]);
float* hostPtr;
cudaMallocHost(&hostPtr, 2 * size);

每个执行流都依次执行三项操作：从主机到设备的复制、一次内核启动、从设备到主机的复制。

for (int i = 0; i < 2; ++i) {
    cudaMemcpyAsync(inputDevPtr + i * size, hostPtr + i * size,
                    size, cudaMemcpyHostToDevice, stream[i]);
    MyKernel<<<100, 512, 0, stream[i]>>>
        (outputDevPtr + i * size, inputDevPtr + i * size, size);
    cudaMemcpyAsync(hostPtr + i * size, outputDevPtr + i * size,
                    size, cudaMemcpyDeviceToHost, stream[i]);
}

每条执行流将主机数组 hostPtr 中由自己负责的那部分数据复制到设备上的 inputDevPtr，调用 MyKernel() 处理，再把 outputDevPtr 的结果复制回 hostPtr 相应位置。有关不同设备能力下两条执行流能够如何重叠，见后面的“重叠行为”。特别需要注意：hostPtr 必须指向页锁定主机内存，才可能实现这种重叠。

执行流使用 cudaStreamDestroy() 释放：

for (int i = 0; i < 2; ++i)
    cudaStreamDestroy(stream[i]);

如果调用 cudaStreamDestroy() 时，该流中的设备操作仍在执行，函数会立即返回；流占用的资源会在设备完成该流中的所有工作后自动释放。

6.2.8.5.2 默认执行流（Default Stream）

不指定流参数时。 不提供流参数的内核启动和主机—设备内存复制，或者将流参数设为 0 的操作，都会被提交到默认执行流，因而在该流内按顺序执行。

每线程默认流。 如果编译时使用 --default-stream per-thread 选项，或者在包含 CUDA 头文件（cuda.h 和 cuda_runtime.h）之前定义了 CUDA_API_PER_THREAD_DEFAULT_STREAM 宏，则默认流是一个普通执行流，每个主机线程都有自己的默认流。

原书注意事项： 使用 nvcc 编译时，不能仅在源文件开头写入 #define CUDA_API_PER_THREAD_DEFAULT_STREAM 1 来启用这一行为，因为 nvcc 会在翻译单元的顶部隐式包含 cuda_runtime.h。需要使用 --default-stream per-thread 编译选项，或者通过编译器选项 -DCUDA_API_PER_THREAD_DEFAULT_STREAM=1 来定义宏。

传统默认流。 使用 --default-stream legacy 编译选项时，默认流是一个特殊的 NULL stream。每个设备有一个由所有主机线程共享的 NULL stream。该流会产生后文“隐式同步”所介绍的行为。

如果编译时没有指定 --default-stream 选项，默认采用 --default-stream legacy。

6.2.8.5.3 显式同步（Explicit Synchronization）

执行流之间可以通过多种方法显式同步：

API 作用
cudaDeviceSynchronize() 等待所有主机线程的所有流中、此前发出的所有命令完成。
cudaStreamSynchronize(stream) 等待指定流中此前发出的所有命令完成；主机可等待指定流，同时允许其他流继续运行。
cudaStreamWaitEvent(stream, event) 令指定流中本次调用之后添加的命令等待给定事件完成后再执行。
cudaStreamQuery(stream) 查询某个流中此前发出的所有命令是否已经完成。
6.2.8.5.4 隐式同步（Implicit Synchronization）

如果在来自两个不同执行流的操作之间，提交了任何一个 NULL stream 上的 CUDA 操作，那么这两个不同流中的操作就不能并发执行。例外情况是这两个执行流为使用 cudaStreamNonBlocking 标志创建的非阻塞执行流。

为提高并发内核执行的可能性，应用程序应遵循两条指导原则：首先提交所有相互独立的操作，再提交依赖其他操作的工作；其次，尽可能延后任何形式的同步。

6.2.8.5.5 重叠行为（Overlapping Behavior）

两个执行流能够重叠执行多少工作，取决于命令提交到各条流的顺序，以及设备是否支持以下能力：数据传输与内核执行重叠（见 6.2.8.3）、并发内核执行（见 6.2.8.2）和／或并发数据传输（见 6.2.8.4）。

例如，假设设备不支持并发数据传输。在 6.2.8.5.1“创建与销毁执行流”的示例中，两条执行流中的工作完全无法重叠：提交给 stream[1] 的主机到设备复制，是在提交给 stream[0] 的设备到主机复制之后才发出的，所以前者只能在后者完成后开始。

如果改为先依次发出所有主机到设备复制，再发出所有内核调用，最后发出所有设备到主机复制（并假设设备支持数据传输与内核执行重叠）：

for (int i = 0; i < 2; ++i)
    cudaMemcpyAsync(inputDevPtr + i * size, hostPtr + i * size,
                    size, cudaMemcpyHostToDevice, stream[i]);

for (int i = 0; i < 2; ++i)
    MyKernel<<<100, 512, 0, stream[i]>>>
        (outputDevPtr + i * size, inputDevPtr + i * size, size);

for (int i = 0; i < 2; ++i)
    cudaMemcpyAsync(hostPtr + i * size, outputDevPtr + i * size,
                    size, cudaMemcpyDeviceToHost, stream[i]);

则提交给 stream[1] 的主机到设备复制能够与提交给 stream[0] 的内核执行重叠。

对于支持并发数据传输的设备，6.2.8.5.1 的原始示例中，两条流本身就能够发生重叠：stream[1] 中的主机到设备复制可以与 stream[0] 中的设备到主机复制重叠；如果设备也支持数据传输与内核执行重叠，还能同时与 stream[0] 的内核执行重叠。

6.2.8.5.6 主机函数（回调）（Host Functions / Callbacks）

CUDA 运行时提供 cudaLaunchHostFunc()，可在执行流中的任意位置插入一个 CPU 函数调用。在该函数之前已经提交给该流的所有命令执行完毕后，主机才会执行此函数。

以下示例为两条流分别添加一个回调 MyCallback。每条流都先完成一次主机到设备复制、一次内核启动以及一次设备到主机复制。每次设备到主机复制结束后，主机函数才会开始执行。

void CUDART_CB MyCallback(void *data) {
    printf("Inside callback %d\n", (size_t)data);
}

// ……前文中已有的准备代码……
for (size_t i = 0; i < 2; ++i) {
    cudaMemcpyAsync(devPtrIn[i], hostPtr[i], size,
                    cudaMemcpyHostToDevice, stream[i]);
    MyKernel<<<100, 512, 0, stream[i]>>>(devPtrOut[i], devPtrIn[i], size);
    cudaMemcpyAsync(hostPtr[i], devPtrOut[i], size,
                    cudaMemcpyDeviceToHost, stream[i]);
    cudaLaunchHostFunc(stream[i], MyCallback, (void*)i);
}

插入到主机函数之后的流命令，必须等主机函数执行完成之后才能开始运行。

重要限制： 插入执行流的主机函数不能直接或间接调用 CUDA API，否则它可能等待一个又依赖自身完成的操作，从而导致死锁。

6.2.8.5.7 执行流优先级（Stream Priorities）

可以在创建执行流时使用 cudaStreamCreateWithPriority() 指定流的相对优先级。cudaDeviceGetStreamPriorityRange() 用于获取可设置的优先级范围，其返回的顺序为 [最高优先级，最低优先级]。

GPU 调度器会利用流优先级决定待执行任务的次序，但优先级只是调度提示，并不提供严格保证。当调度器选择下一项工作时，较高优先级执行流中尚未执行的任务，会优先于较低优先级执行流中的任务。然而，较高优先级的任务不会抢占已经开始运行的低优先级任务。GPU 也不会在任务执行期间重新评估工作队列，因此提高某个流的优先级不会打断正在运行的工作。

由此可见，流优先级会影响调度顺序，却不强制保证严格的先后次序。应用可以借助它改善任务调度，但不能依赖优先级保证程序逻辑的正确性。

以下原书示例获取当前设备允许的优先级范围，并创建一条最高优先级执行流和一条最低优先级执行流：

// 获取当前设备允许的流优先级范围
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// 创建最高优先级流和最低优先级流
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority));
cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);

6.2.8.6 程序化依赖启动与同步（Programmatic Dependent Launch and Synchronization）

程序化依赖启动（Programmatic Dependent Launch，PDL）机制允许次级内核（secondary kernel）在它所依赖的主内核（primary kernel）尚未执行完毕时，就在同一 CUDA 流中开始启动。该机制从计算能力 9.0 的设备开始提供。如果次级内核有大量工作并不依赖主内核产生的结果，那么该技术可能改善性能。

6.2.8.6.2 API 说明（API Description）

程序化依赖启动对 CUDA 内核启动 API 引入了一些变化。实现这里描述的重叠执行，至少需要计算能力 9.0。

使用 PDL 时，主内核与次级内核被提交到同一个 CUDA 流。当主内核准备好允许次级内核开始启动时，应由其所有线程块执行 cudaTriggerProgrammaticLaunchCompletion()。次级内核则必须使用可扩展的启动 API 启动，如下面的原书示例所示。

__global__ void primary_kernel() {
    // 在次级内核启动前必须完成的前期工作

    // 触发次级内核的启动
    cudaTriggerProgrammaticLaunchCompletion();

    // 可以与次级内核重叠执行的工作
}

__global__ void secondary_kernel() {
    // 不依赖主内核结果的工作

    // 等待所有相关主内核完成，并将结果刷新到全局内存
    cudaGridDependencySynchronize();

    // 依赖主内核结果的工作
}

cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;
configSecondary.attrs = attribute;
configSecondary.numAttrs = 1;

primary_kernel<<<grid_dim, block_dim, 0, stream>>>();
cudaLaunchKernelEx(&configSecondary, secondary_kernel);

当次级内核使用 cudaLaunchAttributeProgrammaticStreamSerialization 属性启动时，CUDA 驱动程序可以安全地提前启动次级内核，而不必等到主内核完全结束并刷新所有内存写入后才进行启动。

在所有主内核线程块都已经启动并执行了 cudaTriggerProgrammaticLaunchCompletion() 之后，驱动程序可以启动次级内核。如果主内核没有显式执行该触发操作，则在主内核所有线程块退出后会隐式触发。

数据可见性仍需保证。 无论哪种情况，次级内核的线程块都有可能在主内核写入的数据变得可见之前就开始运行。因此，使用 PDL 的次级内核必须通过 cudaGridDependencySynchronize() 或其他适当方法，确认主内核的结果数据已经可用，然后才能执行依赖这些结果的操作。

这些方法只是为主内核和次级内核提供了并发执行的机会，并不保证一定发生并发。程序不能把这种机会性并发当作正确性前提，否则可能导致死锁。

6.2.8.7 CUDA 图（CUDA Graphs）

CUDA Graphs 为 CUDA 提供了一种新的工作提交模型。**图（graph）**由内核启动等一系列操作以及这些操作之间的依赖关系构成；图的定义与实际执行相互分离，因此可以先定义一次，再反复启动。将定义与执行分离带来两方面优化：一是许多准备工作可以提前完成，从而相对于传统执行流逐项提交减少 CPU 启动开销；二是 CUDA 能够提前看到整个工作流程，并进行在逐项提交模式下可能无法实现的优化。

例如，在传统执行流中，每次将内核加入流，主机驱动程序都需要执行一系列为 GPU 执行做准备的操作。这些设置和启动工作对每个内核都会产生额外开销。对执行时间较短的内核，该开销可能占端到端执行时间的显著比例。CUDA Graphs 将这些可提前完成的工作移到图实例化阶段，从而降低重复启动的成本。

使用 CUDA 图提交工作分为三个阶段：定义、实例化和执行。

  1. 定义阶段：程序创建图的操作描述，并指定这些操作之间的依赖关系。
  2. 实例化阶段：对图模板生成快照、验证图，并完成大部分工作准备和初始化，目的是尽量减少启动时必须执行的操作。由此得到的实例称为可执行图（executable graph）。
  3. 执行阶段：可执行图可以像其他 CUDA 工作一样提交到一个执行流（stream）中。实例化不必重复执行，因此同一个可执行图可以启动任意多次。

6.2.8.7.1 图结构（Graph Structure）

一个操作在图中构成一个节点（node）；操作之间的依赖关系构成边（edge）。这些依赖关系会约束操作的执行顺序。

当某个节点所依赖的节点全部完成后，该节点就可以被调度。具体调度由 CUDA 系统决定。

6.2.8.7.1.1 节点类型（Node Types）

图节点可以是以下类型之一：

  • 内核（kernel）
  • CPU 函数调用
  • 内存复制
  • 内存设置（memset）
  • 空节点
  • 等待事件
  • 记录事件
  • 发出外部信号量
  • 等待外部信号量
  • 条件节点
  • 子图（child graph）：执行一个独立的嵌套图，如图 13 所示。

6.2.8.7.1.2 边数据（Edge Data）

CUDA 12.3 为 CUDA Graph 引入了边数据（edge data）。边数据用于修改由一条边指定的依赖关系，包含三个部分：输出端口、输入端口和类型。

  • 输出端口指定相关边在什么时刻触发。
  • 输入端口指定节点的哪一部分依赖于该边。
  • 类型用于修改两个端点之间的关系。

端口取值取决于节点类型及边的方向；边类型也可能只适用于特定节点类型。所有情况下，零初始化的边数据都表示默认行为：输出端口 0 等待整个任务完成，输入端口 0 会阻塞整个任务，边类型 0 表示具有内存同步行为的完整依赖关系。

可以在若干图 API 中通过与节点并行的数组可选地指定边数据。如果输入参数中省略边数据，则使用零初始化数据。如果在输出（查询）参数中省略边数据，只有在被忽略的边数据全部为零初始化值时，API 才会接受该调用；如果查询会丢失信息，则返回 cudaErrorLossyQuery。

边数据也适用于部分执行流捕获 API：cudaStreamBeginCaptureToGraph()、cudaStreamGetCaptureInfo() 和 cudaStreamUpdateCaptureDependencies()。在这些情形中，下游节点尚不存在，边数据会关联到一条尚未连接的边（半边）；之后它会连接到未来捕获的节点，或者在执行流捕获结束时被丢弃。

请注意，有些边类型并不要求上游节点完全执行完毕才继续。这些边在判断执行流捕获是否已完全重新汇合到起始执行流时会被忽略，并且不能在捕获结束时直接丢弃。详情参见“使用执行流捕获创建图”。

目前，没有节点类型定义额外的输入端口，只有内核节点定义了额外的输出端口。当前唯一的非默认依赖类型是 cudaGraphDependencyTypeProgrammatic，它允许两个内核节点之间使用程序化依赖启动（Programmatic Dependent Launch）。

6.2.8.7.2 使用图 API 创建图（Creating a Graph Using Graph APIs）

创建图有两种机制：显式图 API和执行流捕获。下面示例展示如何创建并执行图 14 所示的图。

// 创建图；初始图为空
cudaGraphCreate(&graph, 0);

// 本例将节点与依赖关系分开创建，以展示这两个步骤可以独立完成。
// 也可以在创建节点时直接指定依赖关系。
cudaGraphAddKernelNode(&a, graph, NULL, 0, &nodeParams);
cudaGraphAddKernelNode(&b, graph, NULL, 0, &nodeParams);
cudaGraphAddKernelNode(&c, graph, NULL, 0, &nodeParams);
cudaGraphAddKernelNode(&d, graph, NULL, 0, &nodeParams);

// 设置各节点之间的依赖关系
cudaGraphAddDependencies(graph, &a, &b, 1);  // A -> B
cudaGraphAddDependencies(graph, &a, &c, 1);  // A -> C
cudaGraphAddDependencies(graph, &b, &d, 1);  // B -> D
cudaGraphAddDependencies(graph, &c, &d, 1);  // C -> D

6.2.8.7.3 使用执行流捕获创建图（Creating a Graph Using Stream Capture）

执行流捕获能够根据已有的、基于执行流的 API 创建图。可以在一段向执行流提交工作的代码前后，分别调用 cudaStreamBeginCapture() 和 cudaStreamEndCapture()；即使这段代码已经存在，也可以这样处理：

cudaGraph_t graph;

cudaStreamBeginCapture(stream);

kernel_A<<< ..., stream >>>(...);
kernel_B<<< ..., stream >>>(...);
libraryCall(stream);
kernel_C<<< ..., stream >>>(...);

cudaStreamEndCapture(stream, &graph);

调用 cudaStreamBeginCapture() 会使执行流进入捕获模式。在捕获期间，提交到该执行流的工作不会进入执行队列，而是追加到一个逐步构建的内部图中。调用 cudaStreamEndCapture() 时，系统会返回该图，同时结束此执行流的捕获模式。正在通过执行流捕获逐步构建的图称为捕获图（capture graph）。

除 cudaStreamLegacy（即“NULL 执行流”）外，任何 CUDA 执行流都可以用于执行流捕获；cudaStreamPerThread 也可以使用。如果程序使用传统执行流，在不改变功能的情况下，有时可以将执行流 0 重新定义为每线程执行流。详情参见“默认执行流”。

可以使用 cudaStreamIsCapturing() 查询某个执行流是否处于捕获状态。

还可以使用 cudaStreamBeginCaptureToGraph() 将工作捕获到一个已有图中。此时，工作会被捕获到用户提供的图，而不是内部创建的图。

6.2.8.7.3.1 跨执行流依赖与事件（Cross-stream Dependencies and Events）

只要被等待的事件已记录到同一个捕获图中，执行流捕获就能处理通过 cudaEventRecord() 和 cudaStreamWaitEvent() 表达的跨执行流依赖关系。

当事件在处于捕获模式的执行流中被记录时，系统会生成一个捕获事件（captured event）。捕获事件表示捕获图中的一组节点。

如果某个执行流等待捕获事件，那么该执行流也会进入捕获模式（如果它尚未处于该模式），并且该执行流中的下一个项目会增加对捕获事件所代表节点的依赖。此后，这两个执行流会被捕获到同一个捕获图中。

当捕获过程中存在跨执行流依赖时，cudaStreamEndCapture() 仍必须在调用 cudaStreamBeginCapture() 的同一个执行流中调用。这个执行流称为起始执行流（origin stream）。由于基于事件的依赖关系而被捕获到同一图中的其他执行流，也必须重新汇合到起始执行流。结束捕获时，所有捕获到同一图中的执行流都会退出捕获模式。如果其他执行流未重新汇合，整个捕获操作就会失败。

// stream1 是起始执行流
cudaStreamBeginCapture(stream1);

kernel_A<<< ..., stream1 >>>(...);

// 分叉到 stream2
cudaEventRecord(event1, stream1);
cudaStreamWaitEvent(stream2, event1);

kernel_B<<< ..., stream1 >>>(...);
kernel_C<<< ..., stream2 >>>(...);

// 将 stream2 重新汇合到起始执行流 stream1
cudaEventRecord(event2, stream2);
cudaStreamWaitEvent(stream1, event2);

kernel_D<<< ..., stream1 >>>(...);

// 在起始执行流中结束捕获
cudaStreamEndCapture(stream1, &graph);

// stream1 和 stream2 均已退出捕获模式

上述代码返回的图见图 14。

注意： 执行流退出捕获模式时，即使中间的某些项目已从捕获中移除，该执行流中下一个未被捕获的项目（如果存在）仍会依赖于最近一个此前未被捕获的项目。

6.2.8.7.3.2 禁止和未处理的操作（Prohibited and Unhandled Operations）

对正在捕获的执行流或捕获事件进行同步，或查询其执行状态，都是无效操作，因为它们并不代表已排入执行队列的项目。如果更大范围的句柄包含正在进行的执行流捕获，例如某个关联执行流正处于捕获模式时查询或同步设备句柄、上下文句柄，同样属于无效操作。

当同一上下文中的任意执行流正在捕获，且该执行流未使用 cudaStreamNonBlocking 创建时，尝试使用传统执行流也是无效的。原因在于，传统执行流句柄始终涵盖这些其他执行流；向传统执行流提交工作会创建对正在捕获的执行流的依赖，而查询或同步传统执行流也会查询或同步这些正在捕获的执行流。

因此，此时调用同步 API 也属于无效操作。例如，cudaMemcpy() 这样的同步 API 会向传统执行流提交工作，并在返回前执行同步。

注意： 一般来说，如果某种依赖关系会连接已被捕获的项目与未被捕获、而是直接排入执行队列的项目，CUDA 倾向于返回错误，而不是忽略该依赖关系。例外情况是执行流进入或退出捕获模式；模式切换会切断紧邻切换点前后添加到执行流中的项目之间的依赖关系。

如果某个执行流正在捕获到一个捕获图，却等待来自另一个捕获图的捕获事件，那么试图合并这两个独立捕获图也是无效的。如果没有指定 cudaEventWaitExternal 标志，捕获中的执行流等待一个未被捕获的事件同样无效。

目前，少数向执行流提交异步操作的 API 尚不支持在图中使用；如果在捕获模式下使用这些 API，例如 cudaStreamAttachMemAsync()，就会返回错误。

6.2.8.7.3.3 捕获失效（Invalidation）

在执行流捕获期间尝试无效操作时，相关捕获图会失效。捕获图失效后，在调用 cudaStreamEndCapture() 结束捕获之前，继续使用与该图相关的捕获执行流或捕获事件都是无效的，并会返回错误。

调用 cudaStreamEndCapture() 会使相关执行流退出捕获模式，但该调用也会返回错误值，并将图句柄设为 NULL。

6.2.8.7.4 CUDA 用户对象（CUDA User Objects）

CUDA 用户对象可用于管理 CUDA 异步工作所使用资源的生命周期。这一功能尤其适用于 CUDA Graph 和执行流捕获。

某些资源管理方案与 CUDA Graph 并不兼容。例如，基于事件的资源池，或“同步创建、异步销毁”的资源管理方式，都可能遇到问题。

下面示例展示一种基于资源池的库 API：

// 使用资源池分配资源的库 API
void libraryWork(cudaStream_t stream) {
    auto &resource = pool.claimTemporaryResource();
    resource.waitOnReadyEventInStream(stream);
    launchWork(stream, resource);
    resource.recordReadyEvent(stream);
}

另一个例子使用异步方式删除资源：

// 异步删除资源的库 API
void libraryWork(cudaStream_t stream) {
    Resource *resource = new Resource(...);
    launchWork(stream, resource);
    cudaStreamAddCallback(
        stream,
        [](cudaStream_t, cudaError_t, void *resource) {
            delete static_cast<Resource *>(resource);
        },
        resource,
        0);
    // 此处省略错误处理相关考虑
}

这类方案难以与 CUDA Graph 配合使用，因为资源的指针或句柄并非固定值，因而可能需要额外的间接访问或更新图；同时，每次提交工作时都需要执行同步 CPU 代码。如果这些问题对库的调用者不可见，或者捕获期间使用了被禁止的 API，那么它们也无法直接用于执行流捕获。可行的解决办法包括让库调用者能够直接访问资源；CUDA 用户对象则提供了另一种方式。

CUDA 用户对象会把用户指定的析构回调与一个内部引用计数关联起来，其机制类似于 C++ 的 shared_ptr。引用可以由 CPU 上的用户代码持有，也可以由 CUDA 图持有。需要注意的是，与 C++ 智能指针不同，用户自己持有的引用并没有对应的对象来代表它；用户必须手动跟踪这些引用。一个典型用法是：创建用户对象后，立即将唯一一个由用户持有的引用转移给 CUDA 图。

当引用关联到 CUDA 图时，CUDA 会自动管理图操作涉及的引用。克隆 cudaGraph_t 时，会按照与源图相同的数量，保留源 cudaGraph_t 所持有的每个引用的副本。实例化得到的 cudaGraphExec_t 也会保留源 cudaGraph_t 中每个引用的副本。如果销毁 cudaGraphExec_t 时执行尚未完成，则这些引用会一直保留，直到执行结束。

下面是一个使用示例：

cudaGraph_t graph;  // 已存在的图

Object *object = new Object;  // C++ 对象，其析构函数可能执行非平凡操作
cudaUserObject_t cuObject;

cudaUserObjectCreate(
    &cuObject,
    object,  // 此处使用 CUDA 提供的模板封装，它会提供删除该 C++ 对象指针的回调
    1,       // 初始引用计数
    cudaUserObjectNoDestructorSync
             // 声明不能通过 CUDA 等待此回调
);

cudaGraphRetainUserObject(
    graph,
    cuObject,
    1,  // 引用数量
    cudaGraphUserObjectMove
        // 转移调用方持有的引用，不改变总引用计数
);

// 当前线程不再持有引用，因此无需调用 release API
cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, nullptr, nullptr, 0);
// 实例化时会再保留一个引用

cudaGraphDestroy(graph);       // graphExec 仍持有一个引用
cudaGraphLaunch(graphExec, 0); // 异步启动的工作可以访问用户对象
cudaGraphExecDestroy(graphExec);
// 启动尚未同步；如果需要，释放操作会延后执行

cudaStreamSynchronize(0);
// 启动同步完成后，剩余引用被释放，析构回调会执行。
// 注意：析构回调本身会异步执行。

如果析构回调会发出某个同步对象的信号，那么此时等待该同步对象就是安全的。

子图节点中的引用会关联到子图，而不是父图。如果子图被更新或删除，相关引用也会随之改变。如果通过 cudaGraphExecUpdate 或 cudaGraphExecChildGraphNodeSetParams 更新可执行图或子图，新源图中的引用会被克隆并替换目标图中的引用。在任一情况下，如果此前启动的工作尚未完成同步，那么原本应被释放的引用会保留到这些启动操作执行完毕。

目前，CUDA API 尚未提供等待用户对象析构函数完成的机制。用户可以在析构代码中手动向同步对象发出信号。此外，与 cudaLaunchHostFunc 的限制类似，析构函数中不允许调用 CUDA API。这样做是为了避免阻塞 CUDA 内部共享线程并妨碍后续工作继续推进。如果依赖关系是单向的，并且执行 API 调用的线程不会阻碍 CUDA 工作取得进展，那么可以通知另一个线程代为执行 API 调用。

用户对象通过 cudaUserObjectCreate 创建；该 API 是了解相关接口的良好起点。

6.2.8.7.5 更新已实例化的图（Updating Instantiated Graphs）

使用 CUDA Graph 提交工作分为三个阶段：定义、实例化和执行。当工作流程保持不变时，定义和实例化的开销可以分摊到多次执行中，因此 CUDA Graph 相较于执行流可能具有明显优势。

图是某个工作流程的快照，其中包含内核、参数和依赖关系，以便尽可能快速、高效地重放该流程。如果工作流程发生变化，原有图就可能过时，需要进行修改。若图结构发生较大变化，例如拓扑结构或节点类型变化，则通常需要重新实例化源图，因为与拓扑相关的各种优化必须重新应用。

反复实例化的成本可能降低图执行带来的整体性能收益。不过，常见情况是只有节点参数发生变化，例如内核参数或 cudaMemcpy 地址改变，而图拓扑保持不变。对此，CUDA 提供一种轻量级机制，称为图更新（Graph Update），可以原地修改部分节点参数，而不必重建整个图。与重新实例化相比，这种方式高效得多。

更新会在下一次启动图时生效，因此不会影响之前已经启动的图，即使这些图当时仍在运行。图可以反复更新并重新启动，所以同一个执行流中可以排入多个更新与启动操作。

CUDA 提供两种更新已实例化图参数的机制：

  • 整体图更新（whole graph update）：用户提供一个拓扑结构相同、但节点参数已更新的 cudaGraph_t 对象。
  • 单个节点更新（individual node update）：用户显式更新指定节点的参数。

当需要更新大量节点，或调用方不知道图的具体拓扑结构（例如图来自某个库调用的执行流捕获）时，使用更新后的 cudaGraph_t 更方便。当需要修改的节点较少，且用户持有这些节点的句柄时，更适合逐个更新节点。单个节点更新会跳过对未更改节点的拓扑检查和比较，因此在许多情况下效率更高。

CUDA 还提供了启用或禁用单个节点的机制，而不会改变该节点当前的参数。下面各节将分别说明这些方法。

6.2.8.7.5.1 图更新的限制（Graph Update Limitations）

内核节点：

  • 该函数所属的 CUDA 上下文不能改变。
  • 原本不使用 CUDA 动态并行的节点，不能更新为使用 CUDA 动态并行的函数。

cudaMemset 和 cudaMemcpy 节点：

  • 操作数所分配或映射到的 CUDA 设备不能改变。
  • 源内存和目标内存必须分别从与原始源内存、目标内存相同的上下文中分配。
  • 只能更改一维的 cudaMemset / cudaMemcpy 节点。

额外的内存复制节点限制：

  • 不支持更改源或目标内存类型（例如 cudaPitchedPtr、cudaArray_t 等），也不支持更改传输类型（即 cudaMemcpyKind）。

外部信号量等待节点和记录节点：

  • 不支持更改信号量的数量。

条件节点：

  • 两张图中句柄的创建顺序和赋值顺序必须一致。
  • 不支持更改节点参数，例如条件节点中的图数量、节点上下文等。
  • 条件节点内部图中的节点参数，仍受上述规则约束。

主机节点、事件记录节点和事件等待节点的更新不受这些限制。

6.2.8.7.5.2 整体图更新（Whole Graph Update）

cudaGraphExecUpdate() 可以使用一张拓扑结构完全相同的图（即“更新图”）中的参数，更新一个已实例化的图（即“原始图”）。

更新图的拓扑结构必须与实例化 cudaGraphExec_t 时使用的原始图完全一致。此外，指定依赖关系的顺序也必须一致。最后，CUDA 还需要以一致的顺序排列汇点节点（即没有依赖关系的节点）。CUDA 依靠特定 API 调用的顺序来确保汇点节点排序一致。

更具体地说，遵守以下规则，可以让 cudaGraphExecUpdate() 确定性地配对原始图和更新图中的节点：

  1. 对于任何参与捕获的执行流，操作该执行流的 API 调用必须保持相同顺序，包括事件等待以及其他不直接对应节点创建的 API 调用。
  2. 直接修改某个图节点入边的 API 调用（包括捕获执行流 API、添加节点 API、添加或移除边的 API）必须保持相同顺序。此外，如果这些 API 通过数组指定依赖关系，数组中依赖项的排列顺序也必须相同。
  3. 汇点节点必须保持一致的顺序。汇点节点是指调用 cudaGraphExecUpdate() 时，最终图中没有后续依赖节点或出边的节点。以下操作会影响汇点节点顺序（如果存在），因此作为一个整体必须保持相同顺序：
    • 添加节点后产生汇点节点的 API 调用；
    • 移除边后使某节点成为汇点节点的操作；
    • cudaStreamUpdateCaptureDependencies() 从捕获执行流的依赖集合中移除汇点节点的操作；
    • cudaStreamEndCapture()。

下面示例展示如何更新一个已实例化的图：

cudaGraphExec_t graphExec = NULL;

for (int i = 0; i < 10; i++) {
    cudaGraph_t graph;
    cudaGraphExecUpdateResult updateResult;
    cudaGraphNode_t errorNode;

    // 本例通过执行流捕获创建图，也可以使用 Graph API 创建。
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

    // 调用用户定义的、基于执行流的工作负载，例如：
    do_cuda_work(stream);

    cudaStreamEndCapture(stream, &graph);

    // 如果已经实例化过图，则尝试直接更新，以避免实例化开销。
    if (graphExec != NULL) {
        // 若更新失败，errorNode 将指向导致失败的节点，
        // updateResult 将包含失败原因代码。
        cudaGraphExecUpdate(graphExec, graph, &errorNode, &updateResult);
    }

    // 首次迭代，或更新因任何原因失败时，重新实例化。
    if (graphExec == NULL || updateResult != cudaGraphExecUpdateSuccess) {

        // 如果此前更新失败，重新实例化前先销毁旧的 cudaGraphExec_t。
        if (graphExec != NULL) {
            cudaGraphExecDestroy(graphExec);
        }

        // 从 graph 实例化 graphExec；此处不使用错误节点和错误消息参数。
        cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
    }

    cudaGraphDestroy(graph);
    cudaGraphLaunch(graphExec, stream);
    cudaStreamSynchronize(stream);
}

典型工作流程是：先通过执行流捕获或 Graph API 创建初始 cudaGraph_t，然后像往常一样实例化并启动它。首次启动之后，再用相同方法创建一张新的 cudaGraph_t，并调用 cudaGraphExecUpdate()。

如果更新成功（如示例中的 updateResult 所示），就启动更新后的 cudaGraphExec_t。如果更新因任何原因失败，则调用 cudaGraphExecDestroy() 销毁原有的 cudaGraphExec_t，再调用 cudaGraphInstantiate() 重新实例化。

也可以直接修改 cudaGraph_t 的节点（例如调用 cudaGraphKernelNodeSetParams()），再更新 cudaGraphExec_t。不过，使用下一节介绍的显式节点更新 API 效率更高。

条件节点的句柄标志和默认值也会作为图更新的一部分进行更新。更多用法和当前限制，请参阅 Graph API 文档。

6.2.8.7.5.3 单个节点更新（Individual Node Update）

可以直接更新已实例化图中节点的参数。这样既省去了重新实例化的开销，也不需要创建新的 cudaGraph_t。如果需要更新的节点数量相对于整张图的节点总数较少，逐个更新节点会更合适。

可用于更新 cudaGraphExec_t 节点的 API 包括：

  • cudaGraphExecKernelNodeSetParams()
  • cudaGraphExecMemcpyNodeSetParams()
  • cudaGraphExecMemsetNodeSetParams()
  • cudaGraphExecHostNodeSetParams()
  • cudaGraphExecChildGraphNodeSetParams()
  • cudaGraphExecEventRecordNodeSetEvent()
  • cudaGraphExecEventWaitNodeSetEvent()
  • cudaGraphExecExternalSemaphoresSignalNodeSetParams()
  • cudaGraphExecExternalSemaphoresWaitNodeSetParams()

更多用法和当前限制，请参阅 Graph API 文档。

6.2.8.7.5.4 单个节点启用（Individual Node Enable）

在已实例化的图中，可以使用 cudaGraphNodeSetEnabled() API 启用或禁用内核节点、memset 节点和 memcpy 节点。这样便可以创建一张包含所需功能超集的图，并在每次启动时按需要进行定制。可以使用 cudaGraphNodeGetEnabled() 查询节点当前是否启用。

节点被禁用时，在功能上等同于空节点，直到该节点重新启用。启用或禁用节点不会影响节点参数。通过单个节点更新或使用 cudaGraphExecUpdate() 进行整体图更新，也不会改变节点的启用状态。在节点被禁用期间所做的参数更新，会在节点重新启用后生效。

可用于启用、禁用 cudaGraphExec_t 中节点并查询其状态的 API 包括：

  • cudaGraphNodeSetEnabled()
  • cudaGraphNodeGetEnabled()

具体用法和当前限制请参阅 Graph API 文档。

6.2.8.7.6 使用图 API（Using Graph APIs）

cudaGraph_t 对象不是线程安全的。用户有责任确保多个线程不会同时访问同一个 cudaGraph_t。

一个 cudaGraphExec_t 不能与自身并发运行。对同一个可执行图的多次启动会按照启动顺序依次排列，后一次启动会排在前一次启动之后。

为了与其他异步工作保持顺序关系，图会在执行流中执行。不过，执行流在这里仅用于排序：它不会限制图内部的并行性，也不会决定图节点在哪里执行。

更多信息请参阅 Graph API 文档。

6.2.8.7.7 设备端图启动（Device Graph Launch）

许多工作流程需要在运行时根据数据作出决策，并依据决策执行不同的操作。与其把决策过程交给主机执行（这可能需要设备与主机之间进行一次往返通信），用户有时更希望直接在设备上完成决策。为此，CUDA 提供了从设备端启动图的机制。

设备端图启动为设备端实现动态控制流提供了方便方式，无论是简单循环，还是复杂的设备端工作调度器，都可以使用这一功能。此功能仅适用于支持统一寻址的系统。

下文将可从设备端启动的图称为设备图（device graph），不能从设备端启动的图称为主机图（host graph）。

设备图既可以从主机端启动，也可以从设备端启动；主机图则只能从主机端启动。与主机端启动不同，如果某个设备图上一次设备端启动尚未结束，就再次从设备端启动同一张图，会导致错误并返回 cudaErrorInvalidValue。因此，同一张设备图不能同时被设备端启动两次。如果同时从主机端和设备端启动同一张设备图，则行为未定义。

6.2.8.7.7.1 创建设备图（Device Graph Creation）

若要从设备端启动一张图，必须显式地将它实例化为可供设备端启动的图。具体做法是在调用 cudaGraphInstantiate() 时传入标志 cudaGraphInstantiateFlagDeviceLaunch。

与主机图一样，设备图的结构在实例化时就固定下来；若要更改结构，必须重新实例化，而且实例化操作只能在主机端执行。要使一张图能够以设备端启动方式实例化，它还必须满足若干要求。

6.2.8.7.7.2 设备图的要求（Device Graph Requirements）

一般要求：

  • 图中的所有节点必须位于同一个设备上。
  • 图中只能包含内核节点、内存复制节点、内存设置节点和子图节点。

内核节点：

  • 图中的内核不允许使用 CUDA 动态并行。
  • 只要未启用 MPS，就允许协作式启动（cooperative launch）。

内存复制节点：

  • 只允许涉及设备内存和/或已固定且映射到设备的主机内存的复制操作。
  • 不允许涉及 CUDA 数组的复制操作。
  • 实例化时，源操作数和目标操作数都必须能由当前设备访问。即使复制目标是另一台设备上的内存，复制操作仍会由承载该图的设备执行。

6.2.8.7.7.3 将设备图上传到设备（Device Graph Upload）

要在设备端启动一张图，必须先将其上传到设备，以创建所需的设备资源。可以通过以下两种方式完成：显式调用 cudaGraphUpload()，或在调用 cudaGraphInstantiateWithParams() 实例化时要求同时上传；也可以先从主机端启动该图，借此隐式完成上传。

// 实例化后显式上传
cudaGraphInstantiate(&deviceGraphExec1, deviceGraph1,
                     cudaGraphInstantiateFlagDeviceLaunch);
cudaGraphUpload(deviceGraphExec1, stream);

// 在实例化过程中显式上传
cudaGraphInstantiateParams instantiateParams = {0};
instantiateParams.flags =
    cudaGraphInstantiateFlagDeviceLaunch |
    cudaGraphInstantiateFlagUpload;
instantiateParams.uploadStream = stream;
cudaGraphInstantiateWithParams(&deviceGraphExec2, deviceGraph2,
                               &instantiateParams);

// 通过主机端启动隐式上传
cudaGraphInstantiate(&deviceGraphExec3, deviceGraph3,
                     cudaGraphInstantiateFlagDeviceLaunch);
cudaGraphLaunch(deviceGraphExec3, stream);

6.2.8.7.7.4 更新设备图（Device Graph Update）

设备图只能从主机端更新。可执行图更新后，必须重新将设备图上传到设备，更新内容才会生效。可以使用上一节所述的相同方法完成上传。

与主机图不同，如果在更新操作进行期间从设备端启动设备图，行为将未定义。

6.2.8.7.7.5 设备端启动（Device Launch）

设备图既可以从主机端，也可以从设备端通过 cudaGraphLaunch() 启动；该函数在设备端和主机端具有相同的函数签名。主机端和设备端使用同一个句柄来启动设备图。

当从设备端启动时，设备图必须由另一张图启动。

设备端图启动以线程为单位进行，因此不同线程可能同时发起多次启动。用户需要选择一个唯一线程来负责启动指定图，避免多个线程重复启动。

6.2.8.7.7.6 设备端启动模式（Device Launch Modes）

与主机端启动不同，设备图不能启动到普通 CUDA 执行流中，而只能启动到具有特定名称、分别表示不同启动模式的执行流中。

cudaStreamGraphTailLaunch 尾部启动（Tail launch）

6.2.8.7.7.7 发起后不等待的启动（Fire and Forget Launch）

顾名思义，发起后不等待的启动会立即提交到 GPU，并独立于启动它的图执行。在这种情形中，启动图是父图，被启动的图是子图。

__global__ void launchFireAndForgetGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphFireAndForget);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化并上传设备图
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2,
                         cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化负责启动的图
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchFireAndForgetGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，由它进一步启动设备图
    cudaGraphLaunch(gExec1, stream);
}

6.2.8.7.7.8 图的执行环境（Graph Execution Environments）

要完整理解设备端同步模型，首先需要理解**执行环境（execution environment）**这一概念。

从设备端启动图时，该图会在自己的执行环境中运行。某张图的执行环境包含图中的全部工作，以及该图生成的所有发起后不等待的工作。只有当图本身执行完成、并且所有生成的子工作都已完成时，才能认为这张图执行完毕。

当图由主机端启动时，会存在一个执行流环境（stream environment），作为被启动图的执行环境的父环境。执行流环境包含整个启动过程生成的所有工作。只有当整个执行流环境被标记为完成时，执行流启动才算完成；此时依赖于该工作之后的任务才可以继续运行。

6.2.8.7.7.9 尾部启动（Tail Launch）

与主机端不同，GPU 不能通过 cudaDeviceSynchronize() 或 cudaStreamSynchronize() 等传统方法与设备图进行同步。为实现串行工作之间的依赖关系，CUDA 提供了另一种启动模式——尾部启动（tail launch）。

当一张图的执行环境被判定为完成时，尾部启动才会执行。也就是说，图本身及其所有子图都完成后，尾部启动列表中的下一张图才会运行。此时，下一张图的执行环境会取代已经完成的执行环境，成为父执行环境的子环境。

与发起后不等待的启动类似，一张图可以排入多个尾部启动。下面的代码可以生成相应执行流程。

图 19：简单的尾部启动（A Simple Tail Launch）。

__global__ void launchTailGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphTailLaunch);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化并上传设备图
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2,
                         cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化负责启动的图
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchTailGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，由它进一步启动设备图
    cudaGraphLaunch(gExec1, stream);
}

同一张图排入的尾部启动会按照入队顺序逐个执行：最先入队的图先运行，随后执行第二张，依此类推。

由某张尾部图排入的新尾部启动，会先于尾部启动列表中此前图所排入的尾部启动执行；这些新启动仍然按照自身入队顺序执行。

一张图最多可以有 255 个待处理的尾部启动。

6.2.8.7.7.10 尾部自启动（Tail Self-launch）

设备图可以将自身排入尾部启动，但同一张图在任意时刻最多只能排入一次自启动。

为了查询当前正在运行、并可再次启动的设备图，CUDA 新增了一个设备端函数：

cudaGraphExec_t cudaGetCurrentGraphExec();

如果当前运行的是设备图，该函数会返回当前图的句柄。如果当前执行的内核并不是设备图中的节点，该函数会返回 NULL。

下面的示例使用该函数实现循环式重新启动：

__device__ int relaunchCount = 0;

__global__ void relaunchSelf() {
    int relaunchMax = 100;

    if (threadIdx.x == 0) {
        if (relaunchCount < relaunchMax) {
            cudaGraphLaunch(cudaGetCurrentGraphExec(),
                            cudaStreamGraphTailLaunch);
        }

        relaunchCount++;
    }
}

6.2.8.7.7.11 兄弟启动（Sibling Launch）

兄弟启动是发起后不等待启动的一种变体。被启动的图并不是作为启动图执行环境的子环境，而是作为启动图父执行环境的子环境。换言之，兄弟启动等价于从启动图的父执行环境中执行一次发起后不等待的启动。

图 22：简单的兄弟启动（Simple Sibling Launch）。

下面示例展示如何使用兄弟启动：

__global__ void launchSiblingGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphFireAndForgetAsSibling);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化并上传设备图
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2,
                         cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化负责启动的图
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchSiblingGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，由它进一步启动设备图
    cudaGraphLaunch(gExec1, stream);
}

由于兄弟启动并不在启动图自己的执行环境中运行，因此它不会阻止启动图排入的尾部启动继续执行。

6.2.8.7.8 条件图节点（Conditional Graph Nodes）

条件节点允许对条件节点内部的图进行条件执行和循环执行。这样可以完全在图内部表示动态、迭代式的工作流程，使主机 CPU 能够同时处理其他工作。

当条件节点的所有依赖都满足后，条件值会在设备端进行判断。条件节点包括以下类型：

  • 条件 IF 节点：执行该节点时，如果条件值非零，就执行一次其内部图。
  • 条件 WHILE 节点：执行该节点时，如果条件值非零，就执行其内部图；此后持续重复执行，直到条件值变为零。

条件值通过条件句柄（conditional handle）访问，并且必须在创建条件节点之前创建。设备端代码可以通过 cudaGraphSetConditional() 设置条件值。创建句柄时还可以指定一个默认值，该默认值会在每次图启动时应用。

创建条件节点时，系统会同时创建一个空图，并将句柄返回给用户，以便用户填充该图。条件节点内部的图既可以通过 Graph API 填充，也可以通过 cudaStreamBeginCaptureToGraph() 捕获工作来填充。

条件节点可以嵌套使用。

6.2.8.7.8.1 条件句柄（Conditional Handles）

条件值由 cudaGraphConditionalHandle 表示，并通过 cudaGraphConditionalHandleCreate() 创建。

每个句柄必须关联到一个条件节点。句柄不能被销毁。

如果创建句柄时指定了 cudaGraphCondAssignDefault，那么在每次图执行开始时，条件值都会被初始化为指定的默认值。如果未提供该标志，则每次图执行开始时的条件值都是未定义的，代码不应假定条件值会在多次执行之间保留。

整体图更新时，与句柄关联的默认值和标志也会一并更新。

6.2.8.7.8.2 条件节点内部图的要求（Conditional Node Body Graph Requirements）

一般要求：

  • 图中的所有节点必须位于同一设备上。
  • 图中只能包含内核节点、空节点、内存复制节点、内存设置节点、子图节点和条件节点。

内核节点：

  • 图中的内核不允许使用 CUDA 动态并行。
  • 只要未启用 MPS，就允许协作式启动。

  • 不允许涉及 CUDA 数组的复制或设置操作。

6.2.8.7.8.4 条件 WHILE 节点（Conditional WHILE Nodes）

WHILE 节点的内部图会持续执行，直到条件值为零。条件值会在节点开始执行时，以及每次内部图执行完成后重新评估。图 24 展示了一个包含三个节点的图，其中中间节点 B 是条件节点。

图 24：条件 WHILE 节点（Conditional WHILE Node）。

__global__ void loopKernel(cudaGraphConditionalHandle handle)
{
    static int count = 10;
    cudaGraphSetConditional(handle, --count ? 1 : 0);
}

void graphSetup() {

    cudaGraphExec_t graphExec;
    cudaGraphNode_t node;

    cParams.conditional.type = cudaGraphCondTypeWhile;
    cParams.conditional.size = 1;
    cudaGraphAddNode(&node, graph, NULL, 0, &cParams);

    cudaGraph_t bodyGraph = cParams.conditional.phGraph_out[0];

    cudaGraphNodeParams params = { cudaGraphNodeTypeKernel };
    params.kernel.func = (void *)loopKernel;
    params.kernel.gridDim.x = params.kernel.gridDim.y =
        params.kernel.gridDim.z = 1;
    params.kernel.blockDim.x = params.kernel.blockDim.y =
        params.kernel.blockDim.z = 1;
    params.kernel.kernelParams = kernelArgs;
    kernelArgs[0] = &handle;
    cudaGraphAddNode(&node, bodyGraph, NULL, 0, &params);

    cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
    cudaGraphLaunch(graphExec, 0);
    cudaDeviceSynchronize();

    cudaGraphExecDestroy(graphExec);
    cudaGraphDestroy(graph);
}

6.2.8.8 事件（Events）

CUDA 运行时还提供了监视设备执行进度和进行精确计时的机制。应用程序可以在程序任意位置异步记录事件，并查询事件何时完成。

当事件之前的所有任务（或者按需指定的、某个执行流中所有命令）都完成后，事件即视为完成。对于零号执行流中的事件，只有在所有执行流中位于该事件之前的任务和命令全部完成后，该事件才算完成。

6.2.8.8.1 创建和销毁事件（Creation and Destruction of Events）

以下代码创建两个事件：

cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

使用下面的方式销毁它们：

cudaEventDestroy(start);
cudaEventDestroy(stop);

6.2.8.8.2 经过时间（Elapsed Time）

前面创建的事件可以用来测量执行流创建与异步工作示例所需的时间：

cudaEventRecord(start, 0);
for (int i = 0; i < 2; ++i) {
    cudaMemcpyAsync(inputDev + i * size, inputHost + i * size,
                    size, cudaMemcpyHostToDevice, stream[i]);
    MyKernel<<<100, 512, 0, stream[i]>>>
               (outputDev + i * size, inputDev + i * size, size);
    cudaMemcpyAsync(outputHost + i * size, outputDev + i * size,
                    size, cudaMemcpyDeviceToHost, stream[i]);
}
cudaEventRecord(stop, 0);
cudaEventSynchronize(stop);
float elapsedTime;
cudaEventElapsedTime(&elapsedTime, start, stop);

6.2.8.9 同步调用（Synchronous Calls）

调用同步函数时，在设备完成所请求的任务之前，控制权不会返回给主机线程。

主机线程在等待期间是让出处理器、阻塞等待还是进行自旋等待，可以通过 cudaSetDeviceFlags() 指定特定标志来设置。必须在该主机线程执行任何其他 CUDA 调用之前完成设置，具体选项请参阅参考手册。

6.2.9 多设备系统（Multi-Device System）

6.2.9.1 枚举设备（Device Enumeration）

一个主机系统可能包含多台设备。下面的代码示例枚举设备、查询设备属性，并确定支持 CUDA 的设备数量。

int deviceCount;
cudaGetDeviceCount(&deviceCount);

int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\\n",
           device, deviceProp.major, deviceProp.minor);
}

6.2.9.2 选择设备（Device Selection）

主机线程可以随时通过调用 cudaSetDevice() 设置当前操作的设备。设备内存分配和内核启动都发生在当前设备上；执行流和事件也会与当前设备关联。如果没有调用 cudaSetDevice()，当前设备默认为设备 0。

以下代码展示当前设备设置如何影响内存分配和内核执行：

size_t size = 1024 * sizeof(float);

cudaSetDevice(0);             // 将设备 0 设为当前设备
float* p0;
cudaMalloc(&p0, size);        // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0);  // 在设备 0 上启动内核

cudaSetDevice(1);             // 将设备 1 设为当前设备
float* p1;
cudaMalloc(&p1, size);        // 在设备 1 上分配内存
MyKernel<<<1000, 128>>>(p1);  // 在设备 1 上启动内核

6.2.9.3 执行流与事件的行为（Stream and Event Behavior）

如果向一个不属于当前设备的执行流发起内核启动，该启动就会失败。例如：

cudaSetDevice(0);               // 将设备 0 设为当前设备
cudaStream_t s0;
cudaStreamCreate(&s0);          // 在设备 0 上创建执行流 s0
MyKernel<<<100, 64, 0, s0>>>(); // 在设备 0 的 s0 中启动内核

cudaSetDevice(1);               // 将设备 1 设为当前设备
cudaStream_t s1;
cudaStreamCreate(&s1);          // 在设备 1 上创建执行流 s1
MyKernel<<<100, 64, 0, s1>>>(); // 在设备 1 的 s1 中启动内核

// 以下内核启动会失败：
MyKernel<<<100, 64, 0, s0>>>(); // 当前设备为 1，但 s0 属于设备 0

即使内存复制提交到一个不属于当前设备的执行流中，复制仍可能成功。事件相关 API 则有不同的限制：

  • 如果输入事件和输入执行流属于不同设备，cudaEventRecord() 会失败。
  • 如果两个输入事件属于不同设备，cudaEventElapsedTime() 会失败。
  • 即使输入事件关联的设备不是当前设备，cudaEventSynchronize() 和 cudaEventQuery() 仍会成功。
  • 即使输入执行流与输入事件属于不同设备，cudaStreamWaitEvent() 仍会成功。因此，可以使用它在多台设备之间建立同步关系。

每台设备都有自己的默认执行流。因此，不同设备各自默认执行流中的命令，可能乱序执行，也可能彼此并发执行。

6.2.9.4 对等设备内存访问（Peer-to-Peer Memory Access）

根据系统属性，尤其是 PCIe 和/或 NVLink 的拓扑结构，不同设备可能能够直接访问彼此的内存。也就是说，在一台设备上执行的内核，可以解引用指向另一台设备内存的指针。

如果对这两台设备调用 cudaDeviceCanAccessPeer() 后返回 true，则它们支持对等设备内存访问（peer-to-peer memory access）。

对等设备内存访问只支持 64 位应用程序，并且必须调用 cudaDeviceEnablePeerAccess() 在两台设备之间启用。在未启用 NVSwitch 的系统上，每台设备最多支持系统范围内的八个对等连接。

由于两台设备使用统一地址空间（参见“统一虚拟地址空间”），同一个指针可以用于访问两台设备上的内存：

cudaSetDevice(0);                   // 将设备 0 设为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设为当前设备
cudaDeviceEnablePeerAccess(0, 0);   // 启用对设备 0 的对等访问

// 在设备 1 上启动内核。
// 该内核可以通过地址 p0 访问设备 0 上的内存。
MyKernel<<<1000, 128>>>(p0);

6.2.9.4.1 Linux 上的 IOMMU（IOMMU on Linux）

仅在 Linux 上，CUDA 和显示驱动不支持启用 IOMMU 的裸机 PCIe 对等内存复制，但支持通过虚拟机直通（VM pass-through）使用 IOMMU。

因此，在原生裸机 Linux 系统上运行时，用户应禁用 IOMMU。对于虚拟机，则应启用 IOMMU，并使用 VFIO 驱动进行 PCIe 直通。

Windows 不存在上述限制。另请参阅“在 64 位平台上分配 DMA 缓冲区”。

6.2.9.5 对等设备内存复制（Peer-to-Peer Memory Copy）

可以在两台不同设备的内存之间执行复制。如果两台设备使用统一地址空间（参见“统一虚拟地址空间”），则可以使用“设备内存”一节介绍的常规内存复制函数。

否则，应使用 cudaMemcpyPeer()、cudaMemcpyPeerAsync()、cudaMemcpy3DPeer() 或 cudaMemcpy3DPeerAsync()。例如：

cudaSetDevice(0);                   // 将设备 0 设为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存

cudaSetDevice(1);                   // 将设备 1 设为当前设备
float* p1;
cudaMalloc(&p1, size);              // 在设备 1 上分配内存

cudaSetDevice(0);                   // 将设备 0 设为当前设备
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设为当前设备
cudaMemcpyPeer(p1, 1, p0, 0, size); // 将 p0 复制到 p1
MyKernel<<<1000, 128>>>(p1);        // 在设备 1 上启动内核

在隐式 NULL 执行流中执行两台设备之间的内存复制时：

  • 只有在两台设备此前提交的所有命令均已完成后，复制才会开始；
  • 复制完成之前，之后提交到任一设备的命令都不能开始执行。

与执行流的常规行为一致，不同设备之间的异步复制可以与其他执行流中的复制或内核重叠执行。

如果已通过 cudaDeviceEnablePeerAccess() 在两台设备之间启用对等访问，那么两台设备之间的对等内存复制就不再需要经过主机中转，因此速度会更快。

6.2.10 统一虚拟地址空间（Unified Virtual Address Space）

当应用程序以 64 位进程运行时，主机和所有计算能力为 2.0 及以上的设备使用一个统一地址空间。通过 CUDA API 进行的所有主机内存分配，以及受支持设备上的所有设备内存分配，都位于该虚拟地址范围内。因此：

  • 对于通过 CUDA 分配的主机内存，或使用统一地址空间的设备内存，可以通过指针值调用 cudaPointerGetAttributes() 来确定内存所在位置。
  • 向使用统一地址空间的设备内存复制数据，或从中复制数据时，可以将 cudaMemcpy*() 的 cudaMemcpyKind 参数设置为 cudaMemcpyDefault，由 CUDA 根据指针判断内存位置。只要当前设备使用统一寻址，这一方式也适用于未通过 CUDA 分配的主机指针。
  • 通过 cudaHostAlloc() 分配的内存会自动成为可供所有使用统一地址空间的设备访问的可移植内存（参见“可移植内存”）。返回的指针可以直接用于这些设备上运行的内核，无需再调用 cudaHostGetDevicePointer() 获取设备指针。

应用程序可以通过检查设备属性 unifiedAddressing 是否等于 1，来查询指定设备是否使用统一地址空间。

6.2.11 进程间通信（Interprocess Communication）

由某个主机线程创建的设备内存指针或事件句柄，可以直接被同一进程中的其他线程引用。但它们在进程外无效，因此不能被另一个进程中的线程直接引用。

若要在不同进程之间共享设备内存指针和事件，应用程序必须使用进程间通信（IPC）API。该 API 在参考手册中有详细说明。IPC API 仅支持 Linux 上的 64 位进程，以及计算能力为 2.0 及以上的设备。请注意，该 API 不支持通过 cudaMallocManaged() 分配的内存。

使用此 API 时，应用程序可以通过 cudaIpcGetMemHandle() 获取指定设备内存指针的 IPC 句柄，再通过标准进程间通信机制（例如进程间共享内存或文件）将句柄传给另一个进程。另一个进程可以调用 cudaIpcOpenMemHandle()，从该句柄获取一个在当前进程中有效的设备指针。事件句柄也可以通过类似的接口共享。

出于性能原因，cudaMalloc() 分配的内存有时会从更大的内存块中进行子分配。在这种情况下，CUDA IPC API 会共享整个底层内存块，可能导致其他子分配区域也被共享，从而产生进程间信息泄露的风险。为避免这种情况，建议只共享大小按 2 MiB 对齐的分配区域。

一种典型用法是由一个主进程生成一批输入数据，再将数据提供给多个辅助进程，从而避免重复生成或复制数据。相互之间使用 CUDA IPC 通信的应用程序，应使用相同的 CUDA 驱动程序和运行时进行编译、链接和运行。

注意： 从 CUDA 11.5 开始，对于计算能力为 7.x 及以上的 L4T 和嵌入式 Linux Tegra 设备，仅支持事件共享 IPC API；Tegra 平台仍不支持内存共享 IPC API。

6.2.12 错误检查（Error Checking）

所有运行时函数都会返回错误代码。但对于异步函数（参见“异步并发执行”），由于函数会在设备完成任务之前返回，因此返回代码无法报告设备上可能发生的异步错误。它只能报告任务执行前在主机上发生的错误，通常与参数验证有关。若发生异步错误，该错误会由后续某次无关的运行时函数调用报告。

因此，若要在调用某个异步函数后立即检查异步错误，唯一的方法是在该调用之后进行同步，例如调用 cudaDeviceSynchronize()（或使用“异步并发执行”一节介绍的其他同步机制），并检查同步函数返回的错误代码。

运行时会为每个主机线程维护一个错误变量，初始值为 cudaSuccess。每次发生错误时（无论是参数验证错误还是异步错误），该变量都会被新的错误代码覆盖。cudaPeekAtLastError() 返回此变量；cudaGetLastError() 返回此变量并将其重置为 cudaSuccess。

内核启动不会返回错误代码，因此必须在启动后立即调用 cudaPeekAtLastError() 或 cudaGetLastError()，以获取启动前的错误。为了确保返回的错误不是由内核启动前的调用引起，应在启动内核之前确认运行时错误变量为 cudaSuccess，例如在启动前调用一次 cudaGetLastError()。

由于内核启动是异步的，若要检查异步错误，应用程序必须在内核启动与调用 cudaPeekAtLastError() 或 cudaGetLastError() 之间执行同步。

cudaStreamQuery() 和 cudaEventQuery() 可能返回 cudaErrorNotReady，但该状态不被视为错误，因此不会由 cudaPeekAtLastError() 或 cudaGetLastError() 报告。

6.2.13 调用栈（Call Stack）

对于计算能力为 2.x 及以上的设备，可以使用 cudaDeviceGetLimit() 查询调用栈大小，并使用 cudaDeviceSetLimit() 设置调用栈大小。

如果调用栈溢出，并且应用程序正在 CUDA 调试器（CUDA-GDB、Nsight）中运行，那么内核调用会以栈溢出错误失败；否则，可能会报告未指定的启动错误。

如果编译器无法确定栈大小，就会发出警告：Stack size cannot be statically determined。递归函数通常会触发此警告。如果出现该警告，而默认栈大小又不足，用户就需要手动设置栈大小。

6.2.14 纹理与表面内存（Texture and Surface Memory）

CUDA 支持 GPU 为图形处理而设计的纹理硬件的一个子集，用于访问纹理内存和表面内存。与从全局内存读取数据相比，从纹理内存或表面内存读取数据可能带来若干性能优势，详见“设备内存访问”。

6.2.14.1 纹理内存（Texture Memory）

内核通过“纹理函数”一节所述的设备函数读取纹理数据。调用这些函数读取纹理的过程称为纹理读取（texture fetch）。每次纹理读取都需要指定一个纹理对象（texture object），以便通过纹理对象 API 访问对应的纹理。

纹理对象会指定以下属性。

纹理资源与维数

  • 纹理资源：即本次读取所访问的纹理内存区域。纹理对象在运行时创建，创建时指定纹理资源，详见“纹理对象 API”。
  • 维数：指定纹理是一维数组、二维数组还是三维数组，分别需要一个、两个或三个纹理坐标。数组中的元素称为 texel，即 texture element（纹理元素）。纹理的宽度、高度和深度分别表示数组在各维度上的大小。不同计算能力对应的最大纹理宽度、高度和深度见技术规格表。

纹理元素类型与读取模式

  • 纹理元素类型：仅限基本整数类型、单精度浮点类型，以及由这些基本类型构成的“内置向量类型”一节所定义的 1、2 或 4 分量向量类型。
  • 读取模式：可以是 cudaReadModeNormalizedFloat 或 cudaReadModeElementType。如果使用 cudaReadModeNormalizedFloat，并且纹理元素为 8 位或 16 位整数，则读取结果会转换为浮点数：无符号整数的完整取值范围映射到 \([0.0,1.0]\)，有符号整数的完整取值范围映射到 \([-1.0,1.0]\)。例如，值为 0xff 的无符号 8 位纹理元素会读取为 1。如果使用 cudaReadModeElementType，则不进行转换。

纹理坐标是否归一化

默认情况下，纹理函数使用浮点坐标，坐标范围为 \([0,N-1]\)，其中 \(N\) 是对应维度的纹理大小。例如，大小为 64×32 的纹理，其 x 坐标范围为 \([0,63]\)，y 坐标范围为 \([0,31]\)。

归一化纹理坐标则使用 \([0.0,1.0-1/N]\) 的范围。因此，同一个 64×32 纹理在 x、y 两个维度上的归一化坐标范围分别为 \([0,1-1/64]\) 和 \([0,1-1/32]\)。如果希望坐标不受纹理尺寸影响，归一化坐标会很有用。

寻址模式（Addressing Mode）

即使坐标超出范围，也可以调用纹理函数。寻址模式决定越界时如何处理。

默认模式是将坐标钳制到有效范围：非归一化坐标为 \([0,N)\)，归一化坐标为 \([0.0,1.0)\)。如果使用边界模式，越界坐标的纹理读取会返回 0。

对于归一化坐标，还可以使用环绕模式和镜像模式：

  • 环绕模式将坐标 \(x\) 转换为 \(\mathrm{frac}(x)=x-\lfloor x\rfloor\)。
  • 镜像模式在 \(\lfloor x\rfloor\) 为偶数时使用 \(\mathrm{frac}(x)\)，为奇数时使用 \(1-\mathrm{frac}(x)\)。

寻址模式由长度为 3 的数组指定，其第 1、2、3 个元素分别对应第 1、2、3 个纹理坐标。可选值为 cudaAddressModeBorder、cudaAddressModeClamp、cudaAddressModeWrap 和 cudaAddressModeMirror。其中 cudaAddressModeWrap 与 cudaAddressModeMirror 仅支持归一化纹理坐标。

过滤模式（Filtering Mode）

过滤模式决定如何根据输入纹理坐标计算读取值。线性纹理过滤只适用于配置为返回浮点数据的纹理，它会对相邻 texel 进行低精度插值。

  • 一维纹理使用线性插值。
  • 二维纹理使用双线性插值。
  • 三维纹理使用三线性插值。

过滤模式为 cudaFilterModePoint 或 cudaFilterModeLinear。点过滤返回纹理坐标最近的 texel；线性过滤则对最近的两个（一维）、四个（二维）或八个（三维）texel 进行线性插值。cudaFilterModeLinear 仅适用于返回浮点类型值的情况。

“纹理对象 API”介绍纹理对象接口；“16 位浮点纹理”介绍如何处理 16 位浮点纹理；纹理还可以按“分层纹理”一节所述方式进行分层。“立方体贴图纹理”和“分层立方体贴图纹理”介绍一种特殊的纹理类型——立方体贴图纹理。

6.2.14.1.1 纹理对象 API（Texture Object API）

纹理对象通过 cudaCreateTextureObject() 创建。创建时需要提供资源描述 struct cudaResourceDesc，用于指定纹理资源，以及一个纹理描述 struct cudaTextureDesc：

struct cudaTextureDesc
{
    enum cudaTextureAddressMode addressMode[3];
    enum cudaTextureFilterMode filterMode;
    enum cudaTextureReadMode    readMode;
    int                         sRGB;
    int                         normalizedCoords;
    unsigned int                maxAnisotropy;
    enum cudaTextureFilterMode  mipmapFilterMode;
    float                       mipmapLevelBias;
    float                       minMipmapLevelClamp;
    float                       maxMipmapLevelClamp;
};

各字段含义如下：

  • addressMode 指定寻址模式。
  • filterMode 指定过滤模式。
  • readMode 指定读取模式。
  • normalizedCoords 指定纹理坐标是否归一化。
  • sRGB、maxAnisotropy、mipmapFilterMode、mipmapLevelBias、minMipmapLevelClamp 和 maxMipmapLevelClamp 的详细说明请参阅参考手册。

下面的示例对纹理应用一个简单的坐标变换。

// 简单变换内核
__global__ void transformKernel(float* output,
                                cudaTextureObject_t texObj,
                                int width, int height,
                                float theta)
{
    // 计算归一化纹理坐标
    unsigned int x = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int y = blockIdx.y * blockDim.y + threadIdx.y;

    float u = x / (float)width;
    float v = y / (float)height;

    // 变换坐标
    u -= 0.5f;
    v -= 0.5f;
    float tu = u * cosf(theta) - v * sinf(theta) + 0.5f;
    float tv = v * cosf(theta) + u * sinf(theta) + 0.5f;

    // 从纹理读取，并写入全局内存
    output[y * width + x] = tex2D<float>(texObj, tu, tv);
}

主机端代码分配 1024×1024 的浮点数组，将其复制到设备上的 CUDA 数组，设置纹理资源和纹理对象参数，执行变换内核，再把结果复制回主机：

int main()
{
    const int height = 1024;
    const int width = 1024;
    float angle = 0.5;

    // 分配并初始化主机数据
    float *h_data = (float *)std::malloc(sizeof(float) * width * height);
    for (int i = 0; i < height * width; ++i)
        h_data[i] = i;

    // 在设备内存中分配 CUDA 数组
    cudaChannelFormatDesc channelDesc =
        cudaCreateChannelDesc(32, 0, 0, 0, cudaChannelFormatKindFloat);
    cudaArray_t cuArray;
    cudaMallocArray(&cuArray, &channelDesc, width, height);

    // 设置源数据的 pitch（以字节计的每行宽度，包括填充）。
    // 本例中没有额外填充。
    const size_t spitch = width * sizeof(float);

    // 将主机内存 h_data 中的数据复制到设备内存
    cudaMemcpy2DToArray(cuArray, 0, 0, h_data, spitch,
                        width * sizeof(float), height,
                        cudaMemcpyHostToDevice);

    // 指定纹理资源
    struct cudaResourceDesc resDesc;
    memset(&resDesc, 0, sizeof(resDesc));
    resDesc.resType = cudaResourceTypeArray;
    resDesc.res.array.array = cuArray;

    // 指定纹理对象参数
    struct cudaTextureDesc texDesc;
    memset(&texDesc, 0, sizeof(texDesc));
    texDesc.addressMode[0] = cudaAddressModeWrap;
    texDesc.addressMode[1] = cudaAddressModeWrap;
    texDesc.filterMode = cudaFilterModeLinear;
    texDesc.readMode = cudaReadModeElementType;
    texDesc.normalizedCoords = 1;

    // 创建纹理对象
    cudaTextureObject_t texObj = 0;
    cudaCreateTextureObject(&texObj, &resDesc, &texDesc, NULL);

    // 在设备内存中分配变换结果
    float *output;
    cudaMalloc(&output, width * height * sizeof(float));

    // 调用内核
    dim3 threadsperBlock(16, 16);
    dim3 numBlocks((width + threadsperBlock.x - 1) / threadsperBlock.x,
                   (height + threadsperBlock.y - 1) / threadsperBlock.y);
    transformKernel<<<numBlocks, threadsperBlock>>>(
        output, texObj, width, height, angle);

    // 将数据从设备复制回主机
    cudaMemcpy(h_data, output, width * height * sizeof(float),
               cudaMemcpyDeviceToHost);

    // 销毁纹理对象
    cudaDestroyTextureObject(texObj);

    // 释放设备内存
    cudaFreeArray(cuArray);
    cudaFree(output);

    // 释放主机内存
    free(h_data);

    return 0;
}

6.2.14.1.2 16 位浮点纹理（16-Bit Floating-Point Textures）

CUDA 数组支持的 16 位浮点格式（也称 half 格式）与 IEEE 754-2008 的 binary16 格式相同。

CUDA C++ 没有与之对应的原生数据类型，但提供了通过 unsigned short 在 16 位和 32 位浮点格式之间转换的内置函数：__float2half_rn(float) 和 __half2float(unsigned short)。这些函数只能在设备代码中使用。主机代码中可使用功能等效的函数，例如 OpenEXR 库中的相应函数。

在纹理读取过程中，16 位浮点分量会先提升为 32 位浮点数，然后才执行过滤。

可以通过调用 cudaCreateChannelDescHalf*() 系列函数，为 16 位浮点格式创建通道描述。

6.2.14.1.3 分层纹理（Layered Textures）

一维或二维分层纹理（在 Direct3D 中也称 texture array，在 OpenGL 中也称 array texture）由一系列图层组成；每个图层都是常规纹理，并且所有图层具有相同的维数、大小和数据类型。

一维分层纹理使用一个整数索引和一个浮点纹理坐标进行寻址：整数索引表示图层，纹理坐标表示该图层内的纹理元素。二维分层纹理使用一个整数索引和两个浮点纹理坐标进行寻址；整数索引选择图层，两个坐标定位该图层中的纹理元素。

分层纹理只能通过调用 cudaMalloc3DArray() 创建为 CUDA 数组，并设置 cudaArrayLayered 标志；对于一维分层纹理，高度必须设置为零。

分层纹理由 tex1DLayered() 和 tex2DLayered() 等设备函数读取。纹理过滤只会在单个图层内部执行，不会跨图层进行过滤。分层纹理仅支持计算能力为 2.0 及以上的设备。

6.2.14.1.4 立方体贴图纹理（Cubemap Textures）

立方体贴图纹理是一种特殊的二维分层纹理，包含代表立方体六个面的六个图层：

  • 每个图层的宽度等于高度。
  • 立方体贴图使用三个纹理坐标 \(x\)、\(y\)、\(z\) 进行寻址。这三个坐标被解释为从立方体中心指向某个面的方向向量，并用于定位该面上的纹理元素。

具体来说，系统会选取绝对值最大的坐标分量，其符号决定立方体的具体面；随后使用表 3 中定义的 \(s\) 和 \(t\)，以 \((s/m+1)/2\) 和 \((t/m+1)/2\) 计算该图层中的坐标，其中 \(m\) 是绝对值最大的坐标分量。

6.2.14.1.5 分层立方体贴图纹理（Cubemap Layered Textures）

分层立方体贴图纹理是一种分层纹理，其中每个图层本身都是尺寸相同的立方体贴图。

它使用一个整数索引和三个浮点纹理坐标进行寻址：整数索引用于选择序列中的立方体贴图，三个坐标用于定位该立方体贴图中的纹理元素。

分层立方体贴图必须通过调用 cudaMalloc3DArray()，同时设置 cudaArrayLayered 和 cudaArrayCubemap 标志来创建为 CUDA 数组。读取时使用 texCubemapLayered()。纹理过滤仅在单个图层内部执行，不会跨图层进行过滤。该功能仅支持计算能力为 2.0 及以上的设备。

6.2.14.1.6 纹理聚集读取（Texture Gather）

纹理聚集读取（texture gather）是一种特殊的纹理读取方式，仅适用于二维纹理。它通过 tex2Dgather() 执行，参数与 tex2D() 相同，但额外包含一个 comp 参数，其值可以是 0、1、2 或 3。

该函数返回四个 32 位数值，分别对应普通纹理读取进行双线性过滤时会用到的四个纹理元素中，分量 comp 的值。例如，假设四个纹理元素的值分别为 (253, 20, 31, 255)、(250, 25, 29, 254)、(249, 16, 37, 253) 和 (251, 22, 30, 250)，当 comp 为 2 时，tex2Dgather() 返回 (31, 29, 37, 30)。

纹理坐标的小数部分仅使用 8 位精度。因此，在普通 tex2D() 的某个权重可能恰好为 1.0 的情况下，tex2Dgather() 可能返回意料之外的结果。例如，当 x 纹理坐标为 2.49805 时，\(x_B=x-0.5=1.99805\)，但其小数部分会以 8 位定点格式存储。由于 0.99805 更接近 \(256/256\) 而不是 \(255/256\)，\(x_B\) 会被表示为 2。在这种情况下，tex2Dgather() 会返回 x 方向索引 2 和 3 的元素，而不是索引 1 和 2。

纹理聚集读取只支持使用 cudaArrayTextureGather 标志创建的 CUDA 数组，并且宽度和高度必须小于表 21 中规定的纹理聚集读取最大尺寸；该尺寸限制小于普通纹理读取的最大尺寸。该功能仅支持计算能力为 2.0 及以上的设备。

6.2.14.2 表面内存（Surface Memory）

对于计算能力为 2.0 及以上的设备，如果 CUDA 数组在创建时设置了 cudaArraySurfaceLoadStore 标志（参见“立方体贴图表面”），就可以通过表面对象（surface object）以及“表面函数”一节所述的函数对其进行读取和写入。

设备支持的最大表面宽度、高度和深度取决于计算能力，相关限制列在表 21 中。

6.2.14.2.1 表面对象 API（Surface Object API）

表面对象通过 cudaCreateSurfaceObject() 创建，参数为类型 struct cudaResourceDesc 的资源描述。

与纹理内存不同，表面内存使用字节寻址。这意味着，如果要通过表面函数访问纹理函数所访问的同一纹理元素，必须将纹理坐标中的 x 坐标乘以元素的字节大小。

例如，对于绑定到纹理对象 texObj 和表面对象 surfObj 的一维浮点 CUDA 数组，纹理坐标为 x 的元素可以通过纹理对象调用 tex1D(texObj, x) 读取；通过表面对象读取时，则使用 surf1Dread(surfObj, 4*x)。

类似地，对于二维浮点 CUDA 数组，纹理坐标为 (x, y) 的元素可通过 tex2D(texObj, x, y) 访问；通过表面对象读取时使用 surf2Dread(surfObj, 4*x, y)。其中 y 坐标的字节偏移由 CUDA 根据底层 CUDA 数组的行跨度（pitch）自动计算。

下面的复制内核展示了表面读取和写入：

__global__ void copyKernel(cudaSurfaceObject_t inputSurfObj,
                           cudaSurfaceObject_t outputSurfObj,
                           int width, int height)
{
    unsigned int x = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < width && y < height) {
        uchar4 data;
        surf2Dread(&data, inputSurfObj, x * 4, y);
        surf2Dwrite(data, outputSurfObj, x * 4, y);
    }
}

主机端代码需要为输入、输出分别分配启用了表面读写的 CUDA 数组，设置资源描述并创建表面对象，然后启动内核，最后将结果复制回主机并释放资源。

6.2.14.3 CUDA 数组（CUDA Arrays）

CUDA 数组是一种经过优化、适合纹理读取的、不透明内存布局。它可以是一维、二维或三维数组，由多个元素组成；每个元素包含 1、2 或 4 个分量。分量可以是有符号或无符号的 8、16、32 位整数，16 位浮点数，或 32 位浮点数。

内核只能通过纹理读取（参见“纹理内存”）或表面读取与写入（参见“表面内存”）访问 CUDA 数组。

6.2.14.4 读写一致性（Read/Write Coherency）

纹理内存和表面内存都使用缓存。在同一次内核调用期间，缓存不会针对全局内存写入和表面内存写入保持一致。因此，如果某个地址在同一次内核调用中已经通过全局内存写入或表面写入被修改，那么随后对该地址执行纹理读取或表面读取将返回未定义的数据。

换言之，只有当纹理或表面内存位置在此前的内核调用或内存复制操作中已经更新时，线程才能安全地读取该位置；如果该位置是在同一次内核调用中由当前线程或其他线程更新的，则不能保证读取结果。

6.2.15 图形互操作（Graphics Interoperability）

OpenGL 和 Direct3D 的部分资源可以映射到 CUDA 的地址空间。这样，CUDA 就能够读取由 OpenGL 或 Direct3D 写入的数据，也能够写入供 OpenGL 或 Direct3D 后续使用的数据。

资源必须先注册到 CUDA，之后才能通过“OpenGL 互操作”和“Direct3D 互操作”一节所述的函数进行映射。这些函数会返回类型为 struct cudaGraphicsResource 的 CUDA 图形资源指针。

资源注册可能产生较高开销，因此通常每个资源只需注册一次。可以通过 cudaGraphicsUnregisterResource() 取消注册。每个准备使用该资源的 CUDA 上下文都必须分别注册该资源。

资源注册后，可以根据需要多次调用 cudaGraphicsMapResources() 和 cudaGraphicsUnmapResources() 进行映射与取消映射。还可以调用 cudaGraphicsResourceSetMapFlags() 指定使用提示（例如只写或只读），供 CUDA 驱动程序优化资源管理。

映射后的资源可以由内核读取或写入：对于缓冲区，使用 cudaGraphicsResourceGetMappedPointer() 返回的设备内存地址；对于 CUDA 数组，则使用 cudaGraphicsSubResourceGetMappedArray() 返回的数组。

当资源处于映射状态时，如果同时通过 OpenGL、Direct3D 或另一个 CUDA 上下文访问该资源，结果将未定义。“OpenGL 互操作”和“Direct3D 互操作”分别介绍了各图形 API 的具体要求与代码示例；“SLI 互操作”介绍系统处于 SLI 模式时的相关细节。

6.2.15.1 OpenGL 互操作（OpenGL Interoperability）

可以映射到 CUDA 地址空间的 OpenGL 资源包括 OpenGL 缓冲区对象、纹理对象和渲染缓冲区对象。

缓冲区对象使用 cudaGraphicsGLRegisterBuffer() 注册。在 CUDA 中，它表现为设备指针，因此内核可以读写该缓冲区，也可以通过 cudaMemcpy() 访问它。

纹理对象或渲染缓冲区对象使用 cudaGraphicsGLRegisterImage() 注册。在 CUDA 中，它们表现为 CUDA 数组。内核可以将该数组绑定到纹理引用或表面引用后读取；如果资源使用 cudaGraphicsRegisterFlagsSurfaceLoadStore 标志注册，也可以通过表面写入函数写入。还可以通过 cudaMemcpy2D() 读取或写入该数组。

cudaGraphicsGLRegisterImage() 支持具有 1、2 或 4 个分量，并且内部类型为浮点数（例如 GL_RGBA_FLOAT32）、归一化整数（例如 GL_RGBA8、GL_INTENSITY16）或非归一化整数（例如 GL_RGBA8UI）的纹理格式。请注意，非归一化整数格式需要 OpenGL 3.0，因此只能由着色器写入，不能通过固定功能管线写入。

执行任何 OpenGL 互操作 API 调用时，资源所属的 OpenGL 上下文必须在调用该 API 的主机线程中处于当前状态。

注意： 一旦 OpenGL 纹理被设为无绑定状态（bindless），例如通过 glGetTextureHandle* 或 glGetImageHandle* API 请求图像或纹理句柄，就不能再将该纹理注册到 CUDA。应用程序必须在请求图像或纹理句柄之前完成互操作注册。

下面的示例使用内核动态修改存储在顶点缓冲区对象中的二维 width × height 顶点网格。

表面对象复制示例：主机端代码

下面补全上一节表面复制示例的主机端部分，包括 CUDA 数组分配、数据复制、表面对象创建、内核启动、结果回传与资源释放。

int main()
{
    const int height = 1024;
    const int width = 1024;

    unsigned char *h_data =
        (unsigned char *)std::malloc(sizeof(unsigned char) * width * height * 4);
    for (int i = 0; i < height * width * 4; ++i)
        h_data[i] = i;

    cudaChannelFormatDesc channelDesc =
        cudaCreateChannelDesc(8, 8, 8, 8, cudaChannelFormatKindUnsigned);

    cudaArray_t cuInputArray;
    cudaMallocArray(&cuInputArray, &channelDesc, width, height,
                    cudaArraySurfaceLoadStore);
    cudaArray_t cuOutputArray;
    cudaMallocArray(&cuOutputArray, &channelDesc, width, height,
                    cudaArraySurfaceLoadStore);

    const size_t spitch = 4 * width * sizeof(unsigned char);
    cudaMemcpy2DToArray(cuInputArray, 0, 0, h_data, spitch,
                        4 * width * sizeof(unsigned char), height,
                        cudaMemcpyHostToDevice);

    struct cudaResourceDesc resDesc;
    memset(&resDesc, 0, sizeof(resDesc));
    resDesc.resType = cudaResourceTypeArray;

    resDesc.res.array.array = cuInputArray;
    cudaSurfaceObject_t inputSurfObj = 0;
    cudaCreateSurfaceObject(&inputSurfObj, &resDesc);

    resDesc.res.array.array = cuOutputArray;
    cudaSurfaceObject_t outputSurfObj = 0;
    cudaCreateSurfaceObject(&outputSurfObj, &resDesc);

    dim3 threadsperBlock(16, 16);
    dim3 numBlocks((width + threadsperBlock.x - 1) / threadsperBlock.x,
                   (height + threadsperBlock.y - 1) / threadsperBlock.y);
    copyKernel<<<numBlocks, threadsperBlock>>>(
        inputSurfObj, outputSurfObj, width, height);

    cudaMemcpy2DFromArray(h_data, spitch, cuOutputArray, 0, 0,
                          4 * width * sizeof(unsigned char), height,
                          cudaMemcpyDeviceToHost);

    cudaDestroySurfaceObject(inputSurfObj);
    cudaDestroySurfaceObject(outputSurfObj);
    cudaFreeArray(cuInputArray);
    cudaFreeArray(cuOutputArray);
    free(h_data);

    return 0;
}

6.2.15.3 SLI 互操作（SLI Interoperability）

在多 GPU 系统中，所有支持 CUDA 的 GPU 都可以通过 CUDA 驱动程序和运行时作为独立设备访问。不过，当系统处于 SLI 模式时，需要注意以下事项。

首先，在一块 GPU 的 CUDA 设备上进行的内存分配，也会占用 Direct3D 或 OpenGL 设备所使用的 SLI 配置中其他 GPU 的内存。因此，分配可能会比预期更早失败。

其次，应用程序应当为 SLI 配置中的每块 GPU 分别创建一个 CUDA 上下文。虽然这不是硬性要求，但这样可以避免设备之间不必要的数据传输。

对于 Direct3D，可以使用 cudaD3D[9|10|11]GetDevices()；对于 OpenGL，可以使用 cudaGLGetDevices()，以确定当前帧和下一帧中负责渲染的设备所对应的 CUDA 设备句柄。根据这些信息，应用程序通常会选择适当的设备，并将 Direct3D 或 OpenGL 资源映射到这些函数返回的 CUDA 设备上。查询时，deviceList 参数可设置为 cudaD3D[9|10|11]DeviceListCurrentFrame 或 cudaGLDeviceListCurrentFrame。

请注意，通过 cudaGraphicsD3D[9|10|11]RegisterResource() 和 cudaGraphicsGLRegisterBuffer() / cudaGraphicsGLRegisterImage() 注册的资源，只能在执行注册操作的设备上使用。因此，在 SLI 配置中，如果不同帧的数据由不同 CUDA 设备计算，就必须分别在每台设备上注册资源。

CUDA 运行时与 Direct3D、OpenGL 互操作的详细信息，请参阅相应的 Direct3D 互操作和 OpenGL 互操作章节。

6.2.16 外部资源互操作（External Resource Interoperability）

外部资源互操作允许 CUDA 导入由其他 API 显式导出的特定资源。这些对象通常通过操作系统原生句柄导出，例如 Linux 上的文件描述符或 Windows 上的 NT 句柄；也可以通过 NVIDIA Software Communication Interface 等统一接口导出。

可导入的资源分为两类：内存对象和同步对象。

内存对象可以通过 cudaImportExternalMemory() 导入 CUDA。导入后，内核可以通过映射到该内存对象的设备指针访问它，这些指针由 cudaExternalMemoryGetMappedBuffer() 获取；也可以通过 cudaExternalMemoryGetMappedMipmappedArray() 获取映射到该对象的 CUDA mipmapped array。根据内存对象类型，同一个对象可能允许建立多个映射，但这些映射必须与导出 API 中设置的映射一致；映射不匹配会导致未定义行为。

导入的内存对象必须使用 cudaDestroyExternalMemory() 释放。销毁内存对象不会自动释放它的映射。因此，映射到该对象的设备指针必须通过 cudaFree() 显式释放，映射到该对象的 CUDA mipmapped array 则必须通过 cudaFreeMipmappedArray() 显式释放。对象销毁后，继续访问其映射是非法的。

同步对象可以通过 cudaImportExternalSemaphore() 导入。导入后，可以使用 cudaSignalExternalSemaphoresAsync() 发出信号，并使用 cudaWaitExternalSemaphoresAsync() 等待信号。对应的信号尚未发出之前，不允许提交等待操作。此外，根据导入的同步对象类型，发出信号和等待信号的方式可能还受到后续小节所述的其他限制。

导入的信号量对象必须通过 cudaDestroyExternalSemaphore() 释放。销毁信号量对象前，所有尚未完成的信号和等待操作都必须完成。

6.2.16.1.1 匹配设备 UUID（Matching Device UUIDs）

导入 Vulkan 导出的内存对象和同步对象时，必须在创建这些对象的同一设备上导入并映射它们。可以比较 CUDA 设备的 UUID 与创建这些对象的 Vulkan 物理设备的 UUID，确定对应的 CUDA 设备，如下例所示。

请注意，Vulkan 物理设备不应属于包含多个 Vulkan 物理设备的设备组。通过 vkEnumeratePhysicalDeviceGroups 返回、且包含指定 Vulkan 物理设备的设备组，其物理设备数量必须为 1。

int getCudaDeviceForVulkanPhysicalDevice(
    VkPhysicalDevice vkPhysicalDevice)
{
    VkPhysicalDeviceIDProperties vkPhysicalDeviceIDProperties = {};
    vkPhysicalDeviceIDProperties.sType =
        VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_ID_PROPERTIES;
    vkPhysicalDeviceIDProperties.pNext = NULL;

    VkPhysicalDeviceProperties2 vkPhysicalDeviceProperties2 = {};
    vkPhysicalDeviceProperties2.sType =
        VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_PROPERTIES_2;
    vkPhysicalDeviceProperties2.pNext = &vkPhysicalDeviceIDProperties;

    vkGetPhysicalDeviceProperties2(vkPhysicalDevice,
                                   &vkPhysicalDeviceProperties2);

    int cudaDeviceCount;
    cudaGetDeviceCount(&cudaDeviceCount);

    for (int cudaDevice = 0; cudaDevice < cudaDeviceCount; cudaDevice++) {
        cudaDeviceProp deviceProp;
        cudaGetDeviceProperties(&deviceProp, cudaDevice);

        if (!memcmp(&deviceProp.uuid,
                    vkPhysicalDeviceIDProperties.deviceUUID,
                    VK_UUID_SIZE)) {
            return cudaDevice;
        }
    }

    return cudaInvalidDeviceId;
}

6.2.16.1.2 导入内存对象（Importing Memory Objects）

在 Linux 和 Windows 10 上，可以将 Vulkan 导出的专用或非专用内存对象导入 CUDA。在 Windows 7 上，只能导入专用内存对象。导入 Vulkan 专用内存对象时，必须设置 cudaExternalMemoryDedicated 标志。

通过 VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_FD_BIT 导出的 Vulkan 内存对象，可以使用与该对象关联的文件描述符导入 CUDA。成功导入后，CUDA 会接管该文件描述符的所有权；此后继续使用该文件描述符会导致未定义行为。

cudaExternalMemory_t importVulkanMemoryObjectFromFileDescriptor(
    int fd, unsigned long long size, bool isDedicated)
{
    cudaExternalMemory_t extMem = NULL;
    cudaExternalMemoryHandleDesc desc = {};

    memset(&desc, 0, sizeof(desc));
    desc.type = cudaExternalMemoryHandleTypeOpaqueFd;
    desc.handle.fd = fd;
    desc.size = size;

    if (isDedicated) {
        desc.flags |= cudaExternalMemoryDedicated;
    }

    cudaImportExternalMemory(&extMem, &desc);

    // 此后不应再使用 fd，因为 CUDA 已接管其所有权。
    return extMem;
}

Vulkan 使用 VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_WIN32_BIT 导出的内存对象，也可以通过关联的 NT 句柄导入 CUDA。CUDA 不会接管该 NT 句柄的所有权；当不再需要该句柄时，应用程序有责任将其关闭。NT 句柄会持有对资源的引用，因此必须先显式释放该句柄，底层内存才能被释放。

6.2.16.3.1 匹配设备 LUID（Matching Device LUIDs）

导入由 Direct3D 12 导出的内存对象和同步对象时，必须在创建这些对象的同一设备上导入并映射。可以比较 CUDA 设备的 LUID 与创建对象的 Direct3D 12 设备的 LUID，确定相应的 CUDA 设备。

注意：Direct3D 12 设备不能创建在链接节点适配器上。也就是说，ID3D12Device::GetNodeCount() 返回的节点数量必须为 1。

6.2.16.4.1 匹配设备 LUID（Matching Device LUIDs）

int getCudaDeviceForD3D11Device(ID3D11Device *d3d11Device)
{

                                (void **)&dxgiDevice);

    IDXGIAdapter *dxgiAdapter;
    dxgiDevice->GetAdapter(&dxgiAdapter);

    DXGI_ADAPTER_DESC dxgiAdapterDesc;
    dxgiAdapter->GetDesc(&dxgiAdapterDesc);
    LUID d3d11Luid = dxgiAdapterDesc.AdapterLuid;

    cudaGetDeviceCount(&cudaDeviceCount);

    for (int cudaDevice = 0; cudaDevice < cudaDeviceCount; cudaDevice++) {
        cudaDeviceProp deviceProp;
        cudaGetDeviceProperties(&deviceProp, cudaDevice);
        char *cudaLuid = deviceProp.luid;

                    sizeof(d3d11Luid.LowPart)) &&
            !memcmp(&d3d11Luid.HighPart,
                    cudaLuid + sizeof(d3d11Luid.LowPart),

}

6.2.16.4.6 对导入的同步对象发出信号和等待（Signaling/Waiting on Imported Synchronization Objects）

void signalExternalSemaphore(cudaExternalSemaphore_t extSem,
                             unsigned long long value,
                             cudaStream_t stream)
{
    cudaExternalSemaphoreSignalParams params = {};
    memset(&params, 0, sizeof(params));
    params.params.fence.value = value;
    cudaSignalExternalSemaphoresAsync(&extSem, &params, 1, stream);
}

{

6.2.16.5 NVIDIA 软件通信接口互操作（NVIDIA Software Communication Interface Interoperability，NvSci）

NvSciBuf 和 NvSciSync 是为以下目的开发的接口：

  • NvSciBuf：允许应用程序分配并交换内存缓冲区。
  • NvSciSync：允许应用程序在操作边界管理同步对象。

这些接口的更多信息可参阅 NVIDIA DRIVE 文档：https://docs.nvidia.com/drive。

6.2.16.5.1 导入内存对象（Importing Memory Objects）

若要分配与某个 CUDA 设备兼容的 NvSciBuf 对象，必须在 NvSciBuf 属性列表中使用 NvSciBufGeneralAttrKey_GpuId 设置相应 GPU 的 ID。

应用程序还可以选择指定以下属性：

  • NvSciBufGeneralAttrKey_NeedCpuAccess：指定缓冲区是否需要由 CPU 访问。
  • NvSciBufRawBufferAttrKey_Align：指定 NvSciBufType_RawBuffer 的对齐要求。
  • NvSciBufGeneralAttrKey_RequiredPerm：为不同用户态驱动（UMD）配置该 NvSciBuf 内存对象实例的访问权限。例如，可以调用 NvSciBufObjDupWithReducePerm()，以 NvSciBufAccessPerm_Readonly 为参数创建一个权限降低的重复对象，再将该对象导入 CUDA，使 GPU 仅具有只读权限。
  • NvSciBufGeneralAttrKey_EnableGpuCache：控制 GPU L2 缓存是否启用。
  • NvSciBufGeneralAttrKey_EnableGpuCompression：指定 GPU 压缩设置。

这些属性及其有效取值的详细信息，请参阅 NvSciBuf 文档。

下面示例展示如何创建 NvSciBuf 对象，并设置相关属性。代码中的 SIZE、dev、属性列表和错误变量需要由应用程序上下文提供。

NvSciBufObj createNvSciBufObject()
{
    // 为 CUDA 创建原始缓冲区属性
    NvSciBufType bufType = NvSciBufType_RawBuffer;
    uint64_t rawsize = SIZE;
    uint64_t align = 0;
    bool cpuaccess_flag = true;
    NvSciBufAttrValAccessPerm perm = NvSciBufAccessPerm_ReadWrite;

    NvSciRmGpuId gpuid[] = {};
    CUuuid uuid;
    cuDeviceGetUuid(&uuid, dev);

    memcpy(&gpuid[0].bytes, &uuid.bytes, sizeof(uuid.bytes));

    // 对设备 dev 禁用缓存
    NvSciBufAttrValGpuCache gpuCache[] = {{gpuid[0], false}};
    NvSciBufAttrValGpuCompression gpuCompression[] = {
        {gpuid[0], NvSciBufCompressionType_GenericCompressible}
    };

    // 填写属性值
    NvSciBufAttrKeyValuePair rawbuffattrs[] = {
        { NvSciBufGeneralAttrKey_Types, &bufType, sizeof(bufType) },
        { NvSciBufRawBufferAttrKey_Size, &rawsize, sizeof(rawsize) },
        { NvSciBufRawBufferAttrKey_Align, &align, sizeof(align) },
        { NvSciBufGeneralAttrKey_NeedCpuAccess, &cpuaccess_flag,
          sizeof(cpuaccess_flag) },
        { NvSciBufGeneralAttrKey_RequiredPerm, &perm, sizeof(perm) },
        { NvSciBufGeneralAttrKey_GpuId, &gpuid, sizeof(gpuid) },
        { NvSciBufGeneralAttrKey_EnableGpuCache, &gpuCache,
          sizeof(gpuCache) },
        { NvSciBufGeneralAttrKey_EnableGpuCompression, &gpuCompression,
          sizeof(gpuCompression) }
    };

    // 通过属性设置创建列表
    err = NvSciBufAttrListSetAttrs(
        attrListBuffer, rawbuffattrs,
        sizeof(rawbuffattrs) / sizeof(NvSciBufAttrKeyValuePair));

    NvSciBufAttrListCreate(NvSciBufModule, &attrListBuffer);

    // 协调属性并分配
    NvSciBufAttrListReconcile(&attrListBuffer, 1,
                              &attrListReconciledBuffer,
                              &attrListConflictBuffer);
    NvSciBufObjAlloc(attrListReconciledBuffer, &bufferObjRaw);
    return bufferObjRaw;
}

如果需要只读 NvSciBuf 内存对象，可以为同一个内存缓冲区创建一个权限降低的重复句柄：

NvSciBufObj bufferObjRo; // 只读 NvSciBuf 内存对象

已分配的 NvSciBuf 内存对象可以通过 NvSciBufObj 句柄导入 CUDA。应用程序应查询已分配对象的属性，以填写 CUDA 外部内存描述符。属性列表和 NvSciBuf 对象应由应用程序负责维护。

如果导入 CUDA 的 NvSciBuf 对象同时也被其他驱动映射，那么应用程序必须根据 NvSciBufGeneralAttrKey_GpuSwNeedCacheCoherency 输出属性的值，酌情使用 NvSciSync 对象作为屏障，以维持 CUDA 与其他驱动之间的缓存一致性。

cudaExternalMemory_t importNvSciBufObject(NvSciBufObj bufferObjRaw)
{
    // 查询 NvSciBuf 对象属性
    NvSciBufAttrKeyValuePair bufattrs[] = {
        { NvSciBufRawBufferAttrKey_Size, NULL, 0 },
        { NvSciBufGeneralAttrKey_GpuSwNeedCacheCoherency, NULL, 0 },
        { NvSciBufGeneralAttrKey_EnableGpuCompression, NULL, 0 }
    };

    NvSciBufAttrListGetAttrs(
        retList, bufattrs,
        sizeof(bufattrs) / sizeof(NvSciBufAttrKeyValuePair));

    ret_size = *(static_cast<const uint64_t*>(bufattrs[0].value));

    // 缓存和压缩属性按 GPU 区分，因此要通过 UUID 读取对应 GPU 的值。
    int numGpus = bufattrs[1].len / sizeof(NvSciBufAttrValGpuCache);
    NvSciBufAttrValGpuCache* cacheVal =
        (NvSciBufAttrValGpuCache*)bufattrs[1].value;
    bool ret_cacheVal;

    for (int i = 0; i < numGpus; i++) {
        if (memcmp(gpuid[0].bytes, cacheVal[i].gpuId.bytes,
                   sizeof(CUuuid)) == 0) {
            ret_cacheVal = cacheVal[i].cacheability;
        }
    }

    // 读取 NvSciBuf 授予的压缩属性
    numGpus = bufattrs[2].len / sizeof(NvSciBufAttrValGpuCompression);
    NvSciBufAttrValGpuCompression* compVal =
        (NvSciBufAttrValGpuCompression*)bufattrs[2].value;

    NvSciBufCompressionType ret_compVal;
    for (int i = 0; i < numGpus; i++) {
        if (memcmp(gpuid[0].bytes, compVal[i].gpuId.bytes,
                   sizeof(CUuuid)) == 0) {
            ret_compVal = compVal[i].compressionType;
        }
    }

    // 向 CUDA 注册 NvSciBuf
    cudaExternalMemoryHandleDesc memHandleDesc;
    memset(&memHandleDesc, 0, sizeof(memHandleDesc));
    memHandleDesc.type = cudaExternalMemoryHandleTypeNvSciBuf;
    memHandleDesc.handle.nvSciBufObject = bufferObjRaw;

    // 此处应设置具有所需访问权限的 NvSciBuf 对象
    memHandleDesc.handle.nvSciBufObject = bufferObjRo;
    memHandleDesc.size = ret_size;

    cudaImportExternalMemory(&extMemBuffer, &memHandleDesc);
    return extMemBuffer;
}

}

6.2.16.5.4 导入同步对象（Importing Synchronization Objects）

可以使用 cudaDeviceGetNvSciSyncAttributes() 生成与指定 CUDA 设备兼容的 NvSciSync 属性。返回的属性列表可以用来创建一个保证与指定 CUDA 设备兼容的 NvSciSyncObj。

NvSciSyncObj createNvSciSyncObject()
{
    NvSciSyncObj nvSciSyncObj;
    int cudaDev0 = 0;
    int cudaDev1 = 1;

    NvSciSyncAttrList signalerAttrList = NULL;
    NvSciSyncAttrList waiterAttrList = NULL;
    NvSciSyncAttrList reconciledList = NULL;
    NvSciSyncAttrList newConflictList = NULL;

    NvSciSyncAttrListCreate(module, &signalerAttrList);
    NvSciSyncAttrListCreate(module, &waiterAttrList);

    NvSciSyncAttrList unreconciledList[2] = {NULL, NULL};
    unreconciledList[0] = signalerAttrList;
    unreconciledList[1] = waiterAttrList;

    cudaDeviceGetNvSciSyncAttributes(
        signalerAttrList, cudaDev0, CUDA_NVSCISYNC_ATTR_SIGNAL);
    cudaDeviceGetNvSciSyncAttributes(
        waiterAttrList, cudaDev1, CUDA_NVSCISYNC_ATTR_WAIT);

    NvSciSyncAttrListReconcile(unreconciledList, 2,
                               &reconciledList, &newConflictList);
    NvSciSyncObjAlloc(reconciledList, &nvSciSyncObj);

    return nvSciSyncObj;
}

如上创建的 NvSciSync 对象可以通过 NvSciSyncObj 句柄导入 CUDA。即使导入后，该句柄的所有权仍属于应用程序。

cudaExternalSemaphore_t importNvSciSyncObject(void* nvSciSyncObj)
{
    cudaExternalSemaphore_t extSem = NULL;
    cudaExternalSemaphoreHandleDesc desc = {};

    memset(&desc, 0, sizeof(desc));
    desc.type = cudaExternalSemaphoreHandleTypeNvSciSync;
    desc.handle.nvSciSyncObj = nvSciSyncObj;

    cudaImportExternalSemaphore(&extSem, &desc);

    // 此后删除或释放 nvSciSyncObj 会导致 CUDA 中的行为未定义。
    return extSem;
}

6.2.16.5.5 对导入的同步对象发出信号和等待（Signaling/Waiting on Imported Synchronization Objects）

可以对导入的 NvSciSync 对象发出信号。发出信号时，会初始化作为输入参数传入的 fence。与该信号对应的等待操作会等待此 fence。等待操作必须在信号操作之后提交。

如果标志设置为 cudaExternalSemaphoreSignalSkipNvSciBufMemSync，则默认作为信号操作一部分、针对本进程中所有已导入 NvSciBuf 执行的内存同步操作会被跳过。当 NvSciBufGeneralAttrKey_GpuSwNeedCacheCoherency 为 FALSE 时，应设置此标志。

void signalExternalSemaphore(cudaExternalSemaphore_t extSem,
                             cudaStream_t stream, void* fence)
{
    cudaExternalSemaphoreSignalParams signalParams = {};
    memset(&signalParams, 0, sizeof(signalParams));

    signalParams.params.nvSciSync.fence = (void*)fence;
    signalParams.flags = 0; // 或 cudaExternalSemaphoreSignalSkipNvSciBufMemSync

    cudaSignalExternalSemaphoresAsync(&extSem, &signalParams, 1, stream);
}

等待导入的 NvSciSync 对象时，操作会一直等待，直到对应信号发出方触发输入 fence。同样，信号必须先于等待操作提交。

如果标志设置为 cudaExternalSemaphoreWaitSkipNvSciBufMemSync，则默认作为等待操作一部分、针对本进程中所有已导入 NvSciBuf 执行的内存同步操作会被跳过。当 NvSciBufGeneralAttrKey_GpuSwNeedCacheCoherency 为 FALSE 时，应设置此标志。

void waitExternalSemaphore(cudaExternalSemaphore_t extSem,
                           cudaStream_t stream, void* fence)
{
    cudaExternalSemaphoreWaitParams waitParams = {};
    memset(&waitParams, 0, sizeof(waitParams));

    waitParams.params.nvSciSync.fence = (void*)fence;
    waitParams.flags = 0; // 或 cudaExternalSemaphoreWaitSkipNvSciBufMemSync

    cudaWaitExternalSemaphoresAsync(&extSem, &waitParams, 1, stream);
}

6.3 版本管理与兼容性（Versioning and Compatibility）

开发 CUDA 应用程序时，需要关注两个版本号：

  • 计算能力（compute capability）：描述计算设备的一般规格与功能，详见“计算能力”章节。
  • CUDA 驱动程序 API 版本：描述驱动程序 API 和运行时所支持的功能。

驱动程序 API 版本在驱动头文件中通过 CUDA_VERSION 定义。开发者可以利用该版本号判断应用程序是否需要比当前已安装驱动程序更新的版本。

这一点很重要，因为驱动程序 API 向后兼容：使用某一版本驱动程序 API 编译的应用程序、插件和库（包括 CUDA Runtime），可以继续在后续版本的设备驱动程序上运行，如图 25 所示。但驱动程序 API 不向前兼容：针对某一版本驱动程序 API 编译的应用程序、插件和库（包括 CUDA Runtime），不能在更早版本的设备驱动程序上运行。

还需要注意，受支持的版本组合存在以下限制：

  • 一个系统中只能安装一个版本的 CUDA Driver。因此，已安装驱动程序的版本必须与应用程序、插件或库构建时使用的最高 Driver API 版本相同或更高。
  • 一个应用程序使用的所有插件和库必须使用相同版本的 CUDA Runtime；如果它们静态链接到 Runtime，则可以在同一进程空间中共存多个运行时版本。请注意，如果使用 nvcc 链接应用程序，默认会使用静态版本的 CUDA Runtime 库，并且所有 CUDA Toolkit 库都静态链接到 CUDA Runtime。
  • 一个应用程序使用的所有插件和库，必须使用相同版本的、依赖 Runtime 的库（例如 cuFFT、cuBLAS 等），除非这些库采用静态链接。

对于 Tesla GPU 产品，CUDA 10 为 CUDA Driver 的用户态组件引入了一条新的向前兼容升级路径。该功能详见 CUDA Compatibility。此处所述的 CUDA Driver 版本要求适用于用户态组件的版本。

6.4 计算模式（Compute Modes）

在运行 Windows Server 2008 或更高版本的 Windows 系统、或 Linux 的 Tesla 解决方案上，可以使用 NVIDIA 系统管理界面（NVIDIA System Management Interface，nvidia-smi）将系统中的任意设备设置为以下三种计算模式之一。nvidia-smi 是随驱动程序提供的工具。

  • 默认计算模式（Default compute mode）：多个主机线程可以同时使用该设备。使用 Runtime API 时，可以通过对该设备调用 cudaSetDevice()；使用 Driver API 时，可以将与该设备关联的上下文设为当前上下文。
  • 独占进程计算模式（Exclusive-process compute mode）：在整个系统范围内，该设备只能创建一个 CUDA 上下文。创建该上下文的进程内部，可以让任意数量的线程将其设为当前上下文。
  • 禁止计算模式（Prohibited compute mode）：该设备上不能创建 CUDA 上下文。

特别需要注意的是，如果主机线程使用 Runtime API，却没有显式调用 cudaSetDevice()，那么当设备 0 处于禁止模式，或处于独占进程模式且已被另一个进程使用时，该线程可能会关联到设备 0 以外的设备。可以使用 cudaSetValidDevices() 从按优先级排列的设备列表中设置可用设备。

另外，从 Pascal 架构开始（计算能力主版本号为 6 或更高）的设备支持计算抢占（Compute Preemption）。这允许计算任务以指令级粒度被抢占，而较早的 Maxwell 和 Kepler GPU 架构只能以线程块粒度抢占。因此，可以避免长时间运行的内核独占系统或导致超时。不过，计算抢占会产生上下文切换开销；在支持该功能的设备上，系统会自动启用它。

可以使用 cudaDeviceGetAttribute()，并将属性设置为 cudaDevAttrComputePreemptionSupported，来查询当前设备是否支持计算抢占。如果用户希望避免不同进程之间上下文切换造成的开销，可以选择独占进程模式，以确保 GPU 上只有一个进程处于活动状态。

应用程序可以通过检查设备属性 computeMode 查询设备的计算模式，详见“设备枚举”。

6.5 显示模式切换（Mode Switches）

具有显示输出的 GPU 会在 DRAM 中为所谓的**主表面（primary surface）**保留一部分内存。主表面用于刷新用户正在查看的显示设备。

当用户通过 NVIDIA 控制面板或 Windows 的“显示”控制面板更改显示分辨率或位深时，主表面所需的内存容量也会变化。例如，将显示分辨率从 1280×1024、32 位改为 1600×1200、32 位时，系统需要为主表面分配 7.68 MB，而不是 5.24 MB。启用了抗锯齿的全屏图形应用程序可能需要更多显示内存。

在 Windows 上，其他可能引发显示模式切换的事件包括启动全屏 DirectX 应用程序、按 Alt+Tab 从全屏 DirectX 应用程序切换到其他任务，或按 Ctrl+Alt+Del 锁定计算机。

如果模式切换增加了主表面所需的内存，系统可能不得不占用原本分配给 CUDA 应用程序的内存。因此，模式切换会导致 CUDA Runtime 的调用失败，并返回无效上下文错误。

6.6 Windows 的 Tesla 计算集群模式（Tesla Compute Cluster Mode for Windows）

可以使用 NVIDIA 系统管理界面（nvidia-smi），将 Windows 设备驱动程序设置为 TCC（Tesla Compute Cluster，Tesla 计算集群）模式。Tesla 和 Quadro 系列设备支持此模式。

TCC 模式会移除所有图形功能支持。
