第十章 C++ 语言扩展（C++ Language Extensions）

10.1 函数执行空间说明符（Function Execution Space Specifiers）

函数执行空间说明符用于指定函数是在主机（host）还是设备（device）上执行，以及它可以由主机还是设备调用。

10.1.1 __global__

__global__ 执行空间说明符用于将函数声明为内核。此类函数：

  • 在设备上执行；
  • 可以由主机调用；
  • 对于计算能力为 5.0 或更高的设备，也可以由设备调用（详见“CUDA 动态并行”）。

__global__ 函数的返回类型必须是 void，并且不能是类的成员函数。

任何对 __global__ 函数的调用都必须指定执行配置，详见“执行配置”。

对 __global__ 函数的调用是异步的，也就是说，调用会在设备完成执行之前返回。

10.1.2 __device__

__device__ 执行空间说明符声明的函数：

  • 在设备上执行；
  • 只能由设备调用。

__global__ 和 __device__ 执行空间说明符不能同时用于同一个函数。

10.1.3 __host__

__host__ 执行空间说明符声明的函数：

  • 在主机上执行；
  • 只能由主机调用。

显式声明函数带有 __host__，与不指定 __host__、__device__ 或 __global__ 中任何说明符的效果相同：函数只为主机编译。

__global__ 和 __host__ 不能同时用于同一个函数。不过，__device__ 和 __host__ 可以同时使用，此时函数会同时为主机和设备编译。可以使用“应用程序兼容性”一节介绍的 __CUDA_ARCH__ 宏，在主机和设备代码路径之间进行区分：

__host__ __device__ func()
{
#if __CUDA_ARCH__ >= 800
    // 计算能力 8.x 的设备代码路径
#elif __CUDA_ARCH__ >= 700
    // 计算能力 7.x 的设备代码路径
#elif __CUDA_ARCH__ >= 600
    // 计算能力 6.x 的设备代码路径
#elif __CUDA_ARCH__ >= 500
    // 计算能力 5.x 的设备代码路径
#elif !defined(__CUDA_ARCH__)
    // 主机代码路径
#endif
}

10.1.4 未定义行为（Undefined Behavior）

以下跨执行空间调用（cross-execution space call）属于未定义行为：

  • 当定义了 __CUDA_ARCH__ 时，从 __global__、__device__ 或 __host__ __device__ 函数内部调用 __host__ 函数；
  • 当未定义 __CUDA_ARCH__ 时，从 __host__ 函数内部调用 __device__ 函数。

原书脚注：GeForce GPU（Titan GPU 除外）对应的脚注编号与上述限制相关；请结合原版 PDF 的脚注和对应架构说明核对。

10.1.5 __noinline__ 和 __forceinline__

编译器会在认为合适时内联 __device__ 函数。

__noinline__ 函数限定符可以作为提示，尽可能阻止编译器内联该函数。

__forceinline__ 函数限定符则用于强制编译器内联函数。

__noinline__ 和 __forceinline__ 不能同时使用，而且两者都不能应用于已经声明为 inline 的函数。

10.1.6 __inline_hint__

__inline_hint__ 限定符会促使编译器更积极地进行内联。与 __forceinline__ 不同，它并不意味着函数必须声明为 inline。在使用链接时优化（LTO）时，它可以帮助改善跨模块内联。

__noinline__ 和 __forceinline__ 都不能与 __inline_hint__ 同时用于同一个函数。

10.2 变量内存空间说明符（Variable Memory Space Specifiers）

变量内存空间说明符用于指定变量在设备上的内存位置。

在设备代码中声明的自动变量，如果没有使用本节介绍的 __device__、__shared__ 或 __constant__ 内存空间说明符，通常会存放在寄存器中。不过，在某些情况下，编译器可能会选择将其放入本地内存，这可能造成性能损失，详见“设备内存访问”。

10.2.1 __device__

__device__ 内存空间说明符声明一个驻留在设备上的变量。

在 __device__ 之外，最多可以再搭配使用下一节介绍的三个内存空间说明符之一，以进一步指定变量所属的内存空间。如果没有使用其他说明符，该变量将：

  • 驻留在全局内存空间；
  • 与创建它的 CUDA 上下文具有相同的生命周期；
  • 在每个设备上拥有独立的对象；
  • 可由网格中的所有线程访问，并可由主机通过运行时库访问，例如 cudaGetSymbolAddress()、cudaGetSymbolSize()、cudaMemcpyToSymbol() 和 cudaMemcpyFromSymbol()。

10.2.2 __constant__

__constant__ 内存空间说明符可以与 __device__ 搭配使用，用于声明一个变量，该变量：

  • 驻留在常量内存空间；
  • 与创建它的 CUDA 上下文具有相同的生命周期；
  • 在每个设备上拥有独立的对象；
  • 可由网格中的所有线程访问，并可由主机通过运行时库访问，例如 cudaGetSymbolAddress()、cudaGetSymbolSize()、cudaMemcpyToSymbol() 和 cudaMemcpyFromSymbol()。

如果某个网格正在运行，并且在该网格生命周期内的任意时刻都可能访问某个常量，那么主机同时修改该常量的行为属于未定义行为。

10.2.3 __shared__

__shared__ 内存空间说明符可以与 __device__ 搭配使用，用于声明一个变量，该变量：

  • 驻留在线程块的共享内存空间；
  • 生命周期与线程块相同；
  • 每个线程块拥有独立对象；
  • 只能由该线程块中的线程访问；
  • 不具有固定的常量地址。

如果将共享内存变量声明为外部数组，例如：

extern __shared__ float shared[];

则数组大小会在启动时确定，详见“执行配置”。所有以这种方式声明的变量都会从同一个内存地址开始，因此必须通过偏移量显式管理数组布局。

例如，若要在动态分配的共享内存中实现以下数组：

short array0[128];
float array1[64];
int   array2[256];

可以这样声明并初始化指针：

extern __shared__ float array[];

__device__ void func() // __device__ 或 __global__ 函数
{
    short* array0 = (short*)array;
    float* array1 = (float*)&array0[128];
    int*   array2 = (int*)&array1[64];
}

请注意，指针必须按照其指向的数据类型对齐。因此，下面的代码无法正常工作，因为 array1 没有按 4 字节对齐：

extern __shared__ float array[];

__device__ void func() // __device__ 或 __global__ 函数
{
    short* array0 = (short*)array;
    float* array1 = (float*)&array0[127];
}

10.2.4 __grid_constant__

对于计算架构大于或等于 7.0 的设备，__grid_constant__ 注解可用于非引用类型、带 const 限定的 __global__ 函数参数。此类对象：

  • 生命周期与网格相同；
  • 对网格私有，主机线程和其他网格（包括子网格）中的线程都无法访问；
  • 每个网格有独立对象，但同一网格中的所有线程看到相同地址；
  • 只读。修改 __grid_constant__ 对象或其任何子对象（包括 mutable 成员）都属于未定义行为。

使用要求：

  • 使用 __grid_constant__ 注解的内核参数必须是带 const 限定的非引用类型；
  • 所有函数声明中，对应参数的 __grid_constant__ 注解必须一致；
  • 函数模板特化必须与主模板声明中的对应注解一致；
  • 函数模板实例化指令必须与主模板声明中的对应注解一致。

如果获取 __global__ 函数参数的地址，编译器通常会将内核参数复制到线程本地内存，并使用副本的地址，以部分支持 C++ 语义（即每个线程都可以修改自己的参数副本）。对 __global__ 函数参数使用 __grid_constant__，可以确保编译器不创建线程本地副本，而是直接使用参数本身的通用地址。避免创建本地副本可能改善性能。

__device__ void unknown_function(S const&);

__global__ void kernel(const __grid_constant__ S s) {
    s.x += threadIdx.x; // 未定义行为：试图修改只读内存

    // 编译器不会为 s 创建每线程本地副本：
    unknown_function(s);
}

10.2.5 __managed__

__managed__ 内存空间说明符可以与 __device__ 搭配使用，用于声明一个变量，该变量：

  • 可同时在设备代码和主机代码中引用，例如，可以获取其地址，也可以直接在设备函数或主机函数中读取、写入；
  • 生命周期与整个应用程序相同。

更多细节见“__managed__ 内存空间说明符”。

10.2.6 __restrict__

nvcc 支持通过 __restrict__ 关键字声明受限指针。

受限指针最初由 C99 引入，用于缓解 C 类语言中的别名问题。别名会妨碍编译器执行各种优化，从指令重排到公共子表达式消除都可能受到影响。

下面的示例存在指针别名问题，使用受限指针可以帮助编译器减少指令数量：

void foo(const float* a,
         const float* b,
         float* c)
{
    c[0] = a[0] * b[0];
    c[1] = a[0] * b[0];
    c[2] = a[0] * b[0] * a[1];
    c[3] = a[0] * a[1];
    c[4] = a[0] * b[0];
    c[5] = b[0];
    ...
}

在 C 类语言中，指针 a、b 和 c 可能指向重叠的内存区域。因此，通过 c 执行的写操作可能修改 a 或 b 的元素。为了保证程序正确，编译器不能简单地将 a[0] 和 b[0] 加载到寄存器、计算乘积后，再将结果写入 c[0] 和 c[1]，因为如果 a[0] 实际上与 c[0] 指向同一位置，结果就会与抽象执行模型不一致。这样，编译器便无法利用公共子表达式。

同理，编译器也不能随意将 c[4] 的计算重排到 c[0] 和 c[1] 附近，因为之前对 c[3] 的写入可能改变 c[4] 计算所需的输入。

将 a、b 和 c 声明为受限指针，相当于程序员向编译器保证这些指针实际并不别名；也就是说，通过 c 写入不会覆盖 a 或 b 的元素。函数原型变为：

void foo(const float* __restrict__ a,
         const float* __restrict__ b,
         float* __restrict__ c);

注意：所有指针参数都需要声明为受限指针，编译器优化器才能充分获益。加入 __restrict__ 后，编译器可以自由进行指令重排和公共子表达式消除，同时保持与抽象执行模型相同的功能：

void foo(const float* __restrict__ a,
         const float* __restrict__ b,
         float* __restrict__ c)
{
    float t0 = a[0];
    float t1 = b[0];
    float t2 = t0 * t1;
    float t3 = a[1];

    c[0] = t2;
    c[1] = t2;
    c[4] = t2;
    c[2] = t2 * t3;
    c[3] = t0 * t3;
    c[5] = t1;
    ...
}

这样可以减少内存访问和计算次数，但代价是缓存加载值和公共子表达式会增加寄存器压力。

由于寄存器压力在许多 CUDA 程序中都是关键问题，使用受限指针也可能因降低占用率而对性能产生负面影响。

10.4 内置变量（Built-in Variables）

内置变量用于指定网格和线程块的维度，以及线程块和线程的索引。它们只能在设备端执行的函数中使用。

10.4.1 gridDim

该变量的类型为 dim3，包含网格的维度。

该变量的类型为 uint3，包含线程块在网格中的索引。

10.4.5 warpSize

该变量的类型为 int，包含一个 warp 中的线程数量。warp 的定义见“SIMT 架构”。

10.5 内存栅栏函数（Memory Fence Functions）

CUDA 编程模型假设设备使用弱排序内存模型。也就是说，CUDA 线程向共享内存、全局内存、页锁定主机内存或对等设备内存写入数据的顺序，不一定等于其他 CUDA 线程或主机线程观察到这些写入的顺序。两个线程如果在没有同步的情况下读取或写入同一个内存位置，就会产生未定义行为。

以下示例中，线程 1 执行 writeXY()，线程 2 执行 readXY()：

__device__ int X = 1, Y = 2;

__device__ void writeXY()
{
    X = 10;
    Y = 20;
}

__device__ void readXY()
{
    int B = Y;
    int A = X;
}

两个线程同时读取和写入相同的内存位置 X 和 Y。任何数据竞争都属于未定义行为，没有规定的语义；因此，变量 A 和 B 最终可能得到任意值。

内存栅栏函数可用于强制内存访问遵循顺序一致的排序。不同内存栅栏函数所保证的排序作用域不同，但它们与访问的内存空间无关（包括共享内存、全局内存、页锁定主机内存和对等设备内存）。

__threadfence_block()

void __threadfence_block();

该函数等价于：

cuda::atomic_thread_fence(
    cuda::memory_order_seq_cst,
    cuda::thread_scope_block);

它保证：

  • 调用线程在执行 __threadfence_block() 之前对所有内存进行的写入，会被该线程所在块中的所有线程观察为先于调用之后的所有写入；
  • 调用线程在栅栏之前进行的所有内存读取，都会排在栅栏之后的所有内存读取之前。

__threadfence()

void __threadfence();

该函数等价于：

cuda::atomic_thread_fence(
    cuda::memory_order_seq_cst,
    cuda::thread_scope_device);

它保证：调用线程在执行 __threadfence() 之后进行的任何内存写入，都不会被设备上的任何线程观察为先于该线程在栅栏之前进行的内存写入。

__threadfence_system()

void __threadfence_system();

该函数等价于：

cuda::atomic_thread_fence(
    cuda::memory_order_seq_cst,
    cuda::thread_scope_system);

它将内存排序保证扩展到系统作用域，涉及设备、主机以及系统中的其他相关参与者。具体语义应结合对应 CUDA C++ 内存模型说明理解。

__threadfence_system()（续）

__threadfence_system() 保证调用线程在栅栏之前对所有内存进行的写入，会被设备中的所有线程、主机线程以及对等设备中的所有线程观察为先于该线程在栅栏之后进行的所有内存写入。

__threadfence_system() 仅支持计算能力为 2.x 及以上的设备。

回到前面的示例，可以按如下方式插入栅栏：

__device__ int X = 1, Y = 2;

__device__ void writeXY()
{
    X = 10;
    __threadfence();
    Y = 20;
}

__device__ void readXY()
{
    int B = Y;
    __threadfence();
    int A = X;
}

此代码可能观察到以下结果：

  • A 等于 1，B 等于 2；
  • A 等于 10，B 等于 2；
  • A 等于 10，B 等于 20。

第四种结果不可能出现，因为第一次写入必须在第二次写入之前可见。

如果线程 1 和线程 2 属于同一个线程块，使用 __threadfence_block() 就足够。如果它们不属于同一个线程块，并且是同一设备上的 CUDA 线程，则必须使用 __threadfence()；如果它们来自不同设备，则必须使用 __threadfence_system()。

使用内存栅栏协调线程间数据（示例）

一种常见场景是：线程需要消费由其他线程产生的数据。以下内核示例在一次调用中计算包含 \(N\) 个数的数组之和。

每个线程块先计算数组的一个子集，并将部分和写入全局内存。当所有线程块都完成后，最后完成的线程块会从全局内存读取各个部分和，并将它们相加得到最终结果。

为了确定哪个线程块最后完成，每个线程块都会原子递增一个计数器，表示自己已经完成部分和的计算与存储（原子函数见“原子函数”一节）。当计数器值等于 gridDim.x - 1 时，当前线程块就是最后完成的线程块。

如果在存储部分和与递增计数器之间没有插入栅栏，计数器可能会在部分和真正写入之前递增。这样，计数器可能提前达到 gridDim.x - 1，导致最后一个线程块在部分和更新到内存之前就开始读取它们。

内存栅栏函数只影响单个线程的内存操作顺序；它本身并不能确保这些操作对其他线程可见（这与 __syncthreads() 在线程块内提供的保证不同，参见“同步函数”）。下面示例通过将 result 声明为 volatile，确保对结果变量的内存操作具有所需可见性。

__device__ unsigned int count = 0;
__shared__ bool isLastBlockDone;

__global__ void sum(const float* array, unsigned int N,
                    volatile float* result)
{
    // 每个线程块计算输入数组的一个子集。
    float partialSum = calculatePartialSum(array, N);

    if (threadIdx.x == 0) {
        // 每个线程块的线程 0 将部分和写入全局内存。
        // 因为 result 声明为 volatile，编译器会使用绕过 L1 缓存的存储操作。
        // 这样可确保最后一个线程块读取到其他线程块计算出的正确部分和。
        result[blockIdx.x] = partialSum;

        // 确保部分和写入全局内存之后，才递增 count。
        __threadfence();

        // 发出信号，表示当前线程块已完成。
        unsigned int value = atomicInc(&count, gridDim.x);

        // 判断当前线程块是否是最后完成的线程块。
        isLastBlockDone = (value == (gridDim.x - 1));
    }

    // 同步，确保每个线程读取到正确的 isLastBlockDone 值。
    __syncthreads();

    if (isLastBlockDone) {
        // 最后一个线程块对 result[0 .. gridDim.x-1] 中的部分和求和。
        float totalSum = calculateTotalSum(result);

        if (threadIdx.x == 0) {
            // 最后一个线程块的线程 0 写入总和并重置计数器，
            // 以确保下一次内核调用能够正常工作。
            result[0] = totalSum;
            count = 0;
        }
    }
}

10.6 同步函数（Synchronization Functions）

__syncthreads()

void __syncthreads();

该函数会等待线程块中的所有线程都到达此处，并确保这些线程在调用 __syncthreads() 之前进行的所有全局内存和共享内存访问，对该线程块中的所有线程可见。

__syncthreads() 用于协调同一线程块中线程之间的通信。当线程块中的多个线程访问共享内存或全局内存中的相同地址时，可能发生读后写、写后读或写后写的数据危险。在这些访问之间同步线程，可以避免这类数据危险。

允许在条件代码中调用 __syncthreads()，但条件表达式必须在整个线程块中得到相同结果；否则，程序可能挂起或产生意外副作用。

计算能力为 2.x 及以上的设备还支持以下三个变体。

__syncthreads_count()

int __syncthreads_count(int predicate);

该函数与 __syncthreads() 相同，但会评估线程块中每个线程的 predicate，并返回该表达式结果非零的线程数量。

__syncthreads_and()

int __syncthreads_and(int predicate);

该函数与 __syncthreads() 相同，但会评估所有线程的 predicate；只有当所有线程的表达式结果都非零时，返回值才非零。

__syncthreads_or()

int __syncthreads_or(int predicate);

该函数与 __syncthreads() 相同，但会评估所有线程的 predicate；只要任意线程的表达式结果非零，返回值就非零。

__syncwarp()

void __syncwarp(unsigned mask = 0xffffffff);

执行该函数的线程会等待，直到 mask 中指定的所有 warp lane 都执行了带有相同 mask 的 __syncwarp()，之后才继续执行。

每个调用线程在 mask 中都必须设置自己的对应位；此外，mask 中所有尚未退出的线程都必须执行匹配的 __syncwarp()，否则行为未定义。

执行 __syncwarp() 会确保参与屏障的线程之间具有内存排序。因此，希望通过内存通信的同一 warp 内线程可以先写入内存、执行 __syncwarp()，然后安全地读取其他线程写入的值。

注意： 对于 .target sm_6x 或更低目标架构，mask 中所有线程必须在收敛状态下执行同一个 __syncwarp()，并且所有 mask 值的并集必须等于活动掩码。否则，行为未定义。

10.14 原子函数（Atomic Functions）

原子函数对驻留在全局内存或共享内存中的一个 32 位、64 位或 128 位字执行原子性的“读取—修改—写入”操作。对于 float2 或 float4，该操作分别作用于位于全局内存中的每个向量分量。例如，atomicAdd() 会读取某个地址处的值，将一个数加到该值上，再把结果写回同一地址。整个过程作为一个原子事务执行。原子函数只能在设备函数中使用。

本节中的原子函数采用 cuda::memory_order_relaxed 内存顺序，并且只在特定线程作用域内具有原子性：

  • 带 _system 后缀的原子 API（例如 atomicAdd_system），在满足特定条件时具有 cuda::thread_scope_system 作用域。
  • 不带后缀的原子 API（例如 atomicAdd）具有 cuda::thread_scope_device 作用域。
  • 带 _block 后缀的原子 API（例如 atomicAdd_block）具有 cuda::thread_scope_block 作用域。

以下示例中，CPU 与 GPU 都以原子方式更新地址 addr 处的整数值：

__global__ void mykernel(int *addr) {
    atomicAdd_system(addr, 10); // 仅支持计算能力 6.x 及以上的设备
}

void foo() {
    int *addr;
    cudaMallocManaged(&addr, 4);
    *addr = 0;
    mykernel<<<...>>>(addr);
    __sync_fetch_and_add(addr, 10); // CPU 原子操作
}

任何原子操作都可以基于 atomicCAS()（Compare And Swap，比较并交换）实现。例如，计算能力低于 6.0 的设备不支持双精度浮点数的 atomicAdd()，但可以使用以下实现：

#if __CUDA_ARCH__ < 600
__device__ double atomicAdd(double* address, double val)
{
    unsigned long long int* address_as_ull =
        (unsigned long long int*)address;
    unsigned long long int old = *address_as_ull, assumed;
    do {
        assumed = old;
        old = atomicCAS(address_as_ull, assumed,
                        __double_as_longlong(
                            val + __longlong_as_double(assumed)));
        // 使用整数比较，避免 NaN 情况下因 NaN != NaN 而陷入死循环。
    } while (assumed != old);
    return __longlong_as_double(old);
}
#endif

以下设备级原子 API 还具有系统级和线程块级变体，但存在例外：计算能力低于 6.0 的设备只支持设备级原子操作；计算能力低于 7.2 的 Tegra 设备不支持系统级原子操作。

10.19 Warp 投票函数（Warp Vote Functions）

int __all_sync(unsigned mask, int predicate);
int __any_sync(unsigned mask, int predicate);
unsigned __ballot_sync(unsigned mask, int predicate);
unsigned __activemask();

__any、__all 和 __ballot 已从 CUDA 9.0 起弃用。针对计算能力为 7.x 及以上的设备时，这些旧函数已不可用，应改用带 _sync 后缀的版本。

Warp 投票函数允许一个 warp 中的线程执行归约并广播结果。每个线程提供一个整数谓词，函数将它与零比较，再对 warp 中的活动线程的比较结果进行归约，并将一个返回值广播给参与的线程。

  • __all_sync(unsigned mask, predicate)：评估 mask 中所有尚未退出的线程的 predicate；只有所有线程的结果都非零时，才返回非零值。
  • __any_sync(unsigned mask, predicate)：评估 mask 中所有尚未退出的线程的 predicate；只要其中任意线程的结果非零，就返回非零值。
  • __ballot_sync(unsigned mask, predicate)：评估 mask 中所有尚未退出的线程的 predicate，并返回一个整数。如果 warp 中第 N 个线程处于活动状态且其谓词结果非零，则返回整数的第 N 位会被置为 1。
  • __activemask()：返回一个 32 位掩码，表示调用线程所在 warp 当前所有活动线程。若调用时 warp 中第 N 个 lane 处于活动状态，则返回掩码的第 N 位为 1；非活动线程对应位为 0。已经退出程序的线程始终被标记为非活动。

需要注意：在调用 __activemask() 时处于收敛状态的线程，不保证在后续指令处仍然收敛，除非后续指令本身是同步型 warp 内建函数。

对于 __all_sync、__any_sync 和 __ballot_sync，必须传入 mask 指明参与调用的线程。每个参与线程的 lane ID 对应位都必须在掩码中置 1，以确保硬件执行内建函数前线程已正确收敛。每个调用线程都必须在掩码中包含自己的位；mask 中所有尚未退出的线程必须使用相同的掩码执行相同的内建函数，否则结果未定义。

这些内建函数不隐含内存屏障，也不保证内存访问顺序。

10.20 Warp 匹配函数（Warp Match Functions）

__match_any_sync 和 __match_all_sync 会在 warp 内线程之间，对某个变量执行广播并比较的操作。它们仅支持计算能力为 7.x 及以上的设备。

10.20.1 函数原型（Synopsis）

unsigned int __match_any_sync(unsigned mask, T value);
unsigned int __match_all_sync(unsigned mask, T value, int *pred);

T 可以是 int、unsigned int、long、unsigned long、long long、unsigned long long、float 或 double。

10.20.2 描述（Description）

__match_sync() 内建函数会在同步 mask 指定的线程后，在 warp 内广播并比较 value。

  • __match_any_sync：返回掩码，其中包含 mask 中所有具有相同 value 的线程。
  • __match_all_sync：如果 mask 中所有线程的 value 都相同，则返回 mask；否则返回 0。若所有线程的值相同，pred 指向的谓词会被设为 true，否则设为 false。

带 _sync 的匹配函数通过掩码指定参与调用的线程。每个参与线程的 lane ID 对应位必须在掩码中置 1；每个调用线程都必须在掩码中包含自己的位，且 mask 中所有尚未退出的线程都必须使用相同掩码执行相同的内建函数，否则结果未定义。

这些内建函数不隐含内存屏障，也不保证内存访问顺序。

10.21.1 函数原型（Synopsis）

// 加法、最小值、最大值
unsigned __reduce_add_sync(unsigned mask, unsigned value);
unsigned __reduce_min_sync(unsigned mask, unsigned value);
unsigned __reduce_max_sync(unsigned mask, unsigned value);
int __reduce_add_sync(unsigned mask, int value);
int __reduce_min_sync(unsigned mask, int value);
int __reduce_max_sync(unsigned mask, int value);

// 按位与、或、异或

unsigned __reduce_or_sync(unsigned mask, unsigned value);
unsigned __reduce_xor_sync(unsigned mask, unsigned value);

10.21.2 描述（Description）

__reduce_add_sync、__reduce_min_sync 和 __reduce_max_sync 分别对 mask 中每个线程提供的值执行加法、取最小值或取最大值归约，并返回归约结果。

__reduce_and_sync、__reduce_or_sync 和 __reduce_xor_sync 分别对参与线程提供的值执行按位与、或或异或归约，并返回结果。

mask 指定参与调用的线程。每个参与线程的 lane ID 对应位必须在掩码中置 1；每个调用线程都必须包含自己的位，且 mask 中所有尚未退出的线程必须使用相同掩码执行相同的内建函数，否则结果未定义。这些内建函数不隐含内存屏障，也不保证内存访问顺序。

10.22 Warp 洗牌函数（Warp Shuffle Functions）

__shfl_sync、__shfl_up_sync、__shfl_down_sync 和 __shfl_xor_sync 用于在 warp 内的线程之间交换变量。它们支持计算能力为 5.0 及以上的设备。

__shfl、__shfl_up、__shfl_down 和 __shfl_xor 已从 CUDA 9.0 起弃用；针对计算能力为 7.x 及以上的设备时，这些旧函数不可用，应使用带 _sync 后缀的版本。

10.22.1 函数原型（Synopsis）

T __shfl_sync(unsigned mask, T var, int srcLane, int width=warpSize);
T __shfl_up_sync(unsigned mask, T var, unsigned int delta, int width=warpSize);
T __shfl_down_sync(unsigned mask, T var, unsigned int delta, int width=warpSize);
T __shfl_xor_sync(unsigned mask, T var, int laneMask, int width=warpSize);

T 可以是 int、unsigned int、long、unsigned long、long long、unsigned long long、float 或 double。包含 cuda_fp16.h 后，T 还可以是 __half 或 __half2；包含 cuda_bf16.h 后，还可以是 __nv_bfloat16 或 __nv_bfloat162。

10.22.2 描述（Description）

这些内建函数允许 warp 内线程不通过共享内存交换变量。交换会同时发生在 warp 中所有活动且由 mask 指定的线程之间；每个线程根据数据类型交换 4 或 8 字节数据。

warp 中的线程称为 lane，lane 索引范围为 0 到 warpSize-1。支持四种源 lane 寻址方式：

  • __shfl_sync()：直接从指定 lane 复制；
  • __shfl_up_sync()：从相对调用线程 lane ID 更小的 lane 复制；
  • __shfl_down_sync()：从相对调用线程 lane ID 更大的 lane 复制；
  • __shfl_xor_sync()：根据调用线程 lane ID 与 laneMask 的按位异或结果选择源 lane。

线程只能从正在参与同一 __shfl_sync() 调用的其他线程读取数据。如果目标线程不活动，读取结果未定义。

所有 __shfl_sync() 内建函数都接受可选参数 width，用于改变函数行为。width 必须是 2 的幂，且位于 \([1,\text{warpSize}]\) 范围内，即 1、2、4、8、16 或 32；其他值会导致未定义结果。

__shfl_sync() 返回 srcLane 指定线程持有的 var 值。如果 width 小于 warpSize，warp 会被划分为若干个独立子分区，每个子分区的逻辑 lane ID 从 0 开始。如果 srcLane 超出 \([0,\text{width}-1]\)，返回值相当于从同一子分区中索引为 srcLane 对 width 取模的 lane 读取。

__shfl_up_sync() 将调用线程的 lane ID 减去 delta，并返回该源 lane 的 var。当 width 小于 warp 大小时，各子分区独立工作，源索引不会环绕到 width 的另一端，因此最前面的 delta 个 lane 保持原值。

__shfl_down_sync() 将调用线程的 lane ID 加上 delta，并返回对应源 lane 的 var。源索引不会环绕子分区边界，因此最后面的 delta 个 lane 保持原值。

__shfl_xor_sync() 将调用线程 lane ID 与 laneMask 做按位异或，以确定源 lane 并返回其 var。当 width 小于 warp 大小时，每组连续 width 个线程可以访问较早组中的元素；如果尝试访问较后组的元素，则会返回自身的 var。该模式实现了蝶形寻址，常用于树形归约和广播。

带 _sync 后缀的 shuffle 内建函数通过掩码指定参与线程。每个调用线程都必须在掩码中包含自己的 lane 位，且掩码中所有尚未退出的线程必须使用相同掩码执行相同函数，否则结果未定义。这些函数不隐含内存屏障，也不保证内存访问顺序。

10.22.3 示例（Examples）

10.22.3.1 在整个 warp 中广播单个值

#include <stdio.h>
__global__ void bcast(int arg) {
    int laneId = threadIdx.x & 0x1f;
    int value;
    if (laneId == 0)
        value = arg;
    value = __shfl_sync(0xffffffff, value, 0);
    if (value != arg)
        printf("Thread %d failed.\\n", threadIdx.x);
}
int main() {
    bcast<<<1, 32>>>(1234);
    cudaDeviceSynchronize();
    return 0;
}

线程 0 将 arg 写入 value，随后所有线程通过 __shfl_sync() 从 lane 0 读取该值。若读取值与 arg 不一致，就输出错误消息。

10.22.3.2 在每个 8 线程子分区内执行包含自身的加法扫描

#include <stdio.h>
__global__ void scan4() {
    int laneId = threadIdx.x & 0x1f;
    // 将起始值设为 lane ID 的反向值
    int value = 31 - laneId;

    // 在所属子分区内累计扫描。
    // 对 8 个线程，需要 log2(8) = 3 个逻辑步骤。
    for (int i = 1; i <= 4; i *= 2) {
        // 无条件执行 shuffle，确保所有线程都参与调用；
        // 然后再根据条件决定是否累加。
        int n = __shfl_up_sync(0xffffffff, value, i, 8);
        if ((laneId & 7) >= i)
            value += n;
    }
    printf("Thread %d final value = %d\\n", threadIdx.x, value);
}
int main() {
    scan4<<<1, 32>>>();
    cudaDeviceSynchronize();
    return 0;
}

10.22.3.3 在一个 warp 内执行归约

#include <stdio.h>
__global__ void warpReduce() {
    int laneId = threadIdx.x & 0x1f;
    // 将起始值设为 lane ID 的反向值
    int value = 31 - laneId;

    // 使用 XOR 模式执行蝶形归约
    for (int i = 16; i >= 1; i /= 2)
        value += __shfl_xor_sync(0xffffffff, value, i, 32);

    // 此时 value 包含整个 warp 的求和结果
    printf("Thread %d final value = %d\\n", threadIdx.x, value);
}
int main() {
    warpReduce<<<1, 32>>>();
    cudaDeviceSynchronize();
    return 0;
}

__nanosleep(ns) 会让线程暂停大约 ns 纳秒。最大休眠时长约为 1 毫秒。该函数支持计算能力为 7.0 及以上的设备。

        __nanosleep(ns);
        if (ns < 256) {
            ns *= 2;
        }
    }
}
__device__ void mutex_unlock(unsigned int *mutex) {
    atomicExch(mutex, 0);
}

10.24 Warp 矩阵函数（Warp Matrix Functions）

C++ warp 矩阵操作利用 Tensor Core 加速形如 \(D=A\times B+C\) 的矩阵计算。对于混合精度浮点数据，计算能力为 7.0 及以上的设备支持这些操作。执行时需要一个 warp 中的所有线程协同参与。

只有当条件表达式在整个 warp 中的计算结果完全一致时，才允许在条件代码中调用这些操作；否则，程序很可能挂起。

10.24.1 描述（Description）

以下函数和类型均定义在命名空间 nvcuda::wmma 中。子字节操作属于预览功能，其数据结构和 API 可能发生变化，未来版本也可能不兼容。相关功能位于 nvcuda::wmma::experimental 命名空间。

template<typename Use, int m, int n, int k,
         typename T, typename Layout=void>
class fragment;

void load_matrix_sync(fragment<...> &a,
                      const T* mptr, unsigned ldm);
void load_matrix_sync(fragment<...> &a,
                      const T* mptr, unsigned ldm, layout_t layout);
void store_matrix_sync(T* mptr, const fragment<...> &a,
                       unsigned ldm, layout_t layout);
void fill_fragment(fragment<...> &a, const T& v);
void mma_sync(fragment<...> &d,
              const fragment<...> &a,
              const fragment<...> &b,
              const fragment<...> &c,
              bool satf=false);

fragment

fragment 是一个重载类，其中包含分布在 warp 所有线程之间的矩阵片段。矩阵元素映射到 fragment 内部存储的方式没有指定，并且可能随未来架构变化。

只有部分模板参数组合合法。第一个模板参数指定该 fragment 在矩阵操作中的角色：

  • matrix_a：作为第一个乘数矩阵 A；
  • matrix_b：作为第二个乘数矩阵 B；
  • accumulator：作为源累加器 C 或目标累加器 D。

参数 m、n 和 k 指定参与乘加操作的 warp 级矩阵块形状。A 矩阵块尺寸为 \(m\times k\)，B 矩阵块为 \(k\times n\)，累加器矩阵块为 \(m\times n\)。

乘数矩阵的数据类型 T 可以是 double、float、__half、__nv_bfloat16、char 或 unsigned char；累加器类型可以是 double、float、int 或 __half。支持的类型组合有限，详见“元素类型与矩阵尺寸”。

对于 matrix_a 和 matrix_b fragment，必须指定 Layout 参数。row_major 表示矩阵每一行的元素在内存中连续，col_major 表示每一列的元素在内存中连续。累加器矩阵的 Layout 参数应保留默认值 void；只有在加载或存储累加器时才指定行主序或列主序布局。

load_matrix_sync

该函数会等待 warp 中所有 lane 到达后，再从内存加载矩阵 fragment。

mptr 必须是指向矩阵首元素、按 256 位对齐的指针。ldm 表示相邻行（行主序）或相邻列（列主序）之间的元素跨度：对于 __half，必须是 8 的倍数；对于 float，必须是 4 的倍数，即两种情况都满足 16 字节的倍数。

如果 fragment 是累加器，layout 必须指定为 mem_row_major 或 mem_col_major。对于 matrix_a 和 matrix_b fragment，布局由模板参数推导。warp 中所有线程对 a 使用的 mptr、ldm、layout 和模板参数必须相同。该函数必须由 warp 中所有线程调用，否则结果未定义。

store_matrix_sync

该函数会等待 warp 中所有 lane 到达后，将矩阵 fragment 存储到内存。mptr 必须是指向矩阵首元素、按 256 位对齐的指针。ldm 对 __half 必须是 8 的倍数，对 float 必须是 4 的倍数（即均为 16 字节的倍数）。输出矩阵布局必须指定为 mem_row_major 或 mem_col_major。warp 中所有线程使用的 mptr、ldm、layout 和模板参数必须相同。

fill_fragment

该函数使用常量值 v 填充矩阵 fragment。由于矩阵元素到 fragment 的映射方式没有指定，通常应由 warp 中所有线程使用相同的 v 调用该函数。

mma_sync

该函数等待 warp 中所有 lane 到达后，执行 warp 同步的矩阵乘加运算：

\[ D=A\times B+C \]

也支持原地运算 \(C=A\times B+C\)。warp 中所有线程使用的 satf 值和每个矩阵 fragment 的模板参数必须相同；A、B、C、D fragment 的 m、n、k 参数也必须匹配。该函数必须由 warp 中所有线程调用，否则结果未定义。

如果 satf（饱和到有限值）模式为真，目标累加器还具有以下数值行为：

  • 若结果元素为 \(+\infty\)，对应累加器存储 +MAX_NORM；
  • 若结果元素为 \(-\infty\)，对应累加器存储 -MAX_NORM；
  • 若结果元素为 NaN，对应累加器存储 +0。

由于矩阵元素在各线程 fragment 中的映射方式未指定，若要单独访问矩阵元素，应先调用 store_matrix_sync() 将其存入共享内存或全局内存。特殊情况下，如果 warp 中所有线程都以相同方式对 fragment 的所有元素执行逐元素操作，则可直接使用以下成员：

enum fragment<Use, m, n, k, T, Layout>::num_elements;
T fragment<Use, m, n, k, T, Layout>::x[num_elements];

例如，将累加器矩阵块缩放为原来的一半：

wmma::fragment<wmma::accumulator, 16, 16, 16, float> frag;
float alpha = 0.5f; // warp 中所有线程使用相同值
/* ... */
for (int t = 0; t < frag.num_elements; t++)
    frag.x[t] *= alpha;

10.24.2 替代浮点格式（Alternate Floating Point）

计算能力为 8.0 及以上的设备，其 Tensor Core 支持其他浮点格式。

__nv_bfloat16

该格式是另一种 fp16 格式，其数值范围与 f32 相同，但精度较低（7 位）。可以直接使用 cuda_bf16.h 中的 __nv_bfloat16 类型。使用该类型的矩阵 fragment 必须搭配 float 类型累加器。支持的矩阵形状和操作与 __half 相同。

tf32

tf32 是 Tensor Core 支持的一种特殊浮点格式，其范围与 f32 相同，但精度较低（至少 10 位）。该格式的内部布局由实现决定。若要在 WMMA 操作中使用 tf32，必须手动将输入矩阵转换为 tf32 精度。

CUDA 提供了内建函数 __float_to_tf32 进行转换。该函数的输入和输出参数类型都是 float，但输出数值采用 tf32 精度。此精度仅设计用于 Tensor Core；若与其他浮点类型操作混合使用，结果的精度和范围未定义。

将输入矩阵 A 或 B 转换为 tf32 后，可以使用 precision::tf32 精度的 fragment，并通过 float 类型的 load_matrix_sync() 加载。两个累加器 fragment 都必须使用 float 类型。唯一支持的矩阵尺寸为 \(16\times16\times8\)（m-n-k）。fragment 元素以 float 表示，因此 precision::tf32 对应的存储元素类型为 float。

10.24.3 双精度（Double Precision）

计算能力为 8.0 及以上的设备支持 Tensor Core 双精度浮点操作。要使用该功能，必须使用 double 类型的 fragment。mma_sync 操作采用 .rn 舍入修饰符，即舍入到最近值，平局时取偶数。

10.24.4 子字节操作（Sub-byte Operations）

子字节 WMMA 操作用于访问 Tensor Core 的低精度计算能力。它们属于预览功能，数据结构和 API 可能发生变化，未来版本也可能不兼容。相关接口位于 nvcuda::wmma::experimental 命名空间。

namespace experimental {
namespace precision {
    struct u4; // 4 位无符号
    struct s4; // 4 位有符号
    struct b1; // 1 位
}
enum bmmaBitOp {
    bmmaBitOpXOR = 1, // 最低要求 compute_75
    bmmaBitOpAND = 2  // 最低要求 compute_80
};
enum bmmaAccumulateOp {
    bmmaAccumulateOpPOPC = 1
};
}

对于 4 位精度，API 与常规 WMMA 相同，但必须将 fragment 数据类型指定为 experimental::precision::u4 或 experimental::precision::s4。由于元素被打包存储，num_storage_elements 会小于 num_elements。子字节 fragment 的 num_elements 表示子字节元素的数量；单比特精度也遵循此规则。

元素类型 存储元素类型 每个存储元素包含的元素数
experimental::precision::u4 unsigned 8
experimental::precision::s4 int 8
experimental::precision::b1 unsigned 32
其他类型 T T 1

子字节 fragment 的布局固定为：矩阵 A 使用 row_major，矩阵 B 使用 col_major。调用 load_matrix_sync() 时，若元素类型为 u4 或 s4，ldm 必须是 32 的倍数；若元素类型为 b1，则必须是 128 的倍数（两种情况均相当于 16 字节的倍数）。

  • experimental::precision::u4
  • experimental::precision::s4
  • bmmaBitOp 设置为 bmmaBitOpXOR 时的 experimental::precision::b1

bmma_sync

该函数等待 warp 中所有 lane 到达后，执行 warp 同步的位矩阵乘加操作：

\[ D=(A\ \mathrm{op}\ B)+C \]

其中 op 先执行 bmmaBitOp 指定的逻辑操作，再执行 bmmaAccumulateOp 指定的累加。可用操作包括：

  • bmmaBitOpXOR：对矩阵 A 的一行和矩阵 B 的一列执行 128 位 XOR；
  • bmmaBitOpAND：对矩阵 A 的一行和矩阵 B 的一列执行 128 位 AND，仅支持计算能力 8.0 及以上的设备。

累加操作始终为 bmmaAccumulateOpPOPC，即统计置位比特的数量。

10.24.5 限制（Restrictions）

Tensor Core 所需的特殊数据格式可能因设备主版本和次版本架构而异。由于每个线程只持有整个矩阵的一个 fragment（不透明且与架构相关的 ABI 数据结构），开发者不能假定矩阵元素如何映射到参与矩阵乘加的寄存器。

fragment 与架构有关，因此，如果函数 A 和函数 B 针对不同但链接兼容的架构编译，并链接到同一设备可执行文件中，就不应将 fragment 从 A 传给 B。fragment 的大小和布局可能由某一架构决定，而另一架构调用 WMMA API 可能导致错误结果甚至内存损坏。例如，sm_70 与 sm_75 的 fragment 布局就可能不同。

这种未定义行为在编译时或运行时工具中也可能无法检测，因此必须特别确保 fragment 布局一致。风险尤其可能出现在链接针对不同链接兼容架构构建、且期望接收 WMMA fragment 的旧版库时。弱链接（例如 CUDA C++ 内联函数）也可能让链接器选择任意可用定义，从而隐式地跨编译单元传递 fragment。

为避免此类问题，应先通过 wmma::store_matrix_sync(dst, ...) 将矩阵写入内存，再通过普通指针（例如 float *dst）传给外部函数。

由于 sm_70 可以在 sm_75 上运行，上述示例中的 sm_75 代码可以改为 sm_70 并在 sm_75 上正确运行。不过，与其他单独编译的 sm_75 二进制文件链接时，仍建议应用程序包含 sm_75 原生代码。

10.25 DPX

DPX 是一组硬件加速函数，用于查找最小值、最大值，以及执行融合加法与最小值/最大值操作。它们最多接受三个 16 位或 32 位有符号/无符号整数参数，并可选择应用 ReLU（将结果钳制到零及以上）。

主要函数类别如下。

  • 三个参数： __vimax3_s32、__vimax3_s16x2、__vimax3_u32、__vimax3_u16x2、__vimin3_s32、__vimin3_s16x2、__vimin3_u32、__vimin3_u16x2。
  • 两个参数并应用 ReLU： __vimax_s32_relu、__vimax_s16x2_relu、__vimin_s32_relu、__vimin_s16x2_relu。
  • 三个参数并应用 ReLU： __vimax3_s32_relu、__vimax3_s16x2_relu、__vimin3_s32_relu、__vimin3_s16x2_relu。
  • 两个参数，并返回哪个参数较小/较大： __vibmax_s32、__vibmax_u32、__vibmin_s32、__vibmin_u32、__vibmax_s16x2、__vibmax_u16x2、__vibmin_s16x2、__vibmin_u16x2。
  • 三个参数，比较“第一个参数 + 第二个参数”与第三个参数： __viaddmax_s32、__viaddmax_s16x2、__viaddmax_u32、__viaddmax_u16x2、__viaddmin_s32、__viaddmin_s16x2、__viaddmin_u32、__viaddmin_u16x2。
  • 三个参数并应用 ReLU，同时比较“第一个参数 + 第二个参数”、第三个参数和零： __viaddmax_s32_relu、__viaddmax_s16x2_relu、__viaddmin_s32_relu、__viaddmin_s16x2_relu。

这些指令在计算能力为 9 及以上的设备上由硬件加速，在较旧设备上则通过软件模拟实现。完整 API 见 CUDA Math API 文档。

DPX 对动态规划算法尤其有用，例如基因组学中的 Smith–Waterman 和 Needleman–Wunsch 算法，以及路径优化中的 Floyd–Warshall 算法。

NVIDIA C++ 标准库提供了面向 GPU 的 std::barrier 实现，并扩展了屏障对象的作用域设置功能，相关内容见“线程作用域”。计算能力为 8.0 及以上的设备可通过硬件加速屏障操作，并支持屏障与 memcpy_async 功能集成。计算能力为 7.0 及以上但低于 8.0 的设备也支持这些屏障，不过没有硬件加速。

10.26.1 简单同步模式（Simple Synchronization Pattern）

在没有 arrive/wait 屏障的情况下，可以使用 __syncthreads() 同步线程块中的所有线程，或者在使用 Cooperative Groups 时调用 group.sync()。

#include <cooperative_groups.h>
__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();
    for (int i = 0; i < iteration_count; ++i) {
        /* 同步前的代码 */
        block.sync(); /* 等待所有线程到达 */
        /* 同步后的代码 */
    }
}

线程会在 block.sync() 处阻塞，直到所有线程都到达同步点。同步点之前发生的内存更新，保证在同步点之后对线程块中的所有线程可见。这相当于执行 atomic_thread_fence(memory_order_seq_cst, thread_scope_block)，并同时进行同步。

该模式包含三个阶段：同步前的内存更新、同步点，以及能够观察到同步前更新的后续代码。

10.26.2 时间拆分与同步的五个阶段（Temporal Splitting and Five Stages of Synchronization）

使用 std::barrier 的时间拆分同步模式如下：

#include <cuda/barrier>
#include <cooperative_groups.h>
__device__ void compute(float* data, int curr_iteration);

__global__ void split_arrive_wait(int iteration_count, float *data) {
    using barrier = cuda::barrier<cuda::thread_scope_block>;
    __shared__ barrier bar;
    auto block = cooperative_groups::this_thread_block();

    if (block.thread_rank() == 0)
        init(&bar, block.size());
    block.sync();

    for (int curr_iter = 0; curr_iter < iteration_count; ++curr_iter) {
        /* arrive 之前的代码 */
        barrier::arrival_token token = bar.arrive();
        /* arrive 不会阻塞线程 */
        compute(data, curr_iter);
        bar.wait(std::move(token));
        /* 等待所有参与线程完成 arrive */
        /* wait 之后的代码 */
    }
}

在该模式中，block.sync() 被拆分为到达点 bar.arrive() 和等待点 bar.wait(std::move(token))。线程第一次调用 bar.arrive() 时开始参与屏障。调用 bar.wait(std::move(token)) 时，如果参与线程尚未按 init() 指定的预期到达计数完成 arrive，调用线程就会阻塞。

参与线程在调用 bar.arrive() 之前完成的内存更新，保证在参与线程调用 bar.wait(std::move(token)) 之后对其可见。由于 bar.arrive() 不会阻塞线程，线程可以继续执行其他不依赖于其他线程 arrive 前内存更新的工作。

该模式包含五个阶段：到达前的内存更新、带隐式内存栅栏的 arrive 点、arrive 与 wait 之间的代码、wait 点，以及能够观察到 arrive 前更新的 wait 后代码。

10.26.3 引导初始化、预期到达计数与参与机制（Bootstrap Initialization, Expected Arrival Count, and Participation）

任何线程开始参与 cuda::barrier 之前，都必须先完成初始化。

#include <cuda/barrier>
#include <cooperative_groups.h>
__global__ void init_barrier() {
    __shared__ cuda::barrier<cuda::thread_scope_block> bar;
    auto block = cooperative_groups::this_thread_block();
    if (block.thread_rank() == 0)
        init(&bar, block.size()); // 初始化预期到达总数
    block.sync();
}

必须在任何线程调用 bar.arrive() 前，使用 init() 初始化屏障并指定预期到达计数。本例使用 block.size()。这产生一个引导问题：线程必须先同步才能参与屏障，但屏障本身正是为了同步而创建。本例通过 Cooperative Groups 的 block.sync() 完成初始化阶段的同步；如果整个线程块参与初始化，也可使用 __syncthreads()。

init() 的第二个参数是预期到达计数，即参与线程在某个参与线程从 bar.wait(std::move(token)) 返回前，必须调用 bar.arrive() 的次数。本例中线程块内所有线程都参与，因此计数等于线程块大小。

cuda::barrier 可以灵活指定参与方式和参与线程。相比之下，this_thread_block.sync() 与 __syncthreads() 面向整个线程块，而 __syncwarp(mask) 面向指定 warp 子集。如果只需同步整个线程块或整个 warp，出于性能考虑，建议分别使用 __syncthreads() 和 __syncwarp(mask)。

10.26.4 屏障阶段：到达、倒计时、完成与重置（A Barrier’s Phase: Arrival, Countdown, Completion, and Reset）

随着参与线程调用 bar.arrive()，屏障会从预期到达计数开始倒计时。计数达到零时，当前阶段完成。最后一次使计数归零的 arrive 会自动、以原子方式重置计数，将其恢复为预期到达计数，并使屏障进入下一阶段。

bar.arrive() 返回的 cuda::barrier::arrival_token 与屏障的当前阶段关联。调用 bar.wait(std::move(token)) 时，如果屏障仍处于 token 对应的阶段，调用线程就会阻塞。如果调用 wait 之前阶段已经推进，线程不会阻塞；如果线程在 wait 中阻塞期间阶段推进，线程就会解除阻塞。

在复杂同步模式中必须遵守以下规则：

  • token = bar.arrive() 必须在屏障当前阶段发生；bar.wait(std::move(token)) 必须在同一阶段或下一阶段发生。
  • 调用 bar.arrive() 时，屏障计数必须非零。若该调用使倒计时归零，则在屏障下一次重用前，必须完成相应的 wait 调用。
  • bar.wait() 只能使用当前阶段或紧邻前一阶段的 token。其他 token 会导致未定义行为。

对于简单的 arrive/wait 同步模式，遵守这些规则通常比较直接。

10.26.5 空间分区（又称 Warp 专门化）（Spatial Partitioning / Warp Specialization）

一个线程块可以进行空间分区，让不同 warp 专门执行相互独立的计算。该方式常用于生产者/消费者模式：一部分线程产生数据，另一组互不重叠的线程同时消费这些数据。

生产者/消费者模式需要两个单向同步操作来管理数据缓冲区：

生产者 消费者
等待缓冲区准备好被填充 发出缓冲区已准备好被填充的信号
生成数据并填充缓冲区 等待缓冲区填充完成
发出缓冲区已填满的信号 消费缓冲区中的数据

生产者线程等待消费者线程发出“缓冲区可填充”的信号，但消费者不等待这一信号。消费者等待生产者发出“缓冲区已填满”的信号，但生产者不等待这一信号。为了实现完整的并发，通常至少需要双缓冲；每个缓冲区都需要两个 cuda::barrier。

#include <cuda/barrier>
#include <cooperative_groups.h>
using barrier = cuda::barrier<cuda::thread_scope_block>;

__device__ void producer(barrier ready[], barrier filled[],
                         float* buffer, float* in, int N, int buffer_len) {
    for (int i = 0; i < (N / buffer_len); ++i) {
        ready[i % 2].arrive_and_wait(); // 等待缓冲区可填充
        /* 生成数据并填充 buffer_(i%2) */
        barrier::arrival_token token = filled[i % 2].arrive();
        /* 缓冲区已填满 */
    }
}

__device__ void consumer(barrier ready[], barrier filled[],
                         float* buffer, float* out, int N, int buffer_len) {
    barrier::arrival_token token1 = ready[0].arrive();
    barrier::arrival_token token2 = ready[1].arrive();

    for (int i = 0; i < (N / buffer_len); ++i) {
        filled[i % 2].arrive_and_wait(); // 等待缓冲区填满
        /* 消费 buffer_(i%2) */
        barrier::arrival_token token = ready[i % 2].arrive();
        /* 缓冲区可重新填充 */
    }
}

// N 是输入与输出数组中的 float 元素总数
__global__ void producer_consumer_pattern(
    int N, int buffer_len, float* in, float* out) {
    // 共享缓冲区大小为 2 * buffer_len，在两个缓冲区间交替工作。
    // buffer_0 = buffer，buffer_1 = buffer + buffer_len
    __shared__ extern float buffer[];

    // bar[0]、bar[1] 跟踪两个缓冲区是否可填充；
    // bar[2]、bar[3] 分别跟踪两个缓冲区是否已填满。
    __shared__ barrier bar[4];

    auto block = cooperative_groups::this_thread_block();
    if (block.thread_rank() < 4)
        init(bar + block.thread_rank(), block.size());
    block.sync();

    if (block.thread_rank() < warpSize)
        producer(bar, bar + 2, buffer, in, N, buffer_len);
    else
        consumer(bar, bar + 2, buffer, out, N, buffer_len);
}

本例将第一个 warp 专门用作生产者，其余 warp 专门用作消费者。所有生产者和消费者线程都会参与四个屏障中的每一个，因此预期到达计数均等于 block.size()。

生产者线程等待消费者发出共享缓冲区可填充的信号。它可以先调用 ready[i%2].arrive() 获得 token，再调用 ready[i%2].wait(token)；为简化代码，ready[i%2].arrive_and_wait() 合并了这两个操作：

bar.arrive_and_wait();
/* 等价于 */
bar.wait(bar.arrive());

生产者填充缓冲区后，通过 filled[i%2].arrive() 发出缓冲区已填满的信号。此时生产者不会等待，而是继续运行，直到下一轮中另一个缓冲区准备好填充。

消费者线程一开始就发出两个缓冲区均已准备好填充的信号，但不会在此处等待。随后消费者等待当前迭代的缓冲区填满，再消费数据，最后调用 ready[i%2].arrive() 通知生产者该缓冲区可以重新填充，然后等待下一轮数据。

10.26.6 提前退出（退出参与）（Early Exit / Dropping out of Participation）

如果参与一系列同步操作的线程必须提前退出，就必须在退出之前显式放弃参与。其余参与线程随后仍可正常执行 cuda::barrier 的 arrive 和 wait 操作。

#include <cuda/barrier>
#include <cooperative_groups.h>
__device__ bool condition_check();

__global__ void early_exit_kernel(int N) {
    using barrier = cuda::barrier<cuda::thread_scope_block>;
    __shared__ barrier bar;
    auto block = cooperative_groups::this_thread_block();

    if (block.thread_rank() == 0)
        init(&bar, block.size());
    block.sync();

    for (int i = 0; i < N; ++i) {
        if (condition_check()) {
            bar.arrive_and_drop();
            return;
        }

        /* 其他线程可以正常继续 */
        barrier::arrival_token token = bar.arrive();
        /* arrive 与 wait 之间的代码 */
        bar.wait(std::move(token));
        /* wait 之后的代码 */
    }
}

arrive_and_drop() 会先到达当前阶段，以履行该线程在当前阶段的到达义务；随后减少下一阶段的预期到达计数，使屏障不再期待该线程参与后续阶段。

10.26.7 完成函数（Completion Function）

cuda::barrier<Scope, CompletionFunction> 的 CompletionFunction 每个阶段执行一次，时机是在最后一个线程到达之后、任何线程从 wait 解除阻塞之前。

参与线程在该阶段到达屏障前执行的内存操作，对执行 CompletionFunction 的线程可见；而 CompletionFunction 内部执行的所有内存操作，在等待线程解除阻塞后，对这些线程可见。

#include <cuda/barrier>
#include <cooperative_groups.h>
#include <functional>
namespace cg = cooperative_groups;

__device__ int divergent_compute(int*, int);
__device__ int independent_computation(int*, int);

__global__ void psum(int* data, int n, int* acc) {
    auto block = cg::this_thread_block();
    constexpr int BlockSize = 128;
    __shared__ int smem[BlockSize];
    assert(BlockSize == block.size());
    assert(n % 128 == 0);

    auto completion_fn = [&] {
        int sum = 0;
        for (int i = 0; i < 128; ++i) sum += smem[i];
        *acc += sum;
    };

    using completion_fn_t = decltype(completion_fn);
    using barrier_t =
        cuda::barrier<cuda::thread_scope_block, completion_fn_t>;
    __shared__ std::aligned_storage<sizeof(barrier_t),
                                    alignof(barrier_t)> bar_storage;

    barrier_t* bar = (barrier_t*)&bar_storage;
    if (block.thread_rank() == 0) {
        assert(*acc == 0);
        assert(blockDim.x == blockDim.y && blockDim.y == blockDim.z);
        assert(blockDim.z == 1);
        new (bar) barrier_t{block.size(), completion_fn};
        // 等价于：init(bar, block.size(), completion_fn);
    }
    block.sync();

    for (int i = 0; i < n; i += block.size()) {
        smem[block.thread_rank()] = data[i] + *acc;
        auto t = bar->arrive();
        /* 此处可以执行独立计算 */
        bar->wait(std::move(t));
        /* 所有线程均已使用完共享内存，可在下一轮重用 */
    }
}

各接口的要求和行为如下：

  • __mbarrier_maximum_count()：返回屏障可接受的最大计数。
  • __mbarrier_init()：bar 必须指向共享内存；expected_count 不得超过 __mbarrier_maximum_count()。它将当前阶段和下一阶段的预期到达计数都初始化为 expected_count。
  • __mbarrier_inval()：bar 必须指向位于共享内存中的 mbarrier 对象。若要将对应共享内存改作他用，必须先使屏障失效。
  • __mbarrier_arrive()：必须先初始化屏障，且待处理计数不得为零。该函数以原子方式递减当前阶段的待处理计数，并返回一个 token；该 token 与递减前的屏障状态关联。
  • __mbarrier_arrive_and_drop()：必须先初始化屏障，且待处理计数不得为零。该函数以原子方式递减当前阶段的待处理计数以及下一阶段的预期计数，并返回与递减前状态关联的 token。
  • __mbarrier_test_wait()：token 必须与当前阶段或紧邻前一阶段关联。如果 token 属于屏障的紧邻前一阶段，则返回 true；否则返回 false。

10.27 异步数据复制（Asynchronous Data Copies）

CUDA 11 引入了 memcpy_async API，使设备代码能够显式管理异步数据复制。该功能允许 CUDA 内核将计算与数据移动重叠执行。

10.27.1 memcpy_async API

memcpy_async API 通过以下头文件提供：

  • <cuda/barrier>
  • <cuda/pipeline>
  • <cooperative_groups/memcpy_async.h>

cuda::memcpy_async API 与 cuda::barrier 和 cuda::pipeline 同步原语配合使用；cooperative_groups::memcpy_async 则通过 cooperative_groups::wait 完成同步。

这些 API 的语义非常相似：复制操作将源对象从 src 复制到 dst，其效果如同由另一个线程执行；复制完成后，可以通过 cuda::pipeline、cuda::barrier 或 cooperative_groups::wait 与该复制操作同步。

cuda::barrier 和 cuda::pipeline 对应的 cuda::memcpy_async 重载，其完整 API 文档和示例见 libcudacxx API 文档。cooperative_groups::memcpy_async 的 API 文档见 Cooperative Groups 章节。

使用 cuda::barrier 和 cuda::pipeline 的 memcpy_async API 要求计算能力为 7.0 及以上的设备。在计算能力为 8.0 及以上的设备上，从全局内存复制到共享内存的 memcpy_async 操作可以利用硬件加速。

10.27.2 复制与计算模式：通过共享内存暂存数据（Copy and Compute Pattern — Staging Data Through Shared Memory）

  1. 从全局内存读取数据；
  2. 将数据存储到共享内存；
  3. 对共享内存中的数据执行计算，并可能将结果写回全局内存。

10.27.3 不使用 memcpy_async（Without memcpy_async）

不使用 memcpy_async 时，复制与计算模式中的复制阶段通常写成 shared[local_idx] = global[global_idx]。该赋值会被展开为两步：先从全局内存读取到寄存器，再从寄存器写入共享内存。

当这种模式出现在迭代算法中时，每个线程块都需要在赋值之后进行同步，确保所有共享内存写入完成后才能开始计算阶段；计算阶段结束后还需要再次同步，避免某些线程尚未完成计算时就覆盖共享内存。

#include <cooperative_groups.h>
__device__ void compute(int* global_out, int const* shared_in) {
    // 使用共享内存中的当前批次数据进行计算，
    // 并将当前线程的结果写回全局内存。
}

__global__ void without_memcpy_async(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    extern __shared__ int shared[]; // block.size() * sizeof(int)
    size_t local_idx = block.thread_rank();

    for (size_t batch = 0; batch < batch_sz; ++batch) {
        size_t block_batch_idx =
            block.group_index().x * block.size() + grid.size() * batch;
        size_t global_idx = block_batch_idx + threadIdx.x;

        shared[local_idx] = global_in[global_idx];
        block.sync(); // 等待所有复制完成
        compute(global_out + block_batch_idx, shared);
        block.sync(); // 等待所有共享内存计算完成
    }
}

10.27.4 使用 memcpy_async（With memcpy_async）

使用 memcpy_async 后，原来的共享内存赋值：

shared[local_idx] = global_in[global_idx];

可以替换为 Cooperative Groups 的异步复制操作：

cooperative_groups::memcpy_async(
    group, shared, global_in + batch_idx,
    sizeof(int) * block.size());

cooperative_groups::memcpy_async 会将从 global_in + batch_idx 开始的 sizeof(int) * block.size() 字节复制到共享数据区域。该操作的效果如同由另一个线程执行；复制完成后，该操作会与当前线程调用的 cooperative_groups::wait 同步。在复制完成之前修改全局源数据，或读取/写入共享目标数据，都会产生数据竞争。

计算能力为 8.0 及以上的设备可以对全局内存到共享内存的 memcpy_async 传输进行硬件加速，从而避免数据经过中间寄存器。

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in);

__global__ void with_memcpy_async(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    extern __shared__ int shared[]; // block.size() * sizeof(int)

    for (size_t batch = 0; batch < batch_sz; ++batch) {
        size_t block_batch_idx =
            block.group_index().x * block.size() + grid.size() * batch;

        // 整个线程组协作，将一个完整批次复制到共享内存。
        cooperative_groups::memcpy_async(
            block, shared, global_in + block_batch_idx,
            sizeof(int) * block.size());
        cooperative_groups::wait(block); // 等待全部复制完成
        compute(global_out + block_batch_idx, shared);
        block.sync();
    }
}

10.27.5 使用 cuda::barrier 的异步数据复制（Asynchronous Data Copies using cuda::barrier）

cuda::barrier 对应的 cuda::memcpy_async 重载允许使用屏障同步异步数据传输。该重载会将复制操作视为由另一个与屏障绑定的线程执行：创建复制操作时增加当前阶段的预期计数，复制完成时再将其减一。这样，只有当所有参与线程都已到达，并且绑定到当前阶段的所有 memcpy_async 操作都已完成时，屏障阶段才会推进。

以下示例使用线程块级屏障，线程块中的所有线程都参与。它以 barrier.arrive_and_wait() 替代前例中的等待操作，功能相同。

#include <cooperative_groups.h>
#include <cuda/barrier>

__device__ void compute(int* global_out, int const* shared_in);

__global__ void with_barrier(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    extern __shared__ int shared[];

    // 创建同步对象（C++20 barrier）
    __shared__ cuda::barrier<cuda::thread_scope::thread_scope_block> barrier;
    if (block.thread_rank() == 0)
        init(&barrier, block.size());
    block.sync();

    for (size_t batch = 0; batch < batch_sz; ++batch) {
        size_t block_batch_idx =
            block.group_index().x * block.size() + grid.size() * batch;

        cuda::memcpy_async(
            block, shared, global_in + block_batch_idx,
            sizeof(int) * block.size(), barrier);
        barrier.arrive_and_wait(); // 等待所有复制完成
        compute(global_out + block_batch_idx, shared);
        block.sync();
    }
}

10.27.6 memcpy_async 的性能指导（Performance Guidance for memcpy_async）

对于计算能力为 8.x 的设备，同一 CUDA warp 中的线程共享 pipeline 机制。这种共享会使一个 warp 中的 memcpy_async 批次发生纠缠（entanglement），在某些情况下影响性能。本节说明 warp 纠缠对 commit、wait 和 arrive 操作的影响。

10.27.6.1 对齐（Alignment）

在计算能力为 8.0 的设备上，cp.async 指令族支持异步地将数据从全局内存复制到共享内存，每次可复制 4、8 或 16 字节。如果 memcpy_async 的大小是 4、8 或 16 的倍数，并且传入的两个指针都按相应边界对齐，就可以完全使用异步内存操作实现复制。

为了获得最佳性能，共享内存和全局内存的地址都应按 128 字节对齐。

对于对齐要求只有 1 或 2 字节的类型，编译器通常无法证明指针始终满足更高对齐要求，因此必须延迟到运行时判断能否使用 cp.async。运行时对齐检查会增加代码体积和运行开销。

可以使用 cuda::aligned_size_t<size_t Align>(size_t size) 提供对齐保证：它证明传入 memcpy_async 的两个指针都按 Align 字节对齐，并且大小是 Align 的倍数。

cuda::memcpy_async(
    group, dst, src,
    cuda::aligned_size_t<16>(N * block.size()),
    pipeline);

如果这一对齐保证不正确，行为未定义。

10.27.6.2 可平凡复制类型（Trivially Copyable）

在计算能力为 8.0 的设备上，cp.async 指令族支持从全局内存到共享内存的异步复制。如果传入 memcpy_async 的指针没有指向可平凡复制（TriviallyCopyable）类型，则必须调用每个目标元素的复制构造函数，因而无法使用这些指令加速复制。

10.27.6.3 Warp 纠缠——Commit（Warp Entanglement - Commit）

memcpy_async 批次序列由整个 warp 共享。commit 操作会合并：所有处于收敛状态并调用 commit 的线程只使序列递增一次。若 warp 完全收敛，序列递增 1；若 warp 完全发散，序列递增 32。

  • \(P_B\)：warp 共享 pipeline 的实际批次序列。
  • \(T_B\)：单个线程感知的批次序列，仿佛只有该线程调用 commit 时才递增。

pipeline.producer_commit() 返回的是线程感知的批次序列中的值。线程感知序列的索引总是对应于实际 warp 共享序列中相同或更大的索引；只有所有 commit 操作都由收敛线程调用时，两个序列才相同。

例如，当 warp 完全发散时，实际序列为 \(P_B=\{0,1,2,\ldots,31\}\)，而 warp 中每个线程感知到的序列都只有一个元素 \(\{0\}\)。

10.27.6.4 Warp 纠缠——Wait（Warp Entanglement - Wait）

CUDA 线程可以调用 pipeline_consumer_wait_prior<N>() 或 pipeline.consumer_wait()，等待线程感知序列 \(T_B\) 中的批次完成。pipeline.consumer_wait() 等价于 pipeline_consumer_wait_prior<N>()，其中 \(N=P_L\)。

pipeline_consumer_wait_prior<N>() 会等待实际序列中截至 \(P_L-N\)（包含该批次）的操作完成。由于线程感知序列的最后索引 \(T_L\) 不大于实际序列最后索引 \(P_L\)，等待实际序列会覆盖截至 \(T_L-N\) 的批次。因此，当 \(T_L<P_L\) 时，线程可能会意外等待更多、更新的批次。在 warp 完全发散的极端情况下，每个线程可能都等待全部 32 个批次。

10.27.6.5 Warp 纠缠——Arrive-On（Warp Entanglement - Arrive-On）

warp 发散会影响 arrive_on(bar) 更新屏障的次数。调用 warp 完全收敛时，屏障只更新一次；调用 warp 完全发散时，会对屏障执行 32 次独立更新。

10.27.6.6 保持 Commit 和 Arrive-On 操作收敛（Keep Commit and Arrive-On Operations Converged）

建议由收敛线程调用 commit 和 arrive-on 操作，以避免线程感知的批次序列与实际序列不一致导致过度等待，并尽量减少对屏障对象的更新。

如果这些操作之前的代码使线程发散，应在调用 commit 或 arrive-on 之前通过 __syncwarp() 使 warp 重新收敛。

10.28 使用 cuda::pipeline 的异步数据复制（Asynchronous Data Copies using cuda::pipeline）

CUDA 提供 cuda::pipeline 同步对象，用于管理异步数据移动，并使数据移动与计算重叠执行。

cuda::pipeline 的完整 API 文档见 libcudacxx API。pipeline 对象是一个具有头部和尾部的双端 N 阶队列，按先进先出（FIFO）顺序处理工作。其成员函数如下。

成员函数 说明
producer_acquire 获取 pipeline 内部队列中一个可用阶段
producer_commit 提交在 producer_acquire 后、当前获取阶段上发出的异步操作
consumer_wait 等待 pipeline 最旧阶段上的所有异步操作完成
consumer_release 释放最旧阶段，使其可供 pipeline 重新使用；之后生产者可再次获取该阶段

10.28.1 使用 cuda::pipeline 的单阶段异步数据复制（Single-Stage Asynchronous Data Copies）

前面的示例展示了如何使用 Cooperative Groups 和 cuda::barrier 执行异步数据传输。本节使用单阶段 cuda::pipeline 调度异步复制，后续再扩展为多阶段流水线，使计算和复制重叠执行。

#include <cooperative_groups/memcpy_async.h>
#include <cuda/pipeline>

__device__ void compute(int* global_out, int const* shared_in);

__global__ void with_single_stage(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    constexpr size_t stages_count = 1; // 单阶段流水线
    extern __shared__ int shared[];    // block.size() * sizeof(int)

    __shared__ cuda::pipeline_shared_state<
        cuda::thread_scope::thread_scope_block,
        stages_count
    > shared_state;

    auto pipeline = cuda::make_pipeline(block, &shared_state);

    // 计算当前线程块中批次在全局内存中的偏移量。
    auto block_batch = [&](size_t batch) -> int {
        return block.group_index().x * block.size() + grid.size() * batch;
    };

    for (size_t batch = 0; batch < batch_sz; ++batch) {
        size_t global_idx = block_batch(batch);

        // 集体获取 pipeline 头部阶段。
        pipeline.producer_acquire();

        // 将异步复制提交到 pipeline 当前阶段。
        cuda::memcpy_async(
            block, shared, global_in + global_idx,
            sizeof(int) * block.size(), pipeline);

        // 集体提交并推进 pipeline 头部阶段。
        pipeline.producer_commit();

        // 等待最旧阶段中的操作完成。
        pipeline.consumer_wait();

        // 对共享内存中的当前批次执行计算。
        compute(global_out + global_idx, shared);

        // 集体释放该阶段资源。
        pipeline.consumer_release();
    }
}

10.28.2 使用 cuda::pipeline 的多阶段异步数据复制（Multi-Stage Asynchronous Data Copies）

在前面使用 cooperative_groups::wait 和 cuda::barrier 的示例中，内核线程会立即等待数据传输到共享内存完成。这虽然避免了数据从全局内存经由寄存器传递，但不能通过计算重叠来隐藏 memcpy_async 的延迟。

为此可以使用 CUDA pipeline 管理一系列 memcpy_async 批次，使内核将内存传输与计算重叠。下面的示例实现一个双阶段流水线：

  1. 初始化 pipeline 的共享状态；
  2. 通过提交第一个批次的 memcpy_async 启动流水线；
  3. 循环处理各批次：先为下一批调度复制，等待上一批复制完成，再对上一批执行计算，同时复制下一批数据；
  4. 最后排空流水线，对最后一个批次执行计算。

为与 cuda::pipeline 配合，这里使用 <cuda/pipeline> 头文件中的 cuda::memcpy_async。

#include <cooperative_groups/memcpy_async.h>
#include <cuda/pipeline>

__device__ void compute(int* global_out, int const* shared_in);

__global__ void with_staging(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    constexpr size_t stages_count = 2; // 双阶段流水线
    extern __shared__ int shared[];    // 两个批次都必须放入共享内存
    size_t shared_offset[stages_count] = {0, block.size()};

    __shared__ cuda::pipeline_shared_state<
        cuda::thread_scope::thread_scope_block,
        stages_count
    > shared_state;
    auto pipeline = cuda::make_pipeline(block, &shared_state);

    auto block_batch = [&](size_t batch) -> int {
        return block.group_index().x * block.size() + grid.size() * batch;
    };

    if (batch_sz == 0) return;

    // 先提交第一个批次的复制，启动流水线。
    pipeline.producer_acquire();
    cuda::memcpy_async(
        block, shared + shared_offset[0], global_in + block_batch(0),
        sizeof(int) * block.size(), pipeline);
    pipeline.producer_commit();

    // 流水线复制/计算循环。
    for (size_t batch = 1; batch < batch_sz; ++batch) {
        size_t compute_stage_idx = (batch - 1) % 2;
        size_t copy_stage_idx = batch % 2;
        size_t global_idx = block_batch(batch);

        pipeline.producer_acquire();

        // 为下一轮计算提交异步复制。
        cuda::memcpy_async(
            block, shared + shared_offset[copy_stage_idx],
            global_in + global_idx, sizeof(int) * block.size(), pipeline);
        pipeline.producer_commit();

        // 等待前一个计算阶段所需的复制操作完成。
        pipeline.consumer_wait();

        // 对上一批计算，同时下一批的复制已在进行。
        compute(global_out + global_idx,
                shared + shared_offset[compute_stage_idx]);

        pipeline.consumer_release();
    }

    // 排空流水线，处理最后一批数据。
    pipeline.consumer_wait();
    compute(global_out + block_batch(batch_sz - 1),
            shared + shared_offset[(batch_sz - 1) % 2]);
    pipeline.consumer_release();
}

pipeline 对象是一个双端队列，包含头部和尾部，按 FIFO 顺序处理工作。生产者线程将工作提交到头部，消费者线程从尾部取出工作。上例中所有线程既是生产者，也是消费者：线程先提交下一批复制，再等待上一批复制完成。

向 pipeline 阶段提交工作包括：

  1. 使用 pipeline.producer_acquire() 集体获取头部阶段；
  2. 向该阶段提交 memcpy_async 操作；
  3. 使用 pipeline.producer_commit() 集体提交并推进头部。

使用已提交的阶段包括：

  1. 使用 pipeline.consumer_wait() 等待最旧阶段的操作完成；
  2. 使用 pipeline.consumer_release() 集体释放该阶段。

cuda::pipeline_shared_state<scope, count> 封装了 pipeline 可用的有限资源，允许它同时处理最多 count 个阶段。如果所有资源都在使用，pipeline.producer_acquire() 会阻塞生产者，直到消费者释放下一个阶段所需的资源。

10.28.2（续）统一循环与专门化生产者/消费者

前面的多阶段流水线示例可以进一步简化：将循环的启动阶段和收尾阶段合并到循环本身。

template <size_t stages_count = 2>
__global__ void with_staging_unified(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    assert(size == batch_sz * grid.size());

    extern __shared__ int shared[];
    size_t shared_offset[stages_count];
    for (int s = 0; s < stages_count; ++s)
        shared_offset[s] = s * block.size();

    __shared__ cuda::pipeline_shared_state<
        cuda::thread_scope::thread_scope_block,
        stages_count
    > shared_state;
    auto pipeline = cuda::make_pipeline(block, &shared_state);

    auto block_batch = [&](size_t batch) -> int {
        return block.group_index().x * block.size() + grid.size() * batch;
    };

    // compute_batch：下一批待计算的数据；fetch_batch：下一批待复制的数据。
    for (size_t compute_batch = 0, fetch_batch = 0;
         compute_batch < batch_sz; ++compute_batch) {
        // 内层循环传输数据，确保流水线尽可能保持填满。
        for (; fetch_batch < batch_sz &&
               fetch_batch < (compute_batch + stages_count);
             ++fetch_batch) {
            pipeline.producer_acquire();
            size_t shared_idx = fetch_batch % stages_count;
            size_t block_batch_idx = block_batch(fetch_batch);
            cuda::memcpy_async(
                block, shared + shared_offset[shared_idx],
                global_in + block_batch_idx,
                sizeof(int) * block.size(), pipeline);
            pipeline.producer_commit();
        }

        pipeline.consumer_wait();
        size_t shared_idx = compute_batch % stages_count;
        compute(global_out + block_batch(compute_batch),
                shared + shared_offset[shared_idx]);
        pipeline.consumer_release();
    }
}

pipeline<thread_scope_block> 也支持更灵活的用法：线程块中的任意子集可以参与 pipeline；参与的线程中，也可以指定任意子集分别充当生产者、消费者或同时充当两者。以下示例中，线程 rank 为偶数的线程充当生产者，奇数线程充当消费者。

__device__ void compute(int* global_out, int shared_in);

template <size_t stages_count = 2>
__global__ void with_specialized_staging_unified(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();

    const cuda::pipeline_role thread_role =
        block.thread_rank() % 2 == 0
            ? cuda::pipeline_role::producer
            : cuda::pipeline_role::consumer;

    auto producer_threads = block.size() / 2;
    const int thread_idx = block.thread_rank() / 2;
    auto elements_per_batch = size / batch_sz;
    auto elements_per_batch_per_block =
        elements_per_batch / grid.group_dim().x;

    extern __shared__ int shared[];
    size_t shared_offset[stages_count];
    for (int s = 0; s < stages_count; ++s)
        shared_offset[s] = s * elements_per_batch_per_block;

    __shared__ cuda::pipeline_shared_state<
        cuda::thread_scope::thread_scope_block,
        stages_count
    > shared_state;
    cuda::pipeline pipeline =
        cuda::make_pipeline(block, &shared_state, thread_role);

    auto block_batch = [&](size_t batch) -> int {
        return elements_per_batch * batch
             + elements_per_batch_per_block * blockIdx.x;
    };

    for (size_t compute_batch = 0, fetch_batch = 0;
         compute_batch < batch_sz; ++compute_batch) {
        for (; fetch_batch < batch_sz &&
               fetch_batch < (compute_batch + stages_count);
             ++fetch_batch) {
            if (thread_role == cuda::pipeline_role::producer) {
                pipeline.producer_acquire();
                size_t shared_idx = fetch_batch % stages_count;
                size_t global_batch_idx =
                    block_batch(fetch_batch) + thread_idx;
                size_t shared_batch_idx =
                    shared_offset[shared_idx] + thread_idx;

                cuda::memcpy_async(
                    shared + shared_batch_idx,
                    global_in + global_batch_idx,
                    sizeof(int), pipeline);
                pipeline.producer_commit();
            }
        }

        if (thread_role == cuda::pipeline_role::consumer) {
            pipeline.consumer_wait();
            size_t shared_idx = compute_batch % stages_count;
            size_t global_batch_idx =
                block_batch(compute_batch) + thread_idx;
            size_t shared_batch_idx =
                shared_offset[shared_idx] + thread_idx;

            compute(global_out + global_batch_idx,
                    *(shared + shared_batch_idx));
            pipeline.consumer_release();
        }
    }
}

pipeline 会进行一些优化，例如所有线程同时充当生产者和消费者时。但支持这些灵活特性的成本通常无法完全消除。例如，pipeline 会在共享内存中存储并使用一组屏障进行同步；如果线程块中的所有线程都参与 pipeline，这些额外屏障未必必要。

当线程块中的所有线程都参与 pipeline 时，可以使用 pipeline<thread_scope_thread> 配合 __syncthreads()，获得比 pipeline<thread_scope_block> 更好的性能。每个线程使用自己的 pipeline，复制自身负责的数据，然后通过线程块同步确保该阶段所有异步复制均已完成。

template<size_t stages_count>
__global__ void with_staging_scope_thread(
    int* global_out, int const* global_in,
    size_t size, size_t batch_sz) {
    auto grid = cooperative_groups::this_grid();
    auto block = cooperative_groups::this_thread_block();
    auto thread = cooperative_groups::this_thread();
    assert(size == batch_sz * grid.size());

    extern __shared__ int shared[];
    size_t shared_offset[stages_count];
    for (int s = 0; s < stages_count; ++s)
        shared_offset[s] = s * block.size();

    cuda::pipeline<cuda::thread_scope_thread> pipeline =
        cuda::make_pipeline();

    auto block_batch = [&](size_t batch) -> int {
        return block.group_index().x * block.size() + grid.size() * batch;
    };

    for (size_t compute_batch = 0, fetch_batch = 0;
         compute_batch < batch_sz; ++compute_batch) {
        for (; fetch_batch < batch_sz &&
               fetch_batch < (compute_batch + stages_count);
             ++fetch_batch) {
            pipeline.producer_acquire();
            size_t shared_idx = fetch_batch % stages_count;
            size_t thread_batch_idx =
                block_batch(fetch_batch) + threadIdx.x;

            cuda::memcpy_async(
                thread, shared + shared_offset[shared_idx] + threadIdx.x,
                global_in + thread_batch_idx, sizeof(int), pipeline);
            pipeline.producer_commit();
        }

        pipeline.consumer_wait();
        block.sync(); // 确保线程块内该阶段的所有复制均已完成
        size_t shared_idx = compute_batch % stages_count;
        compute(global_out + block_batch(compute_batch),
                shared + shared_offset[shared_idx]);
        pipeline.consumer_release();
    }
}

如果计算操作只读取当前线程所在 warp 中其他线程写入的共享内存，则使用 __syncwarp() 即可。

10.28.4 Pipeline 原语接口（Pipeline Primitives Interface）

Pipeline 原语是 memcpy_async 功能的类 C 接口。通常包含 <cuda_pipeline.h> 即可使用；如果编译时不使用 ISO C++ 2011 兼容模式，则应包含 <cuda_pipeline_primitives.h>。

10.28.4.1 memcpy_async 原语（memcpy_async Primitive）

void __pipeline_memcpy_async(
    void* __restrict__ dst_shared,
    const void* __restrict__ src_global,
    size_t size_and_align,
    size_t zfill = 0);

该函数请求异步执行以下操作：复制 size_and_align - zfill 字节，再将剩余的 zfill 字节填零。

size_t i = 0;
for (; i < size_and_align - zfill; ++i)
    ((char*)dst_shared)[i] = ((char*)src_global)[i]; // 复制
for (; i < size_and_align; ++i)
    ((char*)dst_shared)[i] = 0; // 填零

要求如下：

  • dst_shared 必须指向共享内存中的目标地址；
  • src_global 必须指向全局内存中的源地址；
  • size_and_align 必须为 4、8 或 16；
  • zfill 不得大于 size_and_align；
  • size_and_align 必须与 dst_shared 和 src_global 的对齐要求一致。

在等待 memcpy_async 完成之前，任何线程修改源内存或观察目标内存都会造成数据竞争。在提交复制与等待完成之间，以下操作都会产生数据竞争：从 dst_shared 加载、向 dst_shared 或 src_global 存储，以及对这些地址执行原子更新。

10.28.4.2 Commit 原语（Commit Primitive）

void __pipeline_commit();

将已提交的 memcpy_async 操作作为当前批次提交到 pipeline。

10.28.4.3 Wait 原语（Wait Primitive）

void __pipeline_wait_prior(size_t N);

设某线程调用 __pipeline_commit() 后形成的批次索引序列为 \(\{0,1,2,\ldots,L\}\)。该函数等待截至 \(L-N\)（包含该批次）的所有批次完成。

10.28.4.4 Arrive-On 屏障原语（Arrive On Barrier Primitive）

void __pipeline_arrive_on(__mbarrier_t* bar);

bar 指向共享内存中的屏障。当此前按顺序发出的所有 memcpy_async 操作完成时，该函数会先将屏障到达计数加一；随后再将计数减一，因此最终对计数的净影响为零。用户必须确保增加到达计数时不会超过 __mbarrier_maximum_count()。

10.29 使用张量内存加速器（TMA）进行异步数据复制（Asynchronous Data Copies using the Tensor Memory Accelerator）

许多应用程序需要在全局内存与其他内存空间之间移动大量数据。数据通常以多维数组形式存储在全局内存中，而且访问模式并不连续。为了减少全局内存访问，计算前常先将这类数组的子块复制到共享内存中。加载和存储这些数据需要反复计算地址，容易出错，也会产生重复工作。

为卸载这些地址计算，计算能力 9.0 引入了张量内存加速器（Tensor Memory Accelerator，TMA）。TMA 的主要目标是为多维数组提供高效的全局内存到共享内存数据传输机制。

术语说明： TMA 是本节所述功能的总称。为保持前向兼容性，并减少与 PTX ISA 的术语差异，本节会根据复制类型将 TMA 操作称为“批量异步复制（bulk-asynchronous copy）”或“批量张量异步复制（bulk tensor asynchronous copy）”。这里的“批量”用于与前面章节的异步内存操作区分。

维度： TMA 支持一维和多维数组复制，最高支持 5 维。一维连续数组的批量异步复制，与多维数组的批量张量异步复制采用不同的编程模型。多维数组的批量张量异步复制需要一个 tensor map（张量映射），用于描述多维数组在全局内存和共享内存中的布局。tensor map 通常在主机端使用 cuTensorMapEncode API 创建，然后作为带 __grid_constant__ 注解的 const 内核参数传给设备端。相比之下，一维连续数组的批量异步复制不需要 tensor map，只需在设备端提供指针和大小参数即可。

源与目标： 批量异步复制操作的源地址和目标地址可以位于共享内存或全局内存。操作可以将数据从全局内存读入共享内存，也可以将数据从共享内存写入全局内存，或者将共享内存数据复制到同一 cluster 中另一个线程块的分布式共享内存。在 cluster 中，还可以指定多播（multicast），将全局内存中的数据传输到 cluster 内多个线程块的共享内存。多播针对 sm_90a 优化，在其他目标架构上性能可能明显下降，因此建议仅对 sm_90a 使用。

异步性： TMA 数据传输是异步的，发起传输的线程可以继续计算，由硬件在后台执行复制。数据传输是否真正异步执行，取决于硬件实现，并且未来可能发生变化。

批量异步操作可使用不同完成机制发出完成信号。对于从全局内存读到共享内存的操作，线程块中的任意线程都可以等待共享内存屏障，直到数据可读。对于从共享内存写入全局内存或分布式共享内存的操作，只有发起操作的线程能够等待其完成；这通过批量异步组（bulk async-group）完成机制实现。

10.29.1 使用 TMA 传输一维数组（Using TMA to transfer one-dimensional arrays）

本节演示如何使用 TMA 编写一个简单内核，对一维数组执行读—修改—写操作。示例展示如何通过批量异步复制加载和存储数据，以及如何同步执行线程与复制操作。

内核执行以下步骤：

  1. 初始化共享内存屏障。
  2. 发起从全局内存到共享内存的批量异步复制。
  3. 在共享内存屏障上到达并等待。
  4. 对共享内存缓冲区中的值加一。
  5. 等待共享内存写入对后续批量异步复制可见，即在下一步前对异步代理中的共享内存写入建立顺序。
  6. 发起从共享内存到全局内存的批量异步复制。
  7. 在内核结束前等待 TMA 完成读取共享内存。

若设备代码针对低于 9.0 的架构编译，应使用编译期检查阻止不兼容的 TMA 代码：

#if defined(__CUDA_MINIMUM_ARCH__) && __CUDA_MINIMUM_ARCH__ < 900
static_assert(false,
    "Device code is being compiled with older architectures that are incompatible with TMA.");
#endif

以下为一维数组加一示例：

#include <cuda/barrier>
#include <cuda/ptx>
using barrier = cuda::barrier<cuda::thread_scope_block>;
namespace ptx = cuda::ptx;

static constexpr size_t buf_len = 1024;

__global__ void add_one_kernel(int* data, size_t offset) {
    // 批量操作的共享内存目标缓冲区应按 16 字节对齐。
    __shared__ alignas(16) int smem_data[buf_len];

    // 初始化共享内存屏障，并使其对异步代理可见。
    #pragma nv_diag_suppress static_var_with_dynamic_init
    __shared__ barrier bar;
    if (threadIdx.x == 0) {
        init(&bar, blockDim.x);
        ptx::fence_proxy_async(ptx::space_shared);
    }
    __syncthreads();

    // 从全局内存复制到共享内存。
    if (threadIdx.x == 0) {
        cuda::memcpy_async(
            smem_data,
            data + offset,
            cuda::aligned_size_t<16>(sizeof(smem_data)),
            bar);
    }

    // 所有线程到达屏障，并等待数据到达。
    barrier::arrival_token token = bar.arrive();
    bar.wait(std::move(token));

    // 对共享内存缓冲区中的每个元素加一。
    for (int i = threadIdx.x; i < buf_len; i += blockDim.x) {
        smem_data[i] += 1;
    }

    // 确保共享内存写入对 TMA 引擎可见。
    ptx::fence_proxy_async(ptx::space_shared);
    __syncthreads();

    // 从共享内存复制回全局内存。
    if (threadIdx.x == 0) {
        ptx::cp_async_bulk(
            ptx::space_global,
            ptx::space_shared,
            data + offset, smem_data, sizeof(smem_data));

        // 创建批量异步组，并等待该组完成对共享内存的读取。
        ptx::cp_async_bulk_commit_group();
        ptx::cp_async_bulk_wait_group_read(ptx::n32_t<0>());
    }
}

屏障初始化

屏障按参与线程块的线程数初始化，因此只有所有线程都到达屏障时，屏障阶段才会推进。为了让后续批量异步复制能够正确使用初始化后的屏障，需要执行 fence.proxy.async.shared::cta 指令。

TMA 读取

批量异步复制指令要求硬件将一大块数据复制到共享内存，并在读取完成后更新共享内存屏障的事务计数。通常，尽量少发起、每次复制尽可能大的数据块，性能会更好；由于复制由硬件异步执行，没有必要将其拆分成许多较小的块。

发起复制的线程会通过 mbarrier.expect_tx 到达屏障并指定预期到达的字节数（事务计数）；cuda::memcpy_async 会自动执行这一步。只需一个线程更新预期事务计数。如果多个线程更新，预期事务数将是各次更新之和。只有所有线程都到达且所有预期字节均已到达，屏障才会推进。屏障推进后，线程和后续批量异步复制都可以安全读取共享内存中的数据。

屏障等待

等待屏障推进可使用 mbarrier.try_wait。该函数返回 true 表示等待结束，返回 false 可能表示超时；调用方可以在循环中重试，直到完成。

共享内存写入与同步

为使对共享内存的写入对后续批量异步复制可见，需要使用 fence.proxy.async.shared::cta。它会将共享内存写入排在通过异步代理执行的后续读取之前。各线程先对自己的共享内存写入执行该栅栏，再通过 __syncthreads() 确保所有线程的操作都先于线程 0 发起的异步操作。

TMA 写入与同步

从共享内存写入全局内存的操作同样由单个线程发起，但其完成状态不由共享内存屏障跟踪，而是由线程本地机制跟踪。多个写入可以批量组成一个 bulk async-group；之后发起线程可以等待该组完成读取共享内存，或等待其完成写入全局内存，使写入对发起线程可见。

批量异步复制和普通异步复制使用不同的异步组机制：分别对应 cp.async.bulk.wait_group 和 cp.async.wait_group。

地址或大小 对齐要求
全局内存地址 必须按 16 字节对齐
共享内存地址 必须按 16 字节对齐
共享内存屏障地址 必须按 8 字节对齐（cuda::barrier 会保证）
传输大小 必须是 16 字节的倍数

10.29.2 使用 TMA 传输多维数组（Using TMA to transfer multi-dimensional arrays）

一维与多维 TMA 复制的主要区别是：多维场景必须在主机端创建 tensor map，并将其传给 CUDA 内核。本节介绍如何通过 CUDA Driver API 创建 tensor map、传输到设备，以及在设备端使用。

Driver API：获取 cuTensorMapEncodeTiled 函数指针

tensor map 使用 Driver API cuTensorMapEncodeTiled 创建。可以直接链接 CUDA Driver（-lcuda），也可以使用 cudaGetDriverEntryPoint 获取该函数的入口。

#include <cudaTypedefs.h> // PFN_cuTensorMapEncodeTiled, CUtensorMap

PFN_cuTensorMapEncodeTiled_v12000 get_cuTensorMapEncodeTiled() {
    cudaDriverEntryPointQueryResult driver_status;
    void* cuTensorMapEncodeTiled_ptr = nullptr;

    CUDA_CHECK(cudaGetDriverEntryPointByVersion(
        "cuTensorMapEncodeTiled",
        &cuTensorMapEncodeTiled_ptr,
        12000, cudaEnableDefault, &driver_status));

    assert(driver_status == cudaDriverEntryPointSuccess);
    return reinterpret_cast<PFN_cuTensorMapEncodeTiled_v12000>(
        cuTensorMapEncodeTiled_ptr);
}

创建 tensor map

创建 tensor map 需要多个参数，包括全局内存数组的基地址、数组尺寸（元素数量）、相邻行之间的字节跨度，以及共享内存缓冲区尺寸（元素数量）。

以下代码为一个大小为 GMEM_HEIGHT × GMEM_WIDTH 的二维行主序数组创建 tensor map。注意参数顺序：变化最快的维度放在最前面。

CUtensorMap tensor_map{};

// 数组维数。
constexpr uint32_t rank = 2;
uint64_t size[rank] = {GMEM_WIDTH, GMEM_HEIGHT};

// 相邻两行起始元素之间的字节跨度，必须是 16 的倍数。
uint64_t stride[rank - 1] = {GMEM_WIDTH * sizeof(int)};

// 作为 TMA 目标的共享内存缓冲区尺寸。
uint32_t box_size[rank] = {SMEM_WIDTH, SMEM_HEIGHT};

// 元素步长，以 sizeof(element) 为单位。
// 例如，对复数张量可以用步长 2 只加载实部。
uint32_t elem_stride[rank] = {1, 1};

auto cuTensorMapEncodeTiled = get_cuTensorMapEncodeTiled();

CUresult res = cuTensorMapEncodeTiled(
    &tensor_map, // CUtensorMap *tensorMap
    CUtensorMapDataType::CU_TENSOR_MAP_DATA_TYPE_INT32,
    rank,        // tensorRank
    tensor_ptr,  // 全局内存基地址
    size,        // 全局维度
    stride,      // 全局内存字节跨度
    box_size,    // 传输块尺寸
    elem_stride, // 元素步长

    // 交错模式可加速加载小于 4 字节的值。
    CUtensorMapInterleave::CU_TENSOR_MAP_INTERLEAVE_NONE,

    // Swizzling 可用于避免共享内存存储体冲突。
    CUtensorMapSwizzle::CU_TENSOR_MAP_SWIZZLE_NONE,

    // L2 promotion 可将缓存策略扩展到更多 L2 缓存行。
    CUtensorMapL2promotion::CU_TENSOR_MAP_L2_PROMOTION_NONE,

    // 越界元素不填零。
    CUtensorMapFloatOOBfill::CU_TENSOR_MAP_FLOAT_OOB_FILL_NONE
);

从主机传输到设备（Host-to-device transfer）

可以通过三种方式让设备代码访问 tensor map。推荐方式是将它作为带 __grid_constant__ 注解的 const 内核参数传入。其他方式包括使用 cudaMemcpyToSymbol 将其复制到设备常量内存，或通过全局内存访问。

将 tensor map 作为参数传递时，某些版本的 GCC C++ 编译器可能发出警告：“the ABI for passing parameters with 64-byte alignment has changed in GCC 4.6”。该警告可以忽略。

#include <cuda.h>

__global__ void kernel(const __grid_constant__ CUtensorMap tensor_map) {
    // 在此使用 tensor_map。
}

int main() {
    CUtensorMap map;
    // 初始化 map
    kernel<<<1, 1>>>(map);
}

也可以使用全局常量变量代替 __grid_constant__ 内核参数：

#include <cuda.h>

__constant__ CUtensorMap global_tensor_map;

__global__ void kernel() {
    // 在此使用 global_tensor_map。
}

int main() {
    CUtensorMap local_tensor_map;
    // 初始化 local_tensor_map
    cudaMemcpyToSymbol(global_tensor_map, &local_tensor_map,
                       sizeof(CUtensorMap));
    kernel<<<1, 1>>>();
}

最后，也可以将 tensor map 复制到全局内存。若使用设备全局内存中的 tensor map 指针，则每个线程块在使用更新后的 tensor map 之前都需要执行 fence。除非 tensor map 再次被修改，否则该线程块后续使用时不需要重复执行 fence。与前两种方式相比，这种机制可能更慢。

#include <cuda.h>
#include <cuda/ptx>
namespace ptx = cuda::ptx;

__device__ CUtensorMap global_tensor_map;

__global__ void kernel(CUtensorMap *tensor_map) {
    // 获取 tensor map 的可见性。
    ptx::n32_t<128> size_bytes;
    // 主机通过 cudaMemcpy 修改 tensor map，因此作用域应为 .sys。
    ptx::fence_proxy_tensormap_generic(
        ptx::sem_acquire, ptx::scope_sys, tensor_map, size_bytes);

    // 在此线程中，fence 之后即可安全使用 tensor_map。
}

int main() {
    CUtensorMap local_tensor_map;
    // 初始化 local_tensor_map
    cudaMemcpy(&global_tensor_map, &local_tensor_map,
               sizeof(CUtensorMap), cudaMemcpyHostToDevice);
    kernel<<<1, 1>>>(global_tensor_map);
}

使用 tensor map

以下内核从较大的二维数组中加载一个大小为 SMEM_HEIGHT × SMEM_WIDTH 的二维块。x 和 y 指定该块左上角的坐标。数据块被加载到共享内存，修改后再写回全局内存。

#include <cuda.h>       // CUtensorMap
#include <cuda/barrier>
using barrier = cuda::barrier<cuda::thread_scope_block>;
namespace cde = cuda::device::experimental;

__global__ void kernel(
    const __grid_constant__ CUtensorMap tensor_map, int x, int y) {
    // 批量张量操作的共享内存目标缓冲区必须按 128 字节对齐。
    __shared__ alignas(128) int smem_buffer[SMEM_HEIGHT][SMEM_WIDTH];

    #pragma nv_diag_suppress static_var_with_dynamic_init
    __shared__ barrier bar;

    if (threadIdx.x == 0) {
        init(&bar, blockDim.x);
        cde::fence_proxy_async_shared_cta();
    }
    __syncthreads();

    barrier::arrival_token token;
    if (threadIdx.x == 0) {
        // 发起批量张量复制。
        cde::cp_async_bulk_tensor_2d_global_to_shared(
            &smem_buffer, &tensor_map, x, y, bar);
        // 到达屏障并指定预期传输字节数。
        token = cuda::device::barrier_arrive_tx(
            bar, 1, sizeof(smem_buffer));
    } else {
        token = bar.arrive();
    }

    bar.wait(std::move(token)); // 等待数据到达

    // 修改共享内存中的一行数据。
    smem_buffer[0][threadIdx.x] += threadIdx.x;

    // 等待共享内存写入对 TMA 引擎可见。
    cde::fence_proxy_async_shared_cta();
    __syncthreads();

    if (threadIdx.x == 0) {
        // 从共享内存写回全局内存。
        cde::cp_async_bulk_tensor_2d_shared_to_global(
            &tensor_map, x, y, &smem_buffer);

        cde::cp_async_bulk_commit_group();
        cde::cp_async_bulk_wait_group_read<0>();
    }

    // 使屏障失效，以便后续计算可重用其共享内存区域。
    if (threadIdx.x == 0)
        (&bar)->~barrier();
}

负索引与越界： 从全局内存复制到共享内存时，若数据块的一部分越界，对应共享内存区域会填零；数据块左上角坐标也可以为负数。将数据从共享内存写回全局内存时，数据块可以部分越界，但左上角坐标不能为负数。

尺寸与跨度（Size and stride）

张量某一维的 size 表示该维的元素数量；所有尺寸必须大于 1。stride 表示该维相邻元素之间的字节距离。例如，4×4 的整数矩阵尺寸为 4 和 4，元素大小为 4 字节，因此 stride 为 4 和 16 字节。

受对齐要求限制，一个 4×3 的行主序整数矩阵也必须使用 4 和 16 字节的 stride；每行需要填充额外的 4 字节，以保证下一行起始地址按 16 字节对齐。

10.29.3 TMA Swizzle（TMA 数据重排）

默认情况下，TMA 引擎按照数据在全局内存中的排列顺序，将数据加载到共享内存。但对于某些共享内存访问模式，这种布局可能并非最优，因为它可能造成共享内存存储体冲突。

共享内存有 32 个存储体，连续的 32 位字会映射到连续的存储体。每个存储体每个时钟周期的带宽为 32 位。如果一次事务多次访问同一个存储体，就会发生存储体冲突，导致带宽下降。为了让共享内存布局更适合用户代码、减少冲突，可以使用 swizzle 模式重新排列数据：TMA 在写入共享内存前对数据进行重排，在从共享内存复制回全局内存时再恢复对应布局。tensor map 中的 swizzle mode 字段指定所使用的重排模式。

10.29.3.1 示例：矩阵转置（Example “Matrix Transpose”）

矩阵转置是一个典型示例：数据在全局内存中按行主序存储，但在共享内存中希望按列访问，这可能导致存储体冲突。

本例将全局内存中的 8×8 int4 矩阵加载到共享内存，然后每组八个线程从共享内存读取一行，并将其写入另一个共享内存缓冲区中的一列。普通布局下，转置写入会发生八路存储体冲突。最后再将转置缓冲区写回全局内存。

通过 CU_TENSOR_MAP_SWIZZLE_128B 布局，可以避免这些冲突。该模式与 128 字节的行跨度相匹配，并改变共享内存布局，使按行和按列访问都不再让同一事务中的元素集中到相同存储体。

图 26：未使用 swizzle 时的共享内存布局。索引与全局内存索引相同，转置时同一列的元素落入同一个存储体，写入被串行化，形成八路冲突。

图 27：使用 CU_TENSOR_MAP_SWIZZLE_128B 后的共享内存布局。行与列访问中的矩阵元素映射到不同存储体，因此可避免存储体冲突。

下面代码展示矩阵转置的关键内核部分。目标共享内存缓冲区使用 128 字节 swizzle 时，必须满足对应的对齐要求。

__global__ void kernel_tma(
    const __grid_constant__ CUtensorMap tensor_map) {
    __shared__ alignas(1024) int4 smem_buffer[8][8];
    __shared__ alignas(1024) int4 smem_buffer_tr[8][8];

    #pragma nv_diag_suppress static_var_with_dynamic_init
    __shared__ barrier bar;
    if (threadIdx.x == 0) {
        init(&bar, blockDim.x);
        cde::fence_proxy_async_shared_cta();
    }
    __syncthreads();

    barrier::arrival_token token;
    if (threadIdx.x == 0) {
        cde::cp_async_bulk_tensor_2d_global_to_shared(
            &smem_buffer, &tensor_map, 0, 0, bar);
        token = cuda::device::barrier_arrive_tx(
            bar, 1, sizeof(smem_buffer));
    } else {
        token = bar.arrive();
    }
    bar.wait(std::move(token));

    // 对矩阵转置：按 swizzle 对应的共享内存索引访问。
    for (int sidx_j = threadIdx.x; sidx_j < 8; sidx_j += blockDim.x) {
        for (int sidx_i = 0; sidx_i < 8; ++sidx_i) {
            const int swiz_j_idx = (sidx_i % 8) ^ sidx_j;
            const int swiz_i_idx_tr = (sidx_j % 8) ^ sidx_i;
            smem_buffer_tr[sidx_j][swiz_i_idx_tr] =
                smem_buffer[sidx_i][swiz_j_idx];
        }
    }

    cde::fence_proxy_async_shared_cta();
    __syncthreads();

    if (threadIdx.x == 0) {
        cde::cp_async_bulk_tensor_2d_shared_to_global(
            &tensor_map, 0, 0, &smem_buffer_tr);
        cde::cp_async_bulk_commit_group();
        cde::cp_async_bulk_wait_group_read<0>();
    }

    if (threadIdx.x == 0)
        (&bar)->~barrier();
}

创建 tensor map 时，swizzle 模式设为 CU_TENSOR_MAP_SWIZZLE_128B，共享内存块的内层维度应与 swizzle 跨度匹配。原书示例明确指出，此代码用于说明 swizzle 原理；“按原样”实现并非高性能实现，也无法扩展到示例之外的尺寸。

10.29.3.2 Swizzle 模式（The Swizzle Modes）

共有四种模式：无 swizzle、32 字节、64 字节和 128 字节。swizzle 模式定义沿指定宽度排列的 16 字节数据块如何映射到存储体子组。

图 28：TMA Swizzle 模式概览。

应用 swizzle 时需要遵循以下内存要求：

  • 全局内存对齐： 全局内存必须按 128 字节对齐。
  • 共享内存对齐： 为简化处理，建议共享内存按 swizzle 模式的重复跨度对齐。如果缓冲区没有按该跨度对齐，swizzle 模式与共享内存起始位置之间会产生偏移。
  • 内层维度： 共享内存块的内层维度必须满足表 10 中的要求，否则指令无效。如果 swizzle 宽度大于内层维度，则必须分配足够的共享内存来容纳完整的 swizzle 宽度。
  • 粒度： swizzle 映射的粒度固定为 16 字节，设计内存布局和访问模式时必须考虑这一点。

10.30 在设备端编码 Tensor Map（Encoding a Tensor Map on Device）

前面章节介绍了如何通过 CUDA Driver API 在主机端创建 tensor map。本节介绍如何在设备端编码 tiled 类型的 tensor map。当一次内核启动需要处理尺寸不同的一批张量，而常规的 const __grid_constant__ 内核参数传递方式不合适时，这种方式会很有用。

推荐流程如下：

  1. 在主机端使用 Driver API 创建 tensor map 模板 template_tensor_map。
  2. 在设备内核中复制该模板、修改副本、将其存储到全局内存，并执行适当的内存栅栏。
  3. 在后续内核中通过适当的栅栏使用更新后的 tensor map。

整体结构如下：

// 初始化设备上下文
CUDA_CHECK(cudaDeviceSynchronize());

// 使用 Driver API 创建 tensor map 模板
CUtensorMap template_tensor_map = make_tensormap_template();

// 在全局内存中分配 tensor map 和张量
CUtensorMap* global_tensor_map;
CUDA_CHECK(cudaMalloc(&global_tensor_map, sizeof(CUtensorMap)));
char* global_buf;
CUDA_CHECK(cudaMalloc(&global_buf, 8 * 256));

// 填充全局缓冲区
fill_global_buf<<<1, 1>>>(global_buf);

// 指定将在设备端创建的 tensor map 参数
tensormap_params p{};
p.global_address = global_buf;
p.rank = 2;
p.box_dim[0] = 128; // 共享内存块宽度是完整缓冲区的一半
p.box_dim[1] = 4;   // 共享内存块高度是完整缓冲区的一半
p.global_dim[0] = 256;
p.global_dim[1] = 8;
p.global_stride[0] = 256;
p.element_stride[0] = 1;
p.element_stride[1] = 1;

// 在设备端编码 tensor map
encode_tensor_map<<<1, 32>>>(template_tensor_map, p, global_tensor_map);

// 在另一个内核中使用它
consume_tensor_map<<<1, 1>>>(global_tensor_map);

// 检查错误
CUDA_CHECK(cudaDeviceSynchronize());

10.30.1 在设备端编码和修改 Tensor Map（Device-side Encoding and Modification）

推荐在全局内存中编码 tensor map 的步骤如下：

  1. 将已有 tensor map 模板传给内核。与直接在 cp.async.bulk.tensor 指令中使用 tensor map 的内核不同，模板可以通过多种方式传入，例如全局内存指针、内核参数或常量变量。
  2. 将模板值复制初始化到共享内存中的 tensor map。
  3. 使用 cuda::ptx::tensormap_replace 系列函数修改共享内存中的 tensor map。这些函数封装了 PTX tensormap.replace 指令，可以修改 tiled 类型 tensor map 的任意字段，包括基地址、尺寸和跨度。
  4. 使用 cuda::ptx::tensormap_copy_fenceproxy 将修改后的 tensor map 从共享内存复制到全局内存，并执行必要的内存栅栏。

下面的内核为了完整展示流程，修改了 tensor map 的所有字段；实际内核通常只需要修改少数几个字段。

#include <cuda/ptx>
namespace ptx = cuda::ptx;

// 使用一个 warp 启动。
__launch_bounds__(32)
__global__ void encode_tensor_map(
    const __grid_constant__ CUtensorMap template_tensor_map,
    tensormap_params p, CUtensorMap* out) {
    __shared__ alignas(128) CUtensorMap smem_tmap;

    if (threadIdx.x == 0) {
        // 将模板复制到共享内存。
        smem_tmap = template_tensor_map;
        const auto space_shared = ptx::space_shared;

        ptx::tensormap_replace_global_address(
            space_shared, &smem_tmap, p.global_address);

        // rank 字段使用从零开始的编号，因此新值应为目标 rank 减一。
        ptx::tensormap_replace_rank(space_shared, &smem_tmap, p.rank - 1);

        // 设置共享内存块尺寸。
        if (0 < p.rank) ptx::tensormap_replace_box_dim(
            space_shared, &smem_tmap, ptx::n32_t<0>{}, p.box_dim[0]);
        if (1 < p.rank) ptx::tensormap_replace_box_dim(
            space_shared, &smem_tmap, ptx::n32_t<1>{}, p.box_dim[1]);
        if (2 < p.rank) ptx::tensormap_replace_box_dim(
            space_shared, &smem_tmap, ptx::n32_t<2>{}, p.box_dim[2]);
        if (3 < p.rank) ptx::tensormap_replace_box_dim(
            space_shared, &smem_tmap, ptx::n32_t<3>{}, p.box_dim[3]);
        if (4 < p.rank) ptx::tensormap_replace_box_dim(
            space_shared, &smem_tmap, ptx::n32_t<4>{}, p.box_dim[4]);

        // 设置全局维度。
        if (0 < p.rank) ptx::tensormap_replace_global_dim(
            space_shared, &smem_tmap, ptx::n32_t<0>{},
            (uint32_t)p.global_dim[0]);
        if (1 < p.rank) ptx::tensormap_replace_global_dim(
            space_shared, &smem_tmap, ptx::n32_t<1>{},
            (uint32_t)p.global_dim[1]);
        if (2 < p.rank) ptx::tensormap_replace_global_dim(
            space_shared, &smem_tmap, ptx::n32_t<2>{},
            (uint32_t)p.global_dim[2]);
        if (3 < p.rank) ptx::tensormap_replace_global_dim(
            space_shared, &smem_tmap, ptx::n32_t<3>{},
            (uint32_t)p.global_dim[3]);
        if (4 < p.rank) ptx::tensormap_replace_global_dim(
            space_shared, &smem_tmap, ptx::n32_t<4>{},
            (uint32_t)p.global_dim[4]);

        // 设置全局跨度。
        if (1 < p.rank) ptx::tensormap_replace_global_stride(
            space_shared, &smem_tmap, ptx::n32_t<0>{}, p.global_stride[0]);
        if (2 < p.rank) ptx::tensormap_replace_global_stride(
            space_shared, &smem_tmap, ptx::n32_t<1>{}, p.global_stride[1]);
        if (3 < p.rank) ptx::tensormap_replace_global_stride(
            space_shared, &smem_tmap, ptx::n32_t<2>{}, p.global_stride[2]);
        if (4 < p.rank) ptx::tensormap_replace_global_stride(
            space_shared, &smem_tmap, ptx::n32_t<3>{}, p.global_stride[3]);

        // 设置元素跨度。
        if (0 < p.rank) ptx::tensormap_replace_element_size(
            space_shared, &smem_tmap, ptx::n32_t<0>{}, p.element_stride[0]);
        if (1 < p.rank) ptx::tensormap_replace_element_size(
            space_shared, &smem_tmap, ptx::n32_t<1>{}, p.element_stride[1]);
        if (2 < p.rank) ptx::tensormap_replace_element_size(
            space_shared, &smem_tmap, ptx::n32_t<2>{}, p.element_stride[2]);
        if (3 < p.rank) ptx::tensormap_replace_element_size(
            space_shared, &smem_tmap, ptx::n32_t<3>{}, p.element_stride[3]);
        if (4 < p.rank) ptx::tensormap_replace_element_size(
            space_shared, &smem_tmap, ptx::n32_t<4>{}, p.element_stride[4]);

        // 下列常量的合法值见 PTX ISA 的 tensor map 文档。
        ptx::tensormap_replace_elemtype(
            space_shared, &smem_tmap, ptx::n32_t<0>{});
        ptx::tensormap_replace_interleave_layout(
            space_shared, &smem_tmap, ptx::n32_t<0>{});
        ptx::tensormap_replace_swizzle_mode(
            space_shared, &smem_tmap, ptx::n32_t<0>{});
        ptx::tensormap_replace_fill_mode(
            space_shared, &smem_tmap, ptx::n32_t<0>{});
    }

    // 同步 warp 中的修改。
    __syncwarp();

    // 集体复制到全局内存，并使更新对其他设备线程可见。
    ptx::n32_t<128> bytes_128;
    ptx::tensormap_cp_fenceproxy(
        ptx::sem_release, ptx::scope_gpu, out, &smem_tmap, bytes_128);
}

tensor map 的格式可能随时间变化。因此，cuda::ptx::tensormap_replace 函数及对应的 tensormap.replace.tile PTX 指令被标记为仅适用于 sm_90a。使用时应通过 nvcc -arch sm_90a ... 编译。

提示：在 sm_90a 上，也可以将零初始化的共享内存缓冲区作为初始 tensor map 值，从而完全在设备端编码 tensor map，而无需先通过 Driver API 编码模板。

设备端修改仅支持 tiled 类型 tensor map；其他类型不能在设备端修改。更多信息请参阅 Driver API 参考文档。

10.30.2 使用修改后的 Tensor Map（Usage of a Modified Tensor Map）

与将 tensor map 作为 const __grid_constant__ 内核参数传递不同，在全局内存中使用 tensor map 时，必须在修改它的线程与使用它的线程之间，显式建立 tensor map 代理的 release-acquire 模式。

release 部分通过前一节的 cuda::ptx::tensormap_cp_fenceproxy 完成。acquire 部分使用 cuda::ptx::fence_proxy_tensormap_generic，它封装 PTX fence.proxy.tensormap::generic.acquire 指令。

如果两个参与线程位于同一设备，.gpu 作用域就足够；如果线程位于不同设备，则必须使用 .sys 作用域。某个线程获取 tensor map 后，同一线程块中的其他线程可以在适当同步后使用它，例如通过 __syncthreads()。执行 fence 的线程与使用 tensor map 的线程必须位于同一线程块。

如果线程位于同一 cluster 的不同线程块、同一 grid 的不同线程块或不同内核中，仅调用 Cooperative Groups 的 cluster/grid 同步或使用流顺序同步，并不足以建立 tensor map 更新的顺序关系。其他线程块仍需在正确作用域获取 tensor map 代理后才能使用更新后的映射。如果中间没有再次修改 tensor map，就不必在每条 cp.async.bulk.tensor 指令之前重复执行 fence。

以下代码展示如何获取全局内存中的 tensor map，并使用它发起 TMA 传输：

// 全局内存 tensor map 的消费者
__global__ void consume_tensor_map(CUtensorMap* tensor_map) {
    ptx::n32_t<128> size_bytes;
    ptx::fence_proxy_tensormap_generic(
        ptx::sem_acquire, ptx::scope_sys, tensor_map, size_bytes);

    __shared__ uint64_t bar;
    __shared__ alignas(128) char smem_buf[4][128];

    if (threadIdx.x == 0) {
        ptx::mbarrier_init(&bar, 1);
        ptx::fence_proxy_async(ptx::space_shared);

        ptx::cp_async_bulk_tensor(
            ptx::space_cluster, ptx::space_global,
            smem_buf, tensor_map, {0, 0}, &bar);

        ptx::mbarrier_arrive_expect_tx(
            ptx::sem_release, ptx::scope_cta, ptx::space_shared,
            &bar, sizeof(smem_buf));
    }

    const int parity = 0;
    while (!ptx::mbarrier_try_wait_parity(&bar, parity)) {}

    printf("Got:\\n\\n");
    for (int j = 0; j < 4; ++j) {
        for (int i = 0; i < 128; ++i) {
            printf("%3d ", smem_buf[j][i]);
            if (i % 32 == 31) printf("\\n");
        }
        printf("\\n");
    }
}

10.31 性能分析器计数器函数（Profiler Counter Function）

每个多处理器都具有 16 个硬件计数器，应用程序可以调用 __prof_trigger()，通过一条指令递增其中一个计数器。

void __prof_trigger(int counter);

该函数会使指定索引 counter 对应的每多处理器硬件计数器按每个 warp 加 1。计数器 8–15 为保留项，应用程序不应使用。

计数器 0–7 的值可通过 nvprof 查询，例如：

nvprof --events prof_trigger_0x

其中 x 为 0–7。每次内核启动前，所有计数器都会重置。注意，收集计数器时，内核启动是同步的，详见“主机与设备之间的并发执行”。

10.32 断言（Assertion）

断言仅支持计算能力为 2.x 及以上的设备。

void assert(int expression);

如果 expression 等于零，assert() 会停止内核执行。如果程序在调试器中运行，则会触发断点，方便检查设备当前状态。否则，在通过 cudaDeviceSynchronize()、cudaStreamSynchronize() 或 cudaEventSynchronize() 与主机同步后，每个表达式为零的线程都会向 stderr 输出消息。消息格式如下：

<filename>:<line number>:<function>:
block: [blockId.x,blockId.y,blockIdx.z],
thread: [threadIdx.x,threadIdx.y,threadIdx.z]
Assertion `<expression>` failed.

同一设备后续的主机同步调用都会返回 cudaErrorAssert。在调用 cudaDeviceReset() 重新初始化设备之前，不能再向该设备提交命令。如果表达式非零，内核执行不受影响。

示例：

#include <assert.h>
__global__ void testAssert(void) {
    int is_one = 1;
    int should_be_one = 0;

    assert(is_one);       // 不产生影响
    assert(should_be_one); // 停止内核执行
}

int main(int argc, char* argv[]) {
    testAssert<<<1, 1>>>();
    cudaDeviceSynchronize();
    return 0;
}

示例会输出类似如下的消息：

test.cu:19: void testAssert(): block: [0,0,0], thread: [0,0,0]
Assertion `should_be_one` failed.

断言用于调试，可能影响性能，因此建议在生产代码中禁用。可以在包含 assert.h 之前定义预处理宏 NDEBUG 来关闭断言。断言表达式不应包含副作用（例如 (++i > 0)），否则关闭断言后会改变程序功能。

10.35 格式化输出（Formatted Output）

格式化输出仅支持计算能力为 2.x 及以上的设备。

int printf(const char *format[, arg, ...]);

该函数允许内核将格式化输出写入主机端输出流。

设备端 printf() 的行为与标准 C 库 printf() 类似。格式字符串会输出到主机端流中，并在遇到格式说明符时使用参数列表中的值进行替换。完整行为可参阅主机系统的手册页。

设备端 printf() 像其他设备函数一样，按线程执行并处于调用线程的上下文中。因此，在多线程内核中，普通的 printf() 调用会由每个遇到该语句的线程执行，并使用该线程自己的数据。主机输出流中会出现多份输出，每个执行到该语句的线程输出一份。如果只希望输出一行，应由程序员限制仅一个线程调用 printf()。

与标准 C 的 printf() 返回打印的字符数量不同，CUDA 的 printf() 返回解析的参数数量。如果格式字符串后没有参数，则返回 0；如果格式字符串为 NULL，则返回 -1；如果发生内部错误，则返回 -2。

10.35.1 格式说明符（Format Specifiers）

与标准 printf() 一样，格式说明符形式为：

%[flags][width][.precision][size]type

支持的字段如下：

  • Flags： #、空格、0、+、-
  • Width： *、0–9
  • Precision： 0–9
  • Size： h、l、ll
  • Type： %cdiouxXpeEfgGaAs

CUDA 的 printf() 会接受任意组合的标志、宽度、精度、大小和类型，即使组合整体上并不是有效的格式说明符。例如，%hd 也会被接受，而 printf() 会期望相应参数位置上是一个双精度变量。因此，若格式字符串含有无效组合，输出可能未定义。

10.35.2 限制（Limitations）

printf() 的最终格式化发生在主机系统上，因此格式字符串必须能被主机系统的编译器和 C 库理解。CUDA 尽量支持最常见主机编译器都具备的格式说明符子集，但实际行为仍取决于主机操作系统。

除格式说明符问题外，还有以下限制：

  • 除格式字符串外，printf() 最多接受 32 个参数。超出部分会被忽略，相关格式说明符会按原样输出。
  • 64 位 Windows 上 long 为 4 字节，而其他 64 位平台通常为 8 字节。如果在非 Windows 的 64 位系统上编译内核，却在 Win64 上运行，包含 %ld 的格式字符串可能导致输出损坏。建议编译平台与执行平台一致。
  • printf() 输出缓冲区在内核启动前设置固定大小，并采用循环缓冲方式。若输出超过容量，较早的输出会被覆盖。

缓冲区会在以下事件发生时刷新：

  • 通过 <<<>>> 或 cuLaunchKernel() 启动内核（启动开始时刷新；若设置 CUDA_LAUNCH_BLOCKING=1，启动结束时也刷新）；
  • 调用 cudaDeviceSynchronize()、cuCtxSynchronize()、cudaStreamSynchronize()、cuStreamSynchronize()、cudaEventSynchronize() 或 cuEventSynchronize() 同步；
  • 执行任意阻塞版本的 cudaMemcpy*() 或 cuMemcpy*()；
  • 调用 cuModuleLoad() 或 cuModuleUnload() 加载/卸载模块；
  • 调用 cudaDeviceReset() 或 cuCtxDestroy() 销毁上下文；
  • 执行通过 cudaStreamAddCallback 添加的流回调之前。

程序退出时不会自动刷新缓冲区，因此应像示例中那样显式调用 cudaDeviceReset() 或 cuCtxDestroy()。

printf() 内部使用共享数据结构，因此调用它可能改变线程的执行顺序。调用 printf() 的线程可能比未调用它的线程执行路径更长，而且开销取决于参数。不过，除显式的 __syncthreads() 屏障外，CUDA 不保证线程执行顺序，因此无法判断顺序变化究竟由 printf() 还是硬件调度造成。

10.35.3 相关主机端 API（Associated Host-Side API）

以下 API 用于获取和设置向主机传输 printf() 参数及内部元数据的缓冲区大小。默认大小为 1 MB。

  • cudaDeviceGetLimit(size_t* size, cudaLimitPrintfFifoSize)
  • cudaDeviceSetLimit(cudaLimitPrintfFifoSize, size_t size)

10.35.4 示例（Examples）

第一个示例让每个线程都输出一行：

#include <stdio.h>
__global__ void helloCUDA(float f) {
    printf("Hello thread %d, f=%f\\n", threadIdx.x, f);
}
int main() {
    helloCUDA<<<1, 5>>>(1.2345f);
    cudaDeviceSynchronize();
    return 0;
}

输出包含 5 行，每个线程输出一次。全局参数 f 对所有线程相同，而局部值 threadIdx.x 对每个线程不同。输出行的顺序不保证固定。

若只希望输出一行，可以将调用限制到线程 0：

#include <stdio.h>
__global__ void helloCUDA(float f) {
    if (threadIdx.x == 0)
        printf("Hello thread %d, f=%f\\n", threadIdx.x, f);
}
int main() {
    helloCUDA<<<1, 5>>>(1.2345f);
    cudaDeviceSynchronize();
    return 0;
}

此时只会输出线程 0 的一行。

10.36 动态全局内存分配与操作（Dynamic Global Memory Allocation and Operations）

动态全局内存分配与相关操作仅支持计算能力为 2.x 及以上的设备。

__host__ __device__ void* malloc(size_t size);
__device__ void* __nv_aligned_device_malloc(size_t size, size_t align);
__host__ __device__ void free(void* ptr);

__host__ __device__ void* memcpy(
    void* dest, const void* src, size_t size);
__host__ __device__ void* memset(
    void* ptr, int value, size_t size);

这些函数允许从全局内存中的固定大小堆动态分配和释放内存。memcpy() 将 src 指向的 size 字节复制到 dest；memset() 将 ptr 指向的内存块中的 size 字节设置为 value（按无符号字符解释）。

设备端 malloc() 至少分配 size 字节，并返回分配内存的指针。如果内存不足，则返回 NULL。返回的指针保证按 16 字节对齐。

设备端 __nv_aligned_device_malloc() 至少分配 size 字节，并返回满足指定对齐要求的指针。如果无法满足大小或对齐要求，则返回 NULL。返回地址必须是 align 的倍数；align 必须是非零的 2 的幂。

设备端 free() 释放由先前的 malloc() 或 __nv_aligned_device_malloc() 返回的内存。如果 ptr 为 NULL，则忽略调用。对同一个指针重复调用 free() 会导致未定义行为。

某个 CUDA 线程通过 malloc() 或 __nv_aligned_device_malloc() 分配的内存，会一直保留到 CUDA 上下文生命周期结束，或直到显式调用 free() 释放。该内存可以被其他 CUDA 线程使用，也可以在后续内核启动中继续使用。任意 CUDA 线程都可以释放另一个线程分配的内存，但必须确保同一个指针不会被释放多次。

10.36.1 堆内存分配（Heap Memory Allocation）

设备内存堆大小固定，必须在任何使用 malloc()、__nv_aligned_device_malloc() 或 free() 的程序加载到上下文之前指定。如果程序使用了 malloc() 或 __nv_aligned_device_malloc()，但没有显式设置堆大小，则默认分配 8 MB。

以下 API 可获取和设置堆大小：

  • cudaDeviceGetLimit(size_t* size, cudaLimitMallocHeapSize)
  • cudaDeviceSetLimit(cudaLimitMallocHeapSize, size_t size)

实际授予的堆大小至少为 size 字节。cuCtxGetLimit() 和 cudaDeviceGetLimit() 返回当前请求的堆大小。

堆的实际内存分配发生在模块加载到上下文时：可以通过 CUDA Driver API 显式加载，也可以由 CUDA Runtime API 隐式加载。如果分配失败，模块加载会产生 CUDA_ERROR_SHARED_OBJECT_INIT_FAILED 错误。

模块加载后，堆大小不能再更改，也不会根据需求动态扩容。设备堆预留的内存与通过主机端 CUDA API（例如 cudaMalloc()）分配的内存相互独立。

10.36.2 与主机内存 API 的互操作性（Interoperability with Host Memory API）

通过设备端 malloc() 或 __nv_aligned_device_malloc() 分配的内存，不能通过 Runtime API 的内存释放函数释放。反过来，通过 Runtime API 分配的内存也不能使用设备端 free() 释放。

此外，设备代码中通过 malloc() 或 __nv_aligned_device_malloc() 分配的内存，不能用于 Runtime 或 Driver API 调用，例如 cudaMemcpy()、cudaMemset() 等。

10.36.3 示例（Examples）

10.36.3.1 每线程分配（Per Thread Allocation）

#include <stdlib.h>
#include <stdio.h>

__global__ void mallocTest() {
    size_t size = 123;
    char* ptr = (char*)malloc(size);
    memset(ptr, 0, size);
    printf("Thread %d got pointer: %p\\n", threadIdx.x, ptr);
    free(ptr);
}

int main() {
    // 必须在启动任何内核前设置堆大小。
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128 * 1024 * 1024);
    mallocTest<<<1, 5>>>();
    cudaDeviceSynchronize();
    return 0;
}

每个线程都会执行 malloc() 和 memset()，因此每个线程都会获得并初始化自己的内存分配。指针的具体值会因运行而异。

10.36.3.2 每线程块分配（Per Thread Block Allocation）

#include <stdlib.h>

__global__ void mallocTest() {
    __shared__ int* data;

    // 只由线程块中的第一个线程执行分配，
    // 再通过共享内存把指针传给其他线程。
    if (threadIdx.x == 0) {
        size_t size = blockDim.x * 64;
        data = (int*)malloc(size);
    }
    __syncthreads();

    if (data == NULL)
        return;

    int* ptr = data;
    for (int i = 0; i < 64; ++i)
        ptr[i * blockDim.x + threadIdx.x] = threadIdx.x;

    // 确保所有线程都完成后再释放内存。
    __syncthreads();

    // 只能由一个线程释放内存。
    if (threadIdx.x == 0)
        free(data);
}

int main() {
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128 * 1024 * 1024);
    mallocTest<<<10, 128>>>();
    cudaDeviceSynchronize();
    return 0;
}

10.36.3.3 跨内核启动保留分配（Allocation Persisting Between Kernel Launches）

#include <stdlib.h>
#include <stdio.h>
#define NUM_BLOCKS 20

__device__ int* dataptr[NUM_BLOCKS]; // 每个线程块的指针

__global__ void allocmem() {
    // 每个线程块只分配一次。
    if (threadIdx.x == 0)
        dataptr[blockIdx.x] = (int*)malloc(blockDim.x * 4);

    __syncthreads();

    if (dataptr[blockIdx.x] == NULL)
        return;

    // 所有线程并行清零数据。
    dataptr[blockIdx.x][threadIdx.x] = 0;
}

__global__ void usemem() {
    int* ptr = dataptr[blockIdx.x];
    if (ptr != NULL)
        ptr[threadIdx.x] += threadIdx.x;
}

__global__ void freemem() {
    int* ptr = dataptr[blockIdx.x];
    if (ptr != NULL)
        printf("Block %d, Thread %d: final value = %d\\n",
               blockIdx.x, threadIdx.x, ptr[threadIdx.x]);

    // 只由一个线程释放。
    if (threadIdx.x == 0)
        free(ptr);
}

int main() {
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128 * 1024 * 1024);

    allocmem<<<NUM_BLOCKS, 10>>>();
    usemem<<<NUM_BLOCKS, 10>>>();
    usemem<<<NUM_BLOCKS, 10>>>();
    usemem<<<NUM_BLOCKS, 10>>>();
    freemem<<<NUM_BLOCKS, 10>>>();

    cudaDeviceSynchronize();
    return 0;
}

10.37 执行配置（Execution Configuration）

每次调用 __global__ 函数时，都必须指定执行配置。执行配置定义函数在设备上执行时使用的网格和线程块维度，以及关联的执行流。

执行配置通过在函数名与括号参数列表之间插入 <<<Dg, Db, Ns, S>>> 指定：

  • Dg：类型为 dim3，指定网格维度和大小，Dg.x * Dg.y * Dg.z 等于启动的线程块数。
  • Db：类型为 dim3，指定每个线程块的维度和大小，Db.x * Db.y * Db.z 等于每个线程块的线程数。
  • Ns：类型为 size_t，指定本次调用每个线程块额外动态分配的共享内存字节数（不包含静态分配部分）。这些内存用于声明为外部数组的 __shared__ 变量。该参数可选，默认值为 0。
  • S：类型为 cudaStream_t，指定关联的执行流。该参数可选，默认值为 0。

例如：

__global__ void Func(float* parameter);

// 调用方式
Func<<<Dg, Db, Ns>>>(parameter);

执行配置参数会在实际函数参数之前求值。如果 Dg 或 Db 超出设备允许的最大尺寸，或者 Ns 大于设备可用共享内存（减去静态分配所需内存），函数调用会失败。

计算能力为 9.0 及以上的设备允许在编译期指定线程块集群维度，以便内核使用 CUDA 的集群层次结构。可使用 __cluster_dims__([x, [y, [z]]]) 指定编译期集群维度，例如：

__global__ void __cluster_dims__(2, 1, 1) Func(float* parameter);

不带参数的 __cluster_dims__() 表示该内核以集群网格方式启动，但将集群维度留给启动时指定。如果既没有在编译期指定维度，也没有在启动时指定维度，则会产生启动错误。

也可以在运行时指定线程块集群维度，并通过 cudaLaunchKernelEx 启动内核：

__global__ void Func(float* parameter);

{
    cudaLaunchConfig_t config = {0};
    config.gridDim = Dg;
    config.blockDim = Db;
    config.dynamicSmemBytes = Ns;

    cudaLaunchAttribute attribute[1];
    attribute[0].id = cudaLaunchAttributeClusterDimension;
    attribute[0].val.clusterDim.x = 2;
    attribute[0].val.clusterDim.y = 1;
    attribute[0].val.clusterDim.z = 1;
    config.attrs = attribute;
    config.numAttrs = 1;

    float* parameter;
    cudaLaunchKernelEx(&config, Func, parameter);
}

集群启动不会改变网格维度的含义：网格仍按线程块数枚举，并且网格大小应是集群大小的整数倍。

10.38 启动边界（Launch Bounds）

如“多处理器层面”一节所述，内核使用的寄存器越少，多处理器上就越可能同时驻留更多线程和线程块，从而提高性能。

编译器会使用启发式方法减少寄存器使用，同时尽量避免寄存器溢出和指令数增加。应用程序可以通过在 __global__ 函数定义中使用 __launch_bounds__() 限定符，向编译器提供额外信息：

__global__ void
__launch_bounds__(maxThreadsPerBlock,
                  minBlocksPerMultiprocessor,
                  maxBlocksPerCluster)
MyKernel(...)
{
    ...
}
  • maxThreadsPerBlock：应用程序启动 MyKernel() 时，每个线程块使用的线程数不会超过该值。它会编译为 PTX 指令 .maxntid。
  • minBlocksPerMultiprocessor（可选）：指定每个多处理器期望的最小驻留线程块数。它会编译为 .minnctapersm。
  • maxBlocksPerCluster（可选）：指定应用程序启动 MyKernel() 时，每个 cluster 中线程块数量的最大值。它会编译为 .maxclusterrank。

指定启动边界后，编译器首先根据这些值推导寄存器使用上限 \(L\)，确保至少有 minBlocksPerMultiprocessor 个线程块（若未指定该参数，则至少一个线程块）能够在多处理器上驻留，且每个线程块包含 maxThreadsPerBlock 个线程。之后，编译器按以下方式优化寄存器使用：

  • 如果初始寄存器使用量高于 \(L\)，编译器会继续降低寄存器用量，直到不超过 \(L\)，通常代价是增加本地内存使用量和/或指令数。
  • 如果初始寄存器使用量低于 \(L\)：
    • 若指定了 maxThreadsPerBlock，但未指定 minBlocksPerMultiprocessor，编译器会用最大线程数确定驻留线程块数量发生变化时的寄存器阈值，并使用与未指定启动边界时类似的启发式方法。
    • 若同时指定 minBlocksPerMultiprocessor 和 maxThreadsPerBlock，编译器可能将寄存器用量提高到 \(L\)，以减少指令数并更好地隐藏单线程指令延迟。

如果实际启动时每个线程块的线程数超过 maxThreadsPerBlock，内核启动会失败；如果每个 cluster 的线程块数超过 maxBlocksPerCluster，内核启动同样会失败。

CUDA 内核的每线程资源需求可能会以不理想的方式限制最大线程块大小。为了保持对未来硬件和工具包的前向兼容，并确保至少一个线程块可以在 SM 上运行，开发者应使用单参数形式 __launch_bounds__(maxThreadsPerBlock)，指定内核启动时可能使用的最大线程块大小。否则可能出现“too many resources requested for launch”错误。双参数形式 __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor) 在某些情况下可以提高性能，但合适的最小驻留块数应针对具体内核详细分析。

同一个内核在不同主架构版本上的最佳启动边界通常不同。下面示例通过 __CUDA_ARCH__ 选择不同架构的参数：

#define THREADS_PER_BLOCK 256
#if __CUDA_ARCH__ >= 200
#define MY_KERNEL_MAX_THREADS (2 * THREADS_PER_BLOCK)
#define MY_KERNEL_MIN_BLOCKS 3
#else
#define MY_KERNEL_MAX_THREADS THREADS_PER_BLOCK
#define MY_KERNEL_MIN_BLOCKS 2
#endif

__global__ void
__launch_bounds__(MY_KERNEL_MAX_THREADS, MY_KERNEL_MIN_BLOCKS)
MyKernel(...)
{
    ...
}

不能直接在主机代码中将 MY_KERNEL_MAX_THREADS 用作启动线程数，因为主机代码中未定义 __CUDA_ARCH__。例如，即使设备满足 __CUDA_ARCH__ >= 200，主机代码也可能仍以 256 个线程启动内核。线程数应通过不依赖 __CUDA_ARCH__ 的宏在编译期确定，或在运行时根据设备计算能力确定。

编译器可通过 --ptxas-options=-v 报告寄存器使用量；驻留线程块数量则可以根据 CUDA profiler 报告的占用率推导。

10.39 每线程最大寄存器数（Maximum Number of Registers per Thread）

为了进行底层性能调优，CUDA C++ 提供了 __maxnreg__() 函数限定符，将性能调优信息传递给后端优化编译器。它指定一个线程块中的每个线程最多可分配的寄存器数量。

__global__ void
__maxnreg__(maxNumberRegistersPerThread)
MyKernel(...)
{
    ...
}

maxNumberRegistersPerThread 指定内核 MyKernel() 中每个线程允许分配的最大寄存器数，并编译为 PTX 指令 .maxnreg。

__launch_bounds__() 和 __maxnreg__() 不能同时应用于同一个内核。也可以使用编译器选项 maxrregcount 控制文件中所有 __global__ 函数的寄存器使用量，但对使用 __maxnreg__ 限定符的函数，该选项会被忽略。

10.40 #pragma unroll

默认情况下，编译器会展开迭代次数已知的小循环。#pragma unroll 可以控制指定循环的展开行为，必须紧挨循环之前放置，并且只作用于紧随其后的循环。

该指令可以选择性地带一个整型常量表达式（ICE）：

  • 如果没有参数，且循环迭代次数是常量，则完全展开循环；
  • 如果 ICE 的值为 1，则禁止展开；
  • 如果 ICE 为非正整数，或大于 int 可表示的最大值，则忽略该 pragma。

示例：

struct S1_t { static const int value = 4; };

template <int X, typename T2>
__device__ void foo(int *p1, int *p2) {
    // 未指定参数：循环完全展开。
    #pragma unroll
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 2;

    // 展开参数为 8。
    #pragma unroll (X + 1)
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 4;

    // 展开参数为 1：禁止展开。
    #pragma unroll 1
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 8;

    // 展开参数为 4。
    #pragma unroll (T2::value)
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 16;
}

__global__ void bar(int *p1, int *p2) {
    foo<7, S1_t>(p1, p2);
}

整型常量表达式的定义见 C++ 标准。

10.41 SIMD 视频指令（SIMD Video Instructions）

PTX ISA 3.0 引入了 SIMD（Single Instruction, Multiple Data，单指令多数据）视频指令，可对一对 16 位值或四个 8 位值执行操作。这些指令支持计算能力为 3.0 的设备。

SIMD 视频指令包括：

  • vadd2、vadd4
  • vsub2、vsub4
  • vavrg2、vavrg4
  • vabsdiff2、vabsdiff4
  • vmin2、vmin4
  • vmax2、vmax4
  • vset2、vset4

可以通过汇编语句 asm() 在 CUDA 程序中包含这些 PTX 指令。asm() 的基本语法为：

asm("template-string" : "constraint"(output)
    : "constraint"(input));

以下示例使用 vabsdiff4 计算四个字节的 SIMD 绝对差之和：

asm("vabsdiff4.u32.u32.u32.add %0, %1, %2, %3;"
    : "=r"(result)
    : "r"(A), "r"(B), "r"(C));

该指令会以 SIMD 方式计算无符号整数 A 和 B 中每个字节的绝对差，并使用可选的 .add 累加操作将这些差值相加。内联 PTX 汇编的详细用法见《Using Inline PTX Assembly in CUDA》；具体指令语义见所使用 PTX 版本的 PTX ISA 文档。

10.42 诊断 Pragma（Diagnostic Pragmas）

以下 pragma 可用于控制发出诊断消息时的严重程度：

#pragma nv_diag_suppress
#pragma nv_diag_warning
#pragma nv_diag_error
#pragma nv_diag_default
#pragma nv_diag_once

使用形式为：

#pragma nv_diag_xxx error_number, error_number ...

需要处理的诊断消息通过警告消息中的错误编号指定。任何诊断都可以提升为错误；但只有警告可以被抑制，或在提升为错误后恢复为警告。nv_diag_default 会将诊断严重程度恢复为所有 pragma 生效前的状态，即命令行选项修改后的默认严重程度。

例如，以下代码抑制 foo 声明中“已声明但从未引用”的警告：

#pragma nv_diag_suppress 177
void foo() {
    int i = 0;
}
#pragma nv_diag_default 177
void bar() {
    int i = 0;
}

还可以通过以下 pragma 保存和恢复当前诊断状态：

#pragma nv_diagnostic push
#pragma nv_diagnostic pop

例如：

#pragma nv_diagnostic push
#pragma nv_diag_suppress 177
void foo() {
    int i = 0;
}
#pragma nv_diagnostic pop

void bar() {
    int i = 0;
}

这些 pragma 只影响 nvcc 的 CUDA 前端编译器，不影响主机编译器。

移除说明： 从 CUDA 12.0 开始，不带 nv_ 前缀的诊断 pragma 支持已移除。如果它们出现在设备代码中，会发出“无法识别的 pragma”警告；否则会传递给主机编译器。若要控制 CUDA 代码，应使用带 nv_ 前缀的版本。

10.43 自定义 ABI Pragma（Custom ABI Pragmas）

#pragma nv_abi 指令允许采用分离编译模式的应用程序实现接近整程序编译的性能。

语法如下，其中 ICE 表示整型常量表达式：

#pragma nv_abi preserve_n_data(ICE) preserve_n_control(ICE)

#pragma nv_abi 后的参数均为可选项，可以按任意顺序提供，但至少必须指定一个参数。preserve_n 参数用于限制函数调用期间保留的寄存器数量：

  • preserve_n_data(ICE)：限制数据寄存器数量；
  • preserve_n_control(ICE)：限制控制寄存器数量。

该 pragma 可以放在设备函数声明或定义之前，也可以直接放在设备函数中的 C++ 表达式语句内、间接函数调用之前。支持通过函数指针进行的普通函数间接调用，但不支持通过函数参数引用或类成员函数进行的间接调用。

如果 pragma 应用于设备函数声明或定义，它会修改对该函数的调用所使用的自定义 ABI 属性。如果放在间接函数调用位置，则只影响该次间接调用。与直接调用不同，若要改变间接调用的 ABI 属性，必须将 pragma 放在调用点之前。

__device__ int foo() {
    int value{0};
    ...
    return value;
}

__device__ int bar() {
    int value{0};
    ...
    return value;
}

__device__ void baz() {
    int result{0};
    int (*fptr)() = foo; // 函数指针

    #pragma nv_abi preserve_n_data(16) preserve_n_control(8)
    result = fptr(); // pragma 影响通过 fptr 对 foo() 的间接调用

    #pragma nv_abi preserve_n_data(16) preserve_n_control(8)
    result = (*fptr)(); // 间接调用的另一种写法

    #pragma nv_abi preserve_n_data(16) preserve_n_control(8)
    result += bar(); // pragma 不影响对 bar() 的直接调用
}

要修改直接函数调用的 ABI 属性，必须将 pragma 放在函数声明或定义之前：

#pragma nv_abi preserve_n_data(16)
__device__ void foo();

如果函数声明与对应定义上的 pragma 参数不一致，程序格式不正确。
