使用 nvcc 编译的 CUDA 源文件可以同时包含主机代码和设备代码。对于 C++ 输入，CUDA 前端编译器力求模拟主机编译器的行为。输入源代码依据 C++ ISO/IEC 14882:2003、14882:2011、14882:2014 或 14882:2017 规范处理；CUDA 前端编译器也会尽可能模拟主机编译器偏离 ISO 规范的行为。

17.5 限制（Restrictions）

17.5.1 主机编译器扩展（Host Compiler Extensions）

主机编译器专有的语言扩展不支持在设备代码中使用。

  • __Complex 类型仅支持主机代码。
  • __int128 类型在与支持该类型的主机编译器配合编译时，也支持用于设备代码。
  • __float128 类型仅适用于计算能力为 10.0 及以上、且配合支持该类型的主机编译器编译的设备。编译器处理 __float128 常量表达式时，可能使用精度较低的浮点表示。

17.5.2 预处理器符号（Preprocessor Symbols）

17.5.2.1 __CUDA_ARCH__

  1. 下列实体的类型签名不得取决于 __CUDA_ARCH__ 是否定义，也不得取决于它的具体取值：

    • __global__ 函数及函数模板；
    • __device__ 和 __constant__ 变量；
    • 纹理和表面对象。

    例如，以下代码非法，因为设备变量 xxx 和内核 foo 的类型会随 __CUDA_ARCH__ 改变：

    #if !defined(__CUDA_ARCH__)
typedef int mytype;
#else
typedef double mytype;
#endif

__device__ mytype xxx; // 错误：xxx 的类型依赖于 __CUDA_ARCH__

__global__ void foo(
    mytype in,         // 错误：foo 的类型依赖于 __CUDA_ARCH__
    mytype *ptr) {
    *ptr = in;
}

  2. 如果一个 __global__ 函数模板由主机实例化并启动，那么无论 __CUDA_ARCH__ 是否定义、取值为何，该模板都必须使用相同的模板参数实例化。

  3. 在分离编译模式下，具有外部链接的函数或变量定义是否存在，不得依赖于 __CUDA_ARCH__ 是否定义或其具体取值。

  4. 在分离编译模式下，不得在头文件中以可能导致不同目标文件出现不同运行行为的方式使用 __CUDA_ARCH__；或者必须保证所有目标文件都针对相同的计算架构编译。如果头文件中定义的弱函数或模板函数依赖 __CUDA_ARCH__，不同目标文件针对不同架构编译时，可能生成彼此冲突的实例。

    例如，若头文件中的模板在 compute_70 下返回空指针、在其他架构下返回共享内存数组地址，而两个源文件针对不同架构编译并实例化相同类型，那么链接时只会采用其中一个版本，程序行为将取决于最终选中的版本。应将这些源文件编译为相同计算架构，或避免在共享头文件函数中用 __CUDA_ARCH__ 控制行为。

编译器不保证一定会针对上述不受支持的 __CUDA_ARCH__ 用法生成诊断信息。

17.5.3 限定符（Qualifiers）

17.5.3.1 设备内存空间说明符（Device Memory Space Specifiers）

__device__、__shared__、__managed__ 和 __constant__ 内存空间说明符不能用于：

  • class、struct 和 union 的数据成员；
  • 形式参数；
  • 在主机端执行的函数内部、且不是 extern 的变量声明。

在设备端执行的函数中，变量声明如果既不是 extern 也不是 static，则不能使用 __device__、__constant__ 或 __managed__ 内存空间说明符。

使用 __device__、__constant__、__managed__ 或 __shared__ 定义的变量，其类类型不能具有非空构造函数或非空析构函数。

在翻译单元的某一点，如果类的构造函数是平凡构造函数，或满足以下全部条件，则可视为“空构造函数”：构造函数已定义；没有参数；初始化列表为空；函数体为空；类没有虚函数、虚基类或非静态数据成员初始化器；所有基类及类类型的非静态数据成员的默认构造函数也都可视为空构造函数。

析构函数若为平凡析构函数，或满足以下全部条件，则可视为“空析构函数”：析构函数已定义且函数体为空；类没有虚函数和虚基类；所有基类及类类型的非静态数据成员的析构函数也都可视为空析构函数。

17.5.3.2 __managed__ 内存空间说明符（__managed__ Memory Space Specifier）

使用 __managed__ 声明的托管变量受到以下限制：

  • 托管变量的地址不是常量表达式。
  • 托管变量不能具有 const 限定类型或引用类型。
  • 当 CUDA Runtime 可能尚未处于有效状态时，不得使用托管变量的地址或值，包括静态/动态初始化或销毁静态、线程局部对象的过程；调用 exit() 后执行的代码；以及 CUDA Runtime 可能尚未初始化时执行的代码。
  • 托管变量不能作为未加括号的 id-expression 参数用于 decltype()。
  • 托管变量具有与动态分配托管内存相同的一致性和连贯性行为。
  • 在多 GPU 执行平台上，托管变量只分配一次，不会为每块 GPU 分别分配。
  • 主机函数内部不能声明没有 extern 链接属性的托管变量；设备函数内部不能声明既不是 extern 也不是 static 的托管变量。

示例：

__device__ __managed__ int xxx = 10; // 正确

int *ptr = &xxx; // 错误：静态初始化时使用托管变量

struct S1_t {
    int field;
    S1_t() : field(xxx) {}
};

struct S2_t {
    ~S2_t() { xxx = 10; }
};

S1_t temp1; // 错误：动态初始化时使用托管变量
S2_t temp2; // 错误：静态存储期对象的析构函数中使用托管变量

__device__ __managed__ const int yyy = 10; // 错误：const 限定类型
__device__ __managed__ int &zzz = xxx;     // 错误：引用类型

template <int *addr> struct S3_t {};
S3_t<&xxx> temp; // 错误：托管变量的地址不是常量表达式

__global__ void kern(int *ptr) {
    assert(ptr == &xxx); // 正确
    xxx = 20;            // 正确
}

int main() {
    int *ptr = &xxx; // 正确
    kern<<<1, 1>>>(ptr);
    cudaDeviceSynchronize();
    xxx++;

    decltype(xxx) qqq;       // 错误：未加括号的托管变量 id-expression
    decltype((xxx)) zzz = yyy; // 正确
}

17.5.3.3 volatile 限定符（Volatile Qualifier）

只要遵守内存栅栏函数规定的内存排序语义和同步函数规定的内存可见性语义，编译器就可以优化对全局内存或共享内存的读写，例如将全局内存读取缓存到寄存器或 L1 缓存中。

可以使用 volatile 关键字关闭这些优化：如果位于全局内存或共享内存中的变量声明为 volatile，编译器就会假定其他线程可能随时更改或使用其值，因此对该变量的每次引用都会生成实际的内存读取或写入指令。

17.5.4 指针（Pointers）

在主机代码中解引用指向全局内存或共享内存的指针，或在设备代码中解引用指向主机内存的指针，都会导致未定义行为，通常表现为段错误并终止应用程序。

通过获取 __device__、__shared__ 或 __constant__ 变量地址得到的地址，只能在设备代码中使用。通过 cudaGetSymbolAddress()（见“设备内存”一节）获得的 __device__ 或 __constant__ 变量地址，则只能在主机代码中使用。

17.5.5 运算符（Operators）

17.5.5.1 赋值运算符（Assignment Operator）

__constant__ 变量只能由主机代码通过 Runtime 函数赋值，不能在设备代码中赋值。__shared__ 变量的声明不能包含初始化。任何 CUDA 内建变量都不允许被赋值。

17.5.5.2 取地址运算符（Address Operator）

不允许获取任何 CUDA 内建变量的地址。

17.5.6 运行时类型信息（Run Time Type Information，RTTI）

以下 RTTI 相关特性支持用于主机代码，但不支持用于设备代码：

  • typeid 运算符；
  • std::type_info；
  • dynamic_cast 运算符。

17.5.7 异常处理（Exception Handling）

异常处理仅支持主机代码，不支持设备代码。__global__ 函数不支持异常规范。

17.5.8 标准库（Standard Library）

除非另有说明，标准库仅支持主机代码，不支持设备代码。

17.5.9 命名空间保留（Namespace Reservations）

除非另有明确例外，向 cuda::、nv::、cooperative_groups:: 或其任何嵌套命名空间中添加声明或定义，都属于未定义行为。

例如，在保留命名空间 cuda 中直接声明类或定义函数是不允许的：

namespace cuda {
    // 错误：向保留命名空间添加类声明。
    struct foo {};

    // 错误：向保留命名空间添加函数定义。
    cudaStream_t make_stream() {
        cudaStream_t s;
        cudaStreamCreate(&s);
        return s;
    }
}

在 cuda::utils 等嵌套命名空间中添加定义同样不允许。不过，在用户自己的命名空间内部嵌套使用名为 cuda 的命名空间是允许的：

namespace utils {
    namespace cuda {
        cudaStream_t make_stream() {
            cudaStream_t s;
            cudaStreamCreate(&s);
            return s;
        }
    }
}

但如果随后在全局作用域使用 using namespace utils;，使用户定义的 utils::cuda 等价于向全局保留的 cuda 命名空间添加符号，则同样不允许。

17.5.10 函数（Functions）

17.5.10.1 外部链接（External Linkage）

设备代码调用使用 extern 声明的函数时，该函数必须与设备代码定义在同一编译单元中。编译单元可以是单个文件，也可以是使用可重定位设备代码和 nvlink 链接在一起的多个文件。

17.5.10.2 隐式声明和显式默认化的函数（Implicitly-declared and Explicitly-defaulted Functions）

设函数 \(F\) 为隐式声明的函数，或在首次声明时显式默认化的函数。\(F\) 的执行空间说明符（__host__、__device__）是所有调用它的函数的执行空间说明符的并集；在该分析中，__global__ 调用者按 __device__ 调用者处理。

例如，若 Derived 的隐式构造函数只由设备函数调用，它会被视为 __device__ 函数；若 Other 的隐式构造函数同时由主机函数和设备函数调用，则会被视为 __host__ __device__ 函数。

此外，如果 \(F\) 是虚析构函数，那么所有由 \(F\) 覆盖、且不是隐式定义或并非在首次声明时默认化的虚析构函数，其执行空间也会加入 \(F\) 的执行空间集合。

17.5.10.3 函数参数（Function Parameters）

__global__ 函数参数通过常量内存传递到设备。从 Volta 架构开始，参数总量限制为 32,764 字节；较旧架构的限制为 4 KB。

__global__ 函数不能使用可变数量的参数，也不能通过引用传递参数。

在分离编译模式下，如果某个翻译单元对 __device__ 或 __global__ 函数进行了 ODR-use，则该函数的参数类型和返回类型必须在该翻译单元中完整定义。

例如，如果一个源文件仅前置声明了类型 S，便声明接受 S 的设备函数并取得其地址，而另一个源文件才定义 S 和该函数，那么在使用 -rdc=true 编译并链接时，nvlink 会因函数原型与定义不匹配而报错。

17.5.10.3.1 __global__ 函数参数处理（__global__ Function Argument Processing）

从设备代码启动 __global__ 函数时，每个参数都必须可平凡复制且可平凡析构。

从主机代码启动 __global__ 函数时，参数类型可以不可平凡复制或不可平凡析构，但参数处理方式会偏离标准 C++ 模型，用户必须确保这不会破坏程序正确性。主要有两方面差异。

1. 使用 memcpy 而不是调用复制构造函数

编译器降低主机端内核启动代码时，会生成桩函数（stub），按值复制参数一次或多次，最终使用 memcpy 将参数复制到设备端内核参数内存。即使参数类型不可平凡复制，也可能如此；如果复制构造函数有副作用，程序行为就可能与预期不同。

#include <cassert>

struct S {
    int x;
    int *ptr;
    __host__ __device__ S() {}
    __host__ __device__ S(const S &) { ptr = &x; }
};

__global__ void foo(S in) {
    // 可能断言失败：编译器生成的代码会 memcpy 参数，
    // 跳过复制构造函数，因此 in.ptr 不一定指向 &in.x。
    assert(in.ptr == &in.x);
}

int main() {
    S tmp;
    foo<<<1, 1>>>(tmp);
    cudaDeviceSynchronize();
}

另一个例子是复制构造函数递增托管变量计数器。由于主机端桩函数可能按值复制参数多次，不能假定计数器只增加一次。

2. 析构函数可能在 __global__ 函数执行结束前被调用

内核启动相对于主机执行是异步的。因此，如果 __global__ 函数参数具有非平凡析构函数，该析构函数可能在内核执行完成之前就在主机端运行。若析构函数具有副作用，这可能破坏程序正确性。

struct S {
    int *ptr;
    S() : ptr(nullptr) {}
    S(const S &) { cudaMallocManaged(&ptr, sizeof(int)); }
    ~S() { cudaFree(ptr); }
};

__global__ void foo(S in) {
    // 该写入可能访问已被析构函数释放的内存。
    *(in.ptr) = 4;
}

int main() {
    S V;
    foo<<<1, 1>>>(V);
    cudaDeviceSynchronize();
}

在该示例中，主机端桩函数返回时可能调用 S::~S() 并释放内存，而 GPU 内核仍在异步执行。

17.5.10.3.2 工具包与驱动兼容性（Toolkit and Driver Compatibility）

要编译、启动和调试参数大小超过 4 KB 的内核，必须使用 CUDA 12.1 工具包和 R530 或更高版本的驱动程序。若在较旧驱动程序上启动这类内核，CUDA 会返回 CUDA_ERROR_NOT_SUPPORTED。

17.5.10.3.3 不同工具包修订版本之间的链接兼容性（Link Compatibility across Toolkit Revisions）

链接设备目标文件时，如果至少一个目标文件包含参数大小超过 4 KB 的内核，那么在链接之前，必须使用 CUDA 12.1 或更高版本的工具包，从各自的设备源文件重新编译所有目标文件。否则会产生链接错误。

17.5.10.4 函数内部的静态变量（Static Variables within Function）

在函数 F 的直接或嵌套代码块作用域内声明静态变量 V 时，只有当 F 是 __global__、仅带 __device__ 的函数，或处于设备编译阶段的 __host__ __device__ 函数时，才允许使用变量内存空间说明符。若声明中没有显式说明符，设备编译期间会隐式添加 __device__。V 的初始化限制与在命名空间作用域中使用相同内存空间说明符声明的变量相同；例如，__device__ 变量不能具有非空构造函数，也不允许动态初始化。

__device__ void f1() {
    static int i1;               // 正确：隐式 __device__
    static int i2 = 11;          // 正确：隐式 __device__
    static __managed__ int m1;   // 正确
    static __device__ int d1;    // 正确
    static __constant__ int c1;  // 正确
    static __shared__ int i5;    // 正确

    int x = 33;
    static int i6 = x;           // 错误：动态初始化
}

在 __host__ __device__ 函数中，可用 #ifdef __CUDA_ARCH__ 将设备专用静态变量声明限制在设备编译阶段；否则，这些声明在主机编译阶段可能报错。

17.5.10.5 函数指针（Function Pointers）

在主机代码中取得的 __global__ 函数地址不能在设备代码中使用；反之，在设备代码中取得的 __global__ 函数地址也不能在主机代码中使用。在主机代码中不允许取得 __device__ 函数的地址。

17.5.10.6 函数递归（Function Recursion）

__global__ 函数不支持递归。

17.5.10.7 友元函数（Friend Functions）

不能在 friend 声明中定义 __global__ 函数或函数模板。可以在 friend 声明中进行声明，但不能直接提供函数体。

17.5.10.8 运算符函数（Operator Function）

运算符函数不能是 __global__ 函数。

17.5.10.9 分配与释放函数（Allocation and Deallocation Functions）

用户自定义的 operator new、operator new[]、operator delete 或 operator delete[] 不能替换编译器提供的对应 __host__ 或 __device__ 内建函数。

17.5.11 类（Classes）

17.5.11.1 数据成员（Data Members）

除同时带有 const 限定的静态数据成员外，其他静态数据成员均不受支持（见“带 const 限定的变量”）。

17.5.11.2 成员函数（Function Members）

静态成员函数不能是 __global__ 函数。

17.5.11.3 虚函数（Virtual Functions）

派生类函数覆盖基类虚函数时，被覆盖函数和覆盖函数的执行空间说明符（__host__、__device__）必须一致。

不能将具有虚函数的类对象作为参数传给 __global__ 函数。如果对象在主机代码中创建，却在设备代码中调用其虚函数，行为未定义；如果对象在设备代码中创建，却在主机代码中调用其虚函数，行为同样未定义。使用 Microsoft 主机编译器时，还需遵守 Windows 专用限制。

17.5.11.4 虚基类（Virtual Base Classes）

不能将派生自虚基类的类对象作为参数传给 __global__ 函数。使用 Microsoft 主机编译器时，还需遵守 Windows 专用限制。

17.5.11.5 匿名联合体（Anonymous Unions）

命名空间作用域中的匿名联合体，其成员变量不能在 __global__ 或 __device__ 函数中引用。

17.5.11.6 Windows 专用限制（Windows-Specific）

CUDA 编译器遵循 IA-64 ABI 的类布局规则，而 Microsoft 主机编译器采用不同规则。对于成员指针类型，以及具有虚函数、虚基类、特定多重继承或特定空基类布局的类型，CUDA 编译器计算出的类布局和大小可能与 Microsoft 主机编译器不同。

若类型 C 本身是上述类型，或 C 的字段类型/基类类型包含上述类型，若 C 只在主机代码或只在设备代码中使用，程序通常可以正确工作；但在主机与设备之间传递 C 对象（例如作为 __global__ 参数或通过 cudaMemcpy*()）属于未定义行为。

如果对象在主机代码中创建，则在设备代码中访问该对象或其子对象、或调用其成员函数，行为未定义。反之，如果对象在设备代码中创建，则在主机代码中访问该对象或其子对象、或调用其成员函数，也属于未定义行为。若怀疑布局不一致，可分别在主机和设备端输出 sizeof(C) 与 offsetof(C, field) 进行排查。

17.5.12 模板（Templates）

如果满足以下任一条件，则某个类型或模板不能用作 __global__ 函数模板实例化，或 __device__ / __constant__ 变量实例化的类型、非类型或模板模板参数：

  • 该类型或模板定义在 __host__ 或 __host__ __device__ 函数内部；
  • 该类型或模板是具有 private 或 protected 访问权限的类成员，并且其外围类不是定义在 __device__ 或 __global__ 函数内部；
  • 该类型是未命名类型，或由上述类型组合而成。

例如，不能通过模板参数访问类外部不可见的私有嵌套类型。C++14 中还有额外限制：函数局部类型不能用于实例化设备变量模板；lambda 闭包类型不能用于变量模板实例化。

17.5.13 三字符组与双字符组（Trigraphs and Digraphs）

所有平台均不支持三字符组（trigraphs）；Windows 平台不支持双字符组（digraphs）。

17.5.14 带 const 限定的变量（Const-qualified Variables）

设 V 是命名空间作用域变量或类静态成员变量，其类型带有 const 限定，且没有 __device__、__constant__、__shared__ 等执行空间注解。这样的 V 被视为主机变量。

只有当 V 在使用位置之前已通过常量表达式初始化、类型没有 volatile 限定，并且类型为内建整数类型或内建浮点类型时，才可以在设备代码中直接使用其值。Microsoft 主机编译器是例外：此时不支持直接使用内建浮点类型的此类变量值。

设备源代码不能引用 V 本身，也不能取得 V 的地址。例如，已用常量表达式初始化的 const int xxx = 10 可用于设备端数组长度或值计算；但引用 xxx、取得 &xxx，或使用尚未在使用点之前通过常量表达式初始化的 extern const int，均不允许。

17.5.15 long double

设备代码不支持 long double 类型。

17.5.16 弃用注解（Deprecation Annotation）

当主机编译器为 GCC、Clang、xlC、ICC 或 PGI 时，nvcc 支持 deprecated 属性；当主机编译器为 cl.exe 时，支持相应的 declspec。启用 C++14 方言后，也支持标准属性 [[deprecated]]。

在设备编译阶段（定义了 __CUDA_ARCH__）中，如果 __device__、__global__ 或 __host__ __device__ 函数体引用了已弃用实体，CUDA 前端编译器会生成弃用诊断。其他引用由主机编译器处理。

CUDA 前端编译器不支持各种主机编译器提供的 #pragma gcc diagnostic 或 #pragma warning 机制。因此，这些 pragma 不会影响 CUDA 前端生成的弃用诊断，但会影响主机编译器生成的诊断。可用 NVIDIA 专用的 #pragma nv_diag_suppress 抑制设备代码的警告；nvcc 选项 -Wno-deprecated-declarations 可抑制所有弃用警告，-Werror=deprecated-declarations 则可将其提升为错误。

17.5.17 noreturn 注解（Noreturn Annotation）

当主机编译器为 GCC、Clang、xlC、ICC 或 PGI 时，nvcc 支持 noreturn 属性；当主机编译器为 cl.exe 时，支持相应的 declspec。启用 C++11 方言后，也支持标准属性 [[noreturn]]。这些属性或说明符既可用于主机代码，也可用于设备代码。

17.5.18 [[likely]] / [[unlikely]] 标准属性

所有支持 C++ 标准属性语法的配置都接受这两个属性。它们可以向设备编译器优化器提示：相对于不包含该语句的其他路径，某条语句更有可能或更不可能执行。

__device__ int foo(int x) {
    if (x < 10) [[likely]] {
        return 4;
    }
    if (x < 20) [[unlikely]] {
        return 1;
    }
    return 0;
}

如果在主机编译阶段（__CUDA_ARCH__ 未定义时）使用这些属性，主机编译器也会看到它们；若该编译器不支持这些属性，可能产生警告，例如 Clang 11 可能报告未知属性。

17.5.19 GNU const 与 pure 属性（const and pure GNU Attributes）

当所用语言方言和主机编译器支持 GNU 属性时，这两个属性可用于主机函数和设备函数。

  • 对带 pure 属性的设备函数，设备优化器假定函数不会更改调用者可见的任何可变状态（例如内存）。
  • 对带 const 属性的设备函数，设备优化器假定函数不会访问或更改调用者可见的任何可变状态。

例如，将 get(int) 标记为 const 后，优化器可能识别出同一参数的第二次 get(in) 调用可以复用第一次调用的结果。

17.5.20 __nv_pure__ 属性（__nv_pure__ Attribute）

__nv_pure__ 属性支持主机函数和设备函数。对于主机函数，如果所用语言方言支持 GNU pure 属性，该属性会转换为 GNU pure；如果使用 MSVC 作为主机编译器，则会转换为 MSVC noalias 属性。

对于带 __nv_pure__ 属性的设备函数，设备优化器假定该函数不会更改调用者可见的可变状态（例如内存）。

17.5.21 Intel 主机编译器专用说明（Intel Host Compiler Specific）

CUDA 前端编译器解析器无法识别 Intel 编译器（例如 icc）支持的某些内建函数。因此，当使用 Intel 编译器作为主机编译器时，nvcc 会在预处理阶段定义宏 __INTEL_COMPILER_USE_INTRINSIC_PROTOTYPES。该宏会在相关头文件中启用 Intel 内建函数的显式声明，使 nvcc 能够在主机代码中支持这些函数。由于额外声明较多，这可能会增加编译时间。

17.5.22 C++11 特性（C++11 Features）

主机编译器默认启用的 C++11 特性也受 nvcc 支持，但仍受本文档中的限制约束。使用 nvcc -std=c++11 会启用全部 C++11 特性，并以相应的 C++11 方言选项调用主机预处理器、编译器和链接器。原文指出，该选项当时支持的主机编译器包括 GCC 4.7 及更高版本、Clang、ICC 15 及更高版本，以及 XL C 13.1 及更高版本。

17.5.22.1 Lambda 表达式（Lambda Expressions）

Lambda 表达式对应闭包类的所有成员函数（包括 operator()）的执行空间说明符由编译器推导。编译器会在包含 lambda 表达式的最小代码块、类或命名空间作用域中创建闭包类型，然后查找包围该闭包类型的最内层函数作用域，并将该函数的执行空间说明符赋给闭包类成员函数。如果不存在外围函数作用域，则默认为 __host__。

例如，全局作用域中的 lambda 默认为 __host__；在 __device__ 函数中定义的 lambda 默认为 __device__；在 __host__ __device__ 函数中定义的 lambda 则具有 __host__ __device__ 执行空间。

除非 lambda 定义在 __device__ 或 __global__ 函数内部，否则其闭包类型不能用于 __global__ 函数模板实例化的类型参数或非类型参数。

17.5.22.2 std::initializer_list

默认情况下，CUDA 编译器会隐式地将 std::initializer_list 的成员函数视为具有 __host__ __device__ 执行空间，因此设备代码可以直接调用这些函数。使用 nvcc --no-host-device-initializer-list 可关闭此行为；此时这些成员函数会被视为 __host__ 函数，不能从设备代码直接调用。

17.5.22.3 右值引用（Rvalue References）

默认情况下，CUDA 编译器会隐式地将 std::move 和 std::forward 函数模板视为具有 __host__ __device__ 执行空间，因此设备代码可以直接调用。使用 nvcc --no-host-device-move-forward 可关闭此行为；此时 std::move 和 std::forward 会被视为 __host__ 函数，不能从设备代码直接调用。

17.5.22.4 constexpr 函数与函数模板（Constexpr Functions and Function Templates）

默认情况下，不能从执行空间不兼容的函数调用 constexpr 函数。实验性选项 --expt-relaxed-constexpr 可移除此限制：启用后，主机代码可以调用 __device__ constexpr 函数，设备代码也可以调用 __host__ constexpr 函数。指定该选项后，nvcc 会定义宏 __CUDACC_RELAXED_CONSTEXPR__。注意，即使函数模板带有 constexpr 关键字，模板实例化后的函数也不一定是 constexpr 函数。

17.5.22.5 constexpr 变量（Constexpr Variables）

设 V 为命名空间作用域变量或类静态成员变量，带有 constexpr，且没有 __device__、__constant__ 或 __shared__ 等执行空间注解。这样的 V 被视为主机代码变量。

如果 V 是标量类型（long double 除外），且类型没有 volatile 限定，则可以在设备代码中直接使用其值。若 V 是非标量类型，则只有在调用为常量表达式的 constexpr __device__ 或 __host__ __device__ 函数内部，才能使用 V 的标量元素。设备源代码不能引用 V 本身，也不能取得 V 的地址。

constexpr int xxx = 10;
constexpr int yyy = xxx + 4;
struct S1_t { static constexpr int qqq = 100; };
constexpr int host_arr[] = {1, 2, 3};

constexpr __device__ int get(int idx) {
    return host_arr[idx];
}

__device__ int foo(int idx) {
    int v1 = xxx + yyy + S1_t::qqq; // 正确
    const int &v2 = xxx;            // 错误：引用主机 constexpr 变量
    const int *v3 = &xxx;           // 错误：取得主机 constexpr 变量地址
    v1 += get(2);                   // 正确：常量表达式
    v1 += get(idx);                 // 错误：不是常量表达式
    v1 += host_arr[2];              // 错误：host_arr 不是标量类型
    return v1;
}

17.5.22.6 内联命名空间（Inline Namespaces）

编译 CUDA 翻译单元时，CUDA 编译器可能会调用主机编译器编译其中的主机代码，并插入引用 __global__ 函数、__device__ / __constant__ 变量以及表面或纹理类型变量的生成代码。

如果这类实体定义在内联命名空间中，而外围命名空间又定义了同名且类型签名相同的实体，生成代码中的引用可能被主机编译器判定为歧义，导致主机端编译失败。避免此问题的方法之一，是为内联命名空间中定义的实体使用唯一名称。

17.5.22.6.1 内联未命名命名空间（Inline Unnamed Namespaces）

在内联未命名命名空间的命名空间作用域中，不能声明以下实体：

  • __managed__、__device__、__shared__ 和 __constant__ 变量；
  • __global__ 函数和函数模板；
  • 表面或纹理类型变量。

17.5.22.7 thread_local

设备代码不允许使用 thread_local 存储说明符。

17.5.22.8 __global__ 函数与函数模板（__global__ Functions and Function Templates）

如果 lambda 闭包类型用于 __global__ 函数模板实例化的模板参数，那么该 lambda 必须定义在 __device__ 或 __global__ 函数的直接或嵌套代码块作用域内，或者必须是扩展 lambda。

此外：

  • __global__ 函数或函数模板不能声明为 constexpr；
  • __global__ 函数或函数模板不能有 std::initializer_list 或 va_list 类型的参数；
  • __global__ 函数不能有右值引用类型的参数；
  • 可变参数 __global__ 函数模板只能有一个参数包，并且参数包必须位于模板参数列表的最后。

17.5.22.9 __managed__ 与 __shared__ 变量

__managed__ 和 __shared__ 变量不能使用 constexpr 关键字。

17.5.22.10 默认化函数（Defaulted Functions）

对在首次声明时就显式默认化的函数，CUDA 编译器会忽略其执行空间说明符，并按“隐式声明和显式默认化的函数”一节中的规则推导执行空间。

如果函数不是在首次声明时默认化，则不会忽略其执行空间说明符。例如，首次声明为 __host__ S2() 的构造函数，即使后来写为 S2::S2() = default，其执行空间仍固定为 __host__，因此设备函数不能调用它。

17.5.23 C++14 特性（C++14 Features）

主机编译器默认启用的 C++14 特性也受 nvcc 支持。传入 nvcc -std=c++14 会启用全部 C++14 特性，并以相应的 C++14 方言选项调用主机预处理器、编译器和链接器。原文指出，当时该选项支持 GCC 5.1 及更高版本、Clang 3.7 及更高版本，以及 ICC 17 及更高版本。

17.5.23.1 返回类型推导函数（Functions with Deduced Return Type）

__global__ 函数不能使用返回类型推导。

如果 __device__ 函数使用返回类型推导，CUDA 前端编译器会在调用主机编译器之前，将该函数声明转换为返回 void 的形式。这可能影响主机代码对设备函数推导返回类型的检查。因此，除非相关引用在 __CUDA_ARCH__ 未定义时不存在，否则在设备函数体以外引用这种推导返回类型会产生编译错误。

例如，可以在设备函数体内部调用 __device__ auto fn1(int)，但不能在主机代码中使用 decltype(fn1(10))、获取函数指针，或在主机端模板参数中引用其推导类型。

17.5.23.2 变量模板（Variable Templates）

使用 Microsoft 主机编译器时，__device__ / __constant__ 变量模板不能具有带 const 限定的类型。例如，template <typename T> __device__ const T d1(2); 会报错；但指向 const T 的指针变量模板（例如 template <typename T> __device__ const T *d3;）是允许的。

17.5.24 C++17 特性（C++17 Features）

主机编译器默认启用的 C++17 特性也受 nvcc 支持。使用 nvcc -std=c++17 会启用全部 C++17 特性，并以相应的 C++17 方言选项调用主机预处理器、编译器和链接器。原文指出，当时该选项支持 GCC 7.0 及更高版本、Clang 8.0 及更高版本、Visual Studio 2017 及更高版本、PGI 19.0 及更高版本，以及 ICC 19.0 及更高版本。

17.5.24.1 内联变量（Inline Variable）

在整程序编译模式下，命名空间作用域的内联变量如果使用 __device__、__constant__ 或 __managed__ 内存空间说明符，则必须具有内部链接。

inline __device__ int xxx;        // 整程序编译模式下错误
                                  // 分离编译模式下正确
inline __shared__ int yyy0;       // 正确
static inline __device__ int yyy; // 正确：内部链接

namespace {
    inline __device__ int zzz;    // 正确：内部链接
}

使用 G++ 主机编译器时，带 __managed__ 内存空间说明符的内联变量可能无法在调试器中显示。

17.5.24.2 结构化绑定（Structured Binding）

结构化绑定声明不能带变量内存空间说明符。例如：

struct S { int x; int y; };
__device__ auto [a1, b1] = S{4, 5}; // 错误

17.5.25 C++20 特性（C++20 Features）

主机编译器默认启用的 C++20 特性也受 nvcc 支持。使用 nvcc -std=c++20 会启用全部 C++20 特性，并以相应的 C++20 方言选项调用主机预处理器、编译器和链接器。原文指出，当时该选项支持 GCC 10.0 及更高版本、Clang 10.0 及更高版本、Visual Studio 2022 及更高版本，以及 nvc++ 20.7 及更高版本。

17.5.25.1 模块支持（Module Support）

CUDA C++ 的主机代码和设备代码均不支持模块。使用 module、export 和 import 关键字会被诊断为错误。

17.5.25.2 协程支持（Coroutine Support）

设备代码不支持协程。在设备函数作用域内使用 co_await、co_yield 或 co_return 会在设备编译期间被诊断为错误。

17.5.25.3 三路比较运算符（Three-way Comparison Operator）

三路比较运算符 <=> 同时支持主机代码和设备代码，但某些用法会隐式依赖主机实现提供的标准模板库功能。此类用法可能需要指定 --expt-relaxed-constexpr 来消除警告，而且主机标准库实现必须满足设备代码的要求。

17.5.25.4 consteval 函数（Consteval Functions）

通常不允许跨执行空间调用函数，编译器会发出警告或错误。但被调用函数若声明为 consteval，则不受此限制。因此，__device__ 或 __global__ 函数可以调用 __host__ consteval 函数，主机函数也可以调用 __device__ consteval 函数。

17.6 多态函数包装器（Polymorphic Function Wrappers）

头文件 <nvfunctional> 提供多态函数包装器类模板 nvstd::function。该模板的实例可以存储、复制并调用任意可调用目标，例如 lambda 表达式。nvstd::function 可用于主机代码和设备代码。

#include <nvfunctional>

__device__ int foo_d() { return 1; }
__host__ __device__ int foo_hd() { return 2; }
__host__ int foo_h() { return 3; }

__global__ void kernel(int *result) {
    nvstd::function<int()> fn1 = foo_d;
    nvstd::function<int()> fn2 = foo_hd;
    nvstd::function<int()> fn3 = []() { return 10; };
    *result = fn1() + fn2() + fn3();
}

主机代码中的 nvstd::function 不能用 __device__ 函数地址，或 operator() 为 __device__ 函数的仿函数初始化。设备代码中的 nvstd::function 不能用 __host__ 函数地址，或 operator() 为 __host__ 函数的仿函数初始化。不能在运行时将 nvstd::function 实例从主机传到设备，或从设备传到主机；如果 __global__ 函数由主机启动，则其参数类型不能是 nvstd::function。

该类提供主机/设备构造函数、析构函数、复制和移动赋值、swap、布尔状态转换、函数调用运算符，以及与 nullptr 比较的重载。函数调用运算符 operator() 仅标记为 __device__；其他所列基本操作同时支持 __host__ 和 __device__。

17.7 扩展 Lambda（Extended Lambdas）

nvcc 选项 --extended-lambda 允许在 lambda 表达式中显式标注执行空间。注解应放在 lambda 引入符之后、可选的 lambda 声明符之前。指定该选项后，nvcc 会定义宏 __CUDACC_EXTENDED_LAMBDA__。使用 ICC 主机编译器时，该选项要求 ICC 版本至少为 1800。

  • 扩展 __device__ lambda： 显式标记为 __device__，并定义在 __host__ 或 __host__ __device__ 函数的直接或嵌套代码块作用域内。
  • 扩展 __host__ __device__ lambda： 显式标记为 __host__ __device__，并定义在 __host__ 或 __host__ __device__ 函数的直接或嵌套代码块作用域内。
  • 扩展 lambda： 上述两类 lambda 的统称。它们可用于 __global__ 函数模板实例化的类型参数。

如果没有显式指定执行空间注解，编译器会根据闭包类所在的外围作用域推导执行空间，并将注解应用于闭包类的所有成员函数。

void foo_host() {
    auto lam1 = [] {};                     // 不是扩展 lambda：没有显式注解
    auto lam2 = [] __device__ {};          // 扩展 __device__ lambda
    auto lam3 = [] __host__ __device__ {}; // 扩展 host-device lambda
    auto lam4 = [] __host__ {};            // 不是扩展 lambda：仅标记 host
}

__device__ void foo_device() {
    // 本函数内的 lambda 都不是扩展 lambda，因为外围函数不是
    // __host__ 或 __host__ __device__ 函数。
    auto lam1 = [] {};
    auto lam2 = [] __device__ {};
    auto lam3 = [] __host__ __device__ {};
}

17.7.1 扩展 Lambda 类型特征（Extended Lambda Type Traits）

编译器提供以下类型特征，用于在编译期识别扩展 lambda 的闭包类型：

  • __nv_is_extended_device_lambda_closure_type(type)：如果 type 是扩展 __device__ lambda 的闭包类，则为真。
  • __nv_is_extended_device_lambda_with_preserved_return_type(type)：如果 type 是扩展 __device__ lambda 的闭包类，且该 lambda 的尾置返回类型满足保留条件，则为真。若尾置返回类型引用 lambda 参数名，则返回类型不会被保留。
  • __nv_is_extended_host_device_lambda_closure_type(type)：如果 type 是扩展 __host__ __device__ lambda 的闭包类，则为真。

这些类型特征在所有编译模式下均可使用；但如果未启用扩展 lambda 模式，它们始终返回假。

17.7.2 扩展 Lambda 的限制（Extended Lambda Restrictions）

在调用主机编译器之前，CUDA 编译器会把扩展 lambda 替换为命名空间作用域中定义的占位类型实例。该占位类型的模板参数需要取得包含原始 lambda 的函数地址，以确保使用扩展 lambda 闭包类型作为模板参数的 __global__ 函数模板能够正确执行。由此产生以下限制：

  1. 不能嵌套定义扩展 lambda。 扩展 lambda 不能定义在另一个扩展 lambda 表达式内部。
  2. 不能定义在泛型 lambda 内部。 扩展 lambda 不能位于泛型 lambda 表达式内部。
  3. 如果扩展 lambda 位于一个或多个嵌套 lambda 的直接或嵌套代码块作用域内，那么最外层的这些 lambda 必须定义在某个函数的直接或嵌套代码块作用域内。
  4. 包含扩展 lambda 的外围函数必须有名称，且其地址必须可取得。如果外围函数是类成员函数，则所有外围类都必须有名称，成员函数在父类中不能是 private 或 protected，所有外围类在各自父类中也不能是 private 或 protected。
  5. 在扩展 lambda 定义的位置，必须能够无歧义地取得外围函数地址。如果类型别名遮蔽同名模板参数等情况导致地址表达式不明确，则不支持。
  6. 不能在函数局部类中定义扩展 lambda。
  7. 扩展 lambda 的外围函数不能使用返回类型推导。
  8. 扩展 __host__ __device__ lambda 不能是泛型 lambda。
  9. 如果外围函数是函数模板实例或成员函数模板，和/或它是类模板成员，则模板参数必须满足以下条件：最多只能有一个可变参数包且必须位于参数列表末尾；模板参数必须命名；模板实例化参数类型不能涉及函数局部类型（扩展 lambda 闭包类型除外），也不能涉及 private 或 protected 类成员。
  10. 使用 Visual Studio 主机编译器时，外围函数必须具有外部链接，因为该编译器不支持将无外部链接函数的地址作为模板参数。
  11. 使用 Visual Studio 主机编译器时，不能在 if constexpr 代码块的主体内定义扩展 lambda。
  12. 捕获变量限制：
    • 变量只能按值捕获，不能按引用捕获；
    • 数组维度超过 7 的数组变量不能被捕获；
    • 对数组捕获，生成给主机编译器的代码会先默认初始化闭包类中的数组字段，再逐元素复制赋值，因此数组元素类型必须能在主机代码中默认构造并复制赋值；
    • 可变参数包中的函数参数不能被捕获；
    • 捕获变量的类型不能涉及函数局部类型（扩展 lambda 闭包类型除外），也不能涉及 private 或 protected 类成员；
    • 对扩展 __host__ __device__ lambda，其 operator() 的参数和返回类型也不能涉及上述不支持的类型；
    • 扩展 __host__ __device__ lambda 不支持初始化捕获；扩展 __device__ lambda 支持初始化捕获，但数组类型和 std::initializer_list 类型除外；
    • 扩展 lambda 的函数调用运算符不是 constexpr，闭包类型不是字面类型，声明中不能使用 constexpr 或 consteval；
    • 不能在扩展 lambda 内部词法嵌套的 if constexpr 块中首次隐式捕获变量，除非该变量已在块外捕获或已出现在显式捕获列表中。
  13. 同一函数中的扩展 lambda 会被编译器按出现顺序编号，该编号用于生成传给主机编译器的命名类型。因此，扩展 lambda 的存在与否、数量和相对声明顺序不能依赖 __CUDA_ARCH__ 是否定义或其具体值。
  14. 对扩展 __device__ lambda，除非 __nv_is_extended_device_lambda_with_preserved_return_type() 返回真，否则传给主机编译器的占位类型不会定义与原 lambda 完全等价的 operator()。因此，在主机代码中推导这类 lambda 的返回类型或参数类型可能得到不正确结果；在设备代码中进行此类检查则允许。该限制不适用于扩展 __host__ __device__ lambda，也不适用于返回类型被保留的扩展 __device__ lambda。
  15. 对扩展设备 lambda，operator() 参数类型只能在设备代码中进行类型检查；返回类型也只能在设备代码中检查，除非上述“保留返回类型”特征为真。
  16. 如果扩展 lambda 仿函数从主机传到设备（例如作为 __global__ 参数），lambda 函数体中涉及变量捕获的表达式必须在 __CUDA_ARCH__ 未定义和不同取值时保持一致，否则主机与设备编译时闭包布局可能不同，导致程序错误。
  17. 扩展 __device__ lambda 在传给主机编译器的代码中会替换为占位类型。该占位类型在主机代码中不提供函数指针转换运算符，但在设备代码中提供；扩展 __host__ __device__ lambda 不受此限制。
  18. 占位类型可能定义构造函数、析构函数等 C++ 特殊成员函数，因此 CUDA 前端与主机编译器对扩展 lambda 闭包类型的某些标准类型特征结果可能不同，包括 std::is_trivially_copyable、std::is_trivially_constructible、std::is_trivially_copy_constructible、std::is_trivially_move_constructible 和 std::is_trivially_destructible。不要在 __global__ 函数模板实例化或 __device__ / __constant__ / __managed__ 变量模板实例化中依赖这些类型特征的结果。

CUDA 编译器会针对上述第 1–12 类限制中的一部分情形发出诊断；第 13–17 类情形不保证生成诊断，但主机编译器可能无法编译生成的代码。

17.7.3 关于 __host__ __device__ Lambda 的说明（Notes on __host__ __device__ Lambdas）

与 __device__ lambda 不同，__host__ __device__ lambda 也能从主机代码调用。CUDA 编译器会把主机代码中定义的扩展 lambda 替换为命名占位类型；该占位类型通过间接函数调用调用原 lambda 的 operator()。间接调用可能使扩展 __host__ __device__ lambda 比隐式或显式标记为仅 __host__ 的 lambda 更难被主机编译器优化，因为后者更容易将 lambda 函数体内联到调用位置。

17.7.4 按值捕获 *this（*this Capture By Value）

当 lambda 定义在非静态类成员函数内部，并且函数体引用类成员变量时，C++11/C++14 规则要求捕获 this 指针，而不是直接捕获被引用的成员变量。如果扩展 __device__ 或 __host__ __device__ lambda 定义在主机函数中、之后在 GPU 上执行，那么当 this 指针指向主机内存时，在 GPU 上访问相应成员变量会导致运行时错误。

C++17 引入了新的 *this 捕获模式：编译器复制 *this 所表示的对象，而不是按值捕获 this 指针。CUDA 编译器支持在 __device__ 和 __global__ 函数中定义的 lambda 使用该模式，也支持在启用 --extended-lambda 时，在主机代码中定义的扩展 __device__ lambda 使用该模式。

#include <cstdio>

template <typename T>
__global__ void foo(T in) {
    printf("\n value = %d", in());
}

struct S1_t {
    int xxx;
    __host__ __device__ S1_t() : xxx(10) {}

    void doit() {
        // 捕获对象副本，而不是主机端 this 指针。
        auto lam1 = [=, *this] __device__ {
            return xxx + 1;
        };
        foo<<<1, 1>>>(lam1); // 启动成功
        cudaDeviceSynchronize();
    }
};

在主机函数中定义的未标注 lambda，以及扩展 __host__ __device__ lambda，不能使用 *this 捕获模式。在设备函数中定义的 lambda（无论是否显式标注执行空间）可以使用该模式；在 __host__ __device__ 函数中，只允许扩展 __device__ lambda 使用它。

17.7.5 补充说明（Additional Notes）

参数依赖查找（ADL）： 扩展 lambda 会被替换为占位类型，而占位类型的模板参数包含外围函数地址。这可能使更多命名空间参与参数依赖查找（ADL），导致主机编译器为某个函数调用选择错误的重载，或因候选函数歧义而编译失败。因此，如果涉及扩展 lambda 闭包类型的函数参数参与 ADL，应留意额外命名空间带来的影响。

17.8 放宽 constexpr 限制（Relaxed Constexpr，-expt-relaxed-constexpr）

默认情况下，不支持以下跨执行空间调用：

  1. 在主机代码生成阶段（即 __CUDA_ARCH__ 未定义时），主机函数调用仅带 __device__ 的 constexpr 函数。
  2. 在设备代码生成阶段（即定义了 __CUDA_ARCH__ 时），设备函数或 __global__ 函数调用仅带 __host__ 的 constexpr 函数。

实验性选项 --expt-relaxed-constexpr 可以放宽此限制。启用后，规则如下：

  1. 如果跨执行空间调用发生在要求常量求值的上下文中（例如初始化 constexpr 变量），则允许调用。

    constexpr __host__ int H(int x) { return x + 1; }
__global__ void doit() {
    constexpr int val = H(1); // 正确：需要常量求值
}

constexpr __device__ int D(int x) { return x + 1; }
int main() {
    constexpr int val = D(1); // 正确：需要常量求值
}

  2. 在其他上下文中：

    • 设备代码生成期间，如果设备代码调用仅带 __host__ 的 constexpr 函数 H，编译器会将 H 的函数体生成到设备代码中（除非该函数未被使用，或仅在常量表达式上下文中调用）。
    • 被设备代码调用的 __host__ 专用 constexpr 函数 H，必须遵守适用于 __device__ 函数的所有代码限制。不过，编译器可能不会对 H 的这些违规用法发出构建期诊断。

例如，设备端调用的 constexpr __host__ 函数不能引用主机变量，也不能使用异常（throw / catch）或 RTTI（typeid、dynamic_cast）。这些代码可能编译成功，却在运行时行为错误。

  • 主机代码生成期间，仅带 __device__ 的 constexpr 函数 D 的函数体会保留在传给主机编译器的代码中。如果 D 试图 ODR-use 命名空间作用域的设备变量，或仅带 __device__ 的非 constexpr 函数，那么主机代码调用 D 不受支持；代码可能在没有诊断的情况下编译成功，但运行结果不正确。
  • 由于这些限制和诊断缺失，调用标准 C++ 头文件中仅带 __host__ 的 constexpr 函数时应特别谨慎。其实现可能随主机平台或标准库版本而变化；如果实现 ODR-use 了主机变量或函数，代码在移植到其他平台或编译器版本时可能静默失效。

class PixelRGBA {
public:
    __device__ PixelRGBA() : r_(0), g_(0), b_(0), a_(0) {}
    __device__ PixelRGBA(unsigned char r, unsigned char g,
                         unsigned char b, unsigned char a = 255)
        : r_(r), g_(g), b_(b), a_(a) {}
private:
    unsigned char r_, g_, b_, a_;
    friend PixelRGBA operator+(const PixelRGBA&, const PixelRGBA&);
};

__device__ PixelRGBA operator+(const PixelRGBA& p1, const PixelRGBA& p2) {
    return PixelRGBA(p1.r_ + p2.r_, p1.g_ + p2.g_,
                     p1.b_ + p2.b_, p1.a_ + p2.a_);
}

__device__ void func() {
    PixelRGBA p1, p2;
    // 在此初始化 p1 和 p2。
    PixelRGBA p3 = p1 + p2;
}
