19.1 功能可用性（Feature Availability）

引入某项计算功能时，通常希望它在后续架构中继续可用。表 23 中，某功能在引入它的计算能力之后仍标记为“支持”，表示该功能在后续架构中继续提供。

某些架构引入的高度专用计算功能则不保证在后续所有计算能力中继续提供。这些功能用于加速特定操作，可能只面向部分计算能力的小版本，或者可能在未来架构中发生重大变化。

因此，同一计算能力可能对应两组功能：

  • 计算能力 #.#： 主要功能集合，设计目标是让这些功能在后续计算架构中继续可用。表 23 总结了这些功能及其可用性。
  • 计算能力 #.#a： 数量较少、用途高度专门化的功能集合，用于加速特定操作；它们不保证在后续架构中继续提供，也可能发生重大变化。具体内容列在对应计算能力的小节中。

设备代码编译时必须指定目标计算能力；代码中使用的功能必须由该目标支持。例如：

  • 以 compute_90 为编译目标时，可以使用计算能力 9.0 的功能，但不能使用计算能力 9.0a 的专用功能。
  • 以 compute_90a 为编译目标时，可以使用完整功能集合，包括 9.0 和 9.0a 的功能。

19.3 浮点标准（Floating-Point Standard）

所有计算设备均遵循 IEEE 754-2008 二进制浮点算术标准，但存在以下差异：

  • 没有可在运行时动态配置的舍入模式；不过，大多数操作支持多种 IEEE 舍入模式，并通过设备端内建函数提供这些模式。
  • 没有用于检测浮点异常是否发生的机制。所有操作都相当于始终屏蔽 IEEE-754 异常；发生异常事件时，会返回 IEEE-754 对应的屏蔽结果。因此，虽然支持 SNaN（信号 NaN）编码，但它们不会发出信号，而是按静默 NaN 处理。
  • 如果单精度浮点操作的一个或多个输入是 NaN，结果将为位模式 0x7fffffff 的静默 NaN。
  • 双精度浮点绝对值和取负操作对 NaN 的处理不符合 IEEE-754：NaN 会原样传递。
  • 为确保符合 IEEE 标准，代码应使用 -ftz=false、-prec-div=true 和 -prec-sqrt=true 编译；这些也是默认设置，具体参见 nvcc 用户手册。

无论编译选项 -ftz 如何设置：

  • 全局内存上的单精度浮点原子加法始终采用冲零（flush-to-zero）模式，相当于 FADD.F32.FTZ.RN。
  • 共享内存上的单精度浮点原子加法始终支持非规格化数，相当于 FADD.F32.RN。

根据 IEEE-754R 标准，如果 fminf()、fmin()、fmaxf() 或 fmax() 的一个输入是 NaN、另一个不是 NaN，则结果为非 NaN 的输入值。

当浮点值超出目标整数格式的表示范围时，IEEE-754 并未规定转换结果。在 CUDA 计算设备上，转换会钳位到支持范围的端点；这与 x86 架构的行为不同。整数除以零和整数溢出的行为也未由 IEEE-754 定义。CUDA 计算设备没有检测这些整数运算异常的机制；整数除以零会产生未指定、依赖具体机器的值。

关于 NVIDIA GPU 的浮点精度和 IEEE-754 符合性，原文另提供 NVIDIA 的技术说明链接：https://developer.nvidia.com/content/precision-performance-floating-point-and-ieee-754-compliance-nvidia-gpus。

19.4 计算能力 5.x（Compute Capability 5.x）

19.4.1 架构（Architecture）

一个流式多处理器（SM）包含：

  • 128 个 CUDA 核心，用于算术运算；
  • 32 个特殊功能单元，用于单精度浮点超越函数；
  • 4 个 warp 调度器。

SM 获得待执行的 warp 后，会先将它们分配给四个调度器。每次发射指令时，每个调度器都会从分配给自己的 warp 中选择一个已准备好执行的 warp，并为其发射一条指令（如果存在就绪 warp）。

SM 还具有：

  • 只读常量缓存，由所有功能单元共享，用于加速读取位于设备内存中的常量内存；
  • 24 KB 的统一 L1/纹理缓存，用于缓存全局内存读取；
  • 计算能力 5.0 设备上的 64 KB 共享内存，或计算能力 5.2 设备上的 96 KB 共享内存。

统一 L1/纹理缓存也供纹理单元使用，以实现“纹理与表面内存”一节介绍的寻址模式和数据过滤方式。

所有 SM 共享一个 L2 缓存，用于缓存对本地内存或全局内存的访问，包括临时寄存器溢出数据。应用程序可通过设备属性 l2CacheSize 查询 L2 缓存大小。缓存行为（例如读取同时缓存在统一 L1/纹理缓存和 L2，还是只缓存在 L2）可以通过加载指令的修饰符按访问进行部分配置。

19.4.2 全局内存（Global Memory）

全局内存访问始终缓存在 L2 中。

如果数据在整个内核生命周期内只读，也可以通过 __ldg() 函数读取，从而缓存在前文所述的统一 L1/纹理缓存中。当编译器检测到某些数据满足只读条件时，会使用 __ldg() 读取；但编译器不一定总能识别这一条件。将用于读取这些数据的指针同时标记为 const 和 __restrict__，可以提高编译器识别只读条件的可能性。

对于计算能力 5.0 设备，在整个内核生命周期内并非只读的数据不能缓存在统一 L1/纹理缓存中。对于计算能力 5.2 设备，这类数据默认也不缓存在统一 L1/纹理缓存中，但可以通过以下方式启用缓存：

  • 使用内联汇编，并按 PTX 参考手册指定适当的修饰符；
  • 使用编译选项 -Xptxas -dlcm=ca，此时所有读取都会缓存，除非内联汇编修饰符明确禁用缓存；
  • 使用编译选项 -Xptxas -fscm=ca，此时所有读取都会缓存，包括通过内联汇编执行、且未考虑其修饰符的读取。

通过上述任一方式启用缓存后，计算能力 5.2 设备会在统一 L1/纹理缓存中缓存全局内存读取，但线程块消耗过多 SM 寄存器文件的内核启动除外。性能分析器会报告这些例外情况。

19.4.3 共享内存（Shared Memory）

共享内存分为 32 个 bank，连续的 32 位字映射到连续的 bank。每个 bank 每个时钟周期的带宽为 32 位。

如果同一 warp 中的两个线程访问同一个 32 位字内的任意地址，即使这些地址位于同一个 bank，也不会产生 bank 冲突。对于读取，该字会广播给请求它的线程；对于写入，每个地址只会由其中一个线程执行写入，但具体由哪个线程写入并未定义。

19.5 计算能力 6.x（Compute Capability 6.x）

19.5.1 架构（Architecture）

一个 SM 包含：

  • 计算能力 6.0 设备具有 64 个 CUDA 核心，计算能力 6.1 和 6.2 设备具有 128 个 CUDA 核心，用于算术运算；
  • 计算能力 6.0 设备具有 16 个特殊功能单元，计算能力 6.1 和 6.2 设备具有 32 个，用于单精度浮点超越函数；
  • 计算能力 6.0 设备具有 2 个 warp 调度器，计算能力 6.1 和 6.2 设备具有 4 个。

SM 会先将待执行的 warp 分配给各个调度器；每次发射指令时，每个调度器都会从自己负责的 warp 中选择一个就绪 warp 发射指令。

SM 还具有共享的只读常量缓存、用于全局内存读取的统一 L1/纹理缓存，以及共享内存：

  • 计算能力 6.0 和 6.2：L1/纹理缓存 24 KB，共享内存 64 KB；
  • 计算能力 6.1：L1/纹理缓存 48 KB，共享内存 96 KB。

统一 L1/纹理缓存也供纹理单元使用，以实现“纹理与表面内存”一节介绍的寻址模式和数据过滤。所有 SM 共享的 L2 缓存用于缓存本地内存或全局内存访问，包括临时寄存器溢出数据。可通过设备属性 l2CacheSize 查询其大小。加载指令的修饰符可以按访问部分配置缓存行为。

19.5.2 全局内存（Global Memory）

全局内存的行为与计算能力 5.x 设备相同，参见 19.4.2 节。

19.5.3 共享内存（Shared Memory）

共享内存的行为与计算能力 5.x 设备相同，参见 19.4.3 节。

19.6 计算能力 7.x（Compute Capability 7.x）

19.6.1 架构（Architecture）

一个 SM 包含：

  • 64 个 FP32 核心，用于单精度算术运算；
  • 32 个 FP64 核心，用于双精度算术运算（计算能力 7.5 设备为 2 个）；
  • 64 个 INT32 核心，用于整数运算；
  • 8 个混合精度 Tensor Core，用于深度学习矩阵运算；
  • 16 个特殊功能单元，用于单精度浮点超越函数；
  • 4 个 warp 调度器。

SM 将 warp 静态分配给各个调度器。每次发射指令时，每个调度器都会为自己分配的、已准备好执行的某个 warp 发射一条指令。

SM 具有由所有功能单元共享的只读常量缓存，以及统一数据缓存和共享内存。二者总容量在 Volta 上为 128 KB，在 Turing 上为 96 KB。共享内存从统一数据缓存中划分出来，可配置为不同大小；剩余数据缓存用作 L1 缓存，并由纹理单元用于寻址和数据过滤。

19.6.2 独立线程调度（Independent Thread Scheduling）

Volta 架构引入了 warp 内的独立线程调度，使此前无法实现的 warp 内同步模式成为可能，也简化了将 CPU 代码移植到 GPU 时的修改工作。但如果开发者假定旧架构中的 warp 内线程始终同步执行，这种变化可能导致实际参与某段代码的线程集合与预期不同。

以下是需要关注的代码模式及使代码适配 Volta 的建议。

1. 将旧 warp 内建函数替换为带同步的版本

使用 warp 内建函数（例如 __shfl*、__any、__all 和 __ballot）的应用，应迁移到带 *_sync 后缀的安全同步版本。新的 warp 内建函数接收线程掩码，用于明确指定哪些 lane（warp 中的线程）必须参与操作。详情参见“Warp 投票函数”和“Warp Shuffle 函数”。

这些内建函数在 CUDA 9.0 及更高版本中可用，可以通过 CUDART_VERSION 条件编译：

#if defined(CUDART_VERSION) && CUDART_VERSION >= 9000
// 使用带 *_sync 后缀的 warp 内建函数。
#endif

这些函数并非只适用于 Volta 或 Turing，而是可用于所有架构；多数情况下，一个代码版本即可适配所有架构。不过，在 Pascal 及更早架构上，掩码中的所有线程必须在收敛状态下执行同一 warp 内建指令，而且掩码中所有线程的并集必须等于该 warp 的活动掩码。以下代码在 Volta 上有效，但在 Pascal 及更早架构上无效：

if (tid % warpSize < 16) {
    float swapped = __shfl_xor_sync(0xffffffff, val, 16);
} else {
    float swapped = __shfl_xor_sync(0xffffffff, val, 16);
}

__ballot(1) 的替代函数是 __activemask()。但 warp 内线程即使处于同一代码路径，也可能发生分歧；因此 __activemask() 和 __ballot(1) 可能只返回当前路径中的部分线程。

例如，下面的代码试图在 dataLen 不是 32 的倍数时，使用 __activemask() 处理不完整的 warp，但它是无效的：

for (int i = warpLane; i < dataLen; i += warpSize) {
    unsigned active = __activemask();
    unsigned bitPack = __ballot_sync(active, data[i] > threshold);
    if (warpLane == 0) {
        output[i / 32] = bitPack;
    }
}

CUDA 不保证 warp 只会在循环条件处分歧。如果还因其他原因发生分歧，warp 中不同线程子集可能为同一个 32 位输出元素计算出冲突结果。可使用非分歧的循环条件，并通过 __ballot_sync() 安全枚举参与阈值计算的线程：

for (int i = warpLane; i - warpLane < dataLen; i += warpSize) {
    unsigned active = __ballot_sync(0xFFFFFFFF, i < dataLen);
    if (i < dataLen) {
        unsigned bitPack = __ballot_sync(active, data[i] > threshold);
        if (warpLane == 0) {
            output[i / 32] = bitPack;
        }
    }
}

上述“发现模式”（Discovery Pattern）展示了 __activemask() 的一种有效用法。

2. 在 warp 内共享数据的步骤之间加入 __syncwarp()

如果应用使用 warp 同步代码，那么当线程通过全局内存或共享内存交换数据时，应在相关步骤之间插入新的 warp 范围屏障 __syncwarp()。不能再假定线程以锁步方式执行，也不能假定不同线程之间的读写无需同步就能在 warp 内彼此可见。

例如，在蝶形归约的每次读取和写入之间，应按需要插入 __syncwarp()，确保 warp 内数据交换有明确的同步点。

3. 确保线程块内所有未退出线程都到达屏障

虽然文档一直将 __syncthreads() 描述为同步线程块中的所有线程，但在 Pascal 及更早架构上，硬件只能在 warp 级别强制执行同步。在某些情况下，只要每个 warp 中至少有一个线程到达屏障，即使并非所有线程都执行了屏障，屏障也可能成功。

从 Volta 开始，CUDA 内建函数 __syncthreads()、PTX 指令 bar.sync 及其派生指令都按线程强制执行同步：只有线程块中所有尚未退出的线程都到达屏障后，屏障才会成功。利用旧行为的代码很可能发生死锁，必须修改以确保所有尚未退出的线程都能到达屏障。

Compute Sanitizer 提供的 racecheck 和 synccheck 工具可帮助定位违规。迁移期间，开发者也可以选择启用不支持独立线程调度的 Pascal 调度模型，详情参见“应用程序兼容性”。

19.6.3 全局内存（Global Memory）

全局内存的行为与计算能力 5.x 设备相同，参见 19.4.2 节。

19.6.4 共享内存（Shared Memory）

共享内存所占用的统一数据缓存容量可以按内核配置。Volta 架构（计算能力 7.0）的统一数据缓存为 128 KB，共享内存容量可设为 0、8、16、32、64 或 96 KB。Turing 架构（计算能力 7.5）的统一数据缓存为 96 KB，共享内存容量可设为 32 或 64 KB。

与 Kepler 不同，驱动程序会自动为每个内核配置共享内存容量，以避免共享内存占用率成为瓶颈，并尽可能允许该内核与已启动的其他内核并发执行。多数情况下，驱动程序的默认行为应能提供良好性能。

由于驱动程序不一定了解完整工作负载，应用程序有时可以提供所需共享内存配置的提示。例如，共享内存使用量很少或为零的内核，可以请求更大的共享内存划分，以便鼓励后续需要更多共享内存的内核与其并发执行。

新的 cudaFuncSetAttribute() API 可将首选共享内存容量（carveout）设为最大支持容量的百分比。Volta 的最大支持容量为 96 KB，Turing 为 64 KB。与 Kepler 引入的旧接口 cudaFuncSetCacheConfig() 相比，新接口不会将首选容量作为内核启动的硬性要求；驱动程序可在需要时选择不同配置，以保证函数可以执行或避免频繁重新配置造成的抖动。

// 设备代码
__global__ void MyKernel(...) {
    __shared__ float buffer[BLOCK_DIM];
    // ...
}

// 主机代码
int carveout = 50; // 首选最大共享内存容量的 50%
cudaFuncSetAttribute(
    MyKernel,
    cudaFuncAttributePreferredSharedMemoryCarveout,
    carveout);
MyKernel<<<gridDim, BLOCK_DIM>>>(...);

除整数百分比外，还可使用以下枚举值：

  • cudaSharedmemCarveoutDefault（-1）；
  • cudaSharedmemCarveoutMaxL1（0）；
  • cudaSharedmemCarveoutMaxShared（100）。

如果百分比无法精确对应某个受支持的容量，系统会向上取整到下一个可用容量。例如，SM 7.0 支持 0、8、16、32、64 或 96 KB；96 KB 的 50% 是 48 KB，不属于支持值，因此会向上取整为 64 KB。

计算能力 7.x 设备允许单个线程块访问全部共享内存容量：Volta 为 96 KB，Turing 为 64 KB。依赖单个线程块使用超过 48 KB 共享内存的内核具有架构特定性，必须使用动态共享内存（而不是静态大小数组），并显式调用 cudaFuncSetAttribute() 启用相应容量。

// 设备代码
__global__ void MyKernel(...) {
    extern __shared__ float buffer[];
    // ...
}

// 主机代码：Volta 示例，96 KB
int maxbytes = 98304;
cudaFuncSetAttribute(
    MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel<<<gridDim, blockDim, maxbytes>>>(...);

19.7 计算能力 8.x（Compute Capability 8.x）

19.7.1 架构（Architecture）

一个 SM 包含：

  • 计算能力 8.0 设备具有 64 个 FP32 核心；8.6、8.7 和 8.9 设备具有 128 个；
  • 计算能力 8.0 设备具有 32 个 FP64 核心；8.6、8.7 和 8.9 设备具有 2 个；
  • 64 个 INT32 核心，用于整数运算；
  • 对于计算能力 8.0、8.6 和 8.7，具有 4 个第三代混合精度 Tensor Core，支持 FP16、__nv_bfloat16、TF32、子字节及 FP64 矩阵运算；
  • 对于计算能力 8.9，具有 4 个第四代混合精度 Tensor Core，支持 FP8、FP16、__nv_bfloat16、TF32、子字节及 FP64；
  • 16 个特殊功能单元，用于单精度浮点超越函数；
  • 4 个 warp 调度器。

SM 将 warp 静态分配给各调度器；每次发射指令时，各调度器会为自己负责的就绪 warp 发射一条指令。

SM 具有共享的只读常量缓存，以及统一数据缓存和共享内存：计算能力 8.0 和 8.7 的总容量为 192 KB，计算能力 8.6 和 8.9 的总容量为 128 KB。共享内存从统一数据缓存中划分出来；剩余部分作为 L1 缓存，也供纹理单元用于寻址和数据过滤。

19.7.2 全局内存（Global Memory）

全局内存的行为与计算能力 5.x 设备相同，参见 19.4.2 节。

19.7.3 共享内存（Shared Memory）

与 Volta 类似，统一数据缓存中分配给共享内存的容量可按内核配置。Ampere 架构的统一数据缓存容量如下：

  • 计算能力 8.0 和 8.7：192 KB；
  • 计算能力 8.6 和 8.9：128 KB。

计算能力 8.0 和 8.7 的共享内存容量可设为 0、8、16、32、64、100、132 或 164 KB；计算能力 8.6 和 8.9 可设为 0、8、16、32、64 或 100 KB。

应用程序可通过 cudaFuncSetAttribute() 设置首选 carveout：

cudaFuncSetAttribute(
    kernel_name,
    cudaFuncAttributePreferredSharedMemoryCarveout,
    carveout);

carveout 可以是最大支持共享内存容量的整数百分比（计算能力 8.0/8.7 为 164 KB，8.6/8.9 为 100 KB），也可以是 cudaSharedmemCarveoutDefault、cudaSharedmemCarveoutMaxL1 或 cudaSharedmemCarveoutMaxShared。按百分比设置时，容量向上取整到最近的受支持值。例如，计算能力 8.0 的 50% 会映射到 100 KB，而不是 82 KB。该设置只是提示；如有需要，驱动程序可以选择其他配置。

计算能力 8.0 和 8.7 的单个线程块最多可访问 163 KB 共享内存；计算能力 8.6 和 8.9 的单个线程块最多可访问 99 KB。单个线程块使用超过 48 KB 共享内存的内核必须使用动态共享内存，而不是静态大小数组，并通过 cudaFuncSetAttribute() 设置 cudaFuncAttributeMaxDynamicSharedMemorySize 显式启用。

注意：每个线程块可用的最大共享内存小于每个 SM 可划分的最大共享内存。未提供给线程块使用的 1 KB 共享内存保留给系统使用。

19.8 计算能力 9.0（Compute Capability 9.0）

19.8.1 架构（Architecture）

一个 SM 包含：

  • 128 个 FP32 核心，用于单精度算术运算；
  • 64 个 FP64 核心，用于双精度算术运算；
  • 64 个 INT32 核心，用于整数运算；
  • 4 个第四代混合精度 Tensor Core，支持 FP8 输入格式 E4M3 或 E5M2、FP16、__nv_bfloat16、TF32、INT8 和 FP64 矩阵运算，并支持稀疏性；
  • 16 个特殊功能单元，用于单精度浮点超越函数；
  • 4 个 warp 调度器。

SM 将 warp 静态分配给各调度器。每次发射指令时，各调度器会为自己负责的就绪 warp 发射一条指令。

SM 具有共享的只读常量缓存，以及统一数据缓存和共享内存。计算能力 9.0 设备的统一数据缓存与共享内存总容量为 256 KB，约为 NVIDIA Ampere 架构 192 KB 容量的 1.33 倍。共享内存从统一数据缓存中划分出来；剩余部分作为 L1 缓存，也供纹理单元实现寻址和数据过滤。

19.8.2 全局内存（Global Memory）

全局内存的行为与计算能力 5.x 设备相同，参见 19.4.2 节。

19.8.3 共享内存（Shared Memory）

与 NVIDIA Ampere 架构类似，统一数据缓存中分配给共享内存的容量可按内核配置。H100 Tensor Core GPU（计算能力 9.0）的统一数据缓存为 256 KB，共享内存容量可设为 0、8、16、32、64、100、132、164、196 或 228 KB。

应用程序可以配置首选共享内存容量（carveout）。计算能力 9.0 的单个线程块最多可访问 227 KB 共享内存。依赖单个线程块使用超过 48 KB 共享内存的内核具有架构特定性，必须使用动态共享内存，而不是静态大小数组，并显式调用 cudaFuncSetAttribute() 设置 cudaFuncAttributeMaxDynamicSharedMemorySize。

每个线程块可用的最大共享内存小于每个 SM 可划分的最大容量；未提供给线程块的 1 KB 共享内存保留给系统使用。

19.8.4 加速专用计算的功能（Features Accelerating Specialized Computations）

NVIDIA Hopper 架构提供了用于加速矩阵乘加（MMA）计算的功能，包括：

  • MMA 指令的异步执行；
  • 作用于跨越一个 warp-group 的大型矩阵的 MMA 指令；
  • 在 warp-group 之间动态重新分配寄存器容量，以支持更大的矩阵；
  • 直接从共享内存访问操作数矩阵。

这组功能只能通过内联 PTX 在 CUDA 编译工具链中使用。原文强烈建议应用程序通过 cuBLAS、cuDNN 或 cuFFT 等 CUDA-X 库使用这些复杂功能；设备内核则建议通过 CUTLASS 使用。CUTLASS 是一组 CUDA C++ 模板抽象，可用于在 CUDA 的不同层级和规模上实现高性能矩阵乘法（GEMM）及相关计算。

19.9 计算能力 10.0（Compute Capability 10.0）

19.9.1 架构（Architecture）

一个 SM 包含：

  • 128 个 FP32 核心，用于单精度算术运算；
  • 64 个 FP64 核心，用于双精度算术运算；
  • 64 个 INT32 核心，用于整数运算；
  • 4 个第五代混合精度 Tensor Core，支持 FP8 输入格式 E4M3 或 E5M2、FP16、__nv_bfloat16、TF32、INT8 和 FP64 矩阵运算，并支持稀疏性；
  • 16 个特殊功能单元，用于单精度浮点超越函数；
  • 4 个 warp 调度器。

SM 将 warp 静态分配给各调度器；每次发射指令时，各调度器会为自己负责的就绪 warp 发射一条指令。

SM 具有共享的只读常量缓存，以及容量为 256 KB 的统一数据缓存和共享内存。共享内存从统一数据缓存中划分出来；剩余部分作为 L1 缓存，也供纹理单元用于寻址和数据过滤。

19.9.2 全局内存（Global Memory）

全局内存的行为与计算能力 5.x 设备相同，参见 19.4.2 节。

19.9.3 共享内存（Shared Memory）

统一数据缓存中分配给共享内存的容量可按内核配置，其行为与计算能力 9.0 相同。计算能力 10.0 设备的统一数据缓存为 256 KB，共享内存容量可设为 0、8、16、32、64、100、132、164、196 或 228 KB。

应用程序可以配置首选 carveout。计算能力 10.0 的单个线程块最多可访问 227 KB 共享内存。单个线程块使用超过 48 KB 共享内存的内核必须使用动态共享内存，而不是静态大小数组，并通过 cudaFuncSetAttribute() 设置 cudaFuncAttributeMaxDynamicSharedMemorySize 显式启用。

每个线程块可用的最大共享内存小于每个 SM 可划分的最大容量；未提供给线程块的 1 KB 共享内存保留给系统使用。

19.9.4 加速专用计算的功能（Features Accelerating Specialized Computations）

NVIDIA Blackwell 架构扩展了 NVIDIA Hopper 架构中用于加速矩阵乘加（MMA）的功能。这些功能只能通过内联 PTX 在 CUDA 编译工具链中使用。

原文建议应用程序通过 cuBLAS、cuDNN 或 cuFFT 等 CUDA-X 库使用这些复杂功能，并建议设备内核通过 CUTLASS 使用这些功能。CUTLASS 提供用于实现高性能 GEMM 及相关计算的 CUDA C++ 模板抽象。

19.10 计算能力 12.0（Compute Capability 12.0）

19.10.1 架构（Architecture）

一个 SM 包含：

  • 128 个 FP32 核心；
  • 2 个 FP64 核心；
  • 64 个 INT32 核心；
  • 第五代混合精度 Tensor Core，支持 FP8 输入格式 E4M3 或 E5M2、FP16、__nv_bfloat16、TF32、INT8 和 FP64 矩阵运算，并支持稀疏性；
