第八章 性能指南（Performance Guidelines）

8.1 整体性能优化策略（Overall Performance Optimization Strategies）

性能优化围绕四项基本策略展开：

  • 尽可能增加并行执行，以充分利用计算资源；
  • 优化内存使用，以获得最高内存吞吐量；
  • 优化指令使用，以获得最高指令吞吐量；
  • 尽量减少内存抖动（memory thrashing）。

对于应用程序的某个部分，哪种策略能带来最大的性能提升，取决于该部分的性能瓶颈。例如，如果某个内核主要受内存访问限制，那么优化它的指令使用通常不会带来显著的性能提升。

因此，优化工作应持续依据测量结果和性能瓶颈监控来指导，例如使用 CUDA profiler。还可以将某个内核的浮点运算吞吐量或内存吞吐量（选择更有意义的一项）与设备对应的理论峰值吞吐量进行比较，从而判断该内核还有多少优化空间。

8.2 最大化利用率（Maximize Utilization）

为了最大化利用率，应用程序应当尽可能暴露并行性，并将这些并行工作高效映射到系统的不同组成部分，使它们在大部分时间里都保持繁忙。

8.2.1 应用程序层面（Application Level）

在较高层面上，应用程序应使用异步函数调用和执行流，最大化主机、设备以及连接主机与设备的总线之间的并行执行，详见“异步并发执行”。

应将最适合每类处理器的工作分配给它：串行工作交给主机， 并行工作交给设备。

对于并行工作，当算法中的某些线程需要同步并共享数据，从而打断并行执行时，通常有两种情况：

  • 如果这些线程属于同一个线程块，应使用 __syncthreads()，并在同一次内核调用中通过共享内存交换数据。
  • 如果这些线程属于不同线程块，则必须通过全局内存交换数据，并使用两次独立的内核调用：一次写入全局内存，另一次从全局内存读取。

第二种方式效率较低，因为它增加了内核调用开销和全局内存流量。因此，应尽可能按照 CUDA 编程模型重新组织算法，让需要线程间通信的计算尽可能在同一个线程块内完成。

8.2.2 设备层面（Device Level）

在更低的层面上，应用程序应最大化同一设备中不同多处理器之间的并行执行。

一个设备可以并发执行多个内核，因此也可以通过使用执行流来启用足够多的内核并发执行，从而提高利用率，详见“异步并发执行”。

8.2.3 多处理器层面（Multiprocessor Level）

在更低的层面上，应用程序应最大化多处理器内部不同功能单元之间的并行执行。

如“硬件多线程”一节所述，GPU 多处理器主要依靠线程级并行来最大化功能单元的利用率。因此，利用率与驻留 warp 的数量直接相关。每次发出指令时，warp 调度器都会选择一条已准备好执行的指令。该指令可以是同一 warp 中另一条相互独立的指令（利用指令级并行），但更常见的情况是选择另一个 warp 的指令（利用线程级并行）。

如果选中了就绪指令，就会将其发给该 warp 的活动线程。一个 warp 从发出一条指令到能够执行下一条指令所需的时钟周期数称为延迟（latency）。当所有 warp 调度器在延迟期间的每个时钟周期，都始终有某个 warp 的指令可供发出时，就实现了充分利用率；换言之，延迟被完全“隐藏”了。

隐藏 \(L\) 个时钟周期的延迟所需的指令数，取决于这些指令各自的吞吐量，详见“算术指令”。如果假设指令具有最大吞吐量，则所需指令数为：

  • 对于计算能力为 5.x、6.1、6.2、7.x 和 8.x 的设备，需要 \(4L\) 条指令。这些设备的多处理器每个时钟周期可为四个 warp 各发出一条指令。
  • 对于计算能力为 6.0 的设备，需要 \(2L\) 条指令，因为这些设备每个时钟周期发出的两条指令分别属于两个不同的 warp。

warp 无法执行下一条指令的最常见原因，是该指令的输入操作数尚未就绪。

如果所有输入操作数都位于寄存器中，延迟通常来自寄存器依赖，也就是某些输入操作数由尚未执行完毕的前序指令写入。此时，延迟等于前序指令的执行时间，warp 调度器必须在这段时间里调度其他 warp 的指令。执行时间取决于指令类型。例如，在计算能力为 7.x 的设备上，大多数算术指令通常需要 4 个时钟周期。这意味着，在假设 warp 以最大吞吐量执行指令的情况下，每个多处理器需要 16 个活动 warp（4 个周期 × 4 个 warp 调度器）来隐藏算术指令延迟；如果 warp 内部存在指令级并行性，则所需 warp 数量可以更少，因为同一个 warp 中的多条独立指令可以连续发出。

如果某个输入操作数位于片外内存，延迟就会高得多，通常达到数百个时钟周期。隐藏这种高延迟所需的 warp 数量，取决于内核代码及其指令级并行程度。一般来说，没有片外内存操作数的指令（通常是算术指令）与具有片外内存操作数的指令之比越低，就需要越多 warp。这个比值通常称为程序的算术强度（arithmetic intensity）。

warp 尚未就绪的另一个原因，是它正在等待某个内存栅栏（参见“内存栅栏函数”）或同步点（参见“同步函数”）。同步点可能迫使多处理器空闲，因为越来越多的 warp 会等待同一线程块中其他 warp 完成同步点之前的指令。如果一个多处理器上能够同时驻留多个线程块，就有助于减少这种空闲，因为不同线程块中的 warp 不需要在同一个同步点相互等待。

对于某个内核调用，每个多处理器上能够驻留的线程块和 warp 数量，取决于调用的执行配置、该多处理器的内存资源，以及内核的资源需求，详见“硬件多线程”。使用 --ptxas-options=-v 选项编译时，编译器会报告寄存器和共享内存的使用量。

一个线程块所需的共享内存总量，等于静态分配的共享内存与动态分配的共享内存之和。

内核使用的寄存器数量会显著影响可驻留 warp 的数量。例如，对于计算能力为 6.x 的设备，如果内核使用 64 个寄存器、每个线程块有 512 个线程，且只需要很少的共享内存，那么多处理器上可以驻留两个线程块（即 32 个 warp），因为它们需要的寄存器总数 \(2\times512\times64\) 正好等于多处理器可用寄存器数量。但如果内核多使用一个寄存器，就只能驻留一个线程块（即 16 个 warp），因为两个线程块将需要 \(2\times512\times65\) 个寄存器，超过可用数量。

因此，编译器会尝试尽量减少寄存器使用量，同时避免寄存器溢出（参见“设备内存访问”）并尽量减少指令数。可以使用编译器选项 maxrregcount、__launch_bounds__() 限定符或 __maxnreg__() 限定符控制寄存器使用量。

寄存器文件由 32 位寄存器组成。因此，存储在寄存器中的每个变量至少需要一个 32 位寄存器；例如，一个 double 变量需要两个 32 位寄存器。

对于给定内核，执行配置对性能的影响通常取决于内核代码，因此建议通过实验确定合适的配置。应用程序还可以根据寄存器文件大小、共享内存大小、设备计算能力、多处理器数量和内存带宽来参数化执行配置；这些属性都可以通过运行时 API 查询。

每个线程块的线程数应尽量选择为 warp 大小的整数倍，以避免 warp 中线程不足造成计算资源浪费。

8.2.3.1 占用率计算器（Occupancy Calculator）

CUDA 提供多个 API，帮助程序员根据寄存器和共享内存需求选择线程块大小和集群大小。

  • 占用率计算 API cudaOccupancyMaxActiveBlocksPerMultiprocessor 可以根据线程块大小和内核的共享内存用量预测占用率。它以每个多处理器上可并发驻留的线程块数量表示占用率。将该值乘以每个线程块中的 warp 数，可得到每个多处理器上的并发 warp 数；再除以每个多处理器的最大 warp 数，即可得到百分比占用率。
  • 基于占用率的启动配置 API cudaOccupancyMaxPotentialBlockSize 和 cudaOccupancyMaxPotentialBlockSizeVariableSMem，会使用启发式方法计算能够实现最大多处理器占用率的执行配置。
  • 占用率计算 API cudaOccupancyMaxActiveClusters 可以根据集群大小、线程块大小和内核共享内存用量预测占用率。它报告系统中 GPU 对给定集群大小可同时活动的最大集群数。

以下示例计算 MyKernel 的占用率，并以并发 warp 数与每个多处理器最大 warp 数的比值报告占用率。

// 设备代码
__global__ void MyKernel(int *d, int *a, int *b)
{
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    d[idx] = a[idx] * b[idx];
}

// 主机代码
int main()
{
    int numBlocks;   // 以活动线程块数表示的占用率
    int blockSize = 32;

    // 将占用率换算为 warp 数所需的变量
    int device;
    cudaDeviceProp prop;
    int activeWarps;
    int maxWarps;

    cudaGetDevice(&device);
    cudaGetDeviceProperties(&prop, device);

    cudaOccupancyMaxActiveBlocksPerMultiprocessor(
        &numBlocks, MyKernel, blockSize, 0);

    activeWarps = numBlocks * blockSize / prop.warpSize;
    maxWarps = prop.maxThreadsPerMultiProcessor / prop.warpSize;

    std::cout << "Occupancy: "
              << (double)activeWarps / maxWarps * 100
              << "%" << std::endl;

    return 0;
}

以下示例根据用户输入，使用占用率启动配置器来配置 MyKernel 的启动参数。

// 设备代码
__global__ void MyKernel(int *array, int arrayCount)
{
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    if (idx < arrayCount) {
        array[idx] *= array[idx];
    }
}

// 主机代码
int launchMyKernel(int *array, int arrayCount)
{
    int blockSize;    // 启动配置器返回的线程块大小
    int minGridSize;  // 对完整设备启动实现最大占用率所需的最小网格大小
    int gridSize;     // 根据输入规模确定的实际网格大小

    cudaOccupancyMaxPotentialBlockSize(
        &minGridSize, &blockSize, (void*)MyKernel, 0, arrayCount);

    // 根据数组大小向上取整
    gridSize = (arrayCount + blockSize - 1) / blockSize;

    MyKernel<<<gridSize, blockSize>>>(array, arrayCount);
    cudaDeviceSynchronize();

    // 如有需要，可使用 cudaOccupancyMaxActiveBlocksPerMultiprocessor
    // 计算占用率。
    return 0;
}

以下示例展示如何使用集群占用率 API，查找指定集群大小下的最大活动集群数。本例使用大小为 2 的集群，每个线程块包含 128 个线程。

从计算能力 9.0 开始，集群大小 8 具有向前兼容性；但如果 GPU 硬件或 MIG 配置过小，无法支持 8 个多处理器，则最大集群大小会降低。因此，建议在启动集群内核前，先通过 cudaOccupancyMaxPotentialClusterSize 查询最大集群大小。

{
    cudaLaunchConfig_t config = {0};
    config.gridDim = number_of_blocks;
    config.blockDim = 128;  // 每个线程块 128 个线程
    config.dynamicSmemBytes = dynamic_shared_memory_size;

    cudaLaunchAttribute attribute[1];
    attribute[0].id = cudaLaunchAttributeClusterDimension;
    attribute[0].val.clusterDim.x = 2; // 集群大小为 2
    attribute[0].val.clusterDim.y = 1;
    attribute[0].val.clusterDim.z = 1;
    config.attrs = attribute;
    config.numAttrs = 1;

    int max_cluster_size = 0;
    cudaOccupancyMaxPotentialClusterSize(
        &max_cluster_size, (void *)kernel, &config);

    int max_active_clusters = 0;
    cudaOccupancyMaxActiveClusters(
        &max_active_clusters, (void *)kernel, &config);

    std::cout << "Max Active Clusters of size 2: "
              << max_active_clusters << std::endl;
}

CUDA Nsight Compute 用户界面还提供独立的占用率计算器和启动配置器实现，位于 <CUDA_Toolkit_Path>/include/cuda_occupancy.h，可用于不依赖 CUDA 软件栈的场景。Nsight Compute 版本的占用率计算器尤其适合作为学习工具，因为它能够直观显示线程块大小、每线程寄存器数和每线程共享内存等参数变化对占用率的影响。

8.3 最大化内存吞吐量（Maximize Memory Throughput）

要最大化应用程序的整体内存吞吐量，第一步是尽量减少低带宽的数据传输。

这意味着应尽量减少主机与设备之间的数据传输（详见“主机与设备之间的数据传输”），因为它们的带宽远低于全局内存与设备之间的数据传输带宽。

同样，也应尽量减少全局内存与设备之间的数据传输，并尽可能利用片上内存：共享内存和缓存，包括计算能力为 2.x 及以上设备可用的 L1、L2 缓存，以及所有设备都可用的纹理缓存和常量缓存。

共享内存相当于由用户管理的缓存：应用程序显式分配并访问它。一个典型的编程模式是先将来自设备内存的数据暂存到共享内存中。也就是说，线程块中的每个线程会：

  • 将数据从设备内存加载到共享内存；
  • 与线程块中的其他线程同步，以确保每个线程都能安全读取由其他线程填充的共享内存位置；
  • 在共享内存中处理数据。

8.3 最大化内存吞吐量（Maximize Memory Throughput）

为了最大化应用程序整体内存吞吐量，首先应尽量减少低带宽的数据传输。这意味着要尽量减少主机与设备之间的数据传输，因为它们的带宽远低于全局内存与设备之间的数据传输带宽。

同样，也应尽量减少全局内存与设备之间的数据传输，并尽可能利用片上内存：共享内存和缓存，包括计算能力为 2.x 及以上设备可用的 L1、L2 缓存，以及所有设备都可用的纹理缓存和常量缓存。

共享内存相当于由用户管理的缓存：应用程序显式分配并访问它。典型模式是先将设备内存中的数据暂存到共享内存中。通常，线程块中的每个线程会：

  1. 将数据从设备内存加载到共享内存；
  2. 与线程块中的其他线程同步，确保可以安全读取由其他线程填充的共享内存位置；
  3. 在共享内存中处理数据；
  4. 如有必要，再次同步，以确保共享内存已更新为计算结果；
  5. 将结果写回设备内存。

对于某些应用程序（例如全局内存访问模式依赖于数据的应用程序），传统的硬件管理缓存可能更适合利用数据局部性。对于计算能力为 7.x、8.x 和 9.0 的设备，L1 缓存和共享内存使用同一片片上内存；每次内核调用可以配置其中多少容量用于 L1、多少用于共享内存。

根据不同类型内存的访问模式，内核的内存访问吞吐量可能相差一个数量级。因此，提升内存吞吐量的下一步，是按照“设备内存访问”中介绍的最佳访问模式组织内存访问。这一点对全局内存尤其重要，因为与片上带宽和算术指令吞吐量相比，全局内存带宽较低，所以非最优的全局内存访问通常会显著影响性能。

8.3.1 主机与设备之间的数据传输（Data Transfer between Host and Device）

应用程序应尽量减少主机与设备之间的数据传输。一种方法是将更多代码从主机移到设备，即使这意味着某些内核暴露的并行性不足，无法让设备以最高效率运行。

中间数据结构可以在设备内存中创建、由设备处理，并在整个过程中从不映射到主机或复制回主机内存。

此外，每次传输都存在固定开销，因此将许多小型传输合并为一次大型传输，通常总是比逐次执行小型传输性能更好。

在具有前端总线的系统上，使用页锁定主机内存可以提升主机与设备之间的数据传输性能，详见“页锁定主机内存”。

另外，使用映射的页锁定内存时，无需分配设备内存，也无需显式地在主机与设备内存之间复制数据。每次内核访问映射内存时，数据传输都会隐式发生。为了获得最高性能，这些内存访问必须像全局内存访问一样实现合并。如果访问已合并，且映射内存只被读取或写入一次，那么与主机和设备之间的显式复制相比，使用映射的页锁定内存可能更有优势。

在设备内存与主机内存物理上相同的集成系统中，主机与设备之间的复制是多余的，应改用映射的页锁定内存。可以检查设备属性 integrated 是否等于 1，查询设备是否为集成设备。

8.3.2 设备内存访问（Device Memory Accesses）

访问可寻址内存（即全局、本地、共享、常量或纹理内存）的指令，可能需要重复发出多次，具体取决于 warp 内各线程的内存地址分布。地址分布对指令吞吐量的影响取决于内存类型，下面各节将分别介绍。

例如，对于全局内存，一般来说，地址越分散，吞吐量下降得越明显。

全局内存（Global Memory）

全局内存位于设备内存中，设备内存通过 32、64 或 128 字节的内存事务进行访问。这些事务必须自然对齐：只有起始地址是事务大小整数倍的 32、64 或 128 字节对齐片段，才能通过相应事务读取或写入。

当一个 warp 执行访问全局内存的指令时，硬件会根据每个线程访问的字大小，以及各线程地址的分布，将 warp 内线程的访问合并为一个或多个内存事务。

一般而言，需要的事务越多，除线程实际访问的数据外，还会传输越多未使用的数据，从而降低指令吞吐量。例如，如果每个线程访问 4 字节数据，却为每个线程生成一次 32 字节内存事务，那么吞吐量会降低到原来的八分之一。

所需事务数量及其对吞吐量的影响取决于设备计算能力。有关不同计算能力下全局内存访问的处理方式，详见“计算能力 5.x”“计算能力 6.x”“计算能力 7.x”“计算能力 8.x”和“计算能力 9.0”。

为了最大化全局内存吞吐量，应尽可能提高访问合并程度：

  • 按照目标设备计算能力所对应的最佳访问模式组织内存访问；
  • 使用满足下文“大小与对齐要求”的数据类型；
  • 在某些情况下对数据进行填充，例如按照下文“二维数组”一节的方式处理二维数组。
大小与对齐要求（Size and Alignment Requirement）

全局内存指令支持读取或写入大小为 1、2、4、8 或 16 字节的数据。只有当数据类型大小为这些值之一，且数据自然对齐（地址是其大小的整数倍）时，对全局内存数据的访问才会编译为单条全局内存指令。

如果不满足大小与对齐要求，访问会被编译成多条指令，并采用交错的访问模式，导致这些指令无法充分合并。因此，建议对驻留在全局内存中的数据使用满足上述要求的数据类型。

内置向量类型会自动满足对齐要求。对于结构体，可以使用 __align__(8) 或 __align__(16) 对齐说明符强制编译器满足大小与对齐要求，例如：

struct __align__(8) {
    float x;
    float y;
};

struct __align__(16) {
    float x;
    float y;
    float z;
};

任何位于全局内存中的变量地址，或由 Driver/Runtime API 的内存分配函数返回的地址，至少都按 256 字节对齐。

读取未自然对齐的 8 字节或 16 字节数据会产生错误结果（偏差可能达到若干个字），因此必须特别注意这些类型的变量或数组起始地址的对齐。一个容易忽略的情况是自定义全局内存分配方案：程序不再为多个数组分别调用 cudaMalloc() 或 cuMemAlloc()，而是一次分配一个大内存块，再将其划分为多个数组。此时，每个数组的起始地址都相对整个内存块起始地址产生偏移，必须确保各数组仍然满足对齐要求。

二维数组（Two-Dimensional Arrays）

一种常见的全局内存访问模式是：索引为 \((t_x,t_y)\) 的每个线程，访问宽度为 width、基地址为 BaseAddress、元素类型为 type* 的二维数组中的一个元素：

\[ \text{BaseAddress}+\text{width}\times t_y+t_x \]

要让这些访问充分合并，线程块的宽度和数组的宽度都应是 warp 大小的整数倍。

因此，如果数组宽度不是 warp 大小的整数倍，将数组实际分配为宽度向上取整到最近的 warp 大小整数倍，并对每行进行适当填充，通常会更高效。参考手册介绍的 cudaMallocPitch()、cuMemAllocPitch() 及相关内存复制函数，可以帮助程序员以不依赖具体硬件的方式分配满足这些约束的数组。

本地内存（Local Memory）

如“变量内存空间说明符”一节所述，本地内存只会用于某些自动变量。编译器可能将以下自动变量放入本地内存：

  • 编译器无法确定其索引是否为常量的数组；
  • 会占用过多寄存器空间的大型结构体或数组；
  • 当内核使用的寄存器超过可用数量时，被溢出到本地内存的变量（即寄存器溢出）。

使用 -ptx 或 -keep 选项编译后检查 PTX 汇编代码，可以判断变量在初始编译阶段是否被放入本地内存：这类变量会使用 .local 声明，并通过 ld.local 和 st.local 指令访问。即使最初没有被放入本地内存，后续编译阶段仍可能因目标架构的寄存器资源不足而作出不同决定。可以使用 cuobjdump 检查 cubin 对象以确认这一点。使用 --ptxas-options=-v 编译时，编译器还会报告每个内核的本地内存总使用量（lmem）。某些数学函数的实现路径也可能访问本地内存。

本地内存位于设备内存中，因此其访问延迟高、带宽低，与全局内存类似，也受到相同的内存合并要求约束。不过，本地内存的组织方式使连续的 32 位字对应连续递增的线程 ID。因此，只要 warp 中所有线程访问相同的相对地址（例如数组中的同一索引或结构体中的同一成员），访问就可以充分合并。

从计算能力 5.x 开始，设备的本地内存访问与全局内存访问一样，始终缓存在 L2 中。

共享内存（Shared Memory）

共享内存在芯片上，因此其带宽远高于本地内存或全局内存，延迟也低得多。

为了获得高带宽，共享内存被划分为大小相同、可并行访问的存储模块，称为存储体（bank）。如果一次内存请求涉及的 \(n\) 个地址分别落在 \(n\) 个不同存储体中，就可以同时处理，整体带宽可达到单个存储体带宽的 \(n\) 倍。

如果一次请求中的两个地址落在同一个存储体中，就会发生存储体冲突（bank conflict），访问必须串行化。硬件会将存在冲突的请求拆分成若干个互不冲突的请求；吞吐量会按拆分后的请求数量相应下降。如果原始请求最终拆分为 \(n\) 个独立请求，就称其发生了 \(n\) 路存储体冲突。

为了获得最佳性能，需要理解内存地址如何映射到各存储体，并据此安排内存请求，以尽量减少冲突。不同计算能力设备的具体映射方式见相应的“计算能力”章节。

常量内存（Constant Memory）

常量内存空间位于设备内存中，并由常量缓存缓存。

如果一个请求包含多个不同的内存地址，该请求会拆分成与不同地址数量相同的独立请求，吞吐量会按独立请求数量相应下降。若缓存命中，拆分后的请求会以常量缓存的吞吐量处理；若缓存未命中，则以设备内存的吞吐量处理。

纹理与表面内存（Texture and Surface Memory）

纹理内存和表面内存位于设备内存中，并由纹理缓存缓存。因此，纹理读取或表面读取只有在缓存未命中时才会产生一次设备内存读取；若缓存命中，则只需从纹理缓存读取一次。

纹理缓存针对二维空间局部性进行了优化。因此，同一 warp 中读取二维坐标彼此接近的纹理或表面地址的线程，可以获得最佳性能。纹理缓存也针对恒定延迟的流式读取设计：缓存命中能够减少 DRAM 带宽需求，但不会降低读取延迟。

通过纹理或表面读取设备内存，相较于从全局内存或常量内存读取，可能具有以下优势：

  • 如果读取模式不符合全局内存或常量内存获得高性能所需的访问模式，但纹理读取或表面读取仍具有局部性，就可能获得更高带宽；
  • 地址计算由内核之外的专用单元执行；
  • 一次操作可以将打包数据分发到多个独立变量；
  • 8 位和 16 位整数输入数据可以选择转换为 32 位浮点数，范围为 \([0.0,1.0]\) 或 \([-1.0,1.0]\)，详见“纹理内存”。

8.4 最大化指令吞吐量（Maximize Instruction Throughput）

为了最大化指令吞吐量，应用程序应：

  • 尽量减少低吞吐量算术指令的使用。当不会影响最终结果时，可以用精度换取速度，例如用内建函数替代常规函数（内建函数见“内建函数”）、使用单精度而非双精度，或将非规格化数刷新为零；
  • 尽量减少控制流指令引起的 warp 分支发散，详见“控制流指令”；
  • 减少指令数量，例如尽可能消除同步点（详见“同步指令”），或使用受限指针 __restrict__。

本节中的吞吐量以每个多处理器每个时钟周期执行的操作数表示。对于大小为 32 的 warp，一条指令对应 32 次操作。因此，如果每个时钟周期的操作数为 \(N\)，则指令吞吐量为每个时钟周期 \(N/32\) 条指令。

这里列出的吞吐量均针对单个多处理器。要获得整台设备的吞吐量，需要乘以设备中的多处理器数量。

单精度浮点除法（Single-Precision Floating-Point Division）

与除法运算符相比，__fdividef(x, y)（参见“内建函数”）可以更快地执行单精度浮点除法。

单精度浮点倒数平方根（Single-Precision Floating-Point Reciprocal Square Root）

为了保留 IEEE-754 语义，只有当倒数和平方根都允许使用近似计算时（即同时使用 -prec-div=false 和 -prec-sqrt=false），编译器才可以将 1.0/sqrtf() 优化为 rsqrtf()。因此，如果需要倒数平方根，建议直接调用 rsqrtf()。

单精度浮点平方根（Single-Precision Floating-Point Square Root）

单精度浮点平方根采用“先计算倒数平方根，再计算倒数”的方式实现，而不是“先计算倒数平方根，再进行乘法”。这样可以确保在输入为 0 或无穷大时得到正确结果。

正弦与余弦：参数约化（Sine and Cosine: Argument Reduction）

sinf(x)、cosf(x)、tanf(x)、sincosf(x) 及其对应的双精度指令，计算成本都比较高；当参数 \(x\) 的绝对值较大时，开销会更高。

更具体地说，参数约化代码（实现见“数学函数”）包含两条执行路径，分别称为快速路径和慢速路径。参数绝对值足够小时，会使用快速路径，主要由少量乘加运算组成。参数绝对值较大时，会使用慢速路径；为了保证整个参数范围内的结果正确，需要进行较长的计算。

目前，单精度三角函数在参数绝对值小于 105615.0f 时选择快速路径；双精度三角函数在参数绝对值小于 2147483648.0 时选择快速路径。

慢速路径比快速路径需要更多寄存器。为了降低寄存器压力，部分中间变量会存入本地内存；但本地内存的高延迟和低带宽可能影响性能。目前，单精度函数使用 28 字节本地内存，双精度函数使用 44 字节。不过，确切用量可能随版本变化。

由于慢速路径计算量较大，并且会使用本地内存，因此当需要慢速参数约化时，这些三角函数的吞吐量会比快速路径低一个数量级。

整数算术（Integer Arithmetic）

整数除法和取模运算成本较高，编译后最多可能需要 20 条指令。在某些情况下，可以用位运算替代：如果 \(n\) 是 2 的幂，那么：

\[ i/n \equiv i \gg \log_2(n) \]
\[ i \% n \equiv i \mathbin{\&}(n-1) \]

如果 \(n\) 是字面量，编译器会执行这些转换。

__brev 和 __popc 分别映射为单条指令；__brevll 和 __popcll 则需要少量指令。__[u]mul24 是旧式内建函数，现已没有继续使用的理由。

半精度算术（Half Precision Arithmetic）

为了提高 16 位浮点加法、乘法或乘加的性能，建议在半精度计算中使用 half2 数据类型，在 __nv_bfloat16 精度计算中使用 __nv_bfloat162。

这样就可以使用向量内建函数（例如 __hadd2、__hsub2、__hmul2、__hfma2）在一条指令中执行两次操作。与分别调用两次 half 或 __nv_bfloat16 操作相比，使用 half2 或 __nv_bfloat162 也可能提升其他内建函数（例如 warp shuffle）的性能。

内建函数 __halves2half2 用于将两个半精度值转换为 half2；__halves2bfloat162 则用于将两个 __nv_bfloat16 值转换为 __nv_bfloat162。

类型转换（Type Conversion）

有时，编译器必须插入类型转换指令，从而增加执行周期。以下情况可能出现这种问题：

  • 操作 char 或 short 类型变量的函数，其操作数通常需要先转换为 int；
  • 在单精度浮点运算中使用双精度浮点常量（即未带类型后缀的常量），这是 C/C++ 标准所要求的。

第二种情况可以通过使用带 f 后缀的单精度浮点常量来避免，例如 3.141592653589793f、1.0f 和 0.5f。

8.4.2 控制流指令（Control Flow Instructions）

任何控制流指令（if、switch、do、for、while）都可能因同一 warp 中的线程发生分支发散（沿不同执行路径运行），显著降低有效指令吞吐量。如果发生分支发散，不同执行路径必须串行执行，从而增加该 warp 总共执行的指令数量。

当控制流取决于线程 ID 时，应尽量减少分支发散的 warp 数量。由于线程块中的 warp 分布是确定的（详见“SIMT 架构”），可以据此安排控制条件。例如，如果控制条件只依赖于 threadIdx / warpSize，其中 warpSize 是 warp 大小，那么控制条件与 warp 边界完全对齐，不会发生 warp 内分支发散。

有时，编译器会展开循环，或者使用**分支谓词化（branch predication）**来优化掉较短的 if 或 switch 代码块。此时 warp 不会发生分支发散。程序员也可以使用 #pragma unroll 指令控制循环展开，详见相应章节。

使用分支谓词化时，依赖控制条件的指令并不会被跳过。相反，每条指令都会关联一个按线程设置为真或假的条件码（谓词）。虽然这些指令都会被调度执行，但只有谓词为真的指令才真正执行。谓词为假的指令不会写入结果，也不会计算地址或读取操作数。

8.4.3 同步指令（Synchronization Instruction）

__syncthreads() 的吞吐量为：

  • 计算能力 6.0 的设备：每个时钟周期 32 次操作；
  • 计算能力 7.x 和 8.x 的设备：每个时钟周期 16 次操作；
  • 计算能力 5.x、6.1 和 6.2 的设备：每个时钟周期 64 次操作。

请注意，__syncthreads() 可能迫使多处理器空闲，从而影响性能，详见“设备内存访问”。

8.5 尽量减少内存抖动（Minimize Memory Thrashing）

如果应用程序过于频繁地分配和释放内存，分配调用可能会随时间推移而变慢，直到达到某个上限。这通常与内存释放回操作系统、供其重新使用的机制有关。

为了获得最佳性能，建议遵循以下做法：

  • 按需分配内存。 应根据问题规模确定分配量。不要试图通过 cudaMalloc、cudaMallocHost 或 cuMemCreate 分配所有可用内存，因为这会迫使内存立即驻留，并阻止其他应用程序使用这些内存。这会增加操作系统调度器的压力，甚至可能完全阻止其他应用程序使用同一 GPU。
  • 尽早进行合适大小的分配。 尽量在应用程序早期分配适当大小的内存，并只在应用程序不再需要内存时才进行释放。减少应用程序中的 cudaMalloc 与 cudaFree 调用次数，尤其要避免在性能关键区域频繁调用。
  • 在设备内存不足时考虑回退。 如果无法分配足够的设备内存，可以考虑改用其他内存类型，例如 cudaMallocHost 或 cudaMallocManaged。这些方式的性能可能较低，但能让应用程序继续执行。
  • 在支持的平台上考虑统一内存超额使用。 cudaMallocManaged 支持内存超额使用；如果正确设置 cudaMemAdvise 策略，应用程序可以保留大部分、甚至几乎全部 cudaMalloc 的性能。cudaMallocManaged 也不会强制分配立即驻留，只有在实际需要或预取时才驻留，从而减轻操作系统调度器的整体压力，并更好地支持多租户场景。
