第十四章 流有序内存分配器（Stream Ordered Memory Allocator）

对应原 PDF 第 383–396 页（原书印刷页码 367–380）。保留原书章节编号、CUDA API、代码标识符与示例结构。

14.1 简介（Introduction）

使用 cudaMalloc 和 cudaFree 管理内存分配时，会导致 GPU 在所有正在执行的 CUDA 流之间进行同步。流有序内存分配器允许应用程序将内存分配和释放操作，与同一 CUDA 流中提交的其他工作（例如内核启动和异步复制）建立顺序关系。

该分配器利用流排序语义复用内存分配，从而改善应用程序的内存使用情况。它还允许应用程序控制分配器的内存缓存行为。如果设置了合适的释放阈值，当应用程序愿意接受更大的内存占用时，分配器可以通过缓存避免昂贵的操作系统调用。该分配器也支持在进程之间方便且安全地共享内存分配。

对于许多应用程序，流有序内存分配器可以减少对自定义内存管理抽象的需求，并简化高性能内存管理机制的实现。已经使用自定义分配器的应用程序和库，也可以改用流有序内存分配器，让多个库共享由驱动程序管理的内存池，从而减少多余的内存消耗。此外，驱动程序能够结合自身对分配器和其他流管理 API 的了解执行优化。作为 CUDA 11.3 工具包支持的一部分，Nsight Compute 和新一代 CUDA 调试器也能够识别该分配器。

14.2 查询支持情况（Query for Support）

用户可以调用 cudaDeviceGetAttribute() 并查询设备属性 cudaDevAttrMemoryPoolsSupported，判断设备是否支持流有序内存分配器。

从 CUDA 11.3 开始，可以通过设备属性 cudaDevAttrMemoryPoolSupportedHandleTypes 查询 IPC 内存池支持情况。较旧的驱动程序尚未定义该属性枚举，因此会返回 cudaErrorInvalidValue。在查询前检查驱动版本，可以避免触发此错误。

int driverVersion = 0;
int deviceSupportsMemoryPools = 0;
int poolSupportedHandleTypes = 0;

cudaDriverGetVersion(&driverVersion);

if (driverVersion >= 11020) {
    cudaDeviceGetAttribute(
        &deviceSupportsMemoryPools,
        cudaDevAttrMemoryPoolsSupported, device);
}

if (deviceSupportsMemoryPools != 0) {
    // device 支持流有序内存分配器
}

if (driverVersion >= 11030) {
    cudaDeviceGetAttribute(
        &poolSupportedHandleTypes,
        cudaDevAttrMemoryPoolSupportedHandleTypes, device);
}

if (poolSupportedHandleTypes & cudaMemHandleTypePosixFileDescriptor) {
    // 指定设备上的内存池可以使用基于 POSIX 文件描述符的 IPC 创建
}

也可以使用 cudaGetLastError() 清除错误，而不是通过版本检查避免触发错误。

14.3 API 基础：cudaMallocAsync 与 cudaFreeAsync（API Fundamentals）

cudaMallocAsync 和 cudaFreeAsync 是该分配器的核心 API。cudaMallocAsync 返回一个内存分配，cudaFreeAsync 则释放该分配。两个 API 都接受流参数，用于定义分配何时可用，以及何时停止可用。

cudaMallocAsync 返回的指针值会同步确定，因此可用于构造后续工作。需要注意，cudaMallocAsync 在决定分配所在位置时，会忽略当前设备/上下文；它会根据指定的内存池或传入的流来确定驻留设备。最简单的使用模式是在同一个流中分配、使用并释放内存：

void *ptr;
size_t size = 512;
cudaMallocAsync(&ptr, size, cudaStreamPerThread);

// 使用该分配执行工作。
kernel<<<..., cudaStreamPerThread>>>(ptr, ...);

// 异步释放，不需要让 CPU 与 GPU 同步。
cudaFreeAsync(ptr, cudaStreamPerThread);

如果在分配该内存的流以外的其他流中使用它，用户必须保证访问发生在分配操作之后，否则行为未定义。可以通过同步分配流，或使用 CUDA 事件在生产流和消费流之间建立同步来保证顺序。

cudaFreeAsync() 会向指定流插入释放操作。用户必须保证释放操作发生在分配操作以及所有使用该分配的操作之后。释放操作开始后继续使用该分配，会导致未定义行为。应使用事件和/或流同步操作，确保其他流对该分配的访问已经完成，然后释放流才开始释放内存。

cudaMallocAsync(&ptr, size, stream1);
cudaEventRecord(event1, stream1);

// stream2 必须等待分配准备好后才能访问。
cudaStreamWaitEvent(stream2, event1);
kernel<<<..., stream2>>>(ptr, ...);

cudaEventRecord(event2, stream2);

// 释放前，stream3 必须等待 stream2 完成对该分配的访问。
cudaStreamWaitEvent(stream3, event2);
cudaFreeAsync(ptr, stream3);

用户也可以使用 cudaFreeAsync() 释放通过 cudaMalloc() 分配的内存。释放前同样必须保证所有访问都已完成：

cudaMalloc(&ptr, size);
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);

通过 cudaMallocAsync 分配的内存也可以使用 cudaFree() 释放。使用 cudaFree() 释放这类分配时，驱动程序会假定所有访问均已完成，并且不会再执行额外同步。用户可以调用 cudaStreamQuery、cudaStreamSynchronize、cudaEventQuery、cudaEventSynchronize 或 cudaDeviceSynchronize，确保相应的异步工作已完成，GPU 不会再访问该分配。

cudaMallocAsync(&ptr, size, stream);
kernel<<<..., stream>>>(ptr, ...);

// 需要同步，以避免过早释放内存。
cudaStreamSynchronize(stream);
cudaFree(ptr);

14.4 内存池与 cudaMemPool_t（Memory Pools）

内存池封装虚拟地址和物理内存资源，并根据内存池的属性与特性分配和管理这些资源。内存池最重要的属性之一，是它所管理的内存类型及其所在位置。

所有 cudaMallocAsync 调用都会使用某个内存池的资源。如果没有指定内存池，cudaMallocAsync 会使用传入流所属设备的当前内存池。可以通过 cudaDeviceSetMempool 设置某个设备的当前内存池，并通过 cudaDeviceGetMempool 查询。

默认情况下（即没有调用 cudaDeviceSetMempool 时），设备的当前内存池就是该设备的默认内存池。cudaMallocFromPoolAsync 以及 cudaMallocAsync 的 C++ 重载允许用户为某次分配指定内存池，而不必将其设为当前池。cudaDeviceGetDefaultMempool 和 cudaMemPoolCreate 可用于获取内存池句柄。

注意： 每台设备的当前内存池都是该设备本地的。因此，如果分配时没有指定内存池，所得分配始终位于该流所属的设备上。

可以通过 cudaMemPoolSetAttribute 和 cudaMemPoolGetAttribute 控制内存池属性。

14.5 默认/隐式内存池（Default/Implicit Pools）

可以通过 cudaDeviceGetDefaultMempool 获取设备的默认内存池。默认内存池中的分配属于不可迁移的设备内存，并驻留在该设备上；这些分配始终可由该设备访问。

可以通过 cudaMemPoolSetAccess 修改默认内存池的可访问性，并通过 cudaMemPoolGetAccess 查询。由于默认内存池无需显式创建，因此有时也称为隐式内存池。设备的默认内存池不支持 IPC。

14.6 显式内存池（Explicit Pools）

cudaMemPoolCreate 用于创建显式内存池。相比默认/隐式内存池，显式内存池允许应用程序为分配指定更多属性，例如 IPC 能力、内存池最大大小，以及在受支持的平台上让分配驻留于指定 CPU NUMA 节点等。

以下代码创建一个与设备 0 的隐式内存池类似的内存池：

int device = 0;
cudaMemPoolProps poolProps = {};
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = device;
poolProps.location.type = cudaMemLocationTypeDevice;

cudaMemPoolCreate(&memPool, &poolProps);

以下代码展示如何创建一个位于有效 CPU NUMA 节点、且支持通过文件描述符进行 IPC 共享的内存池：

// 创建驻留在 CPU NUMA 节点上的内存池，并支持通过文件描述符进行 IPC 共享。
int cpu_numa_id = 0;
cudaMemPoolProps poolProps = {};
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = cpu_numa_id;
poolProps.location.type = cudaMemLocationTypeHostNuma;
poolProps.handleType = cudaMemHandleTypePosixFileDescriptor;

cudaMemPoolCreate(&ipcMemPool, &poolProps);

14.7 物理页缓存行为（Physical Page Caching Behavior）

默认情况下，分配器会尝试尽量减少内存池持有的物理内存。为了减少操作系统分配和释放物理内存的调用次数，应用程序需要为每个内存池配置一个内存占用目标。

可以通过释放阈值属性 cudaMemPoolAttrReleaseThreshold 设置该值。释放阈值表示内存池在尝试将内存归还给操作系统前应保留的字节数。当内存池持有的内存超过释放阈值时，分配器会在下一次流、事件或设备同步调用时尝试将内存归还给操作系统。将释放阈值设为 UINT64_MAX，可以阻止驱动程序在每次同步后尝试缩小内存池。

cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(
    memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

如果应用程序将 cudaMemPoolAttrReleaseThreshold 设置得足够高，实际上禁用了内存池缩减，则可能希望在适当时机显式缩小内存池占用。cudaMemPoolTrimTo 可以完成这一操作。其参数 minBytesToKeep 允许应用程序保留预计在下一执行阶段仍需使用的内存量。

cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(
    memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

// 当前阶段需要从流有序分配器获得大量内存。
for (i = 0; i < 10; i++) {
    for (j = 0; j < 10; j++) {
        cudaMallocAsync(&ptrs[j], size[j], stream);
    }
    kernel<<<..., stream>>>(ptrs, ...);
    for (j = 0; j < 10; j++) {
        cudaFreeAsync(ptrs[j], stream);
    }
}

// 下一阶段不再需要这么多内存。
// 先同步，使 trim 操作确认这些分配已不再使用。
cudaStreamSynchronize(stream);
cudaMemPoolTrimTo(mempool, 0);

// 缩减操作释放的物理内存，现在可供其他进程或分配机制使用。

14.8 资源使用统计（Resource Usage Statistics）

CUDA 11.3 新增了以下内存池属性，用于查询内存池的内存使用情况：

  • cudaMemPoolAttrReservedMemCurrent
  • cudaMemPoolAttrReservedMemHigh
  • cudaMemPoolAttrUsedMemCurrent
  • cudaMemPoolAttrUsedMemHigh

查询 cudaMemPoolAttrReservedMemCurrent 会返回内存池当前占用的 GPU 物理内存总量。查询 cudaMemPoolAttrUsedMemCurrent 会返回从该内存池分配、且当前不可复用的内存总量。

cudaMemPoolAttr*MemHigh 属性是高水位值，记录自上次重置以来相应 cudaMemPoolAttr*MemCurrent 属性达到的最大值。可以通过 cudaMemPoolSetAttribute 将它们重置为当前值。

// 批量获取使用统计的辅助结构和函数示例。
struct usageStatistics {
    cuuint64_t reserved;
    cuuint64_t reservedHigh;
    cuuint64_t used;
    cuuint64_t usedHigh;
};

void getUsageStatistics(
    cudaMemoryPool_t memPool,
    struct usageStatistics *statistics) {
    cudaMemPoolGetAttribute(
        memPool, cudaMemPoolAttrReservedMemCurrent, &statistics->reserved);
    cudaMemPoolGetAttribute(
        memPool, cudaMemPoolAttrReservedMemHigh, &statistics->reservedHigh);
    cudaMemPoolGetAttribute(
        memPool, cudaMemPoolAttrUsedMemCurrent, &statistics->used);
    cudaMemPoolGetAttribute(
        memPool, cudaMemPoolAttrUsedMemHigh, &statistics->usedHigh);
}

// 将高水位值重置为当前值。
void resetStatistics(cudaMemPool_t memPool) {
    cuuint64_t value = 0;
    cudaMemPoolSetAttribute(
        memPool, cudaMemPoolAttrReservedMemHigh, &value);
    cudaMemPoolSetAttribute(
        memPool, cudaMemPoolAttrUsedMemHigh, &value);
}

14.9 内存复用策略（Memory Reuse Policies）

为满足分配请求，驱动程序会先尝试复用此前通过 cudaFreeAsync() 释放的内存，然后才尝试从操作系统分配更多内存。例如，在某个流中释放的内存，可以立即被同一流中后续的分配请求复用。类似地，当某个流与 CPU 完成同步后，该流中此前释放的内存也可供任意流中的分配复用。

流有序分配器提供了若干可控制的分配策略。内存池属性 cudaMemPoolReuseFollowEventDependencies、cudaMemPoolReuseAllowOpportunistic 和 cudaMemPoolReuseAllowInternalDependencies 用于控制这些策略。升级到较新的 CUDA 驱动程序后，复用策略可能会发生变化、增强、扩展或重新排序。

14.9.1 cudaMemPoolReuseFollowEventDependencies

在分配更多 GPU 物理内存之前，分配器会检查 CUDA 事件建立的依赖关系，并尝试复用在其他流中释放的内存。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);
cudaEventRecord(event, originalStream);

// 等待捕获了另一流中释放操作的事件。
// 启用 cudaMemPoolReuseFollowEventDependencies 后，
// 另一流中的新分配请求就可能复用该内存。
cudaStreamWaitEvent(otherStream, event);
cudaMallocAsync(&ptr2, size, otherStream);

14.9.2 cudaMemPoolReuseAllowOpportunistic

根据 cudaMemPoolReuseAllowOpportunistic 策略，分配器会检查已释放的分配，判断释放操作的流排序条件是否已经满足（例如，该流是否已执行到释放操作所指定的位置）。

禁用此策略后，分配器仍会复用那些在流与 CPU 完成同步后可用的内存。禁用该策略并不会阻止 cudaMemPoolReuseFollowEventDependencies 生效。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 经过一段时间，内核执行完毕。
wait(10);

// 启用 cudaMemPoolReuseAllowOpportunistic 时，
// 分配器可根据 originalStream 的执行进度复用先前的分配。
cudaMallocAsync(&ptr2, size, otherStream);

14.9.3 cudaMemPoolReuseAllowInternalDependencies

如果无法从操作系统分配并映射更多物理内存，驱动程序会查找那些需要等待其他流继续执行才能变为可用的内存。如果找到这样的内存，驱动程序会在分配流中插入所需依赖关系，并复用该内存。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 启用 cudaMemPoolReuseAllowInternalDependencies，且驱动程序无法
// 分配更多物理内存时，可能会在分配流中插入等效于
// cudaStreamWaitEvent 的依赖，使 otherStream 中的后续工作
// 排在 originalStream 中可能访问原分配的工作之后。
cudaMallocAsync(&ptr2, size, otherStream);

14.9.4 禁用复用策略（Disabling Reuse Policies）

虽然可控制的复用策略能够改善内存复用，但用户也可能希望禁用它们。

允许机会式复用（例如 cudaMemPoolReuseAllowOpportunistic）会使每次运行的分配模式受到 CPU 与 GPU 执行交错顺序的影响，从而产生运行间差异。内部依赖插入（例如 cudaMemPoolReuseAllowInternalDependencies）可能以意料之外、且潜在非确定性的方式串行化工作；而用户可能更希望在分配失败时显式同步事件或流。

14.10 多 GPU 的设备可访问性（Device Accessibility for Multi-GPU）

与虚拟内存管理 API 控制分配可访问性的方式类似，内存池分配的可访问性也不遵循 cudaDeviceEnablePeerAccess 或 cuCtxEnablePeerAccess。相反，必须使用 cudaMemPoolSetAccess 指定哪些设备可以访问来自某个内存池的分配。

默认情况下，分配可由其驻留设备访问，而且无法撤销该设备的访问权限。若要允许其他设备访问，访问设备必须与内存池所在设备具备对等访问能力；可以使用 cudaDeviceCanAccessPeer 检查。如果没有检查对等能力，设置访问权限可能返回 cudaErrorInvalidDevice。如果该内存池尚未分配过内存，cudaMemPoolSetAccess 即使在设备不支持对等访问时也可能成功，但后续从该池分配内存时会失败。

cudaMemPoolSetAccess 会影响该内存池的所有分配，而不仅是之后创建的分配。cudaMemPoolGetAccess 返回的可访问性同样适用于该池的所有分配。建议不要频繁更改某个内存池对指定 GPU 的访问设置；一旦允许某台 GPU 访问某个池，最好在该池的整个生命周期内保持这一权限。

cudaError_t setAccessOnDevice(
    cudaMemPool_t memPool, int residentDevice, int accessingDevice) {
    cudaMemAccessDesc accessDesc = {};
    accessDesc.location.type = cudaMemLocationTypeDevice;
    accessDesc.location.id = accessingDevice;
    accessDesc.flags = cudaMemAccessFlagsProtReadWrite;

    int canAccess = 0;
    cudaError_t error = cudaDeviceCanAccessPeer(
        &canAccess, accessingDevice, residentDevice);

    if (error != cudaSuccess) {
        return error;
    } else if (canAccess == 0) {
        return cudaErrorPeerAccessUnsupported;
    }

    // 使地址范围可访问。
    return cudaMemPoolSetAccess(memPool, &accessDesc, 1);
}

14.11 IPC 内存池（IPC Memory Pools）

支持 IPC 的内存池可以方便、高效且安全地在进程之间共享 GPU 内存。CUDA 的 IPC 内存池提供与 CUDA 虚拟内存管理 API 相同的安全优势。

通过内存池在进程间共享内存分为两个阶段。首先，进程需要共享对内存池的访问权限；然后，再共享该池中的特定内存分配。第一阶段用于建立并强制执行安全策略。第二阶段则协调各进程中使用的虚拟地址，以及导入进程中映射何时必须有效。

14.11.1 创建并共享 IPC 内存池（Creating and Sharing IPC Memory Pools）

共享内存池访问权限的步骤如下：通过 cudaMemPoolExportToShareableHandle() 获取该内存池的操作系统原生句柄，将句柄通过操作系统原生 IPC 机制传给导入进程，再通过 cudaMemPoolImportFromShareableHandle() 创建导入的内存池。

要使 cudaMemPoolExportToShareableHandle 成功，创建内存池时必须在内存池属性结构中指定所请求的句柄类型。有关如何在进程间传递操作系统原生句柄的具体 IPC 机制，请参阅相关示例。

以下代码展示导出进程和导入进程的操作。此例使用 POSIX 文件描述符句柄：

// 导出进程：在设备 0 上创建支持 IPC、可导出的内存池。
cudaMemPoolProps poolProps = {};
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = 0;
poolProps.location.type = cudaMemLocationTypeDevice;

// 将 handleTypes 设为非零值，使内存池支持导出（IPC）。
poolProps.handleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;
cudaMemPoolCreate(&memPool, &poolProps);

// 基于文件描述符的句柄是整数类型。
int fdHandle = 0;

// 获取内存池对应的操作系统原生句柄。
// 此处传入句柄存储位置的指针。
cudaMemPoolExportToShareableHandle(
    &fdHandle,
    memPool,
    CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
    0);

// 必须通过相应的操作系统专用 API 将句柄发送给导入进程。

// 导入进程：
int fdHandle;
// 必须通过相应的操作系统专用 API 从导出进程取得句柄。

// 根据可共享句柄创建导入的内存池。
// 注意：这里按值传递句柄。
cudaMemPoolImportFromShareableHandle(
    &importedMemPool,
    (void*)fdHandle,
    CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
    0);

14.11.2 在导入进程中设置访问权限（Set Access in the Importing Process）

导入的内存池最初只能由其驻留设备访问。导入内存池不会继承导出进程设置的任何可访问性。导入进程必须调用 cudaMemPoolSetAccess，为计划访问该内存的 GPU 启用访问权限。

如果导入的内存池属于导入进程中不可见的设备，用户必须使用 cudaMemPoolSetAccess，允许实际使用这些分配的 GPU 进行访问。

14.11.3 创建并共享导出池中的分配（Creating and Sharing Allocations from an Exported Pool）

共享内存池后，导出进程中通过该池的 cudaMallocAsync() 创建的分配，可以与已导入该池的其他进程共享。由于安全策略是在内存池级别建立并验证的，操作系统不需要再为池中的每个具体分配单独维护安全信息。换言之，用于导入池分配的不透明类型 cudaMemPoolPtrExportData，可以通过任意机制发送给导入进程。

即使导出和导入分配时没有与分配流进行同步，导入进程访问分配时仍必须遵守与导出进程相同的规则：对该分配的访问必须发生在分配操作的流排序之后。

以下代码展示如何使用 cudaMemPoolExportPointer() 和 cudaMemPoolImportPointer() 共享分配，并使用 IPC 事件确保导入进程不会在分配准备好之前访问它。

// 在导出进程中准备分配。
cudaMemPoolPtrExportData exportData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t readyIpcEventHandle;

// 用于进程间协调的 IPC 事件。
// cudaEventInterprocess 标志使事件可用于 IPC。
// 原书示例在此处写为 cudaEventCreate，需与目标 SDK 的函数签名核验。
cudaEventCreate(
    &readyIpcEvent,
    cudaEventDisableTiming | cudaEventInterprocess);

// 从导出进程的内存池分配内存。
cudaMallocAsync(&ptr, size, exportMemPool, stream);

// 当分配准备好时记录事件。
cudaEventRecord(readyIpcEvent, stream);
cudaMemPoolExportPointer(&exportData, ptr);
cudaIpcGetEventHandle(&readyIpcEventHandle, readyIpcEvent);

// 使用任意机制向导入进程共享 IPC 事件和指针导出数据。
// 这里将数据复制到共享内存。
shmem->ptrData = exportData;
shmem->readyIpcEventHandle = readyIpcEventHandle;
// 通知消费者数据已准备好。

// 导入分配：
cudaMemPoolPtrExportData *importData = &shmem->ptrData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t *readyIpcEventHandle =
    &shmem->readyIpcEventHandle;

// 使用任意机制从导出进程取得 IPC 事件句柄和导出数据。
// 此例使用共享内存，因此只需同步以确保共享内存已填充。
cudaIpcOpenEventHandle(&readyIpcEvent, readyIpcEventHandle);

// 导入分配。该操作不会阻塞等待分配准备就绪。
cudaMemPoolImportPointer(&ptr, importedMemPool, importData);

// 使用该分配前，等待分配流中此前的操作完成。
cudaStreamWaitEvent(stream, readyIpcEvent);
kernel<<<..., stream>>>(ptr, ...);

释放分配时，必须先在导入进程中释放，再在导出进程中释放。以下代码展示如何使用 CUDA IPC 事件，在两个进程的 cudaFreeAsync 操作之间建立必要同步。

// 导入进程：释放前执行最后一次访问。
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);

// 导入进程释放后，不得再访问该分配。
cudaIpcEventRecord(finishedIpcEvent, stream);

// 导出进程：使自身的释放与导入进程的流顺序协调。
cudaStreamWaitEvent(stream, finishedIpcEvent);
kernel<<<..., stream>>>(ptrInExportingProcess, ...);

// 原书此处提取文本写为 cudFreeAsync，疑为拼写错误，需对照原文校验。
cudFreeAsync(ptrInExportingProcess, stream);

导入进程的释放操作不会阻止导出进程在其释放之前使用该分配。也可以使用 cudaFree() 在两个进程中释放该分配；此外，也可使用其他流同步 API 代替 CUDA IPC 事件。

14.11.4 IPC 导出池的限制（IPC Export Pool Limitations）

目前，IPC 内存池不支持将物理内存块释放回操作系统。因此，cudaMemPoolTrimTo 不会产生效果（no-op），cudaMemPoolAttrReleaseThreshold 也实际上会被忽略。该行为由驱动程序而不是运行时控制，未来的驱动程序更新可能会改变这一行为。

14.11.5 IPC 导入池的限制（IPC Import Pool Limitations）

不允许从导入池中进行分配。具体来说，导入池不能被设为当前内存池，也不能用于 cudaMallocFromPoolAsync API。因此，分配复用策略属性对这些池没有意义。

IPC 内存池目前也不支持将物理内存块释放回操作系统，因此 cudaMemPoolTrimTo 不起作用，cudaMemPoolAttrReleaseThreshold 实际上会被忽略。

资源使用统计属性查询只反映导入到当前进程中的分配及其关联的物理内存。

14.12 同步 API 操作（Synchronization API Actions）

将分配器集成到 CUDA 驱动程序后，可利用同步 API 执行优化。当用户请求 CUDA 驱动程序进行同步时，驱动程序会等待异步工作完成。返回前，驱动程序会确定哪些释放操作已被此次同步保证完成。

这些分配会变为可供分配器复用的内存，不受指定流或已禁用分配策略的影响。驱动程序还会在此时检查 cudaMemPoolAttrReleaseThreshold，并释放任何可以释放的多余物理内存。

14.13 补充说明（Addendums）

14.13.1 cudaMemcpyAsync 对当前上下文/设备的敏感性（Current Context/Device Sensitivity）

在当前 CUDA 驱动程序中，任何涉及 cudaMallocAsync 分配内存的异步内存复制，都应使用指定流所属的上下文作为调用线程的当前上下文。

cudaMemcpyPeerAsync 不受此要求约束，因为该 API 使用其参数中指定的设备主上下文，而不是当前上下文。

14.13.2 cuPointerGetAttribute 查询（Query）

对已调用 cudaFreeAsync 释放的分配再次调用 cuPointerGetAttribute，会导致未定义行为。具体而言，无论该分配是否仍能从某个给定流访问，行为都未定义。

14.13.3 cuGraphAddMemsetNode

cuGraphAddMemsetNode 不能用于通过流有序分配器分配的内存。不过，可以在流捕获期间对这些分配执行 memset 操作。

14.13.4 指针属性（Pointer Attributes）

cuPointerGetAttributes 查询可用于流有序分配。由于流有序分配不与特定上下文关联，查询 CU_POINTER_ATTRIBUTE_CONTEXT 虽然会成功，但 *data 中返回的是 NULL。

可以使用属性 CU_POINTER_ATTRIBUTE_DEVICE_ORDINAL 确定分配所在设备；在选择上下文以执行通过 cudaMemcpyPeerAsync 完成的点对点复制时，这一信息可能很有用。

属性 CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE 从 CUDA 11.3 开始提供，可用于调试，也可用于 IPC 操作前确认某个分配来自哪个内存池。
